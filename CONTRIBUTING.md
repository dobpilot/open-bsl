# Участие в разработке

Спасибо за интерес к `open-bsl`. Проект реализует интерпретатор BSL на Rust и
находится в активной разработке: совместимость с платформой ещё неполная, а
внутренние и публичные API могут меняться.

## С чего начать

Нужны Git и Rust с поддержкой редакции 2024. После клонирования проверьте весь
workspace и запустите небольшой BSL-сценарий:

```bash
cargo build --workspace
cargo run -p bsl-cli -- tests/conformance/fixtures/arithmetic.bsl
cargo test -p bsl-number
```

Затем прочитайте [`README.md`](README.md) для знакомства с возможностями,
[`docs/README.md`](docs/README.md) для навигации по документации и
[`AGENTS.md`](AGENTS.md) для обязательных инженерных правил. Архитектурные
границы описаны в [`docs/architecture/`](docs/architecture/), проверяемое
поведение — в [`openspec/specs/`](openspec/specs/), а ещё не завершённые
изменения — в [`openspec/changes/`](openspec/changes/).

## Куда смотреть в коде

Путь программы через систему задаёт основную карту репозитория:

| Задача | Основное место | Где искать тесты |
|---|---|---|
| Лексика, грамматика, AST | `crates/bsl-syntax` | тесты и snapshots этого крейта |
| Разрешение имён и типов вызовов | `crates/bsl-sema` | `crates/bsl-sema/tests` |
| Инструкции и формат байт-кода | `crates/bsl-bytecode` | `crates/bsl-bytecode/tests` |
| Генерация и оптимизация байт-кода | `crates/bsl-compiler` | `crates/bsl-compiler/tests` |
| Исполнение и JIT | `crates/bsl-vm` | тесты крейта и conformance-корпус |
| Значения, встроенные функции, коллекции | `crates/bsl-rt` | тесты рядом с реализацией |
| Числа и пользовательское форматирование | `crates/bsl-number`, `crates/bsl-format` | тесты соответствующего крейта |
| JSON, XML, HTTP и другие подсистемы | одноимённый компонентный крейт | тесты компонента |
| API встраивания | `crates/open-bsl` | `open-bsl-consumer`, integration-тесты |
| CLI, REPL и DAP | `crates/bsl-cli` | `crates/bsl-cli/tests` |

Для первого изменения начните с узкого поиска: `rg "ИмяФункции" crates tests`.
Посмотрите вызывающий код и историю решений (`git log -S 'ИмяФункции'`), прежде
чем менять локально странное на вид поведение: оно может быть измеренной
совместимостью с 1С или сознательным расхождением.

## Перед изменением

Сначала сформулируйте проверку, которая падает на текущем коде. Исправление
ошибки обычно начинается с минимального регрессионного теста; изменение
наблюдаемого поведения, публичного API, CLI, формата или архитектурной границы
— с OpenSpec proposal и сценариев. Внутренний рефакторинг без изменения
поведения нового OpenSpec не требует.

Поведение платформы 1С нельзя выводить из результата этого интерпретатора.
Если решения ещё нет в измерениях, следуйте процедуре `НЕ ИЗМЕРЕНО` из
[`AGENTS.md`](AGENTS.md#measuring-on-the-1c-platform). Не создавайте `.expected`
из вывода `open-bsl`: conformance-оракул должен происходить из независимого
свидетельства.

Перед добавлением зависимости проверьте стандартную библиотеку и соседние
крейты. Новую внешнюю зависимость нужно обсудить до реализации. Изменяйте
только относящиеся к задаче строки и сохраняйте стиль русских комментариев.

## Тестирование во время работы

Сначала запускайте самый узкий тест, затем расширяйте область:

```bash
cargo test -p bsl-number division_half_up
cargo test -p bsl-compiler --test text_round_trip
cargo test -p bsl-cli -- --nocapture
```

Интеграционные BSL-сценарии находятся в `tests/conformance/fixtures/`; обычно
это пара `name.bsl` и `name.expected`. Изменения VM должны проходить тест
`the_jit_agrees_with_the_interpreter_on_every_script`. Snapshot парсера
принимайте только после чтения `.snap.new`, а не ради зелёного запуска.

После изменения публичных runtime-дескрипторов перегенерируйте справочник:

```bash
cargo run -p bsl-cli -- --emit-api-reference docs/reference/bsl-api/api.md
```

Не редактируйте генерируемый список API вручную. При изменении opcode сверяйте
единые таблицы текстового формата и эффектов, перечисленные в `AGENTS.md`.

## Проверки перед отправкой

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps
```

Для изменений горячего пути VM сначала используйте
`./benchmarks/hot-code-diff.sh`, а утверждения о производительности
подтверждайте чередующимся A/B-замером относительно базового коммита.

## Коммиты и pull request

Делайте небольшие тематические коммиты с коротким повелительным заголовком,
например `Add decimal division regression test`. В pull request объясните
наблюдаемое изменение, перечислите затронутые крейты и выполненные команды.
Свяжите PR с issue или OpenSpec change. Для изменений совместимости приложите
результаты замера на реальной 1С; скриншоты нужны только для видимого поведения
CLI, редактора или диагностики.
