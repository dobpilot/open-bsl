# Дизайн

## Перенос открытого временного носителя

Отдельный TransferableTemporaryFile в bsl-rt содержит Box<FileHandle + Send>
и Box<TemporaryFileResource + Send>. Конструктор требует оба дескриптора;
непереносимые реализации прежних трейтов остаются допустимыми. Метод
FileSystem::create_transferable_temporary_file по умолчанию возвращает
Unsupported без делегирования синхронному созданию. Background-access
по-прежнему предоставляет тот же host, не файловую систему процесса.

В потоке владельца into_local снимает только ограничение Send и использует
прежний OpenedTemporaryFile::new_owned. Регистрация, возврат результата при
закрытом учёте и отсутствие удаления при Drop остаются единственной прежней
реализацией. Путь не заменяет право очистки; повторного открытия нет.
Этот транспорт использует CreateTempFileAsync: worker создаёт переносимую
запись, а mapper в потоке VM передаёт право очистки локальному реестру и
собирает BSL-поток без повторного открытия. Системное удаление остаётся
отдельным host-контрактом. По решению от 2026-09-18 штатное
закрытие `State`/CLI ждёт уже начатую host-операцию
`CreateTempFileAsync`, доставляет её право в локальный реестр и
затем вызывает обычный callback. Это не распространяется на прочие
host-операции и не создаёт восстановительную очистку после `SIGKILL`.

## Измеренное асинхронное создание и системный совместный доступ

Клиентская проба file-temp-async на localhost/test (2026-09-17) дала
32 успешных вызова, 36 ошибок параметров при первом и повторном Ждать
и два синхронных отказа лишнему аргументу. Повторное ожидание успеха
возвращает тот же поток даже после закрытия. Delta добавлена до реализации.
Это не доказывает момент создания до Ждать или поведение отмены.

Async не подменяется синхронным create с готовым обещанием: FileHandle
и TemporaryFileResource существующего host могут быть непереносимыми.
Передача дескриптора и локальная регистрация реализованы; новый worker не получает Rc
реестра. Поздний успешный результат уже начатого создания не должен обогнать
закрытие локального реестра. Поэтому штатное освобождение execution
ждёт только его worker временного файла, переносит право в реестр,
а `State` затем закрывает реестр и вызывает callback.

Независимая часть системного host на Linux — запрет чтения через
FileSystem::read пока жив дескриптор, возвращённый create_temporary_file.
Внутренний учёт хранит пару device/inode открытого файла, а не только путь.
Чтение проверяет собственный открытый дескриптор, без повторного разрешения
пути. Разные SystemFileSystem одного процесса видят один учёт; закрытие
одного носителя освобождает только его запись. Metadata и исходный дескриптор
остаются доступны, Drop не удаляет файл. Это не OS-lock, не запрет внешнему
процессу или std::fs::read и не защита системного удаления от подмены.
Остальные способы open/write и платформы не получают выдуманной общей
модели блокировок. Произвольная FileSystem по-прежнему принадлежит host.
Сквозная BSL-проверка использует низкоуровневое атомарное создание и затем
ДвоичныеДанные: SystemFileSystem ещё не поддерживает право автоочистки.

file-temp-sharing подтвердил перенос носителя и hard link: запрет остаётся
у обеих записей каталога, новый файл по старому пути читается, после закрытия
оба имени исходного носителя доступны. Оба нативных сеанса восстановили
CF/БД/XML. Полный workspace, fmt, Clippy, rustdoc, API reference и все 11
строгих проверок OpenSpec прошли. Свидетельства, тесты и границы этапа:
docs/research/compatibility/file-temp-async-and-sharing-2026-09-17.md.

## Подключение компонента потоков к сеансовому учёту

Синхронный компонентный этап реализован и проверен семью интеграционными
тестами, полным workspace, fmt, Clippy, rustdoc и строгим OpenSpec.
Нативная проба имени обычного потока восстановила CF/БД и совпала с oracle;
API reference регенерирован. Подробности и границы:
docs/research/compatibility/temporary-stream-host-2026-09-17.md.
Исторические этапы ниже описывают состояние до этого подключения;
системное создание из BSL, совместный доступ и Async ещё не завершены.

CallContext получает необязательный дескриптор TemporaryFileRegistry через
отдельный setter: существующие InterpreterServices и minimal/interpreter
не требуют новых полей у вызывающих. VM передаёт реестр из текущего HostEnv
во все компонентные контексты. Менеджер потоков сохраняет клоны реестра
и RandomHandle вместе с прежней исходной FileSystem. Передача самого
менеджера другому State не меняет владельца файлов и очистки.

FileSystem::supports_temporary_file_ownership имеет default false.
Это предварительная проверка перед BSL-созданием, не новое право по пути:
поддерживающий host обязан вернуть new_owned из create_temporary_file.
Прежняя низкоуровневая операция создания без права остаётся доступной;
SystemFileSystem до реализации безопасного токена не начинает создание
через новый BSL-метод. Такая проверка предотвращает создание бесхозного
файла с последующим отказом при регистрации. Нарушивший объявленный
host-контракт результат отвергается без удаления по строковому имени.

Закрытый реестр обнаруживается до вызова host. Если сам host реентерабельно
закрыл реестр во время создания, регистрация отказывает; открытый носитель
освобождается без удаления, как предписывает OpenedTemporaryFile. Это
ошибка host-контракта, не повод удалить неизвестный ресурс по пути.

## Дополнительные измерения параметров и доступа

Серверные file-temp-parameters и file-temp-visibility (2026-09-17) закрепляют
измеренные аргументы в delta. Нулевая длина, чтение/запись/позиционирование
и имя после закрытия подтверждены для 32 успешных вызовов; 38 ошибочных
аргументов отвергаются при вызове. Default и явные 65535/8192 дают одинаковые
наблюдения, но внутренний размер буфера из этого не выводится.

Файл.Размер видит длину записи сразу для 1/8/8191/8192/8193 во всех шести
настройках. Независимое BSL-чтение открытого файла при этом отвергается
совместным доступом, а после Закрыть разрешается. Поэтому простой открытый
std::fs::File ещё не является полной реализацией временного потока.
Механизм совместного доступа остаётся задачей стандартного host; произвольная
FileSystem не заменяется процессной. Это не разрешение вводить не измеренные
общие блокировки всех файловых API.

Граница безопасного системного удаления принята 2026-09-18:
пара inode-check/unlink имеет окно гонки. Подготовленный Linux-ресурс хранит
device/inode, отклоняет уже произошедшую подмену и создаёт файл с режимом 0600,
но это не закрывает окно между проверкой и unlink. Процессы того же Unix UID
считаются доверенными для этой политики. `SystemFileSystem` публикует
системное право очистки только на Linux; это не заявляет защиту от гонки
с доверенным same-UID процессом. Свидетельство измерений:
docs/research/compatibility/file-temp-parameters-server-2026-09-17.md.

## Завершение CLI и стандартный callback

Обычный запуск до этого вызывал process::exit при ошибке BSL с живым State,
обходя его Drop. Завершающий участок исходника сначала печатает/освобождает
результат, затем освобождает State, только потом разрешает выход процесса.
У байткода State уже освобождался при возврате из run; этот путь сохраняется.
Коды 0/1, прежние тексты ошибок и события exited/terminated не меняются.
Общий CLI-builder подключает прежний launcher и callback временных файлов.
Callback потребляет каждый зарегистрированный ресурс через remove, продолжая
пакет после отказа; первый отказ передаётся прежней диагностике State,
которая печатает только ErrorKind. Удаления по строковым путям здесь нет.

REPL не использует State: его Session при завершении сначала освобождает
сохранённые значения, затем закрывает свой реестр и вызывает тот же callback.
Окончание отдельной строки, включая ошибочную, реестр не очищает.
Каталоги не сканируются, аварийные остатки не подбираются.

Это подключение CLI к существующему host-протоколу. Пока SystemFileSystem
не выдаёт безопасный ресурс очистки, а CreateTempFile не реализован,
проверки вручную зарегистрированных host-ресурсов не доказывают очистку
временных файлов, созданных BSL. Эти части плана остаются открытыми.

Проверки этапа: оба новых теста сначала дали пустой список удалений, затем
прошли после подключения callback/Drop. Проверены исходный и загруженный
модули, успех/ошибка BSL, два разных отказа удаления и последующий успешный
ресурс, закрытый реестр, отсутствие повторного удаления и секретного пути
в диагностике. REPL отдельно проверяет освобождение значения перед удалением
ресурсов и сохранение ресурсов между успешной, ошибочной и следующей строками.

Первый полный прогон обнаружил ETXTBSY в system_application при запуске
свежей копии тестового executable; отказ воспроизвёлся в отдельной серии.
Подготовка двух Unix-тестов теперь использует ссылку на текущий executable
под прежним именем с пробелами/shell-символами, без записи в запускаемый файл.
Поведение launcher не менялось; 30 повторных прогонов прошли. После этого
прошли полный workspace, fmt, Clippy --all-targets, rustdoc с запретом
предупреждений, git diff --check и все 11 строгих проверок OpenSpec.
Логи — /tmp/open-bsl-cli-cleanup-*.log; неуспешный workspace сохранён отдельно
от успешного workspace-after. Новые BSL/Rust API и платформенный oracle
этим этапом не добавлялись; существующий тест API reference прошёл.

## Сеансовая передача владения очисткой

Нейтральный host-контракт `TemporaryFileResource` находится в bsl-rt:
путь служит описанием, а потребляющая операция remove реализуется создавшим
ресурс host и удаляет только его собственный объект. Освобождение самого
дескриптора не удаляет файл. Runtime не преобразует путь обратно в право
удаления и не подменяет исходный host текущей FileSystem.

`TemporaryFileRegistry` — локальный разделяемый учёт HostEnv, отдельный от
TempStorageSession. State предоставляет его host и принимает callback
через StateBuilder::temporary_file_cleanup. Явная cleanup_temporary_files
передаёт накопленный пакет, не закрывая сеанс; Drop State закрывает учёт
и передаёт последний пакет. Пустой пакет callback не вызывает. Без callback
удаления нет. После закрытия регистрация возвращает ресурс вызывающему,
не теряя владение. Пакет извлекается до callback, без удержания RefCell-borrow.
Callback получает владение пакетом и отвечает за ошибки отдельных файлов;
его итоговая ошибка пишется в stderr сеанса без изменения результата BSL.
Callback не должен паниковать, поскольку вызывается и при Drop.

Это независимый этап host-протокола: виртуальные тесты проверяют изоляцию,
подмену и переименование через идентичность ресурса, а не только имя.
Системный токен удаления, его защита от гонок и присоединение к
временному потоку остаются отдельными незавершёнными пунктами.
Стандартный callback CLI подключён отдельным этапом, описанным выше.
Проверка inode с последующим unlink
сама по себе не объявляется атомарной защитой от конкурентной подмены.

Проверки host-протокола завершены: шесть новых тестов, полный workspace
(включая plain/optimize, Connector, ZIP, потоки и задания), Clippy и rustdoc
с запретом предупреждений, fmt, регенерация API reference, git diff --check
и все 11 строгих проверок OpenSpec. Логи этого этапа:
`/tmp/open-bsl-temp-registry-{tests,workspace,clippy,doc,api}.log`.
Это проверка политики host, а не новый замер сроков очистки серверной 1С.

## Измеренный SetSize

УстановитьРазмер/SetSize регистрируется процедурой с одним аргументом.
Подготовка использует существующий строгий разбор неотрицательного целого,
а не преобразования индекса массива. Собственная память меняет длину Vec
с предварительным try_reserve; файловый носитель вызывает FileHandle::set_len.
Позиция этих носителей сохраняется, read-only и закрытый поток отказывают.

Буферный носитель заменяется существующим срезом через BuiltinMethod::BufSlice:
это сохраняет общую память, значение 0 означает остаток текущего диапазона,
а расширение за него отвергается. Исходный буфер и соседние потоки не меняют
свои диапазоны. После успешного сокращения позиция ограничивается новым
размером; если прежняя позиция была больше, возвращается ошибка уже после
изменения. Это измерено stream-resize-buffer, не общее правило отката.
Пустой буфер и `ЧтениеДанных.ИсходныйПоток()` измерены
отдельным `stream-resize-edges`: пустой буфер отвергает и 0, и 1,
а reader-прокси меняет тот же носитель. Предельные размеры, прочие
аргументы и точные ошибки остаются `STREAM.RESIZE_EDGES`.

## Изменение длины носителя

FileHandle::set_len(&mut self, u64) дополняет переносимый дескриптор для
будущего изменения размера временного потока. Default возвращает Unsupported
без I/O; std::fs::File делегирует собственной set_len. Это операция над
открытым носителем, а не над повторно разрешённым именем файла: путь не
передаётся, позиция не меняется. Контракт не зависит от решения о моменте
создания временного файла. Новых внешних зависимостей нет.
Это host-контракт Rust; BSL-метод и его преобразования аргументов требуют
своей платформенной проверки и этим этапом не вводятся.

Проверки этого этапа завершены: полный workspace, Clippy и rustdoc с запретом
предупреждений, fmt, git diff --check, регенерация API reference и все 11
строгих проверок OpenSpec. Логи —
`/tmp/open-bsl-handle-resize-{workspace,clippy,doc,api}.log`.

Применяется [общий дизайн серии](../archive/2026-09-18-extend-filesystem-operations/design.md)
в части «Временный поток и очистка». Локальные delta и tasks задают объём отдельной приёмки.
Перед независимым архивированием сохранить относящиеся решения здесь
и обновить ссылку, если общий дизайн уже перенесён в архив.

## Атомарное создание host-файла

Передача в учёт дополняет OpenedTemporaryFile необязательным
TemporaryFileResource. Новый new_owned получает открытый дескриптор и
host-ресурс, берёт описательный путь из самого ресурса: отдельной второй
строки, которая могла бы разойтись с ним, нет. Host гарантирует, что обе
возможности относятся к одному созданному файлу. into_registered_parts
передаёт ресурс реестру и лишь после успешной регистрации отдаёт поток
вызывающему. При закрытом реестре или отсутствии права очистки возвращается
вся исходная запись; дескриптор, позиция, данные и право очистки сохраняются.
Метод сам не вызывает ни файловые операции, ни удаление.

Прежние new/into_parts сохранены. new не выдумывает право удаления по пути;
into_parts сознательно не регистрирует ресурс и освобождает необязательный
дескриптор очистки без удаления. Drop всей записи также не удаляет файл.
Это host-протокол передачи, а не системный токен: SystemFileSystem пока
использует прежний new, и попытка зарегистрировать такой результат явно
возвращает запись. Привязка к временному потоку и системная очистка остаются
отдельными незавершёнными пунктами.

Этап передачи проверен пятью новыми host-тестами и прежними сценариями
атомарного создания/TEMP/TMP. Полный workspace, Clippy и rustdoc с запретом
предупреждений, fmt, регенерация API reference, git diff --check и все 11
строгих проверок OpenSpec прошли. Логи:
`/tmp/open-bsl-temp-transfer-{tests,workspace,clippy,doc,api}.log`.

FileSystem::create_temporary_file принимает 16 байт от существующего источника
случайности и возвращает OpenedTemporaryFile (путь и дескриптор). Конструктор
записи доступен виртуальным host; системный адаптер делает единственный
OpenOptions::create_new с чтением/записью и Unix-mode 0600. Генерация имени
общая с temporary_path, но резервирование с удалением не используется.
Коллизия передаётся вызывающему: host не берёт скрытую системную случайность.
Непредставимый UTF-8 путь отвергается до создания, чтобы не возвращать другой
путь через lossy-преобразование. Выбор TEMP/TMP остаётся общим и выполняется
для каждой операции. Новых внешних зависимостей нет.

В системном адаптере это пока только атомарное создание: результат без
права очистки не регистрируется в State. Путь сам по себе не защищает от
подмены. Идентификация системного ресурса и сквозная проверка подключённого
callback CLI остаются обязательной частью следующего этапа; пункт безопасности
системной очистки этим API не закрыт.

## Принятое решение после серверного замера

Проверка сроков жизни использует смешанный скрипт file-temp-return.bsl:
явный суффикс @onec-server-without-context действует и в клиентской async-
обёртке. Это исправление ранее описанной директивы генератора, не новый
контракт BSL. Создание выполняется на сервере, клиент читает существование
путей до следующего RPC; обычный контрольный файл проверяет общее пространство
localhost. Отдельный режим runner --observe-temp-lifetime снимает metadata
четырёх явно выведенных путей /tmp/v8_* после возврата ENTERPRISE и до LoadCfg.
Этот режим ничего не удаляет, не сканирует temp и не исполняет команды из вывода.
Снимок сохраняется отдельно от oracle; он уточняет границы наблюдения,
но не доказывает точный внутренний момент автоматической очистки 1С.

Реальный прогон 2026-09-15 сохранил все четыре файла после возврата серверной
функции, следующего вызова и перед выходом клиента. После ENTERPRISE, до
LoadCfg, все четыре отсутствуют, включая имя с отдельной записью. Закрытие
потока не равно удалению файла. Политика очистки при штатном выходе согласуется
с этой границей, но системный учёт только временных потоков был бы неполным.
Ошибка, отмена и убийство процесса не проверены этой пробой. Исходные выводы,
контекст и доказательства восстановления —
docs/research/compatibility/file-temp-return-server-2026-09-15.md.

Независимые снимки ОС в
docs/research/compatibility/file-temp-native-server-2026-09-09.md показали
создание файла до записи и до первого получения ИмяФайла. Пользователь
подтвердил немедленное создание: исходная модель «память до лимита →
host-файл» заменена в delta. Это не утверждение о внутренней буферизации
1С; значения и влияние параметров требуют своих измерений.
Работы по callback и идентификации собственных файлов от этого выбора
не освобождаются и завершёнными не считаются.
