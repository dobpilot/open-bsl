# Дизайн

## Отмена при отказе файлового host

Все ветви perform_file_operation возвращают Result общей завершающей
проверке отмены. Оператор ? не должен обходить эту границу на ошибках
создания, удаления или обхода. Внутренние проверки перед следующей операцией
сохраняются; отката уже выполненного I/O нет. Детерминированные host-тесты
разделяют вызов, побочный эффект, отказ и установку флага. Последующая
серверная проба подтвердила отсутствие отката при частичном удалении, а
OpenSpec фиксирует один снимок целей и последовательный `remove_path` без
повторного перечисления.

## Контекст отладочного evaluate

Отладочное вычисление использует тот же poll и DynamicImage, но временно
получает исходный AsyncState, корневое состояние, каталог и RuntimeShapes.
Выбранный кадр определяет программу, таблицу локальных и владельца модуля.
Готовая очередь остановленного исполнения сохраняется отдельно; граница
идентификаторов задач допускает во вложенный poll только задачи выражения.
Результат корня выражения завершает evaluate без ожидания созданных обещаний.
При возврате состояния и новые события передаются обратно даже при ошибке.
Ожидающие задачи старого исполнения не выполняются внутри evaluate.
Это уточнение собственного DAP-контракта open-bsl, не заявление о поведении
отладчика 1С. Второго исполнителя инструкций или формата байткода нет.

## Очередь ошибок async-процедур

file-begin-error-handlers подтвердил 12 вариантов: стандартный флаг async
передаётся по значению, синхронное исключение заменяет исходную ошибку,
async-исключение не опережает её. Дополнительный async-procedure-error-order
подтвердил общий порядок вне callback: вызывающий продолжается, прежнее
оповещение идёт до сообщения, добавленное после исключения — после него.
Оба сеанса localhost/test восстановили CF/БД и подтвердили XML.

Вместо немедленного возврата ошибки Detached-задачи планировщик помещает
ошибку в ту же FIFO, где находятся готовые задачи. Элемент ReadyEvent
содержит TaskId либо Box<RtError>: очередь обычных задач не расширяется
до размера самого RtError. StartAsync сохраняет приоритет пары ребёнок/
вызывающий до первого ожидания. Замороженный синхронный host-вызов по-прежнему
не пропускает чужие события, включая ошибки. Отмена и InvalidBytecode
не откладываются; при остановке всего execution очередь освобождается.

Первый Await синтетического чанка оповещения лишь извлекает результат
операции. Его успешный выход не добавляет второго оборота FIFO: доставка
обработчика сохраняет место уже готового события. Await в пользовательском
обработчике по-прежнему уступает очередь. Это проверяется префиксом native
async-procedure-error-order, а не выводом самого интерпретатора.

Новый механизм не добавляет GUI-продолжение после ошибки: open-bsl возвращает
первую доставленную ошибку и прекращает запуск. Async-функции по-прежнему
разрешают своё обещание. Изменений байткода, эффектов и горячего step нет;
производительность очереди не измерялась и улучшение не заявляется.

## Наблюдение необработанных клиентских ошибок

Native-runner получает явный флаг --observe-client-errors. Только этот
режим дописывает ОбработкаОтображенияОшибки во временный модуль приложения:
ошибка сохраняется в raw-вывод с client.error, стандартное отображение
отключается. Строки CR/LF экранируются, чтобы одна ошибка оставалась одной
строкой. Прежний startup и протокол резервирования/восстановления не меняются.
Это измерительная конфигурация, не добавление обработчика в исходную базу.
Принятие oracle требует отдельной проверки ожидаемого набора ошибок.

Проба file-begin-handler-kinds на localhost/test подтвердила синхронную
функцию, async-функцию/процедуру успеха и синхронную функцию ошибки.
Девять строк совпали с open-bsl; восстановление CF/БД/XML подтверждено.
Ошибки самих обработчиков и async-обработчик ошибки этим не измерены.

Проба file-begin-standard-flags с исправленным трёхпараметровым наблюдателем
подтвердила подавление для Ложь/0/"False" и сохранение исходной ошибки для
остальных восьми значений. finish использует существующий as_condition:
только успешное преобразование в false отключает стандартную обработку;
отказ преобразования не заменяет исходную ошибку. Прочие значения остаются
частью NOTIFY.DELIVERY_EDGES, без нового алгоритма булева преобразования.

Следующая успешная проба file-begin-handler-errors проверила исключения
шести обработчиков успеха. Синхронная процедура/функция и async-процедура
до/после Ждать сообщают ошибку приложению; async-функция оставляет её
в неиспользуемом обещании. Обработчик ошибки операции не вызывается.
В open-bsl это прежнее разделение Detached/Promise и обычный открытый вызов;
host получает исключение вместо UI 1С. Все 48 сочетаний совпали без нового
механизма доставки. Async-обработчик ошибки и его исключения ещё не измерены.

## Импортное окружение динамического фрагмента

Program сохраняет отдельную таблицу ModuleImport { alias, module }:
использованные LinkEntry не восстанавливают ни псевдоним, ни неиспользованный
импорт. Sema переносит объявленные пары в ResolvedProgram; кодоген и текстовый
формат сохраняют их. Формат 31 → 32: секция .imports перед .links,
строка `N module=M "псевдоним"`. Верификатор проверяет имена и цели,
граф циклов и eager-init учитывают также объявленные зависимости.

DynamicRequest заимствует только таблицу импортов текущего Program.
Фасад снимает экспортные сигнатуры ровно этих целей с собственного каталога
и передаёт их общему резолверу фрагмента. VM не зависит от фронтенда.
Прежний compile_dynamic_snippet сохраняется для окружения без импортов;
расширенный вход использует тот же алгоритм с явным окружением.

Фрагмент возвращает собственные LinkEntry. VM добавляет их после связей
окружающего Program, перенумеровывая только ссылки своего нулевого чанка
и ByRefImportedVar в его таблицах аргументов. Статические функции сохраняют
прежние номера, кэш фрагмента не зависит от накопленных связей родителя.
Таблица импортов наследуется на любой глубине. Проверки включают неполные
и испорченные таблицы, source/bytecode, plain/optimize, lazy/eager,
псевдонимы, затенение, чужой модуль и вызовы функций между фрагментами.
Отладочное evaluate остаётся отдельным открытым пунктом: его executor ещё
не разделяет полный каталог/планировщик остановленного исполнения.

Прямой async CallImported по-прежнему запрещён согласно прежнему
ограничению JOB.ASYNC.TARGET; импортное окружение не отменяет его.
Синхронная экспортная функция может вернуть обещание async-вызова через
ЭтотОбъект для ожидания снаружи динамической строки. Оба случая проверены.

## Согласованная ссылка на текущий модуль

Пользователь подтвердил ЭтотОбъект/ThisObject как ссылку на текущий
BSL-модуль. Здесь «BSL-модель» из ответа понимается как модуль, о котором
был вопрос. Это собственный контекст open-bsl, не эмуляция всех свойств
управляемой формы. Ссылка открывает экспортные процедуры и функции;
наличие метода проверяется без вызова, через существующий протокол объекта.
Имена и признак Экспорт берутся из Program.function_names/exported_functions,
а не из второй таблицы методов или повторного разбора исходника.

Владелец — экземпляр модуля исполнения, а не скомпилированный Program.
Вычислить/Выполнить продолжают контекст исходного модуля и не создают нового
получателя. Реализация должна сохранять состояние, тождество и правила
передачи аргументов при прямом вызове и доставке оповещения. BSL-обработчик
исполняется VM; файловый worker только сообщает результат. Существующий
блокирующий FunctionCaller для компонентных callback не считается готовой
реализацией неблокирующей доставки Begin.

Сначала проверяются тождество ссылки и ограничения экспортов, затем
доставка результатов и изменяемого флага ошибки, отмена и один worker.
Все проверки включают прямые/динамические обращения, plain/optimize и
текстовый байт-код. Решение согласовано, но реализация ещё не завершена.

Первый реализационный этап выполнен 2026-09-17: введены значение ссылки и проверка экспортов
конструктором оповещения. Тип open-bsl — МодульBSL/BSLModule, без публичного
конструктора; это не имя типа платформы 1С. Для чтения используется
ЭтотОбъект/ThisObject, также допустима нулевая функциональная форма, как
у других свойств глобального контекста open-bsl. Обычная локальная или
модульная переменная одноимённого написания сохраняет приоритет резолвера.
По последующему решению пользователя ссылка создаётся сразу вместе с
ModuleState и разделяется с динамическим фрагментом; временное пустое
состояние перестановки кадра не создаёт ссылку. Значение не удерживает
переменные модуля и не создаёт цикл владения.

Прежний открытый вызов терял режимы аргументов и пропуски:
CallObjectMethod хранил только диапазон готовых значений. До реализации
модульных вызовов представление расширяется общими режимами ArgMode,
с проверками образа, эффектами и round-trip. Первый этап не объявляет такие вызовы или
доставку Begin реализованными и не подменяет их блокирующим FunctionCaller.

Режимы открытого вызова передаются существующими ResolvedArg и ArgMode,
без параллельного списка булевых признаков. Значения по-прежнему вычисляются
в исходном порядке в окно аргументов. Индекс call_arg_modes сохраняет
возможные ссылочные цели и пропуски; длина набора задаёт размер окна.
CallObjectMethod требует результат, CallObjectProcedure допускает вызов
процедуры и игнорирование результата функции. Отдельный тег и удаление
избыточного count сохраняют размер инструкции восемь байт; дополнительный
Option<u16> рядом с прежними полями увеличивал его до двенадцати.
Новый тег добавлен в конце перечисления, без сдвига существующих тегов.
Для обычного компонентного метода окно остаётся
прежним, для модульного объявления Знач выбирает снятое значение, а не
повторное чтение переменной. Пропуск получает значение по умолчанию только
по контракту фактического метода; для обычного объектного обработчика это
прежнее значение Undefined. Закрытый доказанно ядровой вызов не меняется.
SSA закрепляет потенциально ссылочные локали; таблица эффектов учитывает
чтение/запись этих целей и модульных переменных, а вызов завершает бандл.
Формат повышается с 30 до 31. Верификатор проверяет индекс/длину режимов
и границы всех целей до исполнения.
Передача переменной неизвестному методу снимает доказательство её ядрового
типа: метод может перепривязать её по ссылке. Анализ намеренно консервативен,
поскольку окончательный вердикт по получателю вычисляется после обхода.

Нативный замер `structure-property-output-server` уточнил отдельный выходной
ABI `Структура/ФиксированнаяСтруктура.Свойство`: отсутствие поля пишет
Неопределено, литерал допустим, индекс массива получает значение. Компилятор
поэтому направляет обе формы `Свойство` через существующий открытый опкод.
Для индексной второй позиции он один раз вычисляет объект и индекс, сохраняет
их регистрами в новом `ArgMode::ByRefIndex`, а VM выполняет запись после
успешного вызова. Обычная/модульная/импортированная переменная использует
прежние режимы. Другие методы не получают выходную семантику по совпадению
арности. Текстовый формат повышен с 33 до 34; старый листинг отвергается,
размер `Instr` остаётся восемь байт.

## Исполнение модульного вызова

Этап 2026-09-17 устранил отдельный планировщик обычного динамического вызова:
его код исполняется кадрами исходного запуска, с теми же каталогом,
модульными состояниями, задачами и обещаниями. Динамический образ сохраняет
свою программу, кэши, формы и связанные таблицы до завершения использующих
его кадров, включая async-функцию после возврата самого фрагмента.
Локальные имена фрагмента связываются с ячейками вызывающего кадра;
новые локали принадлежат только фрагменту. Это не завершает перенос
текстового окружения импортов или отладочное evaluate.

Нативный dynamic-async-context подтвердил 18 наблюдений: прямой, динамический,
вложенный и открытый async-вызовы имеют один порядок; фрагмент не ждёт
дочернюю задачу, результат и ошибка повторно доступны через обещание.
Прежние тесты ожидания detached-задачи внутри Выполнить закрепляли ошибочный
join вложенного execution. Они заменены проверками явного ожидания функции
с сохранением локальных/модульных записей; порядок процедуры покрыт oracle.
Срок жизни DynamicImage определяется Rc кадров, а не накопительным списком
в execution. После последнего кадра освобождаются код, формы, кэши и таблицы.
Нулевой динамический чанк отличается от ленивого тела модуля при возврате
и разматывании. Статические скопированные чанки сохраняют links владельца;
новые имена импортов из текста пока не разрешаются.

Прежний DAP step-over сохраняется: крючок не вызывается внутри динамических
кадров или вызванных ими функций. Блокирующее отладочное evaluate использует
тот же подготовитель образа, но пока отдельный исполнитель и прежние
ограничения; его полное выравнивание остаётся открытым. Файловая host-парковка
по-прежнему замораживает execution для синхронного вызова. Это не join
асинхронных задач динамического фрагмента.

Отдельная проба dynamic-async-await выявила отказ платформы оператору
Ждать внутри динамического текста. Прежнее расширение компилятора open-bsl
не исправляется косвенно заменой планировщика; его согласование выделено
отдельной задачей. Успешный возврат обещания из Вычислить не доказывает
допустимость Ждать в самой строке.

Следующий этап реализован в compile_dynamic_snippet: обе ветви
с реестром и без него используют обычный синхронный резолвер фрагмента,
а нулевой чанк не наследует is_async. Ошибка резолвинга возникает до
установки кадра и любых записей. DynamicRequest.caller_is_async остаётся
сведением об исходном кадре для внешних компиляторов, не разрешением Ждать
для штатного фронтенда. Публичные низкоуровневые async-резолверы сохраняются
ради совместимости Rust API, но не используются штатным динамическим
компилятором. Проверяются четыре измеренные строки, RU/EN, оба пути
компиляции и прежние 18 наблюдений возвращаемых обещаний.

Подготовительный внутренний шаг отделяет принадлежащие запуску связанные
таблицы от заимствования RuntimeRegistry. LinkedComponents остаётся
заимствованным представлением реестра, а его таблицы/host-возможности имеют
разделяемого владельца без lifetime программы. Это позволяет сохранять
динамический образ между poll и в дочерней задаче, не копируя таблицы и не
удлиняя заимствование реестра. Проверяется отделение времени жизни и
сохранение общей ячейки кэша; публичный API и формат не меняются. Этот
внутренний рефакторинг сам по себе не меняет наблюдаемое поведение.

Измерение dynamic-local-exceptions подтвердило сохранение локальных записей
при исключении Выполнить. Пока динамика исполняется отдельным execution,
непойманная ошибка корневой задачи должна сохранять её стек для переноса
уже существовавших локалей владельцу. Это отдельное приватное состояние
ошибки, не успешный root_result; тот же перенос нужен после ошибки парковки
и вложенного фрагмента. Возврат результата/продвижение pc выполняются только
при успехе, затем прежний механизм обработчиков получает исходную ошибку.
Локаль, связанная со своим модулем, берётся из восстановленного ModuleState,
а не из корневого снимка: после возврата корня дочерняя задача ещё могла
записать в модуль. Этот выбор одинаков для успешного и ошибочного выхода.

Динамический кэш различает владельца модуля и идентификатор вложенного
фрагмента. В публичный нейтральный DynamicScope добавляется поле
`module: Option<ModuleId>`: None обозначает entry/самостоятельный модуль,
Some — модуль каталога. Program/Chunk и сериализованный формат не меняются.
Номер program по-прежнему выдаёт DynamicCompiler; ROOT означает статические
чанки именно выбранного владельца. LinkedComponents и продолжение
динамического исполнения сохраняют владельца при вложенности, даже когда
вложенный исполнитель использует собственный ROOT_MODULE. Номер каталожного
модуля больше не подставляется вместо номера фрагмента. Это исправление
контекста конфигурационного расширения open-bsl, не новая семантика 1С.

Прямые вызовы подключены к кадрам VM отдельным этапом. Владелец ссылки
ищется среди текущего состояния, root и экземпляров каталога по тождеству
уже созданного значения. Отсутствие владельца — ловимая ошибка, а не
восстановление завершённого сеанса. Экспорты и объявления параметров читаются
из Program/Chunk. Проверки предшествуют изменению pc и стека.
Обычные значения и Знач получают собственные слоты: окно открытого вызова
может быть перенаправлено оптимизатором на живую локальную переменную.
Локальные ссылки используют ParamSlot; модульные и импортированные —
существующую запись при возврате, с общим слотом повторного аргумента.
Запись при разматывании исключения использует тот же путь, что возврат.
Следующим этапом добавлена живая связь `(модуль, слот)` с активной ячейкой
стека: повторные/вложенные аргументы, чтение и запись модульных и импортных
переменных используют её. На границе переключения задачи ячейки публикуются
в ModuleState и обновляются при возобновлении. Динамический фрагмент
сохраняет одинаковые исходные ячейки локальных имён и связи со своим
модулем, включая исключение. Серверные пробы подтвердили 6 обычных и
7 динамических наблюдений; см. module-aliases-2026-09-17.md. Динамический
каталог и чужие аргументы фрагмента остаются незавершёнными; механизм
не объявляется полным покрытием ссылок.

Для обычного Call импортированная цель должна использовать уже существующий
ArgMode::ByRefImportedVar, без нового формата и API. До создания кадра VM
обеспечивает готовность всех затронутых модулей; повтор инструкции после
ленивой инициализации не должен повторять вход в вызываемую функцию.
Материализация использует ту же живую связь, что CallImported и открытый
вызов. Async-вызов сохраняет прежний снимок аргументов своей отдельной
задачи. Это согласование путей конфигурационного расширения open-bsl,
не утверждение о наличии импортируемых переменных общего модуля в 1С.

Этот путь реализован и проверен отдельным этапом. Подготовка владельцев и
чтение импортного аргумента общие для трёх видов вызова. При разматывании
ошибки ленивого тела обработчик владельца ищется у текущей инструкции:
инициализация не продвигает pc. Вычитание единицы остаётся только для
обычного вызова, который уже перешёл на следующую инструкцию.
Граница освобождения кадра Call/CallImported берётся до размещения новых
ячеек модульных аргументов: возврат и исключение сначала сохраняют запись,
затем удаляют эти ячейки вместе с кадром. Ячейка внешнего кадра при повторной
привязке остаётся вне освобождаемого диапазона.

Async-вызов создаёт обычную Task со снимками параметров и передаёт её
существующему StartAsync: она исполняется до первого уступающего ожидания.
step_cold возвращает необязательный TaskId, а не запускает вложенный
блокирующий драйвер. Каталог и entry сохраняют состояния при взаимных
вызовах. Обычный динамический фрагмент теперь использует те же задачи;
отдельный ProgramExecution остался у отладочного evaluate, не у RunDynamic.

## Арность Begin и подготовка значения

Доставка реализуется внутренней задачей существующего AsyncState. Нейтральный
HostPromiseSpawner получает отдельную регистрацию файлового оповещения:
готовый результат либо обычный FileOperationRequest с исходными ФС/зоной,
проверенное описание и признак наличия результата в успешных аргументах.
Default отвергает возможность до I/O; прежние реализации HTTP-only сохраняются.
CallContext не исполняет BSL-обработчик и не передаёт его в файловый поток.

VM готовит проверенный служебный кадр обычных Await/CallObjectProcedure/Return,
затем регистрирует запрос. Это повторное использование диспетчеризации,
арностей и ссылочных параметров, не второй callback-интерпретатор. Кадр
сохраняет программу владельца для обработчика текущего модуля и использует
общий каталог. Задача ставится в очередь без немедленного StartAsync.
Ошибка операции передаётся обработчику с отдельной ссылочной ячейкой флага;
её исходный RtError сохраняется в обещании независимо от исключений,
пойманных самим обработчиком. После обработчика Ложь завершает доставку,
иначе исходная ошибка возвращается host. Для CLI это обычная необработанная
ошибка, а не попытка воспроизвести модальное окно платформы. Ошибка самого
обработчика не становится повторной ошибкой файловой операции.

Кадр доставки владеет кодом через существующий DynamicImage и освобождает
его с последним кадром. Код сначала собирается клонированием программы
владельца с заменой нулевого чанка; оптимизация/кэш таких образов без
измерения не вводится. При отмене execution обработчик не запускается,
уже сделанный I/O не откатывается. Завершение корневого тела не теряет
живую задачу доставки; единственный worker может освободиться на Await.

у 1С не мешает true завершиться с 0; host пока сохраняет отказ для этого
случая, без молчаливого fallback. Shell-операторы не добавляются.

## Описание объектного оповещения

Конструктор и пять readonly-свойств регистрируются в базовом runtime.
Описание хранит BslValue получателей и дополнительных данных без копирования
графа; независимые экземпляры имеют обычное ссылочное равенство ObjectRef.
Арность задаётся существующим Arity::one_of(&[0, 2, 3, 5]). Имена сохраняют
исходное написание, поиск не исполняет метод и не проверяет будущие аргументы.

Для компонентного получателя используется ObjectProtocol::has_method.
Для базового объекта имя сначала разрешается единственной BUILTIN_METHOD_NAMES,
затем измеренная принадлежность метода типу определяется рядом с BuiltinMethod.
Списка RU/EN-имён в конструкторе нет. Принадлежность отражает измеренное
объявление метода, а не успех исполнения: обнаруженные пробелы обработчиков
коллекций должны оставаться отдельными незавершёнными задачами доставки.
Opaque-значение не материализует объект и не становится получателем только
из-за наличия сериализованного представления. Прочие непроверенные аргументы
и точные тексты диагностик регистрируются как открытый вопрос.

Отдельный клиентский oracle `notification-value-list-methods-client`
закрывает семь отсутствовавших пар методов СписокЗначений и полную арность
Добавить/Вставить. Эти методы реализуются в таблице компонентного типа, а не
дублируются в `BuiltinMethod`: диспетчеризация ОписаниеОповещения и обычный
вызов должны видеть одну таблицу. Удалить и Сдвинуть принимают ссылку именно
на элемент этого списка; Скопировать создаёт новые элементы, поэтому копия
не разделяет изменяемое состояние элемента с оригиналом.

У платформы чужой элемент обрабатывается непоследовательно: Индекс возвращает
-1, Удалить отказывает, а Сдвинуть для чужих элементов с позициями 0, 1 и 2
во всех трёх пробах сдвинул первый элемент получателя. Это сохранено как
измеренная совместимость, а не исправлено до более ожидаемого отказа.

Коллекция индексов таблицы реализуется компонентными объектами поверх той же
`ValueTableData`: отдельная обёртка свойства не создаёт отдельного состояния,
а элемент хранит стабильный id. Индексы пока описывают колонки и поверхность
объекта, но не вводят второй ускоряющий индекс строк: существующие Find/FindRows
остаются единственным алгоритмом поиска. Это наблюдаемо эквивалентно для
измеренных операций коллекции и не создаёт неподтверждённую оптимизацию.
Копия таблицы без непустого явного списка колонок клонирует описания с
новыми стабильными id; явный непустой список и `СкопироватьКолонки` их не
переносят. Это сохраняет измеренные тождество и независимость коллекций.

Отдельный индекс помечается внутренним типом, который конструктор оповещения
отвергает до поиска метода. Общий `ObjectProtocol` ради одного запрета не
расширяется; проверка остаётся рядом с известным компонентным типом.

Фиксированные структура и соответствие также живут как компонентные
объекты: их набор членов отличается от изменяемых `BslObject::Structure/Map`, а отдельные
варианты ядра раздули бы все исчерпывающие сопоставления. Конструкторы делают
мелкий снимок пар в порядке источника. Динамические readonly-поля структуры и
`Получить` соответствия читают этот снимок; мутации не имеют обработчиков.
Двухаргументная `Свойство` принимается с той же временной семантикой, что и
`Структура.Свойство`: точный выходной аргумент требует общего изменения ABI методов и не
выдаётся за закрытую совместимость.

Этот этап конструктора сам по себе не вводит ЭтотОбъект для CLI и не
запускает callback. Согласованный последующий этап ссылки на модуль описан
выше; владельца и доставку в VM ещё требуется реализовать.

## Динамический поиск у host-объекта

ObjectProtocol::has_method принимает только имя и по умолчанию использует
find_method_from_table. Новое переопределение не обязательно для существующих
реализаций трейта. Объект с динамической строковой диспетчеризацией явно
объявляет свои доступные имена; runtime не пробует call_method с пустыми
аргументами и не считает все имена доступными по наличию переопределения.
Host обязан сохранять проверку без побочных эффектов и согласовывать её
с вызовом; наличие метода не обещает успешный вызов с произвольной арностью.
Это Rust-контракт для будущих получателей оповещения, не новое измерение 1С.
Проверка не меняет текущий маршрут вызовов или кэш дескрипторов VM.

Проверки этапа: полный cargo test --workspace, Clippy с запретом предупреждений,
rustdoc с запретом предупреждений, регенерация API reference и все 11 строгих
проверок OpenSpec прошли. Логи — `/tmp/open-bsl-object-presence-{workspace,clippy,doc,api}.log`.
После полного прогона выполнено только форматирование двух сигнатур теста;
повторные method_lookup, fmt и git diff --check прошли. Это не закрывает
оставшиеся требования к объектам базового runtime и экспортам BSL-модуля.

## Доступ к массиву для объектных обработчиков

notification-array-insert 2026-09-16 дополняет измеренный контракт Вставить:
48 серверных случаев, RU/EN, расширение с Undefined, default значения,
усечение индекса и отказ в выражении до мутации. Обработчик добавляется
в существующий BuiltinMethod::Insert, без второй таблицы имён.
Подготовка индекса переиспользует array_method_index; другие строки и
предельные платформенные ограничения остаются ARRAY.METHOD_INDEX.
Перед resize/insert выполняется try_reserve для полного нового размера;
отказ не меняет массив. Это защита runtime, не измеренный предел 1С.

Для Insert в выражении sema сохраняет открытый CallObjectMethod с
result_required; runtime отвергает только массив. Вставка оператором
сохраняет прежний выбор закрытого пути, включая структуры/соответствия.
Формат байткода не меняется; plain/optimize/round-trip проверяют оба пути.
Наличие этого обработчика не означает готовности доставки Begin-callback.

Получить/Get и Установить/Set массива подготавливают индекс отдельно от
индексатора: Number усечён к нулю, Boolean становится 0/1, строка разбирается
существующим BslNumber::parse_canonical. Это последнее правило, прочие
дроби и точные ошибки остаются ARRAY.METHOD_INDEX до дополнительных проб;
форматированный разбор Число из VM не выдаётся за измеренную семантику индекса.
Чтение элемента выделяется из существующего индексатора, запись использует
set_index после подготовки. Сам [] остаётся неизменным.
Вызов Установить/Set сохраняет открытый CallObjectMethod, поскольку только
он уже несёт result_required. Для массива результат отвергается до записи;
компонентные получатели сохраняют собственные дескрипторы. Формат образа не
меняется. Это изменение маршрута проверяется plain/optimize/round-trip.

## Поиск компонентного метода

`find_method_from_table` возвращает ссылку на существующий статический
дескриптор по имени, используя folded_eq. Строковый call_method_from_table
и промах кэша VM используют этот же поиск. Кэш и проверка арности при
исполнении сохраняются. Функция не вызывает обработчик, не получает host
и не превращает свойство в метод. Это только компонентная часть проверки
получателя: базовые коллекции и экспорты BSL-модуля требуют продолжения.

## Непрерывные и раздельные арности

Для измеренной формы ОписаниеОповещения добавляется `Arity::one_of`
со статическим непустым строго возрастающим списком допустимых количеств.
Прежние `exact`/`range` и семантика `min`/`max` сохраняются; `accepts`
проверяет принадлежность набору, а не только его границы. Список не требует
новых зависимостей или выделения памяти при вызове. Неверный список
отвергается при создании дескриптора (в том числе const-инициализации).
`Display` представляет полный набор; генератор справочника использует
его для компонентных функций, конструкторов и методов. Регистрация самого
ОписаниеОповещения выполняется отдельно после определения ссылки на модуль.

Набор хранится статическим срезом рядом с границами: это увеличивает Arity
с 2 до 24 байт и MethodDescriptor на x86-64 с 40 до 64 байт. Контрольный
тест размеров обновляется вместе с этим явным решением. Выбрано простое
представление всех значений u8 без unsafe, глобального интернирования
или искусственного ограничения раздельных наборов малыми арностями.
Рост приходится на статические таблицы; отсутствие регрессии скорости
не утверждается без отдельного A/B. Сам формат байткода не меняется.

Применяется [общий дизайн серии](../extend-filesystem-operations/design.md)
в части «Асинхронные файловые операции». Локальные delta и tasks задают объём отдельной приёмки.
Перед независимым архивированием сохранить относящиеся решения здесь
и обновить ссылку, если общий дизайн уже перенесён в архив.

имеет тип Обещание. Это не переносит клиентскую доступность на сервер 1С.

## Межпоточная граница

Клиентский `file-delete-async-types.platform.txt` от 2026-09-10 подтвердил
18 случаев RU/EN: преобразования маски совпали с синхронным методом.
Подготовка использует тот же форматировщик на стороне VM до переноса
нейтрального запроса в поток. Даты, прочие объекты и ошибки форматирования
этой пробой не измерены; реестр вопроса сохраняется.

Обнаруженное при выполнении измерителя смешение таблиц форм динамического
фрагмента — исправление внутренней сборки Program, не новый формат или API.
Требование bytecode-image об отказе операнду за пределами своей таблицы
сохраняется. Статические формы остаются префиксом, формы фрагмента добавляются
после них с пересчётом только его NewStructure; проверка границ не отключается.

FileSystem в HostEnv остаётся Rc и не получает обязательных Send + Sync:
это сломало бы существующие однопоточные виртуальные файловые системы.
Вместо этого background_access возвращает необязательный Arc<dyn FileSystem
+ Send + Sync> того же пространства и полномочий. Системная реализация
предоставляет его явно; default None никогда не означает fallback к std::fs.

Поток файловой операции должен создавать итераторы и дескрипторы внутри себя;
гарантия Send для FileSystem не делает возвращаемые FileHandle или итераторы
переносимыми между потоками. BslValue и Rc также не передаются в канал:
объекты Файл создаются на стороне VM из нейтрального результата. Регистрация
и завершение используют существующую таблицу обещаний Execution, а не второй
event loop. Добавление background_access само по себе ещё не реализует
BSL-обещания, доставку ошибок, отмену или парковку VM.

## Поиск в Execution

Подготовленный FileSearchRequest содержит только строки и булеву рекурсию.
FileSearchPaths и FileSearchError переносимы между потоками; обход остаётся
единственным, общим с синхронным поиском и удалением. Ошибки ввода-вывода,
ресурсного лимита и отмены сохраняют разные классы. BSL-объекты создаются
из путей в VM с исходными Rc файловой системы и зоны, а не с подменённым host.
Неверные BSL-аргументы, отсутствие background_access и отказ создания потока
завершают уже созданное обещание ошибкой. Рабочий поток сообщает завершение
через существующий канал host-операций и будит драйвер Execution. Уничтожение
Execution выставляет отмену обхода; оно не ждёт блокирующую host-операцию.

HostCompletion и его mapper теперь различают HTTP и файловый поиск в одном
канале. HTTP-контракт, отменяемые handle и wake-up драйвера сохранены.
Паника файлового host перехватывается на границе фонового потока и завершает
обещание явной ошибкой без передачи payload в BSL: оставлять Pending после
исчезновения рабочего потока нельзя. Это защитное поведение host, не семантика 1С.

Формат инструкции CallBuiltin не изменялся: новые RU/EN-имена проходят
существующую таблицу BuiltinFn и текстовый lookup. За преобразование пути и
маски отвечает общий форматировщик `Строка`, за рекурсию — измеренный
`boolean_argument`; отдельного асинхронного белого списка типов нет.

Неблокирующее ожидание проверено также через настоящий JobRuntime с одним
worker и BackgroundStateFactory: поисковый job доходит до управляемого
read_dir, после чего другой job завершается до освобождения read_dir.
Проверены пробуждение от completion и отмена до возврата файлового I/O;
после отмены итератор не читает элементы. Это гарантия планировщика open-bsl,
не заявление о доступности асинхронного BSL на сервере 1С.

Создание/удаление/временный каталог присоединяются к тому же файловому
запросу и каналу завершений: FileOperationRequest и FileOperationResult
различают поиск, создание, удаление и временный каталог. FileSearchError
сохраняется как совместимый alias общего FileOperationError. Алгоритм выбора
удаляемых путей и формирование временного каталога общие с синхронным API.
Отмена не откатывает сделанное создание или удаление. Клиентский raw oracle:
tests/conformance/measure/filesystem/file-async-globals.platform.txt.

## Динамические файловые вызовы

Фрагмент сохраняет отдельный стек и прежнюю механику copy-back переменных,
но получает через внутренний HostIo заимствованного владельца файловых
обещаний внешнего AsyncState. Вложенные Вычислить/Выполнить передают того же
владельца, а не создают цепочку новых токенов. Только регистрация файловой
host-операции направляется владельцу: её поток, канал завершений, waker,
отмена и обещание живут во внешнем Execution. Внутренний drive не ждёт
файлового I/O и не уничтожает его handle при выходе из фрагмента.
Решение не меняет владение произвольными пользовательскими async-задачами
или HTTP-обещаниями, для которых требуется отдельная проверка динамического пути.

## Файловые обещания компонентных методов

CallContext предоставляет общий HostPromiseSpawner для HTTP и подготовленных
файловых запросов. Прежнее имя HttpPromiseSpawner сохраняется как alias;
добавленная файловая возможность имеет default-отказ без I/O, поэтому старые
HTTP-only реализации продолжают собираться. Запрос принимает исходные Rc
файловой системы и зоны объекта, не подменяя их сервисами вызывающего сеанса.
VM направляет файловую регистрацию внешнему владельцу динамического вызова,
а HTTP — прежнему локальному AsyncState. Ошибка подготовки запроса передаётся
как Result и сохраняется в обещании. Это расширение host-границы; само по себе
оно не добавляет BSL-методы Файл и не закрывает их приёмку.

## Чтение метаданных Файл

Восемь запросов чтения используют нейтральный FileMetadataQuery и передают
FileMetadata либо io::Error из фонового потока. Общий преобразователь результата
синхронного и асинхронного методов работает в VM с исходной зоной объекта.
FileOperationResult::into_value в этом ещё не принятом файловом API становится
fallible: ошибки отсутствующих атрибутов и диапазона даты должны завершать
обещание, а не превращаться в панику или выдуманное значение. Старый публичный
FileSearchPaths::into_value остаётся неизменным. Проверка отмены после metadata
сохраняется, даже если host вернул ошибку. Raw oracle — file-async-read.platform.txt.

## Асинхронная запись атрибутов

FileMetadataUpdate содержит только boolean атрибута или UTC-секунды даты.
Подготовка даты общая с синхронным setter и выполняется с исходной зоной
объекта до передачи запроса. Ошибка подготовки передаётся исполнителю как
Result и завершает обещание, а не выбрасывается из вызова метода. Запись
проходит через тот же файловый канал и background_access; отмена проверяется
после возврата host, в том числе при его ошибке, без отката записи.
Raw oracle — file-async-write.platform.txt. Инициализация остаётся отдельной
задачей: измеренная немедленная мутация пути не соответствует фоновому
созданию нового независимого Файл.

## Тождество инициализируемого пути

Поля пути Файл хранятся в общем Rc<RefCell<FilePath>>; identity_key использует
адрес этого состояния, а не текст пути. Нормализация общая с конструктором,
разделитель сохраняется при создании. Методы I/O копируют путь до вызова host,
не удерживая RefCell-заём во время внешнего кода или фоновой операции.
ready_file_promise регистрирует готовое BSL-значение в том же владельце
файловых обещаний без фонового потока и без Send для BslValue. Default
старого HTTP-only host явно отказывает. После принятия готового обещания
инициализатор меняет общие поля до возврата; отказ исполнителя не меняет путь.
Дополнительная клиентская матрица `file-initialize-arguments` подтвердила
единое правило `Строка` для структуры, соответствия, Файл, типа, системного
перечисления, двоичных данных, буфера, уникального идентификатора и описания
типов. Во всех случаях путь меняется до возврата обещания, а результат сохраняет
тождество приёмника. Поэтому отдельное предположение `FILE.INIT_ARGUMENTS`
больше не требуется.

## Мобильная библиотека в немобильном runtime

Тонкий клиент серверной базы распознаёт четыре мобильных члена `Файл`, но
в измеренном Linux-контексте три нуль-арных вызова и Begin с одним аргументом
отказывают непосредственно. Async-форма не возвращает обещание. Для Begin
документированная при начальной инвентаризации нулевая арность опровергнута:
платформа требует ровно один аргумент.

Имена и арности входят в общий `MethodDescriptor`; отдельный компонент
картинок или фиктивное значение не вводятся. Общий немобильный обработчик
возвращает ловимую ошибку контекста до обращения к host. Успешный мобильный
контекст остаётся `FILE.MOBILE_LIBRARY`: он требует модели картинки и
отдельной host-возможности, которых у Linux CLI сейчас нет.
