# Решения и последовательность исправления

## Основание

Источником ожидаемых результатов служит
`docs/research/compatibility/job-wait-2026-09-08/platform.tsv`.
`open-bsl.tsv` и `open-bsl-optimize.tsv` описывают текущее расхождение,
но не являются oracle. Замер проведён на серверной 1С 8.3.27.2342,
совместимость `Version8_3_27`.
Дополнительное основание отмены — `cancel-parent.platform.tsv` рядом с ним.
Согласованная цель — серверные 8.3 и 8.5; файловый режим исключён,
отдельный прогон на 8.5 не является условием приёмки.

## Сначала проверяемые тесты

Воспроизвести каждое расхождение на текущем коде. Для проверки состояний
использовать управляемые барьеры в тестовом сервисе и реестре, а не гонку
двух `sleep`. Длительность в платформенном TSV служит подтверждением причины
возврата, не точным эталоном для CI.

Проверки публичного BSL API должны проходить через настоящий `manager_wait`
и `job_wait`: сервисный unit-тест не проверяет подготовку аргументов и
снимков BSL-обёрткой. Проверить обычный foreground и worker-сервис с helping,
сохранив отсутствие тупиков при одном worker и вложенных заданиях.
Добавить прямой тест вложенного менеджерного ожидания: существующие
одно-worker тесты объектного метода не заменяют его.

## Обязательные уточняющие замеры

Матрица дополнена серверными замерами `followup.platform.tsv` и
`legacy.platform.tsv`; интерпретация и ограничения записаны в
`docs/research/compatibility/job-wait-2026-09-08/followup.md`.
Ниже перечислены вопросы, ради которых выполнялся контроль:

- Та же пара заданий с устаревшим `active` и со свежим `completed` снимком
  первого задания при активном втором, с таймаутом и без него. Текущий
  замер одинаково объясняется сравнением с входным снимком и возвратом при
  наличии любого завершённого задания. Обобщение пока не доказано.
- Аналогичные пары с ошибкой и отменой; все задания уже завершены;
  повторное ожидание массива, возвращённого предыдущим вызовом.
- Отмена ожидаемого задания отдельно от уже измеренной отмены родителя.
- Отрицательные таймауты менеджера на двух заданиях разной длительности:
  одноэлементный замер не различает первое завершение и ожидание всех.
- Объектные и менеджерные вызовы старого `ОжидатьЗавершения`: сигнатуры,
  наличие возвращаемого значения, таймауты и результаты окончания.
- Точность дробных секунд и поведение на границе субмиллисекундных значений.

Дополнить delta результатами этих замеров до соответствующей реализации.
Не выбирать между объяснениями по результатам самого open-bsl.

## Менеджерное ожидание

Контроль показал: входное состояние снимка не определяет возврат.
Условие — пустая группа либо наличие любого текущего конечного состояния.
`Queued` и `Running` эквивалентны публичному активному состоянию.
Одна общая проверка условия завершения нужна обоим
путям — `JobRuntimeShared::wait_first_change` и
`WorkerJobService::wait_first_change`.

Убрать зависимость условия изменения состояния от наличия таймаута.
Дедлайн ограничивает ожидание, но не определяет, сколько заданий требуется
дождаться. Сохранять свежие снимки под финальным локом, порядок и количество
элементов результата и существующие проверки закрытия runtime/истории.
Служебные уведомления о старте worker можно сохранить: проснувшийся поток
должен перепроверить публичное состояние и продолжить ожидание.

Тест `a_queued_to_running_transition_wakes_the_manager_wait` сейчас требует
прежнего публично неверного результата. Заменить его проверкой, что один
только внутренний старт не завершает BSL-ожидание, а конечное состояние
завершает. Сохранить тест отсутствия периодического опроса.
Также исправить подготовку теста
`the_documented_manager_surface_works_end_to_end` в `configuration.rs`:
он использует менеджерный метод без таймаута как ожидание всей группы.
После правки этот приём становится гонкой; для подготовки проверки отбора
нужно явно дождаться всех заданий.

Публичные `JobRuntime::wait_terminal` и `BackgroundJobService::wait_terminal`
сохраняют ожидание всех ID. Изменение BSL-менеджера не переносится на них.
Документированный контракт публичного `BackgroundJobService::wait_first_change`
обновляется вместе с его реализациями и отражается в описании изменения API.

## Таймаут

Убрать требование целочисленности. Использовать существующий `bsl-number`
и `std::time::Duration` для перевода секунд с дробной частью. Ноль означает
опрос; отсутствие аргумента и `Неопределено` — отсутствие дедлайна.
Для отрицательных значений предлагается отсутствие дедлайна, согласующееся
с измеренными `-1` и `-0.2` (оба дождались завершения).

Округление дробных секунд уточнить платформенным замером. Экстремально
большие значения не блокируют приёмку при явном оформлении оставшегося
вопроса: маркер, запись реестра, ровно одна измерительная строка по AGENTS.md
и отдельная задача. Проверить оба предела — перевод в `Duration` и сложение
с `Instant`; непредставимый дедлайн не должен приводить к панике.
Не менять `JOB.WAIT.NEGATIVE` задним числом: прежний вывод «вернулось»
оставить как историческое свидетельство, добавить содержательную пробу
с временем и состоянием и связать новый комментарий с новым результатом.

## Аргументы и устаревшее имя

Первый аргумент менеджера — только массив; каждый элемент должен быть
фоновым заданием. Пустой массив допустим. Ошибки сравнивать по наличию и
категории, а не по локализованному полному тексту.

До изменения обработчиков проверить старый `ОжидатьЗавершения`: сегодня
дескрипторы направляют оба имени в одну функцию, хотя справка показывает
разные сигнатуры. При необходимости разделить маршруты, согласовав отдельные
сценарии с платформой. Исправление старого имени входит в эту работу;
не оставлять его просто неподтверждённым синонимом. Изменение дескрипторов
требует регенерации API reference.

## Отмена ожидающего родителя

На платформе отмена родителя А прервала ожидание при ещё активном ребёнке Б
во всех десяти пробах. Б затем завершился самостоятельно. В финальных
сообщениях А отсутствуют маркеры после ожидания и из обработчика исключения;
в контролях без отмены маркеры после ожидания присутствуют.

`Отменить()` вернулся за 0–1 мс, состояние изменилось позже. Нельзя требовать
синхронной отмены или превращать наблюдаемые 2–3 секунды в константу.
Тест должен показать, что А отменяется при ещё удерживаемом активном Б,
не выполняет следующий BSL-оператор, а Б не отменяется автоматически.

Сначала воспроизвести это на open-bsl через публичные BSL-вызовы.
Если отмена теряется внутри helping, передать состояние отмены ожидающего
родителя в цикл и завершать его через существующий путь отмены VM, сохранив
обслуживание ребёнка и припаркованных операций. Проверить объектный и
менеджерный пути с таймаутом и без него при одном и нескольких worker.
Реализацию вынести в отдельный коммит в рамках того же изменения.

## Завершение

Для старого API требуется различать вызов-процедуру и выражение до входа
в обработчик. `MethodDescriptor` получает признак процедуры, а
`CallObjectMethod` — операнд `result_required`. Только внешний вызов
оператора получает `false`; получатель и аргументы по-прежнему вычисляются
как выражения. VM отвергает процедуру в выражении до проверки арности.
Текстовый формат байткода повышается с 29 до 30, round-trip сохраняет
новый операнд. Эффекты инструкции не меняются: регистр результата остаётся.

Старый обработчик использует последовательность `wait_first_change` с
единым бюджетом времени. После каждого возврата он сначала проверяет сбой
или отмену, затем исключает успешно завершённые задания из ожидаемой группы.
Пустая группа означает успех; активные задания по истечении бюджета — ошибку.
Таким образом, завершённый элемент не вызывает цикл немедленных возвратов,
а сбой другого элемента не скрывается ожиданием одного выбранного задания.

Отмена ожидающего worker передаётся через отдельный публичный
`HostErrorCode::Canceled`; `HostError::raise` преобразует именно этот код
в неловимый `RtError::Canceled`. Сервис хранит ID своего родителя и проверяет
его запрос отмены под локом реестра в условии helping и после возврата.
Это не отмена ожидаемых ID и не изменение join-all контракта `wait_terminal`.

После реализации заново исполнить общий BSL-скрипт в обеих средах, включая
`--optimize`; все измеренные расхождения должны исчезнуть. Проверить также
`background_jobs` с ожиданием отдельных объектов: такой benchmark должен
продолжать дожидаться всей группы. Затем выполнить проверку формата, Clippy,
workspace tests и регистр измерений. Публиковать delta в основных specs и
архивировать предложение только после завершения реализации и проверки.
Зелёные существующие тесты сами по себе не закрывают новые расхождения.
Неизмеренные правила истории и закрытия runtime проверяются как сохранение
действующего контракта open-bsl, без заявления о доказанной идентичности 1С.
