# Design

`ConfigurationCodeSnapshot` is an immutable catalog of the configuration identity, logical modules, their kinds and owners, import relationships, and one final source body per module. It contains no connection, credentials, database session, parser state, or provider-specific resource representation. A build selects exactly one code loader for the complete snapshot; modules from database, XML, and EDT sources are never mixed.

The one-source rule applies only to BSL code. The ORM metadata catalog and live data access are separate inputs to `SessionFactory`. They may come from an information base while the code snapshot comes from a future XML or EDT loader. The factory checks their configuration identities and module-owner links once; it does not require the inputs to share a physical provider.

`bsl-config-db` consumes a combined acquisition from `open-sdbl-db`: every reassembled `Config` resource, active-extension resources, `MetadataSnapshot`, and the existing resolution report are obtained in one bounded read-only acquisition. The complete resource set is broader than the bare-GUID and `.1c`/`.9`/`.7` subset selected by the current metadata-only pipeline. The first loader can reduce an active extension only when every extension resource is a direct replacement for an existing numbered source resource; it applies those replacements in platform order. A structural extension, a new resource, or unknown activity is an error naming that extension. This narrow supported form still emits one effective module graph and never presents base sources as effective when it cannot apply the extension.

The neutral snapshot already records the execution attributes of every common module. `SessionFactory` maps those attributes to the existing open-bsl module catalog instead of rewriting BSL source. A non-global common module is visible through its configuration name; exports of a global common module are visible as bare calls. Session and manager modules stay private catalog entries and are entered through the existing host and manager bridges.

The serialized common-module descriptor does not use the XML property order. After its version and identity fields, positions 2 through 9 are `ClientManagedApplication`, `Server`, `ExternalConnection`, `Privileged`, `Global`, `ClientOrdinaryApplication`, `ReturnValuesReuse`, and `ServerCall`. The loader combines the two client flags and does not expose the reuse policy. This order is kept in one decoder and covered by a fixture that makes the positions distinguishable; treating position 2 as `Global` incorrectly turned ordinary client-capable modules into global modules and produced false duplicate-export failures on the authorized `unf` snapshot.

The open-bsl linker therefore indexes every module's exported declarations before it resolves any module body. This is the same existing compiler and VM with a complete static catalog, not a second resolver. It lets two configuration modules refer to each other without making source order an accidental compilation restriction. Explicit file-loader imports retain their current behavior. A module's own declaration keeps its existing priority over the configuration-wide global surface; duplicate bare exports from different global modules are rejected while the engine is built.

The declared-import row in bytecode carries whether an imported module contributes bare global exports. This bit is compile-time context for dynamic snippets; statically resolved calls still use the existing link table. The text format version is advanced rather than guessing the missing bit while reading an older image. Import cycles are valid declaration graphs; initialization still detects an actual recursive attempt to execute a module that is already being initialized.

The combined acquisition is a requested upstream change documented in `docs/plans/open-sdbl-configuration-acquisition-request.md`. It reuses the existing provider queries, part assembly, limits, metadata pipeline, and extension store support. `open-sdbl` remains unaware of BSL module formats. There is no configuration fingerprint check when a session is opened. Updating a base requires the host to load a new snapshot and build a new session factory.

`bsl-config-xml` and `bsl-config-edt` contain crate documentation describing their future responsibility. They expose no loader that always fails, add no CLI options, and initially have no dependencies. Their future implementations must produce the same `ConfigurationCodeSnapshot` contract.
