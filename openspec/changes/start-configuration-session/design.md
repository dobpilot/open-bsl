# Design

`SessionFactory` owns a compiled open-bsl engine, one `ConfigurationCodeSnapshot`, and an immutable ORM metadata catalog produced at acquisition time. The two snapshots may come from different physical sources. It performs compatibility checks once: the code and metadata identify the same configuration, and every linked manager module names an object present in the metadata catalog. Extra database metadata is allowed. The factory does not re-read or hash `Config` for every session; after a configuration update the host builds a new factory.

The session startup handler executes in the server compilation context for web-client, thin-client, and background-job Sessions. The factory therefore includes server common modules and server-side private modules in its open-bsl catalog, and excludes common modules that are client-only or external-connection-only. Duplicate global exports remain an error within the selected server catalog; declarations in mutually exclusive execution contexts never enter that conflict set.

`bsl-session` enables the standard component set through the `open-bsl` facade while compiling the original configuration graph. It does not depend on `bsl-http`, `bsl-xml`, or another component crate directly. This lets an otherwise unrelated server module use an already supported platform constructor without forcing `bsl-session` to duplicate the component or teach the configuration loader about BSL reachability.

The factory names the session module as the compilation root through the `open-bsl` facade. The facade parses the selected server catalog to obtain its declaration surfaces, then uses the existing semantic resolver's imported-symbol links to find the transitive static closure and compiles only that closure. Explicit imports are retained even when the source has no static reference because they define the environment of dynamic snippets. With no roots the facade preserves its current whole-catalog behavior. Root selection belongs to `open-bsl`: `bsl-session` neither scans BSL text nor implements a second resolver.

Global-export conflicts are checked before root pruning. A configuration cannot make an ambiguous bare name acceptable merely because the current startup path does not call it. An unknown root is a build error. Syntax is still parsed while declaration surfaces are collected; root selection isolates resolution and code generation of unrelated bodies, which is the phase that currently rejects supported configuration startup because of an unrelated unresolved platform name.

Each `Session` owns one open-bsl `State`, session module instances, session parameters, execution modes, a frozen principal description, and one live database connection. Database statements use the existing bounded read-only `READ COMMITTED` operations of `open-sdbl-db`; no transaction spans the lifetime of the BSL session. A failed connection, compatibility check, or startup handler returns an error and no usable partial session.

`ТекущийРежимЗапуска()` is derived from the explicit session kind. Web-client and thin-client sessions execute managed application code and return `РежимЗапускаКлиентскогоПриложения.УправляемоеПриложение`. A background-job session returns `Неопределено`; this result was measured inside a real background job on platform 8.3.27.2342 by `measure-session-current-run-mode.bsl`.

The host supplies one non-empty platform version when it constructs `SessionFactory`. The factory stores the string once and every session exposes it through a newly constructed `СистемнаяИнформация` value. The runtime does not substitute the open-bsl crate version or query the database on every session open.

The principal is selected from `v8users` by case-insensitive name or GUID. Only a user with at least one enabled authentication method is selectable. With one selectable user the CLI may choose it automatically; with several it requires `--principal`; with no `v8users` rows it constructs the platform empty user and applies the configuration's main roles. The description is frozen at session creation. Temporary authentication locks are outside this testing host.

The required upstream `open-sdbl` user model must decode every authentication method supported by the selected platform family and expose whether at least one method is enabled. `AdmRole` remains separate from object roles and does not grant unrestricted application data access.

`bsl-orm` owns configuration metadata and data-facing platform objects; it does not load BSL source. The initial surface is the one recorded in `docs/research/session-module-runtime-surface-2026-09-21.md`. It includes the global `РольДоступна`/`IsInRole` function, accepting a role name or metadata role object and answering from the frozen principal's roles. Unknown roles and invalid argument types are errors. Unsupported platform members fail explicitly with their BSL name.

The ORM catalog stores the configuration compatibility mode as a typed immutable value. `Метаданные.РежимСовместимости` returns that value, while `Метаданные.СвойстваОбъектов.РежимСовместимости` returns an indexed metadata-property object rather than the generic runtime enum metatype. The platform measurement exposes its type as `Metadata object enumerated property`, its presentation as `MetadataObjectsPropertyEnumed`, every member value as `Compatibility mode`, and the measurement configuration as `DontUse`. The property object accepts the documented Russian and English member names. This change does not add `РежимСовместимости` as a library global or make either language spelling resolvable through `Тип(...)`, because the real platform rejects all three forms.

`bsl-session` owns the session-parameter container and session lifecycle. It composes `bsl-orm` with the existing open-bsl engine; neither crate implements a second parser, resolver, compiler, VM, or BSL object model already supplied by the facade. Only names and members required by the measured `demo`, `buh`, and `unf` startup paths enter this change.

The immutable ORM catalog also records the complete configuration-extension view obtained during configuration acquisition: database extensions, the applied and disabled subsets for the session, and application issues. `РасширенияКонфигурации` reads only that snapshot. An explicitly complete empty snapshot produces empty arrays; absent or incomplete extension information is an error, so unavailable acquisition data cannot masquerade as a base without extensions. The source and scope system enums remain runtime values supplied by `bsl-rt`, while the extension objects and manager belong to `bsl-orm`.

`--config-db` is an additive CLI modifier. Without it, script execution, commands, debugging, optimization, bytecode operation, and the REPL behave exactly as before. With it, the CLI loads the database configuration, selects the principal, starts a configuration session, and executes the supplied test script in that context. `--principal` is invalid without `--config-db`.
