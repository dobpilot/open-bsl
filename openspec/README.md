# OpenSpec в open-bsl

`openspec/specs/` содержит действующий проверяемый контракт, а
`openspec/changes/` — предлагаемые изменения. Документы в `docs/` объясняют
архитектуру, API, планы и результаты исследований; OpenSpec не заменяет их,
а фиксирует наблюдаемое поведение и критерии приёмки.

## Когда он обязателен

До правки кода нужно проверить действующие `specs/` и незавершённые
`changes/`. Новый или изменённый CLI-контракт, публичный Rust либо BSL API,
поведение языка и runtime, сериализованный формат, обещание совместимости или
архитектурная граница требуют change до реализации.

Новый change не нужен для исправления уже специфицированного поведения,
внутреннего рефакторинга без наблюдаемого эффекта, теста и механической правки
документации. Основание — существующая спецификация или это исключение —
фиксируется в рабочем плане, чтобы решение не осталось неявным.

## Рабочий цикл

1. Создать `openspec/changes/<имя>/proposal.md`.
2. Описать изменение требований в `specs/<возможность>/spec.md` и технические
   решения в `design.md`.
3. Разбить реализацию и проверки в `tasks.md`.
4. После реализации и ревью слить требования в `openspec/specs/` и перенести
   change в `openspec/changes/archive/YYYY-MM-DD-<имя>/`.

Формат совместим с OpenSpec `spec-driven`. CLI не является зависимостью
Rust workspace. При желании его устанавливают отдельно:

```bash
npm install -g @fission-ai/openspec@latest
openspec validate <имя-change>
```

Глобальная установка меняет окружение разработчика, поэтому репозиторий её
не выполняет и не хранит собственную копию Node-зависимостей.
