Реализация в целом сильная: эталон снят платформой и совпадает построчно,

## Блокирующий дефект: паника в `Инвертировать` на огромном `Количество`

- **Файл:** `crates/bsl-rt/src/binbuf.rs:686` — `if p + c > total {`.
- **Симптом (воспроизведён):** скрипт

  ```bsl
  Б = Новый БуферДвоичныхДанных(4);
  Попытка
      Б.Инвертировать(1, 18446744073709551615);
  Исключение
      Сообщить("поймано");
  КонецПопытки;
  ```

  в debug-сборке роняет процесс: `panicked at crates/bsl-rt/src/binbuf.rs:686:16:
  attempt to add with overflow` (проверено запуском `cargo run -p bsl-cli`,
  выход 101). `Попытка` бессильна — это паника, а не `RtError`. В release
  переполнение молча заворачивается (`1 + usize::MAX -> 0`), проверка
  `0 > total` пропускает, и падает уже срез `d.bytes[1..0]` — тоже паника
  (это выведено по коду, отдельным release-прогоном не подтверждалось;
  debug-паники для вердикта достаточно).
- **Нарушенные ворота:** стандарт «никаких новых паник на пользовательском
  вводе»; обещание самого плана в APPROACH («никаких unwrap/паник на
  пользовательских данных»); пункт ACCEPTANCE «границы (ошибки — ловимые
  RtError)» — команда `cargo test -p bsl-rt binbuf` зелёная, но именно этот
  граничный случай ею не покрыт, то есть критерий выполняется вакуумно.
- **Причина и исправление:** соседние `read_int`/`write_int` (`binbuf.rs:378,421`)
  и `bitwise` (`binbuf.rs:640`) для той же проверки используют
  `p.checked_add(..).ok_or(RtError::BadIndex)?` — `invert` единственный
  остался с голым `p + c`. Исправление зеркальное: `let end =
  p.checked_add(c).ok_or(RtError::BadIndex)?; if end > total { ... }`.
  Плюс юнит-тест-регрессия: `invert(&b, &[num(1), dec("18446744073709551615")])`
  обязан вернуть `Err`, а не уронить процесс. Остальные методы я проверил на
  этот класс входа — `checked_pos` глотает огромные позиции корректно,
  переполнение только здесь. В фикстуру случай не вносить, пока не измерено,
  что платформа на нём не уносит сеанс (как с записью байта вне 0..255).

## Замечания без блокировки (на решение следующей итерации/арбитра)

1. **Маркеры `НЕ ИЗМЕРЕНО` не заведены** на неизмеримые случаи (запись байта
   вне 0..255 уносит сеанс платформы). Рационально обосновано: строка `М()`
   в `measure-all.bsl` убила бы весь сеанс замеров; выбор задокументирован в
   трёх местах, реестровый тест зелёный. Формально дисциплина требует
   маркер — нужен механизм «неизмеримо данной оснасткой», это честно
   заявлено в PROGRESS.md.
2. `Б[-0.9]` читает байт 0: усечение применяется до проверки знака. Для
   положительных дробных усечение измерено, для отрицательных — нет; узкий
   неизмеренный край, стоит будущего замера.
3. Имя «Установить» теперь резолвится для любого получателя: `Массив.Установить`
   перестало быть ошибкой компиляции и стало ловимой рантайм-ошибкой. Сам
   метод массива как не был реализован, так и не реализован (давний пробел,
   вне рамок задачи) — просто фиксирую сдвиг момента ошибки.

Итог: после замены `p + c` на `checked_add` в `invert` и регрессионного
юнит-теста задача готова к PASS — остальное выдержало и ворота, и
адверсариальные пробы.
