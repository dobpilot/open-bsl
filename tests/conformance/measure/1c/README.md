# Платформенные измерители

`run-on-1c.sh` — существующий runner одноразовой **файловой** базы.
Его результат не подтверждает поведение серверной `localhost/test`.

## Серверная localhost/test без Unica

`run-on-server-1c.py` использует установленный `1cv8` напрямую. Требуются
работающий кластер, пустые учётные данные базы, DISPLAY и предварительное
разрешение менять её конфигурацию. Runner не запускает службы. На время
прогона исключите параллельное редактирование конфигурации: повторная
XML-проверка перед загрузкой не заменяет блокировку других редакторов.

Пример после получения разрешения:

```sh
python3 tests/conformance/measure/1c/run-on-server-1c.py \
  tests/conformance/measure/filesystem/file-globals.bsl \
  --marker globals-1 --allow-config-mutation
```

Цель фиксирована: `/S localhost/test`. `--platform` (или ONEC_PLATFORM)
задаёт бинарник; по умолчанию используется 8.3.27.2342. `--timeout` ограничивает
каждую native-команду, по умолчанию 120 секунд. ONEC_SHIM указывает существующий
каталог библиотек wk41; runner не создаёт и не меняет установку платформы.
Обычные скрипты оборачиваются серверной процедурой, async-объявления —
клиентской, как в существующем `gen-form-module.py`. Скрипт обязан вывести
одну пару `file.begin`/`file.end` с переданным marker. Клиентский async-скрипт
сам завершает работу системы. Скрипты с отдельным внешним наблюдателем
не запускайте этим способом без подготовки соответствующего наблюдателя.

Runner создаёт приватный каталог `/tmp/open-bsl-server-measure-*` и не
удаляет его. При разных UID параметр `--server-user` (по умолчанию usr1cv8)
предоставляет серверу через `setfacl` только проход к `io/` и доступ внутри
него. CF и каталоги XML остаются приватными; мир не получает права записи.
Необходим `setfacl` и поддержка POSIX ACL временной файловой системой.

Состав артефактов:

- `original.cf`, `original-xml/` — свежие резервные копии до изменения.
- `before-load-xml/`, `probe-xml/` — проверка перед загрузкой и подготовленная конфигурация.
- `io/platform.raw.txt` — исходный вывод, включая неуспешную пробу.
- `restored-xml/`, `restoration.txt` — результат подтверждённого восстановления.
- `platform.txt` — нормализованный вывод только после успешного замера **и** восстановления.
- `*.log`, `*.process.log` — логи каждого шага платформы и процесса.

После начала загрузки даже её ошибка приводит к попытке восстановить CF,
обновить конфигурацию БД и сравнить XML. Игнорируется только корневой
`ConfigDumpInfo.xml`. Ошибки подготовки/очистки пробы и неполные маркеры
не считаются успехом, даже если native вернул 0. При ошибке пробы наличие
`restoration.txt` отдельно подтверждает восстановление; `platform.txt`
в этом случае отсутствует. Общий `platform.tsv` и oracle репозитория
runner не перезаписывает: проверенные результаты переносят отдельно.

Для проб необработанных ошибок callback предусмотрен явный
`--observe-client-errors`. Только в этом режиме временный модуль приложения
получает `ОбработкаОтображенияОшибки`: он пишет `client.error` и описание
в raw-вывод, экранируя CR/LF, и отключает стандартное модальное отображение.
Обычный режим не меняется. Этот флаг не означает успешность пробы: нужно
проверить ожидаемые ошибки, полноту наблюдений и восстановление; маркеры
и запрет `file.setup_error`/`file.cleanup_error` остаются обязательными.
Сами callbacks и их ошибки не перехватываются добавленным кодом формы.

SIGINT/SIGTERM и таймаут останавливают дочернюю группу native до попытки
восстановления. SIGKILL и авария машины не перехватываются. После них,
а также при сообщении «ВОССТАНОВЛЕНИЕ НЕ ПОДТВЕРЖДЕНО», не начинайте новый
замер: сначала убедитесь в остановке предыдущего native-процесса, восстановите
`original.cf` через `/LoadCfg` и `/UpdateDBCfg`, затем выгрузите XML и сравните
с `original-xml/`. Резервные копии не удаляйте до подтверждения восстановления.
Побайтная сверка XML не является проверкой всех данных информационной базы.

## Проверки runner

```sh
python3 -m unittest discover -s tests/conformance/measure/1c -p 'test_*.py'
```

Проверки используют двойник native-команд, собственные временные файлы и
специальный дочерний Python-процесс; настоящая 1С не запускается. Для проверки
ACL нужны `setfacl`/`getfacl`; в user-namespace-песочнице назначение ACL другому
UID может отклоняться. В таком случае тест запускают вне этой песочницы,
не заменяя его пропуском. Offline-тесты не доказывают, что подготовленный XML
принимается конкретной установленной версией 1С: реальная приёмка runner
выполняется отдельно. Первый реальный round-trip и смешанная проба срока жизни
подтверждены 2026-09-15 на 8.3.27.2342:
[отчёт](../../../../docs/research/compatibility/file-temp-return-server-2026-09-15.md).

Для file-temp-return.bsl предусмотрен `--observe-temp-lifetime`: runner
сохраняет `host-after-enterprise.tsv` после выхода клиента и до LoadCfg.
Наблюдаются только четыре уникальных пути lifetime.path.closed/released/open/name
с родителем /tmp и префиксом v8_. Это read-only наблюдение, не автоочистка.
Если сервер запущен напрямую от текущего пользователя, укажите его через
`--server-user`, например `--server-user kan`; статус default-службы не
определяет пользователя или наличие такого прямого запуска.

Для клиентских проб относительных путей предусмотрен явный
`--enterprise-cwd-in-io`. Только процесс `ENTERPRISE` запускается из
приватного `io/enterprise-cwd`; Designer и серверный `rphost` не меняют cwd.
Каталог и все оставленные в нём объекты сохраняются среди артефактов. Флаг
не доказывает серверную семантику относительного пути и не применяется к
обычным измерениям автоматически.
