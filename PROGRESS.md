## 2026-08-07 — vm-call-by-name (implement)

**Задача:** узкий публичный API в `bsl-vm` для вызова процедуры/функции
модуля по имени из рантайма, поверх машинерии изолированного исполнения
`Выполнить`/`Вычислить`.

**Изменённые файлы:** только `crates/bsl-vm/src/lib.rs`.

- Новая `pub fn call_module_function(program, stack, name, args) ->
  Result<(BslValue, Vec<BslValue>), RtError>` рядом с `run_dynamic_snippet`.
  Вход обёрнут в `DynamicDepthGuard::enter()`; имя ищется регистронезависимо
  (`to_uppercase`) по `program.function_names`, попадание `i` даёт чанк
  `chunks[i + 1]`. Стек кадра — `[арг0..аргN-1]` + `push_own_registers`, за
  регистрами копия модульного блока, `Program` поднимается с тем же
  содержимым и `module_base` за регистрами, исполнение через `drive`.
  После возврата модульный блок переносится обратно в `stack` вызывающего,
  а слоты параметров `0..n_params` отдаются вторым элементом пары.
- Неизвестное имя и несовпадение арности — `RtError::DynamicError` с русским
  текстом (перехватываемо `Попытка`), новых вариантов `RtError` не заводил.
  Рассогласованная `Program` (имя есть, чанка нет) и короткий `stack` дают
  `RtError::InvalidBytecode` через `at`/`reg_load`. Голых `unwrap()`/`expect()`
  вне тестов не добавлено.
- Шесть юнит-тестов из ACCEPTANCE в том же `mod tests`, плюс два хелпера
  (`compile_src`, `module_state` — прогоняет верхний уровень через `drive`
  и отдаёт его финальный стек, то есть настоящее состояние модуля).

**Замечания по семантике (не платформенные, замера не требуют):**

- Аргументы передаются по значению: у рантайма нет слота вызывающего,
  который можно было бы алиасить (в отличие от `Instr::Call`, где
  `param_aliases` указывает в кадр вызывающего). Поэтому запись в параметр
  без `Знач` наблюдаема только через возвращаемые финальные значения слотов
  — это и есть будущий канал для `Отказ` на этапе json-callbacks.
- Арность обязана совпадать РОВНО. Проверено по коду: `bsl-sema` добивает
  список аргументов до `n_params` маркером `RExpr::Skipped`
  (`resolver.rs:869`), кодоген превращает его в `LoadSkipped`, а значение по
  умолчанию вычисляет пролог самой функции (`compile_param_defaults`). То
  есть вызывающий этот API может передать `BslValue::Skipped` и получить
  дефолт — отдельного механизма не нужно, но и «передать меньше аргументов»
  нельзя.
- `Program` клонируется целиком на каждый вызов (иначе не поменять
  `module_base`, а `drive` берёт `&Program`) — ровно то же делает
  `run_dynamic_snippet`. На этапе json-callbacks, где вызов идёт на каждый
  элемент документа, это может оказаться заметной стоимостью; сейчас не
  измерено и в задачу не входило.
- Маркеров `НЕ ИЗМЕРЕНО` не добавлял: API внутренний, платформой напрямую
  не наблюдаем, наблюдаемое поведение появится на следующем этапе.
  Реестр `open_questions.rs` не трогал.

**Неизвестное:** поведение при вызове функции модуля, содержащей
`Выполнить`/`Вычислить`, отдельным тестом не покрыто (в ACCEPTANCE такого
пункта нет). По коду путь корректен — `aliased` в `run_dynamic_snippet`

рассуждение, а не прогон.

принимает в этой позиции любое значение, кроме `Неопределено`, и всегда
ищет функцию в модуле исполняемого скрипта: своей системы модулей нет,
воспроизводить различие «не тот тип» / «нет такого метода» нечем. Это
осознанное отклонение, а не открытый вопрос — поведение платформы
измерено и записано в doc comment `callback_name`.

## 2026-08-08 — bin-rw: `ЧтениеДанных` и `ЗаписьДанных` (implement)

**Задача.** `PLAN.md`, `TASK_ID: bin-rw`, difficulty hard. Реализовать
`ЧтениеДанных`/`ЗаписьДанных` поверх готовых потоков, с измеренной семантикой
собственного буфера и с исключением при чередовании с прямой сменой позиции
целевого потока. План велел «сначала замер, потом код» — так и сделано:
восемь разведочных прогонов на 8.3.27.2074, и ни одной тройки `НЕ ИЗМЕРЕНО`
не понадобилось, потому что замерить удалось всё, включая дословный текст
ошибки чередования.

### Главный результат замера: буфера НЕТ, и это опровергает формулировку задачи

Бэклог называл эти типы «буферизованными», а план велел снять «величину
упреждающего чтения». Величина оказалась НУЛЕВОЙ, и это измерено с обеих
сторон:

- сразу после `Новый ЧтениеДанных(Поток)` позиция потока 0, после первого
  `ПрочитатьБайт()` — 1, после второго — 2. То же самое на ФАЙЛОВОМ потоке
  над файлом в 70 000 байт (проверялось именно на нём, чтобы буфер в 4К или
  64К был бы виден);
- у писателя `ЗаписатьБайт(65)` немедленно даёт `Поток.Размер() = 1`;
- метода сброса буфера у платформы нет ни в каком написании — проверены
  `ОчиститьБуфер`, `ОчиститьБуферы`, `Сбросить`, `СброситьБуфер`.

Поэтому в `DataRwState` не `Vec<u8>`, а логическая позиция, которая обязана
совпадать с фактической позицией целевого потока. Это же и делает проверку
чередования тривиально точной.

### Чередование: измерено вместе с текстом ошибки

Дословно с платформы (поэтому `BIN.RW.INTERLEAVE_ERROR`, который план
разрешал завести, НЕ заведён — реестр открытых вопросов не тронут вовсе):

> В процессе работы с объектом 'ЧтениеДанных' произошло изменение позиции
> нижележащего потока извне. Это может привести к некорректной работе
> приложения.

Соседние случаи измерены отдельно и оказались важнее самого факта ошибки:
`Перейти` НА ТУ ЖЕ позицию ошибки не даёт (ни до первого чтения, ни после),
а возврат позиции обратно на ожидаемую ЛЕЧИТ объект — следующая операция
снова работает. То есть это не «сломанный навсегда объект», а сверка на
каждой операции. Отвергнутая `ЗаписатьЦелое32` размера целевого потока не
меняет, так что проверка стоит до побочного эффекта — и у нас тоже.

### Что ещё измерено и воспроизведено

- **`ПорядокБайтов` у читателя — свойство-обманка.** У писателя оно живое
  (`Зп.ПорядокБайтов = BigEndian` меняет байты с `2 1` на `1 2`). У читателя
  присваивание меняет только геттер: над байтами `65 66` геттер говорит
  «Big-endian», а `ПрочитатьЦелое16()` по-прежнему отдаёт 16961. Тот же
  BigEndian ИЗ КОНСТРУКТОРА читается (16706). Отсюда два поля `order_shown`
  и `order_used`. `КодировкаТекста` и `РазделительСтрок` живые у обоих.
- **Перевод строки при записи:** каждый `\n` разворачивается в `\r\n` и в
  теле, и в разделителе. `ЗаписатьСимволы("A\nB")` -> `65 13 10 66`,
  `ЗаписатьСимволы("A\r\nB")` -> `65 13 13 10 66` (то есть `\r` не
  поглощается). Разделитель по умолчанию — один `\n`, поэтому
  `ЗаписатьСтроку("AB")` кладёт `65 66 13 10`, хотя геттер показывает строку
  длины 1. При ЧТЕНИИ обратного перевода нет: разделитель ищется побайтово,
  и `ПрочитатьСтроку()` при разделителе `\n` над `65 66 13 10` отдаёт
  `"AB\r"` — три символа.
- **Сигнатуры (BOM) в поток не пишется** ни в UTF-8 (`208 144 208 145`), ни
  в UTF-16 (`16 4 17 4`). Отсюда `Encoding::encode_without_signature`.
  А при ЧТЕНИИ ведущий BOM НЕ снимается: `ПрочитатьСимволы(3)` над
  `EF BB BF 41 42` даёт коды `[65279 65 66]`. Отсюда `decode_without_bom`.
- **Край источника:** `ПрочитатьБайт()` и `ПрочитатьЦелоеN()` отдают
  `Неопределено`, а `Прочитать`/`ПрочитатьВБуферДвоичныхДанных`/
  `ПрочитатьСимволы` — сколько есть; ноль и пропущенный аргумент у всех трёх
  значат «всё».
- **Неудавшееся `ПрочитатьЦелое32` НИЧЕГО не поглощает:** позиция остаётся
  13 из 16, и следующий `ПрочитатьБайт` отдаёт байт 13-й позиции (78). Первая
  версия кода поглощала остаток — исправлено по замеру.
- **`Пропустить` — это ПЕРЕВОД позиции, а не вычитывание:** `Пропустить(100)`
  над шестнадцатибайтовым потоком уводит поток на позицию 100 и возвращает
  100, а не 16. Первая версия вычитывала в цикле — исправлено по замеру.
- **Наборы источников у сторон РАЗНЫЕ:** читателю годятся поток,
  `ДвоичныеДанные` и имя файла; писателю — только поток и имя файла
  (`ДвоичныеДанные` он отвергает «Несоответствие типов»). Оба отвергают
  число, `БуферДвоичныхДанных` и пустой конструктор.
- **`Закрыть` ничего не закрывает и ничего не запрещает:** целевой поток
  после него жив, повторное закрытие принимается, чтение и запись продолжают
  работать. Сбрасывать нечего — буфера нет.
- **`ПрочитатьСимволы(N)` считает СИМВОЛЫ:** над «АБВГ» в UTF-8 `N=2` съедает
  четыре байта.
- **Английские имена измерены перебором,** а не выдуманы: отсутствующее имя
  платформа отличает («Метод объекта не обнаружен») от существующего, но не
  возвращающего значения («Обращение к процедуре объекта как к функции»). Так
  подтвердились `ReadIntoBinaryDataBuffer` (а не `ReadToBinaryDataBuffer` и
  не `ReadIntoBuffer`), `ReadDataResult` (а не `DataReadResult`) и —
  неожиданно — `LineSplitter` для `РазделительСтрок`: на `LineSeparator`
  платформа отвечает «Поле объекта не обнаружено».

### Проверка гейтов ОТКАТОМ, а не рассуждением

Каждый новый гейт проверен временной правкой кода с последующим
восстановлением файла из копии:

- `bounded_limit_arg` -> `limit_arg` в обоих местах: гейт 1 падает на первом же
  количестве — «ПрочитатьВБуферДвоичныхДанных(4294967296) над памятью
  принято»;
- `>` вместо `>=`: падает гейт 1 (та же строка) — граница уезжает вверх на
  единицу;
- `n >= (1u64 << 32) - 1` (граница на единицу вниз): падает гейт 3
  `the_bound_is_exactly_at_2_32_not_below`;
- проверка перенесена ВНУТРЬ `limit_arg` (то есть протекает в `Прочитать`):
  падает гейт 3 — `Прочитать(2^32)` отвечает `TypeError`;
- `read_limited` откачена к «отдать количество прямо носителю»: гейт 2
  `a_huge_read_over_a_file_is_a_catchable_error_not_an_abort` падает.

### Неожиданность, которую стоит знать (расхождение с текстом PLAN.md)

План утверждал, что при откате поблочного чтения «процесс умирает по SIGABRT».
СЕЙЧАС ЭТО УЖЕ НЕ ТАК: `stream::read_bytes` в файловой ветке обзавёлся
`try_reserve_exact` (`crates/bsl-rt/src/stream.rs:255`) ещё в прошлой итерации,
поэтому откат даёт ЛОВИМЫЙ `TypeError { expected: "Размер, который удаётся
разместить в памяти" }`, а не смерть процесса. Прямое следствие: под СТАРЫМ
утверждением `by_read.is_none_or(|n| n <= size)` этот откат прошёл бы молча —
`Err` превращался в `None`, а `None.is_none_or(..)` истинно. То есть замечание
2 Fable о том, что гейт слабее, чем выглядит, было верным по существу, и
переписанное утверждение (РОВНО 16) теперь этот откат валит. Никакого
«сторожа SIGABRT» в юнит-тестах больше нет и быть не может, пока цела вторая
защита в `stream.rs`; сторожем поблочного чтения тест остаётся, но по другой
причине — по неверному РЕЗУЛЬТАТУ, а не по падению процесса.

Новых `НЕ ИЗМЕРЕНО`-идентификаторов не заведено, и это осознанно: метка — для
решения, принятого рассуждением вместо замера, а здесь замер проведён и на
границе ответил. Под границей (`2^32 - 1`) платформа не отвечает вовсе —
«не вешать сеанс» не является выбором среди правдоподобных вариантов. Тот же
случай уже решён так же, без метки, у края `u64` при записи в `stream.rs`.
