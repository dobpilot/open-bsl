# План совместимости с HTTP-клиентом Connector

Источник анализа — модуль [`КоннекторHTTP`](https://github.com/vbondarevsky/Connector/blob/7e37f1f5cdd35aac220af853b20a551d4da88cdd/src/ru/CommonModules/%D0%9A%D0%BE%D0%BD%D0%BD%D0%B5%D0%BA%D1%82%D0%BE%D1%80HTTP/Ext/Module.bsl)
версии 2.6.0, commit `7e37f1f5cdd35aac220af853b20a551d4da88cdd`,
прочитанный целиком 2026-08-25. Цель — исполнять этот BSL-модуль без
переноса его прикладной логики в Rust. Значит, open-bsl должен реализовать
недостающие объекты и функции платформы, а сам Connector останется верхним
слоем: методы GET/POST/PUT/PATCH/DELETE, сессии, cookies, перенаправления,
повторы, multipart, JSON и схемы аутентификации уже написаны в исходнике.

Полный неизменённый модуль сохранён в compile-contract fixture и
компилируется без test-only подмен. Вся необходимая ему
поверхность, включая `ХешированиеДанных`, MD5, SHA-1 и SHA-256,
реализована; её пограничная семантика закреплена замерами на 1С.

Второй источник — раздел 17.3.1.2 «Общая схема работы с HTTP-запросами»
документации «1С:Предприятие 8.3.27» из локальной выгрузки
`bsl-http.pdf` (страницы 9–11 PDF, SHA-256
`be70bdfe36f52ceeb447f31a7704cb7792aa5af19dd057847d07fe9da531d779`),
проверенный 2026-08-25. Документация
задаёт публичную модель и ожидаемый основной сценарий, Connector сужает
необходимую поверхность, а точные пограничные случаи по правилам проекта
всё равно проверяются на реальной платформе.

## Документированный контракт 1С

- `HTTPСоединение` получает только имя сервера: без схемы и пути. Ресурс,
  включая строку параметров после `?`, принадлежит
  `HTTPЗапрос.АдресРесурса`; обычное
  соединение по умолчанию использует порт 80, а HTTPS выбирается параметром
  `ЗащищенноеСоединение`.
- Тайм-аут конструктора задаётся в секундах и ограничивает выполнение
  запроса. Документация не уточняет, является ли это единым предельным
  сроком или отдельными тайм-аутами подключения, чтения и записи.
- Отсутствующий явный объект прокси означает настройки прокси по умолчанию,
  а не обязательно прямое соединение. Пользователь и пароль соединения —
  отдельные параметры конструктора.
- `HTTPЗапрос` содержит адрес ресурса, заголовки и тело. Заголовки запроса и
  ответа видны BSL как `Соответствие`; query-параметры передаются внутри
  адреса ресурса, платформа не строит их отдельной коллекцией.
- `ВызватьHTTPМетод` принимает произвольное имя метода. Документированные
  короткие методы отображаются так: `Удалить` — DELETE, `Получить` — GET,
  `ПолучитьЗаголовки` — HEAD, `Изменить` — PATCH,
  `ОтправитьДляОбработки` — POST, `Записать` — PUT.
- HTTP-статус, включая не-2xx и перенаправление, возвращается как
  `HTTPОтвет`; инфраструктурный отказ возбуждает исключение. Прикладной код
  анализирует `КодСостояния` и заголовки сам.
Для тела документированы четыре представления:

| Представление | `HTTPЗапрос` | `HTTPОтвет` |
|---|---|---|
| Строка | `ПолучитьТелоКакСтроку`, `УстановитьТелоИзСтроки` | `ПолучитьТелоКакСтроку` |
| Двоичные данные | `ПолучитьТелоКакДвоичныеДанные`, `УстановитьТелоИзДвоичныхДанных` | `ПолучитьТелоКакДвоичныеДанные` |
| Поток | `ПолучитьТелоКакПоток` | `ПолучитьТелоКакПоток` |
| Файл | `ПолучитьИмяФайлаТела`, `УстановитьИмяФайлаТела` | `ПолучитьИмяФайлаТела` |

Синхронные методы предназначены для серверной стороны, асинхронные варианты
с суффиксом `Асинх` — для клиентского приложения. Асинхронный вызов сразу
возвращает `Обещание`, а `Ждать` приостанавливает только текущий BSL-метод:
между отправкой запроса и `Ждать` приложение может выполнять другой код.
Поэтому совместимость включает оба варианта API и не может быть сведена к
блокирующим алиасам с суффиксом `Асинх`.

С 2026-08-27 (этап 5 плана фоновых заданий) «синхронный» здесь означает
только семантику для BSL-кода: вызов возвращает готовый `HTTPОтвет`, а не
`Обещание`. Поток при этом не блокируется — метод объявлен приостанавливающим
(`MethodDescriptor::suspending`) и отдаёт виртуальной машине типизированную
операцию `PendingHostCall::HttpSync`, после чего исполнение паркуется, а
поток занимается другой работой; в пуле фоновых заданий это и есть механизм,
которым ждущее задание освобождает свой worker. Разница с `Асинх` остаётся
прежней: парковка замораживает весь сеанс, тогда как `Ждать` уступает
соседним BSL-задачам того же сеанса.

## Что требуется исходнику

| Возможность Connector | Платформенная поверхность | Состояние open-bsl |
|---|---|---|
| JSON-тело и ответ | `ЧтениеJSON`, `ЗаписьJSON`, настройки и колбэки | Полная форма настроек, потоковый вход, `Закрыть` и максимальная вложенность реализованы и измерены |
| Двоичные тела и multipart | `ДвоичныеДанные`, буферы, потоки, `ЧтениеДанных`/`ЗаписьДанных` | Реализовано; полный Connector формирует точное multipart-тело |
| GZIP через ZIP-контейнер | потоки, временные файлы, `ЧтениеZipФайла`/`ЗаписьZipФайла` | Реализовано; round-trip проверен на 0, 1 и 70 000 байтах |
| JSON/Base64/URL/AWS4/Digest | Base64, hex, URL-кодирование, MD5, SHA-1, SHA-256 | Реализовано и измерено; Digest и AWS4 проходят независимые векторы через полный Connector |
| Собственно HTTP | `HTTPЗапрос`, `HTTPОтвет`, `HTTPСоединение` | Базовые объекты, sync/async-методы и native-транспорт реализованы; TLS и все три режима proxy подключены |
| Асинхронное исполнение | `Асинх`, `Ждать`, `Обещание`, приостановка метода | Язык, bytecode, FIFO promise scheduler, pollable `Execution` и safe-point quantum реализованы |
| HTTPS и прокси | `ИнтернетПрокси`, сертификаты, `ЗащищенноеСоединениеOpenSSL` | Объекты, системные/файловые корни, клиентский PEM, режим без проверки и явный proxy реализованы; loopback IPv4/IPv6 и имя `localhost` измерены |
| Текст ответа | `ЧтениеТекста` над потоком | Реализовано и измерено на 1С для нужной Connector формы |
| Сортировка AWS4 | `СписокЗначений` и элементы списка | Реализована и измерена стабильная сортировка по значению для строк Connector |
| Ошибки и `Retry-After` | `ИнформацияОбОшибке`, представления ошибки, приведение строки к числу/дате | Реализовано и измерено для поверхности Connector |
| Ответ XDTO | `ЧтениеXML` и глобальная конфигурационная `ФабрикаXDTO` | Читатель есть; глобальная фабрика намеренно отвечает ошибкой |

## Границы модулей

Зависимости направлены только к более общему слою:

```text
open-bsl ─┬─> bsl-http ─> bsl-stream ─> bsl-binbuf ─> bsl-rt
          └─> bsl-crypto ───────────────────────────> bsl-rt
```

Tokio, `reqwest` и RustCrypto не видны за пределами своих адаптеров. `bsl-rt` не
зависит от компонентов и содержит только BSL-значения, нейтральные DTO,
`Обещание` и host-контракты. Поддержка `Асинх`/`Ждать` проходит через уже
существующие `bsl-syntax`, `bsl-sema`, `bsl-bytecode`, `bsl-compiler` и
`bsl-vm`; отдельный crate `bsl-async` для неё не нужен.

### 1. Дополнить базовый runtime

В `bsl-rt` нужны функции `Base64Значение`,
`ПолучитьBase64СтрокуИзДвоичныхДанных`,
`ПолучитьДвоичныеДанныеИзBase64Строки`,
`ПолучитьHexСтрокуИзДвоичныхДанных`, `КодироватьСтроку` и
`РаскодироватьСтроку`, а также перечисление `СпособКодированияСтроки`.
URL-кодирование следует измерить отдельно для вариантов `КодировкаURL` и
`URLВКодировкеURL`: нельзя подменять их произвольным percent-encoding.

Там же нужны минимальные платформенные объекты, используемые модулем:

- `СписокЗначений` с `Добавить`, `СортироватьПоЗначению` и элементами
  `Значение`/`Представление`. Предположенный ранее метод `Найти` не
  существует на 1С 8.3.27 и потому не реализуется;
- `КвалификаторыДаты`, `ЧастиДаты.ДатаВремя` и
  `ОписаниеТипов.ПривестиЗначение` для разбора `Retry-After`
  реализованы. Oracle `measure-type-description-convert.bsl` измеряет
  десятичные числа, форму `ГГГГММДДЧЧММСС` и значения по
  умолчанию для негодных строк;
- `ИнформацияОбОшибке`, `ПодробноеПредставлениеОшибки` и перенос текущего
  исключения из VM в неизменяемый снимок реализованы. Oracle
  `measure-error-info.bsl` закрепляет тип, значение вне обработчика,
  сохранение снимка и текст внутренних ошибок. Координаты платформенного
  стека сознательно не имитируются: VM сохраняет безопасный текст без
  транспортных внутренних типов;
- `ПолучитьИмяВременногоФайла`, `ПолучитьРазделительПути`, `УдалитьФайлы`
  поверх host-файловой системы;
- минимальное значение `Метаданные.ОбщиеМодули`, где `Найти` возвращает
  отсутствие модулей. Оно нужно только для необязательного обнаружения БСП
  в `ПроксиПоУмолчанию`; это сознательная модель конфигурации без метаданных,
  а не начало полного `bsl-metadata`.

Вспомогательная поверхность ключа пула Connector также закрыта замерами:
`XMLСтрока(Неопределено/Null)` возвращает пустую строку, а
`Массив.ВГраница()` — последний индекс либо `-1` для пустого массива.

Base64 и hex уже реализованы для XDTO в `bsl-xml/src/xdto`: создавать
вторую реализацию или подключать crate `base64` нельзя. Чистые примитивы
без XML-переносов строк надо поднять в `bsl-rt/src/encoding.rs`, после чего
и `bsl-xml`, и глобальные функции используют их с разной политикой
представления. Измеренные варианты URL-кодирования также живут там: это
чистые преобразования `&str -> Result<String>`, а не часть HTTP-транспорта.

### 2. Расширить `bsl-stream`

Новый crate не нужен. Объекты потоков и читателей остаются в `bsl-stream`.
Следует добавить только то, что реально вызывает Connector:

- `ДвоичныеДанные.ОткрытьПотокДляЧтения()` и
  `ДвоичныеДанные.Записать(Путь)`;
- `Поток.КопироватьВ(Приемник[, Количество])` и
  `ПотокВПамяти.ЗакрытьИПолучитьДвоичныеДанные()`;
- `ЧтениеДанных.ИсходныйПоток()` и `КопироватьВ`;
- `ЗаписьДанных.ЗаписатьБуферДвоичныхДанных`;
- полную шестиместную форму конструктора `ЗаписьДанных`, которую Connector
  использует при сборке multipart;
- `ЧтениеТекста(Поток, Кодировка)` с `Прочитать` и `Закрыть`.

Семантику владения общим потоком, позиции после закрытия, BOM и ошибок
чередования надо измерить на 1С. Реализация должна переиспользовать
`ByteStreamProtocol` и `bsl-rt/src/encoding.rs`. `bsl-http` объявляет
Cargo- и runtime-зависимость от `bsl-stream`: тело `HTTPЗапрос` хранит
готовое значение `ПотокВПамяти`, а `ПолучитьТелоКакПоток` возвращает его
клон-ссылку. Так поток и запрос видят один носитель без нового типа буфера
и без обратной зависимости `bsl-stream -> bsl-http`.

Текущий результат: 33-строчный oracle `measure-connector-stream.bsl`
совпадает с 1С. Реализованы обе формы `КопироватьВ`, повторяемый снимок
`ЗакрытьИПолучитьДвоичныеДанные`, синхронизирующий прокси
`ИсходныйПоток`, запись целого буфера, отключение преобразования LF в
шестом аргументе `ЗаписьДанных` и read-only поток над `ДвоичныеДанные`.
Файловая половина также закрыта девятистрочным oracle
`measure-temp-files.bsl`: `ПолучитьИмяВременногоФайла` возвращает ещё не
существующий путь с дословным суффиксом, `ДвоичныеДанные.Записать` создаёт
и полностью перезаписывает файл, а `УдалитьФайлы` принимает файл,
отсутствующий путь и непустое дерево. Эти операции идут через расширенный
`FileSystem`; системная реализация использует каталог временных файлов
процесса, а реализации host-приложений по умолчанию получают явное «не
поддержано».

Для этого понадобилось узкое расширение ABI. Получатель двух первых методов —
нативный `ДвоичныеДанные` из `bsl-rt`, но результат первого строит
`bsl-stream`, а второй требует `FileSystem`. До расширения component ABI не
умел добавлять методы компонентом к нативному типу, а
`call_builtin_method_ctx` не нёс host-возможности. Переносить
`ПотокВПамяти` в `bsl-rt`, дублировать его реализацию или давать
`bsl-rt -> bsl-stream` нельзя.

Минимальное решение реализовано: имена этих методов остаются в
`BuiltinMethod`, а дескриптор `bsl-stream` содержит необязательное поле
`byte_stream_factory: Option<ByteStreamFactory>`. `RuntimeBuilder` отвергает
два таких поставщика, `RuntimeRegistry` переносит единственный указатель на
функцию в `RuntimeShapes`, а отсутствие поставщика даёт ловимую ошибку
компонента. `ОткрытьПотокДляЧтения` передаёт фабрике неизменяемые байты;
отсутствующий и дублированный поставщик, а также равенство JIT с
интерпретатором покрыты тестами. Для `Записать` таблица
`BuiltinMethod::host_effect()` помечает файловый эффект; интерпретатор
вызывает узкий вход с `FileSystem`, а JIT по той же таблице оставляет эту
инструкцию интерпретатору. Для `CallObjectMethod` классификация выполняется
после связывания имени; соседние инструкции чанка продолжают
компилироваться. Это расширяет существующие механизмы поставщика и
`BuiltinFn::host_effect`, а не создаёт общий реестр методов-расширений ради
двух вызовов. Отсутствующий и дублированный поставщик, точечный JIT
fallback и равенство JIT с интерпретатором покрыты тестами.

### 3. Добавить `bsl-crypto`

Новый компонент должен объявить объект `ХешированиеДанных`. Перечисление
`ХешФункция` добавляется в единственную таблицу перечислений `bsl-rt`, а не
принадлежит компоненту: component ABI сейчас не регистрирует перечисления.
Для Connector достаточно MD5, SHA-1 и SHA-256, методов `Добавить` и свойства
`ХешСумма`; HMAC уже корректно собран из этих примитивов в BSL. Компонент
зависит только от `bsl-rt` и реализаций хешей.

Внутреннее состояние лучше сделать исчерпывающим `enum Hasher`, а не
`Box<dyn DynDigest>`. `ХешСумма` клонирует выбранный hasher и завершает
снимок, не уничтожая накопленное состояние. Oracle
`measure-data-hashing.bsl` подтвердил на 1С 8.3.27, что повторное чтение
возвращает ту же сумму, а последующий `Добавить` продолжает прежний поток
байтов. Он же закрепляет BSL-типы и векторы `abc` для MD5, SHA-1 и SHA-256.
`RefCell` нужен только на границе мутабельного BSL-объекта, чистое обновление
конкретного hasher остаётся внутри короткого займа.

Рекомендуются семейство RustCrypto (`digest`, `md-5`, `sha1`, `sha2`) и
проверка официальными тестовыми векторами. Писать криптографические хеши в
дереве означает несколько тысяч строк чувствительного к ошибкам кода и не
даёт проекту полезной совместимости сверх готовых crate'ов. Это новая
зависимость и перед началом этапа требует явного решения сопровождающего.

### 4. `Асинх`, `Ждать` и `Обещание`

Эта обязательная языковая основа асинхронного HTTP реализована согласованно
во всех слоях:

- `bsl-syntax`: распознать `Асинх` перед `Процедура`/`Функция`, добавить
  признак `is_async` объявления и выражение `Ждать`;
- `bsl-sema`: разрешать `Ждать` только внутри асинхронного метода;
  асинхронная функция всегда имеет результатом `Обещание`, асинхронная
  процедура запускается без возвращаемого обещания, а её параметры всегда
  передаются по значению. Эффективный `by_val` меняется уже здесь, чтобы
  `core_receivers`, статический вызов и динамические сигнатуры не разошлись;
- `bsl-bytecode`: добавить метаданные асинхронного чанка и `Instr::Await`.
  Одновременно обновить `write_instr`, `parse_instr`, `OPCODES`, проверку
  образа, исчерпывающую классификацию эффектов в `bundle.rs`, корпус
  round-trip и `FORMAT_VERSION`;
- `bsl-compiler`: компилировать `Ждать` в точку возможной приостановки,
  переносить `is_async` в `Chunk` и `DynamicSignature`, а динамическому
  фрагменту передавать `caller_is_async`;
- `bsl-rt`: представить обещание внутренним `PromiseValue` через уже
  существующий `BslObject::Extension`, не добавляя публичный вариант
  `BslObject`. Объект хранит `execution_token + promise_id`, имеет отдельный
  `TypeDescriptor`, но не имеет конструктора, методов или свойств;
- `bsl-vm`: выделить из локальных переменных `drive_linked` объект
  `Execution` и набор кооперативных `Task`. Задача владеет стеком, кадрами,
  `pc`, текущим исключением и остатком кванта; `Execution` — общими
  `ModuleState`, `RuntimeShapes`, JIT-кэшем, FIFO-очередью готовых задач,
  таблицей обещаний и completion-каналом.

Состояние обещания — закрытый тип
`Pending { waiters: VecDeque<TaskId> } | Ready(Result<BslValue, RtError>)`.
Несколько задач могут ждать одно обещание; они пробуждаются FIFO, а готовый
результат клонируется без повторения эффекта. `PromiseValue` из завершённого
`run` остаётся пригоден для `ТипЗнч` и диагностики, но его token закрыт, и
новый `Execution` отвергает попытку ожидания.

Через границу потоков проходят только владеющие данными `Send`-объекты:

```rust
struct HostCompletion {
    execution_token: ExecutionToken,
    promise_id: PromiseId,
    payload: Box<dyn CompletionPayload + Send>,
}

trait CompletionPayload: Send {
    fn materialize(
        self: Box<Self>,
        shapes: &mut RuntimeShapes,
    ) -> RtResult<BslValue>;
}
```

Материализация вызывается один раз в VM-потоке и не получает полный
`CallContext`. Передавать в host-задачу `Rc`, `RefCell`, `BslValue`,
`RtError`, `RuntimeShapes` или ссылки на кадр запрещено типами контракта.
`panic`/`JoinError` становится безопасным `Failure`, позднее сообщение с
закрытым token отбрасывается, ID между запусками не переиспользуются.

Модульные переменные нельзя оставлять абсолютными индексами в стеке
корневой задачи: асинхронные задачи должны видеть одно состояние модуля.
Нужен общий `ModuleState: Vec<BslValue>` в потоке VM. Объявленные модульные
имена, включая верхний уровень, компилируются как `ModuleVar`, а адрес
параметра становится `Location::TaskSlot | Location::ModuleSlot`.
`run_dynamic_snippet` и `call_module_function` получают тот же `ModuleState`
вместо копирования туда-обратно. Локальные параметры асинхронного вызова
копируются и не оставляют ссылку на стек вызывающей задачи.

Публичный `State::run` остаётся run-to-completion и внутри использует тот же
драйвер, что новый pollable API. `State::start` создаёт отдельный
`Execution`, а `Execution::poll(host_slice)` возвращает `Complete`,
`Waiting` или `Runnable`. Native-драйвер передаёт неограниченный host-slice;
embedding host и будущий WASM-драйвер могут передавать конечный. Граница
host-slice не меняет текущую BSL-задачу и потому отделена от task-кванта.

Планировщик использует одну FIFO-очередь без приоритетов. При одной живой
BSL-задаче действует unlimited fast path без счётчика. При двух и более
задачах `SchedulerConfig::safe_points_per_quantum` ограничивает число
scheduler safe points: взятых обратных переходов, смены кадров и отдельного
пути `fast_numeric_for`. Исчерпавшая квант задача уходит в конец очереди.
Подтверждённое q44 значение по умолчанию — 1024; host может заменить его
через `StateBuilder::safe_points_per_quantum`. Настройка не сериализуется в
bytecode.

Ошибка асинхронной функции сохраняется в обещании и возбуждается в точке
`Ждать`, чтобы её перехватил окружающий `Попытка`. Для асинхронной процедуры
предварительная политика — ошибка всего `Execution`, но она фиксируется
только после замера платформы.
Повторное ожидание завершённого обещания должно быть стабильным; точную
идентичность значения и ошибки следует измерить.

`Await` и создание BSL-задачи используют существующий поинструкционный
fallback JIT, а не отключают весь чанк; `Await` также служит барьером
VLIW-бандла. На JIT back-edge квант проверяется встроенным decrement/check,
без Rust-shim на каждой итерации, и возвращает
`NativeOutcome::Yield { pc }`. Обязательны одинаковое чередование с
интерпретатором, специальный тест `fast_numeric_for`, сохранение
восьмибайтового `Instr` и A/B-прогон горячих сценариев.

Обычный component ABI остаётся синхронным. Асинхронный HTTP-метод снимает
wire-снимок и через узкую возможность `CallContext::spawn_http` сразу
регистрирует обещание в текущем `Execution`; transport completion содержит
только `Send`-DTO, а `HTTPОтвет` материализуется в VM-потоке. Отдельный вид
method descriptor не нужен: приостанавливает задачу только последующий
`Await`. Синхронный HTTP блокирует весь native `Execution`; браузерный
адаптер и политика синхронного вызова в WASM остаются следующим этапом.

### 5. Компонент `bsl-http`

Это отдельный компонент рантайма, потому что сеть, TLS и жизненный цикл
соединений не принадлежат базовым значениям. Минимальная поверхность:

- `HTTPЗапрос([АдресРесурса])`: записываемые свойства `АдресРесурса`,
  `Заголовки` (`Соответствие`);
  `УстановитьТелоИзСтроки(Текст, Кодировка, ИспользованиеBOM)`,
  `УстановитьТелоИзДвоичныхДанных(Данные)`,
  `ПолучитьТелоКакДвоичныеДанные()`, `ПолучитьТелоКакСтроку()` и
  `ПолучитьТелоКакПоток()`;
- `HTTPОтвет`: читаемые свойства `КодСостояния`, `Заголовки`
  (`Соответствие`) и
  `ПолучитьТелоКакДвоичныеДанные`, `ПолучитьТелоКакСтроку` и
  `ПолучитьТелоКакПоток`;
- `HTTPСоединение(Сервер, Порт, Пользователь, Пароль, Прокси, Таймаут,
  ЗащищенноеСоединение, ИспользоватьАутентификациюОС)` с
  арностью 1–8, синхронными методами `ВызватьHTTPМетод`, `Удалить`,
  `Получить`, `ПолучитьЗаголовки`, `Изменить`,
  `ОтправитьДляОбработки`, `Записать` и обязательными асинхронными
  вариантами `ВызватьHTTPМетодАсинх(Метод, Запрос)`,
  `УдалитьАсинх(Запрос)`, `ПолучитьАсинх(Запрос)`,
  `ПолучитьЗаголовкиАсинх(Запрос)`, `ИзменитьАсинх(Запрос)`,
  `ОтправитьДляОбработкиАсинх(Запрос)` и `ЗаписатьАсинх(Запрос)`;
- `ИнтернетПрокси` с HTTP/HTTPS-настройками, исключениями адресов и
  учётными данными;
- `СертификатыУдостоверяющихЦентровОС`,
  `СертификатыУдостоверяющихЦентровФайл`, `СертификатКлиентаФайл` и
  `ЗащищенноеСоединениеOpenSSL` с читаемыми свойствами, которые участвуют
  в ключе пула Connector.

Все короткие методы — делегирующие обёртки над универсальным методом:
`Удалить[Асинх]` — DELETE, `Получить[Асинх]` — GET,
`ПолучитьЗаголовки[Асинх]` — HEAD, `Изменить[Асинх]` — PATCH,
`ОтправитьДляОбработки[Асинх]` — POST и `Записать[Асинх]` — PUT.
Синхронная и асинхронная ветви используют одну функцию построения
`HttpWireRequest` и одну функцию материализации `HTTPОтвет`; различается
только способ исполнения эффекта. Строковые методы запроса и ответа читают
UTF-8 и снимают BOM; поток ответа строится над тем же неизменяемым снимком.
Файловое тело откладывается: Connector его не использует, а сигнатуры,
момент чтения файла и взаимодействие разных представлений тела раздел
17.3.1.2 не определяет — это требует синтакс-помощника и замеров.

Обе формы регистрируются во всех `State`. Разделение на клиентский и
серверный контексты 1С в этом этапе не моделируется: доступность API не
должна зависеть от способа запуска open-bsl.

Сетевой вызов не должен быть зашит в обработчик BSL-метода. В `bsl-rt`
нужен объектобезопасный host-контракт из двух частей:

- `HttpClientFactory::create(HttpClientConfig) -> Result<Arc<dyn HttpClient +
  Send + Sync>, NetworkError>`;
- `HttpClient::submit(HttpWireRequest, HttpCompletionSink) ->
  Result<RequestHandle, SubmitError>`.

`HttpCompletionSink` принимает только
`Result<HttpWireResponse, NetworkError>`, а `RequestHandle` отменяет future.
После успешного снимка асинхронный метод всегда возвращает обещание: отказ
submitter и транспортные ошибки становятся его `Failure`. Ошибки типов,
адреса, заголовков и чтения тела возникают до снимка и остаются
немедленными. Точную границу подтверждает `HTTP.ASYNC.ERROR_BOUNDARY`.

Все DTO — собственные чистые структуры без `BslValue` и типов конкретной
библиотеки. `HttpClientConfig` хранит `host`, `port`, учётные данные,
`ProxyMode`, тайм-аут в `Duration` и TLS-настройки. `HttpWireRequest`
содержит метод, исходную строку ресурса, `Vec<(String, String)>` заголовков
и байты тела; полный URL собирает системный адаптер. Это сохраняет
документированную границу: схема и сервер принадлежат соединению, путь и
query — запросу. Нельзя нормализовать путь или перекодировать query
повторно без отдельного платформенного контракта.

`ProxyMode` имеет три состояния: `PlatformDefault`, `Direct` и
`Explicit(ProxyConfig)`. Пустой параметр конструктора отображается в
`PlatformDefault`; он не подменяется `Direct`. Каким источникам ОС
соответствует `PlatformDefault`, остаётся политикой системного адаптера и
отдельным замером.

Фабрика принадлежит `HostEnv`, а `HTTPСоединение` получает у неё
настроенный клиент и слабый `ExecutionSubmitter` в конструкторе и хранит их.
Это тот же приём, которым поток захватывает `FileSystem`: методы объекта
работают с сокращённым `CallContext` и не вынуждают все объектные вызовы
уйти с JIT-пути. Закрытый submitter даёт явную ошибку завершённого контекста.

Системный адаптер строится на асинхронном
[`reqwest`](https://docs.rs/reqwest/latest/reqwest/) и одном общем
multi-thread Tokio runtime на процесс. Tokio скрыт внутри адаптера:
`Future`, `JoinHandle` и его ошибки не входят в `bsl-rt`, bytecode или BSL-
значения. `reqwest::Client` переиспользует соединения, а настройки покрывают HTTP proxy,
таймауты, клиентский сертификат, системные или заданные корневые
сертификаты и отключение проверки TLS. Используется узкий набор feature'ов:
без JSON и автоматического GZIP, с rustls и системным проверяющим
сертификаты. Автоматические перенаправления и трактовка HTTP-статусов как
транспортной ошибки отключены. Документация прямо отдаёт анализ `КодСостояния`,
3xx и заголовков прикладному коду, а Connector реализует его сам.

Собственный HTTP/1.1-клиент потребовал бы разбор сообщений, chunked framing,
пул соединений, proxy CONNECT и TLS. TLS всё равно потребует внешний crate;
поэтому in-tree транспорт здесь дороже и опаснее зависимости. Выбор
Tokio/`reqwest` утверждён архитектурным разбором; дополнительный общий
executor trait не вводится, пока HTTP остаётся единственным потребителем.

`СертификатКлиентаWindows` и `ИспользоватьАутентификациюОС` относятся к
платформенным хранилищам и NTLM/Negotiate. В первой версии они должны
возвращать ясную ловимую ошибку, а не игнорироваться. Их межплатформенная
реализация — отдельный этап после основного клиента.

### 6. Подключить компоненты в `open-bsl`

Cargo feature `http` уже включает `bsl-http` и `stream`; feature `crypto`
добавляется после разрешения dependency gate. Полный сценарий Connector
требует `crypto`, `json`, `zip` и `xml`. Библиотеки регистрируются в
`EngineBuilder`, причём
`bsl-http::library()` объявляет зависимость от `bsl-stream` через
`LibraryDependency`.

Сеть становится host-возможностью `Network` рядом с `FileSystem` и
`Random`. `CallContext::network()` выдаёт фабрику транспорта
конструктору `HTTPСоединение`; на сокращённом пути её нет, но методы уже
держат созданный `HttpClient`. `StateBuilder::network(...)` позволяет
внедрить тестовый или ограниченный транспорт, `deny_network()` — явный запрет.
Рекомендуемая политика по умолчанию согласована с существующей файловой:
`bsl-cli` и `State::new()` при включённом feature `http` получают системный
адаптер, sandbox-хост обязан подставить запрет сам. Feature отвечает за
наличие API, host-возможность — за разрешение эффекта в конкретной сессии.

`HostEnv::process()` из `bsl-rt` не может сам создать системный адаптер:
иначе возникнет обратная зависимость на `bsl-http`. Его устанавливает
`open_bsl::HostServices::process()` под feature `http`, а
`StateBuilder::network(...)` заменяет эту реализацию по умолчанию для
конкретной сессии. Публичные трейты и DTO контракта остаются в `bsl-rt`;
функция
`bsl_http::system_factory()` — единственное место сборки
Tokio/`reqwest`-адаптера. Пользовательский host заменяет транспорт целиком,
а не получает публичный `tokio::runtime::Handle`.

Планировщик, promise table и completion receiver принадлежат отдельному
`Execution` одного `run`, а не `State`, `Engine` или process-wide runtime.
`State` хранит только переиспользуемые host-возможности. `State::run`
создаёт `Execution` и ведёт его до результата; pollable API позволяет
embedding host самому вызывать `poll` конечными слайсами. Потерянное чистое
HTTP-обещание не удерживает запуск, но живая асинхронная BSL-функция или
процедура удерживает. При закрытии запуска оставшиеся `RequestHandle`
отменяются.

Для `wasm32-unknown-unknown` та же state machine обязана собираться и
проходить compile-тест. Native `State::run` использует unlimited host-slice,
а будущий браузерный драйвер — конечный; сам `fetch`-адаптер, CORS и
`AbortController` вынесены в следующий вертикальный этап. Tokio и native
`reqwest` подключаются только на подходящих target'ах.

HTTP-конструкторы и обычные методы проходят через существующий component
ABI. Новы только `Instr::Await`, метаданные асинхронного чанка и узкий
host-интерфейс регистрации HTTP-обещания. Compile-проверка переносимой
части выполняется командой `cargo check-wasm`; native Tokio/`reqwest` на
этом target не подключаются.

## Архитектурные решения

### Функциональное ядро и императивная оболочка

Граница проводится до сетевого ввода-вывода, а не вокруг всего HTTP-компонента:

1. BSL-объект снимает короткий неизменяемый снимок своих полей.
2. Чистая функция проверяет типы и строит `HttpWireRequest`.
3. Единственный эффект — `HttpClient::submit`, возвращающий отменяемый
   handle и отправляющий wire-результат в completion sink.
4. `CompletionPayload` в VM-потоке преобразует `HttpWireResponse` в новый
   `HTTPОтвет`.

Нельзя держать `RefCell`-заём запроса, заголовков или таблицы форм во время
внешнего ввода-вывода: кроме риска паники повторного займа это смешивает
состояние BSL и внешний эффект. Снимок также фиксирует семантику: изменения
исходного `HTTPЗапрос` после начала вызова не меняют уже отправляемый пакет.

### Владение и состояние сессии

- `HttpClientFactory` принадлежит `State`, а не `Engine`: разные сессии
  могут иметь разные сетевые политики и тестовые транспорты.
- Один `HTTPСоединение` владеет одним `Arc<dyn HttpClient + Send + Sync>` с неизменяемой
  конфигурацией. Connector уже кеширует такие объекты по серверу, proxy,
  таймауту и TLS; второй глобальный пул в BSL-слое не нужен. Внутренний
  пул соединений `reqwest::Client` остаётся деталью системного адаптера.
- `HTTPЗапрос` мутабелен по правилам BSL, но его адрес, заголовки и тело
  собраны в одном `Rc<RefCell<RequestData>>`. Для нужной Connector
  поверхности `RequestBody` имеет `Empty` и `Memory(BslValue)`, где значение
  — `ПотокВПамяти` из `bsl-stream`. Установка строки или двоичных данных
  атомарно заменяет поток; выдача потока сохраняет алиасинг, а получение
  двоичных данных создаёт снимок через `ByteStreamProtocol::read_all`.
  Вариант `File` добавляется только вместе с измеренным файловым API.
- `HTTPОтвет` хранит `status: u16`, исходный список заголовков и
  неизменяемый `Vec<u8>` тела. Строка, двоичные данные и поток — новые
  представления этого снимка, а не повторное чтение сети. Если измерение
  покажет изменяемость `Заголовки`, свойство может отдавать отдельное BSL-
  `Соответствие`, не меняющее сохранённый транспортный ответ.
- BSL-объекты остаются однопоточными (`Rc`/`RefCell`). Только клиент,
  wire-DTO, completion sink и payload пересекают границу Tokio и потому
  требуют `Send`; расширять этим ограничением весь runtime нельзя. Фабрика
  вызывается в VM-потоке и сама не обязана быть `Send + Sync`.

### Типы отделены от эффектов

`HttpClientConfig`, `HttpWireRequest`, `HttpWireResponse` и `NetworkError`
живут в `bsl-rt`, потому что входят в host-контракт, но ничего не знают о
BSL и транспорте. Конвертация `BslValue <-> DTO` принадлежит `bsl-http`.
Системная реализация `HttpClient` также принадлежит `bsl-http`; только она
видит Tokio и `reqwest`. Это позволяет тестировать три слоя независимо:

- чистые преобразования — обычными unit-тестами без сети;
- BSL-объекты — тестовой `HttpClientFactory` с записываемым журналом запросов;
- системный адаптер — локальным TCP/TLS-сервером.

`HttpClient` ограничен `Debug + Send + Sync`; фабрике достаточно `Debug`.
Конфигурация и wire-запрос передаются по значению, ответ владеет байтами:
никакая ссылка на `RefCell` или стек VM не переживает вызов транспорта. Это
не делает многопоточным сам `Execution`: Tokio исполняет только host-эффекты,
а BSL-задачи планируются последовательно.

`HttpWireResponse` возвращается для любого синтаксически корректного
HTTP-ответа независимо от статуса. `NetworkError` используется только если
ответ не получен из-за DNS, соединения, тайм-аута, TLS, прокси, протокола
или I/O. Такое разделение следует документации и не позволяет случайно
превратить 401, 404 или 500 в ветку `Исключение` Connector.

### Заголовки и ошибки не сводятся к строке раньше времени

Транспортный слой хранит заголовки как `Vec<(String, String)>`, сохраняя порядок,
регистр и повторения (`Set-Cookie` особенно важен). Преобразование в
платформенное `Соответствие` выполняется один раз по измеренному на
8.3.27 правилу: повторы соединяются через `", "` в обратном порядке.
Использовать `HashMap<String, String>` внутри транспорта нельзя.
Документация определяет тип BSL-свойства, но не объясняет, как повторяющиеся
поля HTTP превращаются в единственный ключ `Соответствия`; этот вопрос она
не закрывает.

Системный адаптер вправе формировать обязательные HTTP-поля (`Host`,
`Content-Length` или `Transfer-Encoding`), как обещает документация, но не
должен незаметно менять BSL-свойство `Заголовки`. Какие поля добавляет или
заменяет именно платформа, фиксируется отдельным измерением; умолчания
`reqwest` контрактом 1С не считаются.

`NetworkError` — стабильная и независимая от транспорта классификация: DNS,
таймауты подключения/чтения/записи, TLS, прокси, протокол и I/O.
`reqwest::Error` не выходит из `bsl-http`. VM переносит категорию и безопасный
текст в неизменяемый `ИнформацияОбОшибке`; пароли, учётные данные прокси,
Bearer-токены и ключи AWS в `Debug` и `Display` редактируются.
Секретные строки и байты хранятся в обёртках с ручным `Debug`; для
`HttpClientConfig` нельзя автоматически выводить все поля через `derive`.

### TLS и proxy — значения конфигурации

Объекты сертификатов хранят неизменяемые байты сертификатов/ключа, а
`ИнтернетПрокси` — измеренно изменяемые endpoints, учётные данные и общий
массив исключений. При создании `HTTPСоединение` из proxy снимается
неизменяемый снимок. Чтение файла происходит в
конструкторе через `FileSystem`, а проверка формата и сборка
`reqwest::Client` — один раз при создании `HTTPСоединение`. Это совпадает с
измерением: 1С принимает объект над негодным содержимым и сохраняет его в
`ЗащищенноеСоединениеOpenSSL`, не проверяя сертификат в конструкторе.
Изменяемый объект, лениво перечитывающий путь на каждом запросе, сделал бы
ключ пула Connector недостоверным.

Отключение проверки TLS — отдельный явный вариант конфигурации, не пустой
набор корней. Так нельзя случайно превратить ошибку чтения CA-файла в
соединение без проверки.

### Временные файлы остаются host-эффектом

`ПолучитьИмяВременногоФайла` нельзя реализовать прямым `std::env::temp_dir`
мимо `FileSystem`: это сломает in-memory и sandbox-хосты. После замера,
создаёт ли платформа файл сразу, `FileSystem` получает минимальные методы с
реализациями по умолчанию «не поддержано»: выдача временного пути,
удаление файла/дерева и разделитель пути. Энтропия приходит из уже
существующего `RandomHandle`; проверка и резервирование имени принадлежат
реализации файловой системы.

### Принятые решения и dependency gate

| Вопрос | Решение | Статус |
|---|---|---|
| HTTP-транспорт | async `reqwest` на общем process-wide Tokio runtime | реализовано для native |
| Граница Tokio | только системный host-адаптер; никаких Tokio-типов в VM/BSL | реализовано |
| Асинхронная VM | per-run `Execution`, однопоточные задачи, FIFO и safe-point quantum | реализовано |
| WASM | общая pollable state machine и compile-тест; `fetch` позже | реализовано (`cargo check-wasm`) |
| Мост `ДвоичныеДанные -> Поток` | один `ByteStreamFactory` в component ABI | реализовано и проверено interpreter/JIT |
| Политика сети | системный адаптер при feature `http`, явный `deny_network()` | реализовано |
| Proxy | `PlatformDefault`, `Direct`, `Explicit`, изменяемые credentials и исключения | реализовано; matching loopback и локального имени измерен сетевым oracle |
| Хеши | RustCrypto: `digest`, `md-5`, `sha1`, `sha2` | разрешено и реализовано в `bsl-crypto` |

Tokio не является исполнителем будущих `ФоновыхЗаданий`: это отдельные
изолированные `State` в ограниченном пуле OS-потоков с FIFO-очередью.
Проектирование и реализация этого пула вынесены в самостоятельную задачу.

### Что считается открытым решением

До кода должны быть закрыты замерами, а не выбором Rust-библиотеки:

- алиасинг, начальная позиция и повторное чтение потоков тела запроса и
  ответа;
- правила замены тела между строкой, двоичными данными, потоком и файлом;
- копирует ли присваивание `HTTPЗапрос.Заголовки` соответствие или сохраняет
  ссылку на него;
- регистр и порядок имён заголовков ответа;
- автоматически сформированные `Host`, `Content-Length`,
  `Transfer-Encoding` и `Connection`;
- значения тайм-аута по умолчанию, ноль и отрицательные или дробные
  числа; единица «секунда» задана документацией, а единый deadline на
  заголовки и тело измерен `HTTP.TIMEOUT.SCOPE`;
- устанавливает ли конструктор физическое соединение немедленно или лениво;
- момент отправки Basic auth и поведение при пустых user/password;
- источник настроек `PlatformDefault`, правила исключений прокси и использование
  переменных окружения;
- допустимы ли схема, путь, пустой ресурс и абсолютный URI в параметрах,
  несмотря на документированное разделение сервера и ресурса;
- порт по умолчанию для TLS и правила проверки диапазона порта; Connector
  сам передаёт 443 и от этого ответа не зависит;
- системные корни против встроенного набора, SNI и проверка имени;
- когда именно асинхронный HTTP-вызов снимает копию адреса, заголовков и
  тела запроса и какие ошибки возникают сразу, а какие только в `Ждать`;
- порядок возобновления двух завершившихся обещаний, повторное `Ждать` и
  поведение обещания, потерянного без ожидания;
- дожидается ли среда завершения фоновой асинхронной процедуры при выходе
  из корневого модуля и как сообщает её неперехваченную ошибку.

`reqwest` отвечает только за механизм. Любое его умолчание, не подтверждённое
этими контрактами, явно переопределяется или получает `НЕ ИЗМЕРЕНО`.
Документация уменьшает пространство ожидаемых ответов, но не заменяет
платформенный прогон. Начальный набор измерений:

- `HTTP.CONNECTION.ADDRESS_SPLIT`, `HTTP.CONNECTION.DEFAULT_PORT_PLAIN` и
  `HTTP.CONNECTION.DEFAULT_PORT_TLS`;
- `HTTP.CONNECTION.TIMEOUT_SCOPE` и `HTTP.CONNECTION.CONSTRUCT_LAZY`;
- `HTTP.PROXY.DEFAULT_SOURCE` и `HTTP.PROXY.DIRECT`;
- `HTTP.RESPONSE.STATUS_NOT_ERROR`, `HTTP.HEADERS.DUPLICATES`,
  `HTTP.HEADERS.ASSIGN_ALIAS` и `HTTP.HEADERS.AUTO`;
- `HTTP.BODY.STREAM_ALIAS`, `HTTP.BODY.REPEATED_READ` и
  `HTTP.BODY.REPRESENTATION_SWITCH`;
- `ASYNC.AWAIT.SUSPENDS`, `ASYNC.AWAIT.OUTSIDE_ASYNC`,
  `ASYNC.FUNCTION.RETURNS_PROMISE`, `ASYNC.PROCEDURE.NO_PROMISE`,
  `ASYNC.PARAMS.BY_VALUE`, `ASYNC.ERROR.AT_AWAIT` и
  `ASYNC.PROMISE.REPEATED_AWAIT`;
- `ASYNC.FUNCTION.START_ORDER`, `ASYNC.DEFAULT_ARG.TIMING`,
  `ASYNC.AWAIT.READY_YIELDS`, `ASYNC.AWAIT.NON_PROMISE`,
  `ASYNC.PROMISE.MULTI_WAITER`, `ASYNC.DYNAMIC.AWAIT` и
  `ASYNC.PROCEDURE.UNHANDLED_ERROR`;
- `HTTP.ASYNC.REQUEST_SNAPSHOT`, `HTTP.ASYNC.STARTS_BEFORE_AWAIT`,
  `HTTP.ASYNC.ERROR_BOUNDARY`, `HTTP.ASYNC.COMPLETION_ORDER` и
  `HTTP.ASYNC.DROPPED_PROMISE`.

Каждый ещё не выполненный замер получает одноимённый маркер, запись реестра
и строку `measure-all.bsl`; документированный результат записывается как
ожидание пробы, а не как сгенерированный open-bsl oracle.

## Порядок реализации и проверки

### Этап 0. Зафиксировать падающий контракт

Сохранить SHA источника и Apache-2.0 notice рядом с интеграционным тестом.
Тест должен компилировать полный модуль, а не сокращённую копию. Отдельный
BSL-драйвер дописывается после функций и вызывает экспортный API Connector.
Начальное ожидаемое состояние — ошибка на `Base64Значение`. В описании
теста зафиксировать также версию документации 8.3.27 и раздел 17.3.1.2;
сам PDF в репозиторий не добавлять.

### Этап 1. Кодеки и малые типы runtime

Добавлять функции группами вместе с измерениями `HTTP.CODEC.*`,
`HTTP.VALUELIST.*`, `HTTP.CONVERT.*` и реестром открытых вопросов. Критерий:
парсинг URL, canonical query AWS4 и RFC 7231 выполняются без HTTP-транспорта.

### Этап 2. Потоки и временные файлы

Сначала закрыть предварительное расширение ABI для методов
`ДвоичныеДанные`, затем расширить `bsl-stream`, не копируя его буферную
модель. Критерий: поставщик
проверяется при сборке реестра, JIT совпадает с интерпретатором, а тесты
Connector для multipart и его `ЗаписатьGZip`/`ПрочитатьGZip` дают
байт-в-байт ожидаемое тело на данных 0, 1 и больше внутреннего буфера.

### Этап 3. Криптография

Реализовать `bsl-crypto`; проверить MD5/SHA-1/SHA-256 и HMAC официальными
векторами, затем AWS Signature V4 примером AWS. Критерий: заголовки Digest
и AWS4, сформированные BSL-кодом Connector, совпадают с эталонами.

### Этап 4. Асинхронное ядро языка и VM

Сначала добавить только необходимый синтаксический и bytecode-каркас
`Асинх`/`Ждать`, чтобы контрактные скрипты запускались и в open-bsl, и на
платформе. Затем выполнить все пробы `ASYNC.*` и лишь по их результатам
фиксировать семантику и поведение планировщика. До замеров нельзя угадывать
порядок старта функции, момент вычисления аргументов по умолчанию,
динамический `Ждать` или ошибку асинхронной процедуры. Временные ветви
каркаса получают полный комплект маркера `НЕ ИЗМЕРЕНО`, записи реестра и
строки измерения.

Далее выделить общий `ModuleState`, per-run `Execution`, task-local стеки и
FIFO promise scheduler. Добавить pollable API рядом с run-to-completion
`State::run`, `CompletionPayload`, закрываемые execution token'ы и два вида
method descriptor — немедленный и suspendable. Детерминированные unit-тесты
покрывают обещание, завершённое сразу, позже и с ошибкой; несколько
ожидающих; сохранение локальных значений, `pc` и диапазона `Попытка`;
передачу параметров по значению; общий доступ к модульным переменным;
`Выполнить`/`Вычислить`; закрытый token и возобновление host-вызова без
повторного эффекта.

После корректности включить safe-point quantum. Тесты проверяют FIFO,
переключение на back-edge, при рекурсии, обратном `Goto` и
`fast_numeric_for`, отключение счётчика при одной живой задаче и сохранение
кванта между кадрами. JIT делает inline decrement/check только на safe
points; `Await` и создание задач используют точечный fallback и не
отключают весь чанк.

Критерий: при искусственном обещании код после вызова выполняется до его
завершения, на незавершённом `Ждать` продолжает работу другая задача, а
ошибка возбуждается и перехватывается именно у `Ждать`. Текстовый bytecode
проходит round-trip и проверку образа, бандлы сохраняют инварианты, JIT
совпадает с интерпретатором, A/B-бенчмарки не показывают необъяснённого
регресса, а `bsl-vm` и state machine собираются для `wasm32-unknown-unknown`.

### Этап 5. HTTP без TLS

Сначала реализовать BSL-объекты поверх тестовой фабрики. Контрактный тест
должен увидеть отдельно `host` соединения и неизменённый resource запроса,
порт 80 по умолчанию, `Duration` из секунд, `ProxyMode::PlatformDefault`,
снимок мутабельного запроса и точное преобразование `NetworkError`.

Для тестовой фабрики реализовать одновременно синхронные и асинхронные
методы. Управляемый barrier доказывает, что асинхронный метод возвращает
обещание до ответа, а мутация исходного `HTTPЗапрос` после вызова не меняет
снимок. Табличный тест проверяет все семь соответствий имени и HTTP-метода,
включая `ВызватьHTTPМетодАсинх`, `ЗаписатьАсинх`, `ИзменитьАсинх`,
`ОтправитьДляОбработкиАсинх`, `ПолучитьАсинх`,
`ПолучитьЗаголовкиАсинх` и `УдалитьАсинх`.

Затем реализовать системный адаптер на общем Tokio runtime и async
`reqwest`, не пропуская эти типы через host ABI, и проверить локальным
`TcpListener`-сервером:
произвольные методы и короткие обёртки в обеих формах, заголовки, пустое,
строковое и двоичное тело, 2xx/3xx/4xx/5xx как обычный `HTTPОтвет`,
инфраструктурный отказ как исключение у вызова либо `Ждать`, IPv4/IPv6,
тайм-аут, два одновременно ожидающих запроса и переиспользование
соединения. Синхронный вызов блокирует все BSL-задачи, асинхронный уступает;
отмена закрытого `Execution` прерывает future, а поздний completion
отбрасывается. Автоматическое перенаправление должно быть выключено. Тесты
не зависят от публичного интернета.

Текущая native-матрица локально закрепляет произвольный PATCH, тела и
заголовки, классы 2xx/3xx/4xx/5xx, выключенное auto-redirect, единый
deadline, два одновременно выполняющихся запроса, reuse соединения и
IPv4/IPv6. Отдельные табличные тесты проводят все семь коротких методов и
универсальный вызов в sync/async-формах через одинаковое wire-отображение.

### Этап 6. Поведение полного Connector

Тем же локальным сервером проверить GET query, form-urlencoded, JSON,
multipart, cookies, относительные и абсолютные redirects, 307/308 с
сохранением тела, лимит redirects, `Retry-After`, Basic, Digest, Bearer и
AWS4. Отдельно проверить, что отключённое автоматическое распаковывание не
конфликтует с собственным GZIP-кодом Connector.

Интеграционные тесты исполняют публичный API полного неизменённого
модуля без test-only подмен. В interpreter и JIT проверены query,
form-urlencoded, JSON, cookies, Bearer, Basic, Digest, AWS4, относительные и
абсолютные redirects, переход 302 на GET, сохранение метода и тела для
307/308, лимит redirects и `Retry-After`. Digest и AWS4 сверяются с
независимыми векторами RFC/AWS. Multipart и GZIP проверяются тем же исходником
отдельно; системный адаптер сохраняет сырое тело с `Content-Encoding: gzip`.

### Этап 7. Proxy и TLS

Добавить тестовые HTTP proxy и TLS-сервер с локальным CA. Матрица: системные
корни, файл CA, отключённая проверка, неверное имя хоста, клиентский
сертификат, `PlatformDefault`/`Direct`/`Explicit` и исключения прокси. Секреты
нельзя выводить в ошибки или листинги.

Локальная TLS-матрица реализована на `rustls`: системные корни отвергают
тестовый CA, файл CA даёт успех, неверное имя отвергается, явный insecure-режим
его принимает, а mTLS требует настроенный клиентский PEM. Proxy-тесты
закрепляют все три режима, absolute-form для явного proxy и измеренные loopback-
исключения.

### Этап 8. Ошибки и интеграция

Довести объект информации об ошибке и тексты сетевых отказов. После этого
полный исходник обязан компилироваться и обычный сценарий GET/POST должен
работать и через `bsl-cli`, `State::run` и pollable `Execution`. После
критерия Connector добавить не требующие нового механизма короткие методы,
строковое чтение запроса и строковое/потоковое чтение ответа. Отдельный
интеграционный сценарий должен выполнить асинхронный GET, полезную работу до
`Ждать`, затем получить `HTTPОтвет`; второй сценарий перехватывает сетевую
ошибку вокруг `Ждать`. Файловые тела остаются отдельной задачей.

Текущие локальные end-to-end тесты проводят синхронный POST и асинхронный
GET через настоящий системный адаптер, `State::run` в interpreter/JIT,
pollable `Execution` и отдельный процесс `bsl-cli`; общий тестовый сервер
проверяет метод, resource и тело.

Финальная проверка: `cargo fmt --all -- --check`, `cargo clippy
--workspace --all-targets -- -D warnings`, `cargo test --workspace`,
`RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps` и
`the_jit_agrees_with_the_interpreter_on_every_script`.

## Отложенные границы

- `КакXDTO` нельзя честно закрыть пустой фабрикой: глобальная
  `ФабрикаXDTO` содержит типы конфигурации. Нужен отдельный host-контракт,
  передающий фабрику конфигурации; до него метод должен сохранять текущую
  явную ошибку. `ЧтениеXML` уже реализовано.
- NTLM/Negotiate и Windows certificate store не входят в первый релиз.
- Браузерный `fetch`-адаптер, CORS, proxy policy и `AbortController` —
  следующий WASM-этап. Здесь обязательны только переносимая state machine и
  compile-тест; синхронный HTTP уже представлен suspendable host-вызовом.
- `ФоновыеЗадания` используют отдельные изолированные `State` в
  ограниченном пуле OS-потоков и FIFO-очередь, а не Tokio и не `ModuleState`
  родителя. Их API, сериализация параметров и lifecycle планируются отдельно.
- Файловые тела HTTP документированы, но Connector их не вызывает. Их
  сигнатуры, момент файлового I/O и переключение представлений сначала
  уточняются по синтакс-помощнику и платформенным замерам.
- Полный объект `Метаданные`, HTTP/2, WebSocket и сервер HTTP исходнику не
  нужны и не должны появляться в этой работе.
- Поведение 1С для исключений прокси, таймаутов и
  проверки сертификатов нельзя выводить из поведения `reqwest`: до замера оно
  получает маркеры `НЕ ИЗМЕРЕНО(HTTP.*)` по правилам репозитория.

Работа завершена, когда зафиксированный модуль Connector компилируется без
изменений, синхронная и асинхронная HTTP-матрицы проходят на локальных
серверах, `Ждать` действительно уступает исполнение другой BSL-задаче, а
неподдержанные конфигурационно-зависимые возможности отказывают явно и
документированно.
