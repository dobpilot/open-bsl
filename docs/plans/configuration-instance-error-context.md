# Проверить контекст ошибки после обратного вызова экземпляра

Во время первого повтора `data-processor-object/measure.bsl` новый объект
ещё не умел записывать экспортную переменную через свойство. Запись
`ПервыйПробы.СчетчикПробы = 41` дала `UnknownProperty("СчетчикПробы")`.
Однако находящийся в нативном сценарии обработчик `Исключение` при вызове
`ОписаниеОшибки()` получил вторую ошибку:
`ОписаниеОшибки требует состояния текущего обработчика`.

Временный диагностический повтор без обработчика выявил исходный
`UnknownProperty`; затем исходный тест восстановлен без изменения нативного
сценария. После добавления доступа к экспортным слотам успешный сценарий
совпадает с 1С, но это не проверяет сохранение контекста ошибочного пути.

Это отдельный дефект для исследования. Нужен минимальный независимый контроль
ошибки свойства после вызова экспортного метода экземпляра: снять на платформе,
повторить через existing configuration-instance service и проверить, не
заменяется ли контекст активного обработчика при возвращении nested execution.
Не исправлять его попутно изменением текстов диагностики или отключением
`ОписаниеОшибки` в исходном сценарии.


## Уточнение по исходникам 2026-10-07

Проверка HTML-отказа выявила исходную причину вторичной диагностики:
`crates/bsl-rt/src/component.rs::error_description` безусловно возвращает
«ОписаниеОшибки требует состояния текущего обработчика». Комментарий прямо
фиксирует незавершённую модель состояния обработчика. Наличие этой ошибки
после callback не доказывает потерю состояния при nested execution.

Первоначальная гипотеза о swap-контексте остаётся непроверенной; нельзя чинить
VM callbacks на основании данного симптома. Будущая работа сначала должна
измерить контракт самой ОписаниеОшибки (включая вложенные обработчики и выход
из них), а затем связать его с явным состоянием обработчика. При HTML-диагностике
первая ошибка была заглушкой конструктора ЗаписьHTML, а не callback экземпляра.

## Нативный контроль 2026-10-07

Восемь наблюдений сохранены в
`docs/research/fixtures/error-description-context/`. Вызванная функция
получает пустое описание, вложенный обработчик временно заменяет внешнюю
ошибку, после него внешняя восстанавливается, а после обработчика описание
пусто. Это исключает реализацию через единственное поле последней ошибки
задачи. Контекст конфигурационного callback отдельно ещё не измерен.
Runtime и старые тесты не менялись; OpenSpec реализации ещё не создан.

## Проверка после реализации контекста обработчика

Активное изменение `implement-handler-scoped-error-description` реализует
описание из текущего кадра с явными границами обработчика, сохраняя прежнее
ограничение формата диагностики. Девять новых нативных наблюдений
`error-description-context/instance.bsl` воспроизведены через SessionFactory:
инициализация объекта, экспортные вызовы, локальная обработка и проброс
ошибки объекта сохраняют правильный контекст вызывающего. Дополнительного
исправления swap/nested callback не потребовалось. Прежние четыре теста
обработок также прошли без изменения ожиданий. Это закрывает исходную
гипотезу о потере контекста callback в измеренных сценариях; полный прогон
и архивация изменения ещё ожидают согласования старых тестовых литералов
и ожидания заглушки.
