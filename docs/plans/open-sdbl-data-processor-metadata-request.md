# Запрос изменений open-sdbl: метаданные собственного объекта обработки

Версию и ветку согласовать отдельно. Этот запрос не является заданием менять
уже завершённую ветку 0.9.9 или добавлять новый механизм исполнения BSL.

## Причина

Read-only компиляция исходного demo после поддержки
`ArchiveFileRestoreFilePathsMode` достигает собственного `Создать()` в модуле
менеджера обработки. Полученный объект используется через экспортные методы
его модуля. Нужна настоящая память экземпляра в существующем open-bsl;
пустая структура или успешная заглушка не подходят.

После runtime-реализации на явно полных фикстурах повторная компиляция demo
получила 3953 модуля за 5.29 с, затем через 85.02 с остановилась на
`UndefinedVariable("ОбработчикиОбновления")` в
`Обработка.ОписаниеОбработчиковОбновления.МодульОбъекта`. Тип этого поля не
измерен и не должен угадываться по имени. Прикладной BSL не исполнялся.

SDK 0.9.9 предоставляет полные списки собственных реквизитов и частей для
других классов, но не для DataProcessor. Чтение Config и его бинарный разбор
остаются ответственностью open-sdbl. open-bsl не должен повторять декодер.

Повторная проверка 2026-10-08: в доступном SDK HEAD `2b794f0` (0.9.10)
эти поля всё ещё отсутствуют. В `src/metadata/config.rs` имеются
`business_process_attributes`, `business_process_tabular_sections` и
`business_process_object_type`, но соответствующих полей обработки нет.
В `bsl-config-db` класс обработки распознаётся, однако полного состава
собственного объекта из SDK получить нельзя. Следующий шаг — дополнение
декодера SDK по этому запросу, а затем проекция приобретённых описателей;
добавление второго декодера в open-bsl не устраняет архитектурный пробел.

Готовая точка проверки интеграции —
`crates/bsl-session/tests/data_processor_objects.rs`: существующая реализация
экземпляров использует явно полные фикстуры с
`with_data_processor_attributes` и `with_data_processor_tabular_sections`.
После дополнения SDK нужен отдельный тест загрузчика `bsl-config-db`, который
получает тот же состав из приобретённой конфигурации, включая порядок полей
и различие `None` / `Some([])`. Повторный запуск тестов только с ручными
фикстурами не доказывает устранение препятствия в demo.

## Изменение существующего ConfigDescriptor

Добавить сведения для собственного класса DataProcessor по образцу уже
принятых полей бизнес-процесса:

- `data_processor_attributes: Option<Vec<Guid>>` — полный упорядоченный список
  собственных реквизитов без полей табличных частей;
- `data_processor_tabular_sections: Option<Vec<Guid>>` — полный упорядоченный
  список собственных частей;
- `data_processor_object_type: Option<Guid>` — приобретённый GUID порождённого
  типа объекта, отдельно от типа менеджера.

Использовать существующие описатели реквизитов, типов, квалификаторов,
заполнения и `tabular_section_attributes` для полей частей. Если для обработок
измеренная форма требует дополнить эти общие описатели, показать конкретный
пробел до реализации. Не копировать настройки справочника или документа.

`Some([])` означает проверенную пустую коллекцию. `None` означает неизвестную,
повреждённую либо неполную форму; нельзя публиковать частичный список как
полный. Не выводить состав из имён ресурсов или экспортных переменных BSL.
Выборочное чтение обязано сохранить эти метаданные после отбрасывания байтов
исходных ресурсов. Новых зависимостей и SQL-компилятора не требуется.

## Проверка

До реализации оформить и строго провалидировать OpenSpec. Снять на реальной
1С собственные контролируемые обработки: пустой состав; несколько реквизитов
с различимыми типами/квалификаторами; несколько частей, включая пустую,
с полями в отличном от алфавита порядке. Сохранить нативные XML, ресурсы,
хеши происхождения и сверку полных списков/GUID. Повреждение коллекции не
должно выдавать частичный `Some`. Проверить выборочное чтение и неизменность
остальных классов, fmt, Clippy, tests, rustdoc и strict OpenSpec.

Рабочие базы читать только read-only. Прикладной код конфигураций не исполнять.
Нативный runtime-контроль open-bsl расположен отдельно в
`docs/research/fixtures/data-processor-object/`: он содержит 31 нативную строку поведения экземпляра, строковых/булевых
реквизитов и табличной части. Runtime replay на явно полных метаданных прошёл,
но это не доказывает декодирование списков из Config. В SDK не ограничивать
полный состав только этими двумя типами: все остальные приобретённые объявления
нужно сохранить, а неподдержанную форму явно отличать от известной.

Проверка набора артефактов 2026-10-08: `data-processor-object` содержит
XML, BSL и нативные runtime-квитанции; бинарного описателя Config или CF
в нём нет. Поэтому этот набор нельзя использовать как доказательство
правильности декодера. Для SDK по-прежнему требуется независимая штатная
выгрузка собственного контроля и сопоставление бинарного ресурса с XML.
