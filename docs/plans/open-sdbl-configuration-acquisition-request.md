# Запрос изменений в `open-sdbl` для конфигурационных сеансов

Дата: 2026-09-21.

## Причина

`bsl-config-db` должен получить исходники модулей и `MetadataSnapshot` одной
операцией чтения информационной базы. Сейчас
`open_sdbl_db::acquire_metadata` потоково читает и сразу отбрасывает целые
ресурсы `Config`, а `DatabaseSession::metadata` возвращает только разрешённые
метаданные и отчёт. Повторное чтение тех же таблиц в `bsl-config-db` нарушило бы
границу адаптера БД и без необходимости увеличило бы окно, в котором база может
измениться между чтениями.

Одна операция не означает атомарный снимок: реализованный адаптер сохраняет
`READ COMMITTED`, поэтому отдельные запросы внутри неё могут увидеть разные
зафиксированные состояния. Если хосту нужно обнаружить изменение конфигурации
во время чтения, он сравнивает `CONFIG_FINGERPRINT` до и после операции.

## Требуемый публичный контракт

В `open-sdbl-db` нужна одна операция уровня `DatabaseSession`, условно:

```rust
pub struct AcquiredConfiguration {
    pub metadata: MetadataSnapshot,
    pub report: ResolutionReport,
    pub layout: StorageLayout,
    pub config_resources: Vec<ConfigResource>,
    pub extensions: Vec<AcquiredExtension>,
}

impl DatabaseSession {
    pub async fn configuration(
        &mut self,
        progress: &mut dyn MetadataProgress,
    ) -> Result<AcquiredConfiguration, DbError>;
}
```

Имена могут отличаться. Существенны следующие свойства контракта:

- `metadata`, `report`, базовые ресурсы и ресурсы расширений читаются одной
  ограниченной read-only acquisition на уровне `READ COMMITTED`;
- применяются существующие определение `StorageLayout`, сборка `PartNo`,
  лимиты распаковки, обработка legacy-layout и provider-specific запросы;
- `config_resources` содержит каждый ресурс таблицы `Config`, собранный из
  всех его `PartNo`, включая корневой граф, исходники модулей и служебные
  ресурсы, которые загрузчик кода сам отфильтрует;
- `extension_resources` сохраняет имя и содержимое ресурсов с принадлежностью
  конкретному активному расширению и порядком применения; если плоский
  `Vec<ConfigResource>` этого не выражает, нужен отдельный тип с идентичностью,
  именем, активностью и порядком расширения;
- успешный результат публикуется только после успешного завершения read-only
  acquisition; при ошибке действует существующий rollback;
- прежний `DatabaseSession::metadata` остаётся дешёвым путём, которому не
  требуется удерживать все ресурсы в памяти, и может быть реализован общим
  внутренним pipeline без изменения поведения.

Существующий запрос metadata pipeline выбирает только bare-GUID ресурсы и
суффиксы `.1c`, `.9` и `.7`. Поэтому `configuration()` не может просто вернуть
ресурсы, которые сейчас проходят через `read_config`: этот набор не является
полным графом конфигурации. Для новой операции provider должен прочитать все
строки `Config` в порядке `(FileName, PartNo)`, собрать каждый ресурс один раз
и на тех же байтах выполнить существующее извлечение метаданных. Старый
`metadata()` вправе сохранить нынешний SQL-фильтр и потоковое декодирование.

`bsl-config-db` сам разберёт форматы модулей и соберёт
`ConfigurationCodeSnapshot`. `open-sdbl` не должен узнавать о BSL-модулях,
`open-bsl` или их графе импортов.

## Пользователи информационной базы

Для выбора principal нужен также метод:

```rust
impl InfoBaseUser {
    pub fn can_authenticate(&self) -> bool;
}
```

Он возвращает `true`, если у записи включён хотя бы один поддерживаемый
платформой способ аутентификации. Декодер должен учитывать все такие признаки,
которые хранятся в поддерживаемых вариантах `v8users`; одного `EAuth`
недостаточно, поскольку пользователь может входить через аутентификацию ОС.
`AdmRole` остаётся отдельным признаком и способом аутентификации не считается.

## Проверяемые сценарии

1. Для одной базы `configuration()` возвращает тот же `MetadataSnapshot` и
   `ResolutionReport`, что существующий `metadata()`, вместе со всеми
   ресурсами `Config`, прочитанными в том же acquisition; в результате есть
   как минимум один ресурс вне нынешнего фильтра metadata pipeline.
2. Разбитый ресурс `Config`/`ConfigCAS` возвращается один раз после сборки всех
   `PartNo`; пропуск или повтор части остаётся ошибкой данных.
3. Ресурсы двух активных расширений сохраняют раздельную идентичность и порядок.
4. Ошибка чтения любого ресурса не публикует частичный результат.
5. `can_authenticate()` истинен для стандартной аутентификации и для
   аутентификации ОС, ложен для пользователя без включённых способов и не
   зависит от `AdmRole`.

После появления этого API `open-bsl` зафиксирует зависимость воспроизводимым
Git revision или выпущенной версией и реализует декодирование конфигурационного
графа в `bsl-config-db`.

## Точки изменения в текущем коде `open-sdbl`

Запрос сверён с `open-sdbl` на коммите `494305e`. В нём уже есть большая часть
нужной механики, поэтому новая операция не требует второго pipeline:

- `open-sdbl-db/src/pipeline.rs` уже содержит публичный `ConfigResource` и
  `assemble_parts`; `ConfigResource::compressed` хранит байты в том виде, в
  котором их вернула таблица;
- `MetadataSource` и `acquire_metadata` уже задают единственную read-only
  транзакцию, commit/rollback, определение `StorageLayout`, пределы и получение
  расширений;
- provider-реализации `read_config` сейчас читают только фильтрованный набор,
  заданный `PostgresMetadataQueries::CONFIG` и
  `MsSqlMetadataQueries::CONFIG`;
- `DatabaseSession::metadata` публикует только снимок и отчёт после завершения
  acquisition;
- `open-sdbl-db/src/extensions.rs::ExtensionIndex` объединяет ресурсы всех
  расширений в один закрытый вектор. Для загрузки кода его нельзя выдавать как
  результат новой операции: после объединения теряются владелец ресурса и
  порядок применения расширений.

Практически нужен соседний с `acquire_metadata` pipeline, который внутри той же
транзакции читает полный `Config`, использует эти же байты для существующего
metadata resolution и сохраняет их в результате. Запуск существующего
`acquire_metadata`, а затем второй запрос полного `Config` контракту не
соответствует: первый pipeline уже завершил транзакцию. Новый тип результата и
`ConfigResource` должны быть реэкспортированы из корня `open-sdbl-db`, чтобы
`bsl-config-db` не зависел от внутренних provider-модулей.

Для расширений результат должен иметь явную оболочку примерно такого смысла:

```rust
pub struct AcquiredExtension {
    pub identity: String,
    pub name: String,
    pub active: Option<bool>,
    pub order: u32,
    pub resources: Vec<ConfigResource>,
}
```

`active == None` означает, что адаптер не распознал форму записи активности.
Загрузчик обязан завершиться ошибкой с именем такого расширения: молча считать
его включённым или выключенным нельзя. Два расширения с одинаковым именем
ресурса не сливаются, а `order` задаёт платформенный порядок применения.

Запрошенный контракт реализован в ветке `open-sdbl-v8` на коммите `fc67dba`.
Ресурсы одного хранилища ограничены `config_resource_limit` и
`config_retained_byte_limit`; те же потолки независимо применяются к `Config`
и `ConfigCAS`, которые во время приобретения удерживаются одновременно.
Зависимость в `open-bsl` можно фиксировать после публикации этого коммита в
remote или выпуска версии, содержащей его.

В модели пользователя необходимые признаки уже присутствуют:
`InfoBaseUser::standard_authentication` и `InfoBaseUser::os_name`. Для текущего
контракта допустимость пользователя равна
`standard_authentication || !os_name.trim().is_empty()`; `show_in_list` и
`administrative` на допустимость входа не влияют. Метод `can_authenticate()`
следует разместить на `InfoBaseUser`, чтобы CLI и будущие потребители не
дублировали это правило.
