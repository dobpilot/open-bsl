# Запрос: измеренное разделение данных пользователя информационной базы

Read-only оригинальная инициализация UNF достигает `ПользователиИнформационнойБазы.ТекущийПользователь().РазделениеДанных.Количество() = 0` в функции СеансЗапущенБезРазделителей. Диагностика подтвердила тип получателя ПользовательИнформационнойБазы, а не объект метаданных общего реквизита. Лог: target/diagnostics/readonly-startup/unf-separation-property-host-1013-startup.log,444,66с, код1.

SDK UserData/InfoBaseUser в текущем ../open-sdbl305f4f1 не предоставляет сведения о разделении данных. ORM Principal сохраняет снимок пользователя при открытии сеанса; подстановка пустой структуры без доказанного отсутствия разделителей запрещена.

Нужно измерить на собственной базе хранение пользовательского свойства РазделениеДанных: известный пустой набор и непустой набор реального общего реквизита-разделителя. Нативное чтение свойства сверить с собственным serialized пользовательским ресурсом, сохранить не содержащие секретов фикстуры. Не использовать исходные demo/buh/unf для записей. Не путать список привязок пользователя с текущими значениями параметров сеанса или со всей конфигурацией разделителей.

Добавить минимальный API снимка прочитанных пользовательских привязок через существующий decoder/users acquisition. Известная пустота отличается от неизвестного/неподдержанного формата; неизвестность не превращается в пустую структуру. Имена/типы/значения подтверждаются платформой, секреты из v8users исключаются из API и логов. Поддержать только измеренные формы; не выводить признаки разделения из роли или имени пользователя. Не менять аутентификацию, фильтр can_authenticate и права.

До реализации — OpenSpec, strict validation и предложение публичного API по результатам измерения. Версия пока не назначена; main не менять. Требуются unit/fixture tests и полные fmt/Clippy/tests/doc/strict. Root-проекция в Principal/пользовательский объект будет отдельным аддитивным шагом после доступности фактического SDK API.

Начальный нативный контроль чтения пустого свойства подготовлен в tests/conformance/measure/1c/measure-infobase-user-data-separation.bsl; собственный прогон завершился успешно. Он не доказывает пустоту свойства выбранного пользователя UNF.

Нативный результат сохранён в measure-infobase-user-data-separation.platform.txt. Содержимое относится только к собственной одноразовой базе; тип и число элементов сверяются по этому артефакту, а не по выводу ORM.

Дополнительный нативный контроль `measure-infobase-user-data-separation-values.{bsl,platform.txt}` завершился на собственной одноразовой базе с реальным общим реквизитом-разделителем НаименованиеЯзык1. Проверены назначение структуры новому несохранённому пользователю, последующее чтение ключа/значения и изменение исходной структуры после назначения. Пользователь в базу не записывался; эти результаты не доказывают физическое хранение v8users. Runner переиспользует существующую XML-фикстуру разделителя и параметров, без нового механизма конфигурации.

Третий нативный контроль `measure-current-user-separation-snapshot.{bsl,platform.txt}` проверяет мутацию структуры, полученной от текущего пользователя, повторное чтение того же объекта и новый ТекущийПользователь(), а также присваивание свойства. Использована собственная база без первоначальных пользователей, с тестовым разделителем. Этот особый текущий пользователь не заменяет замер аутентифицированного именованного пользователя; результаты нужно сохранять с этой границей применимости.

Контроль именованного пользователя завершён в собственной отдельной копии файловой базы: docs/research/fixtures/user-data-separation-named/{Module.bsl,native.oracle,receipts.json}. Вход выполнен как собственный ControlAdministrator без изменения описания пользователя. Структура полученного свойства проверена на мутацию и повторное чтение того же/нового текущего пользователя. Пользователь не записывался. Это подтверждение поведения именованного пользователя, но по-прежнему не физической формы v8users.Data.

## Физическая форма собственного ресурса 2026-10-15

В новой собственной PostgreSQL-базе нативный контроль создал отдельных пользователей с пустой и непустой структурой. Read-only извлечение проверено существующим decode_user_data и parse_serialized. У пустого ресурса38полей, поле17—0; у непустого39полей, поле17—1 и поле18—список двух строк НаименованиеЯзык1/own-separator-value. Последующие поля сдвигаются на число привязок. Это доказательство только измеренного варианта записи и строкового значения, не универсальное правило для старых версий. Сырые пользовательские ресурсы с хешами паролей удерживаются только в приватном /tmp-каталоге и в репозиторий не копировались. Безопасная схема обхода в target/diagnostics/user-settings-safe-shapes-1015.log. Native oracle/receipts сохранены в docs/research/fixtures/user-settings-native-1015.


## Черновая реализация SDK — 2026-10-15

В `/tmp/open-sdbl-logical-projection-draft-1013` добавлен и строго провалидирован change `decode-user-data-separation`. `UserData::data_separation` хранит `Option<Vec<(String, String)>>`: полный список строковых привязок измеренной формы, известный пустой список или неизвестность. Несогласованный счётчик, неподдержанный тип, повторное имя и неизвестная форма не дают частичного результата. Повторно использованы существующие XOR-декодер и парсер; пароли и их хеши в API не включены.

Оба собственных нативных файла `OpenBslUserEmpty.data` и `OpenBslUserSeparated.data` проверены новым декодером: результаты точно соответствуют пустому списку и паре `НаименованиеЯзык1` / `own-separator-value`. Приватные записи не копировались в репозиторий и не печатались. Пять новых тестов и все 109 библиотечных тестов прошли; форматирование, Clippy пакета со всеми целями и rustdoc с запретом предупреждений прошли.

Это подготовленный черновик, без изменения версии и публикации SDK. Передача списка в `Principal` и повтор исходной инициализации UNF ещё не выполнены; исходная задача не считается завершённой.


### Проверка оригинальной UNF и адаптера — 2026-10-15
