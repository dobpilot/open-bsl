# Запрос на API open-sdbl для синхронного хоста BSL

Нужен следующий небольшой change в `open-sdbl`. Потребитель — `bsl-config-db`:
он исполняет синхронный BSL и не может добавить `tokio` или `zeroize` в своё
дерево зависимостей, но должен владеть отдельным живым соединением каждого
сеанса.

## Проблема

`open-sdbl-db` уже зависит от `tokio` и `zeroize`, однако наружу отдаёт только
асинхронный `DatabaseSession`. Создать `Credentials::EnvironmentSecret::Present`
тоже нельзя без прямой зависимости потребителя от типа `zeroize::Zeroizing`.
В результате синхронный хост вынужден либо протащить обе внешние зависимости,
либо написать второй небезопасный слой работы с секретами и executor.

Кроме того, документация `AcquiredConfiguration` предлагает сравнивать
`CONFIG_FINGERPRINT` до и после чтения всей конфигурации. Текущий запрос
fingerprint содержит старый фильтр GUID/`.1c`/`.9`/`.7`, поэтому не замечает
изменения остальных ресурсов `Config`, `ConfigCAS`, `_ExtensionsInfo` и
`_ExtensionsRestruct`. Он не может подтверждать неизменность результата whole
configuration acquisition.

## Требуемый публичный API

1. Добавить в `open-sdbl-db` синхронного владельца одного соединения, например
   `BlockingDatabaseSession`. Он внутри крейта владеет однопоточным runtime и
   обычным `DatabaseSession`; нового внешнего dependency это не требует.
2. Дать ему синхронные аналоги уже существующих операций:
   `connect`, `configuration`, `metadata`, `query`, `query_each` и `close`.
   Методы должны вызывать ровно существующую асинхронную реализацию, без второго
   SQL-пути. Значения `Limits`, диагностики, отмена и отравление соединения
   должны сохраняться.
3. Добавить конструктор `Credentials`, принимающий принадлежащие строки или
   `Option<String>` для PostgreSQL, MSSQL и SOCKS5 и заворачивающий их в
   `Zeroizing` внутри `open-sdbl-db`. Публичный API не должен требовать у
   потребителя назвать crate `zeroize`.
4. Не добавлять пароли в `DatabaseConnection`, `Debug` или сообщения ошибок.
   Политика чтения и удаления переменных окружения остаётся у приложения.
5. Исправить рекомендацию про fingerprint одним из двух честных способов:
   либо явно ограничить её только отфильтрованной metadata-частью `Config`,
   либо добавить отдельный fingerprint всей acquisition-поверхности. Если
   добавляется полный fingerprint, он должен учитывать весь `Config` и все
   данные расширений, которые входят в `AcquiredConfiguration`, для обоих
   провайдеров.
6. Дополнить `AcquiredExtension` provider-neutral сведениями, которые уже
   находятся в `_ExtensionsInfo` и в декодированном корневом каталоге:
   версией, hash, safe-mode settings, признаком использования в распределённой
   базе, scope и явными связями extension-local объектов с заимствованными
   base-объектами. Если поле ещё не декодировано надёжно, его тип должен быть
   `Option`, а не значение по умолчанию. Нужен также декодированный корневой
   каталог либо эквивалентная структура, позволяющая `bsl-config-db`
   перечислить классы и объекты расширения. Сырые BSL-модули остаются
   ресурсами: `open-sdbl` не должен знать их слоты или собирать эффективный
   BSL-граф.

## Проверки

- Синхронный и асинхронный пути возвращают одинаковую конфигурацию и одинаковую
  ошибку на искусственном provider.
- Два `BlockingDatabaseSession` владеют разными соединениями; закрытие одного
  не влияет на другое.
- Пароль не появляется в `Debug` и тексте ошибки, а память строки принадлежит
  `Zeroizing` внутри `open-sdbl-db`.
- Вызов синхронного метода после `close` возвращает типизированную ошибку.
- Тест fingerprint меняет ресурс, который старый GUID-фильтр не принимал, и
  расширение; заявленная проверка обязана заметить оба изменения. Если контракт
  сужен, тест вместо этого закрепляет точную границу и документация больше не
  обещает проверку всей конфигурации.
- Fixture расширения закрепляет identity/order/activity и каждое новое
  optional-свойство, а также хотя бы одну явную связь заимствованного объекта с
  объектом базы. Имена ресурсов из `ConfigCAS` не считаются такой связью.
- `cargo fmt --all -- --check`
- `cargo clippy --workspace --all-targets -- -D warnings`
- `cargo test --workspace`
- `RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps`
- отдельный OpenSpec change до реализации и `openspec validate <name> --strict`.

API не должен знать об open-bsl, BSL, параметрах сеанса или ORM. Его задача —
только синхронно провести уже существующие операции одного соединения и скрыть
технические типы собственных зависимостей.
