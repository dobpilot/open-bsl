# Обработчик ожидания нативного контроля

В собственном нативном контроле динамического обновления произошёл отказ
`AttachIdleHandler`: параметр 1 при вызове
`ПодключитьОбработчикОжидания("ШагКонтроля", 1)`.
В подготовленном модуле управляемого приложения процедура `ШагКонтроля`
объявлена без `Экспорт`.

Поиск в синтакс-помощнике платформы 8.3.27.2342 подтвердил, что параметр
`ИмяПроцедуры` указывает экспортируемую процедуру. Локатор:
`platform-syntax-help:syntax-context:objects/Global context/methods/catalog33/AttachIdleHandler512.html`.
Это подтверждение поисковым фрагментом; полный документ через коннектор
не прочитан. Агенту переданы причина и необходимость проверки реально
загруженного исправленного объявления перед повторным контролем.

Предварительный результат `before-A.oracle` существует:
`revision=1;session=12;ru=No;en=No;type=Boolean`. Клиент A PID 1831803
уже отсутствовал при независимой проверке root, а собственный сервер
`ibsrv` PID 1830984 оставался жив. Поэтому этот результат не используется
как свидетельство сохранения одного сеанса до и после динамического
обновления. Для положительного контроля нужен новый исправленный,
непрерывно работающий A, реальное динамическое обновление и новый B.

Отказ измерительного обработчика не требует изменений исходных
demo/buh/unf, реализации idle handler в open-bsl или придуманного значения
динамического признака для CLI.

Последующая проверка обнаружила отдельный отказ перезапуска. Новый сервер
PID 1844661 и клиент PID 1844800 уже отсутствовали. В
`server-corrected.log` записан отказ блокировки каталога данных владельцем
PID 1830984. Проверка `ps` подтвердила, что именно этот старый собственный
`ibsrv` ещё жив; это не повод удалять файл блокировки как устаревший.
Клиентский журнал сообщает невозможность HTTP-подключения. Агенту передана
необходимость завершить свой старый сервер перед повтором.

Квитанция `verify-loaded-export-receipts.json` содержит успешный
`config save --db`, но следующий `config export` завершился с кодом 255:
не найден файл базы в `verify-export-data/db-data/1Cv8.1CD`. Поэтому эта
пара команд ещё не подтверждает реально загруженное объявление `Экспорт`.
Оба отказа относятся к организации контроля, не к измерению признака.

Последующий исправленный экспорт завершился успешно: обе операции,
`save --db` и `export`, вернули код 0 с явно заданным собственным
PostgreSQL-контекстом. Root прочитал фактическую XML-выгрузку и подтвердил
`Процедура ШагКонтроля() Экспорт`, а также правильное имя
`КонфигурацияБазыДанныхИзмененаДинамически` в `DynamicProbe`.
Хеши обоих загруженных модулей и квитанции сохранены в
`fixtures/dynamic-control-loaded/provenance.json`.
Квитанция остановки подтверждает штатное завершение собственного сервера
1830984 без SIGKILL. Повторный положительный контроль ещё предстоит;
успешный экспорт не является его заменой.

Исправленный сервер PID 1851988 и клиент A PID 1852897 независимо
подтверждены живыми. Начальный и повторный результаты до обновления
(`before-A`, `preupdate-A`) фиксируют одинаковые ревизию `1`, сеанс `12`,
русский и английский признаки `No`, тип `Boolean`.
Повторный результат получен через работающий обработчик ожидания;
исходный отказ его регистрации пройден. Эти две квитанции сохранены в
`fixtures/dynamic-control-session-progress/` и подтверждают только
состояние до обновления. Положительный контроль обновления ещё не получен.

Импорт ревизии 2 завершился с кодом 0 (`native-import-receipt.json`).
Сравнение `snapshot-before` и `snapshot-main-only` по хешам содержимого
и метаданным строк, с исключением имён файлов захвата, показало:
`Config` — 9 прежних строк без изменений; `ConfigSave` — 10 добавленных
строк; `DBSchema`, `Params`, `SchemaStorage` — без изменений.
Квитанция сравнения —
`target/diagnostics/dynamic-main-only-snapshot-comparison-1013.json`.
Это не свидетельство динамического обновления конфигурации базы.
Клиент A 1852897 к следующей проверке уже отсутствовал; результат
`main-only-A` не появился. Причина завершения ещё выясняется;
положительный контроль остаётся неполным.
