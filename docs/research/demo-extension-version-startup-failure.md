# Достигнутый отказ поиска версии расширений

После реализации сортировки и выгрузки списка исходный demo завершается
объектной ошибкой с пустыми описанием, кодом и причиной. Изолированная
диагностика зарегистрировала `RaiseDetailed` в корневой программе, pc 189.
Первоначально имя функции выводилось с ошибкой на один индекс:
`function_names[i]` соответствует `chunks[i+1]`. Поэтому напечатанное
`ОписаниеСостоянияЗаданий` не является именем вызывающего метода.
Диагностическое индексирование исправлено только в копии VM.

Отдельное read-only чтение исходников локализовало вызов в
`Справочник.ВерсииРасширений.МодульМенеджера`, метод `ВерсияРасширений`:
после трёх попыток он возбуждает исключение в строке 869. Каждая попытка
повторяет запрос активных версий, при отсутствии подходящей версии запускает
`СтандартныеПодсистемыСервер.ДобавитьНовуюВерсиюРасширений` и ждёт до 15 секунд.
После цикла формируется сообщение о невозможности создать новую версию.

Полный извлечённый модуль сохранён в
`target/diagnostics/readonly-startup/demo-extension-version-source-1013-startup.log`.
Оригинальная база не менялась. Нужно сопоставить вычисленное описание
подключённых расширений с существующими строками и фактическим результатом
запроса. Не доказано, что запись действительно необходима: причиной может
быть расхождение проекции описания или чтения. Поэтому расширять операции
записи или подставлять успешную версию преждевременно.

## Сопоставление описаний и прямой замер свойства

Диагностический запуск `demo-extension-match-1013-startup.log` вернул две
существующие строки и ноль совпадений. Строка `Расширение1` отличается от
вычисленного описания только отсутствующей хеш-суммой; имя, версия,
безопасный режим и описание основной конфигурации совпадают.

В отличие от предварительного предположения, тип свойства нельзя менять
только по этой разнице. Справка 8.3.27.2342 объявляет `Строка`, а отдельный
старый контроль подтверждает пустой результат `Base64Строка(Строка)`.
Поэтому выполнен прямой новый замер на собственной базе с установленным
расширением `ProbeHash1013`: `ТипЗнч(ХешСумма)` равен `ДвоичныеДанные`,
не `Строка`; Base64 совпадает с двадцатью байтами ключа поколения.
Справка в этом месте расходится с измеренным runtime.

Восемь строк и происхождение сохранены в
`docs/research/fixtures/extension-hash-type`. Предыдущий запуск с нулём
расширений не доказывал тип свойства. Getter ORM исправлен через существующий
декодер Base64, реэкспортированный фасадом. SDK, встроенное преобразование
строк и строки базы не менялись. Новый тест воспроизводит весь нативный
контроль, отдельный тест отвергает неверные данные хоста, consumer собирается
только через фасад. Для старой фикстуры `hash-one` подготовлен, но не применён
трёхстрочный патч `target/diagnostics/extension-hash-existing-test-correction.patch`.

Повтор после исправления getter вернул `matches=1` на двух строках.
Вычисленное описание с хешем `icDIE9O50FZS7IzvkeL/bxMT8+A=` совпало с уже
существующей версией. Код прошёл поиск без фонового создания и остановился
на отсутствующем `НачалоСеанса`. Лог:
`target/diagnostics/readonly-startup/demo-extension-binary-hash-1013-startup.log`.
Наблюдавшийся пик RSS — 2 622 112 КиБ; это факт этого запуска, а не A/B
измерение производительности. Никакие строки исходной базы не менялись.
Clippy и rustdoc всего workspace прошли; полный зелёный прогон пока
невозможен из-за неприменённой коррекции старого строкового ожидания.

Наблюдение запусков столкнулось с квотой `/tmp`; один внешний процесс
завершился кодом 120. Это не код BSL-ошибки. Сам read-only лог подтвердил
исходное исключение. Извлечение модуля без компиляции/исполнения завершилось
успешно с кодом 0.
