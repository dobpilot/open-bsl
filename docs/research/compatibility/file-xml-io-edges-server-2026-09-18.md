# Операционный путь файловых входов XML

Измерение выполнено напрямую на серверной `localhost/test`, Linux,
1С 8.3.27.2342. Unica не использовалась. Сессия
`/tmp/open-bsl-server-measure-kddtv95d` завершилась с кодом 0, восстановила
CF и БД; контрольная XML-выгрузка совпала с исходной.

- Исходник `file-xml-io-edges.bsl`: SHA-256
  `aaa097db902f987e058eff7dbb6c77540d2c49c62bb706bca96cb85f49cf01c6`.
- Oracle `file-xml-io-edges.platform.txt`: SHA-256
  `1e366282f8736c6a65a4ba4b723009612c6a0c3ff619b15ad27dc52b65d1b473`.

Writer-проба начинает с `ABC`, записывает пустой элемент `a` и проверяет
байты базового файла. Нормализованный путь даёт `EFBBBF3C612F3E`, сохранённый
суффикс оставляет `414243`. Reader-проба начинает с `<a/>` и проверяет имя
первого прочитанного элемента.

NUL и суффиксы TAB, LF, CR, SPACE, U+0085 и NBSP снимаются до host.
U+007F, U+200B и U+FEFF сохраняются. Writer с начальным NUL отказывает на
каталоге без изменения базового файла. Reader-вариант начального NUL не
включён после зафиксированного зависания другого потокового reader на
каталоге.

До исправления оба XML-объекта передавали исходный путь непосредственно
`FileSystem`. Теперь `ОткрытьФайл` вызывает `prepare_file_operation_path`
через файловую систему соответствующего объекта; writer сохраняет уже
нормализованный путь до `Закрыть`. Сквозной тест сверяет 23 строки в
source/bytecode × plain/optimize.
