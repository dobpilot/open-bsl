# Изоляция динамического кэша по владельцу модуля

Исправлена [зафиксированная коллизия](static-import-arguments-2026-09-17.md#свидетельство-для-следующего-динамического-этапа):
одинаковое `Вычислить("Нужная")` из функций двух модулей читало переменную
по раскладке первого. CLI выдавал `22, 44` вместо `22, 33`.
Новый фасадный тест подтвердил ошибку второго модуля до исправления.

## Контракт и устройство

Публичный `bsl_bytecode::DynamicScope` расширен полем
`module: Option<ModuleId>`: None — entry/самостоятельный модуль,
Some — модуль каталога. Это изменение Rust-контракта динамического
компилятора: внешние реализации должны сохранять новый компонент ключа,
а при создании области самостоятельного модуля указывать `module: None`.
Сценарий и решение добавлены в активную delta до реализации.

`program` остаётся номером фрагмента, выданным host-компилятором, либо ROOT
для статических чанков владельца; `chunk` — номером чанка. Номер модуля
каталога больше не используется вместо program. Это разделяет пространства
номеров модулей и фрагментов, которые ранее также могли пересекаться.

Вложенный исполнитель сохраняет владельца в продолжении и связанной
области: его технический ROOT_MODULE не заменяет исходный модуль в ключе
компиляции. Поэтому вызов статической функции из фрагмента сохраняет
правильный корневой контекст при любом уровне вложенности.

Кэш фасада уже использует DynamicScope целиком; новый компонент участвует
в равенстве и хэше без второго каталога соответствий. Повторное исполнение
той же области переиспользует тот же Rc<DynamicUnit>, а не отключает кэш.
Формат байт-кода остаётся 31, Program и таблицы образа не изменялись.
Платформенный oracle и markers не менялись: это изоляция конфигурационного
расширения open-bsl, а не новое утверждение о платформенной семантике.

## Проверки

`crates/open-bsl/tests/dynamic_module_scope.rs` использует два модуля
с разным порядком переменных. Проверяются чтение из тела, прямой динамический
вызов функции, вложенный Вычислить и вызов статической функции из фрагмента.
Порядок модулей меняется; каждый сценарий повторён дважды в одном State.
Матрица source/bytecode × plain/optimize × порядок даёт восемь комбинаций
с двумя запусками каждой.

Unit-тест `catalog_owners_are_part_of_the_scope_and_reuse_only_their_own_fragments`
сравнивает Rc для entry и двух каталожных владельцев, в ROOT и вложенной
области. Получены ровно шесть компиляций и шесть записей; повтор каждого
запроса возвращает прежний Rc. Прежние тесты тождества модульных ссылок,
параметров и прямых вызовов проходят.

Красный и зелёный логи:
`/tmp/open-bsl-dynamic-owner-{red,test,cache,regressions,cli}.log`.
Первоначальная CLI-проба теперь возвращает `22` и `33`.

Полный workspace завершился с кодом 0, включая conformance,
plain/optimize, bytecode round-trip, API reference и реестр измерений.
Прошли fmt, Clippy workspace/all-targets с `-D warnings`, rustdoc с
запретом предупреждений, `git diff --check` и 11 строгих проверок OpenSpec.
API reference регенерирован. Логи:
`/tmp/open-bsl-dynamic-owner-{workspace,clippy,doc,api,openspec}.log`.

Это не реализация импортов внутри динамического текста, не перенос
каталожных состояний во вложенный исполнитель и не исправление владельца
возвращаемого BSL-обещания. Эти пункты, доставка Begin и весь оставшийся
файловый план сохраняются открытыми. A/B скорости здесь не выполнялось.
