# Запуск приложения на сервере 1С

Измерение выполнено непосредственно на 1С 8.3.27.2342, `/S localhost/test`,
пустые учётные данные, управляемая форма, процедура `&НаСервере`.
Вызовы проб выполняются через `Выполнить` внутри `Попытка`.
Unica не использовалась. XML содержит CompatibilityMode=Version8_3_27;
это не отдельная проверка эффективного режима выполнения.

## Полученные значения

| Вызов | Результат | Код после вызова (до него 12345) |
| --- | --- | --- |
| ЗапуститьПриложение, /usr/bin/true, ждать | Без исключения | 0 |
| RunApp, /usr/bin/true, ждать | Без исключения | 0 |
| ЗапуститьПриложение, /usr/bin/true, не ждать | Без исключения | Пустое строковое представление |
| ЗапуститьПриложение, отсутствующий executable, ждать | Без исключения | 127 |
| ЗапуститьПриложениеАсинх через Выполнить | Исключение при вызове метода контекста | 12345 |

Асинхронная проба не проверяет `Ждать` и не доказывает отсутствие метода:
получена ошибка **вызова**, а не ошибка неизвестного имени.
Тип очищенного выходного параметра этой пробой не записан. Код 127 сам по себе
не доказывает использование shell — нужны отдельные пробы командной строки.

Эти вопросы затем проверены в [уточняющей пробе](file-runapp-details-server-2026-09-09.md):
без ожидания получается Неопределено, а shell-операторы действительно исполняются.

## Значение для плана

Предположение об обязательном отказе синхронного RunApp на сервере опровергнуто
для этого измеренного контекста. Нельзя строить реализацию серверной
совместимости на таком отказе. Отказ ОС в Rust `Command::spawn` также нельзя
без измерений отождествлять с BSL-исключением: отсутствующая программа здесь
дала обычное завершение вызова с выходным кодом 127.
Проверка других версий, контекстов, политики безопасности и командной строки
остаётся открытой. Host API без shell — отдельное согласованное решение,
а не автоматически доказанная эквивалентность платформе.
