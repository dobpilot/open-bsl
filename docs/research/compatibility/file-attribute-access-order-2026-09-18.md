# Приоритет ошибок setter атрибута

## Контур и восстановление

Замер выполнен 2026-09-18 на 1С 8.3.27.2342, Linux, серверной
`/S localhost/test`, в клиентском модуле формы. CompatibilityMode в XML —
Version8_3_27, эффективный режим — НеИспользовать. Версия 8.5,
файловая база и Windows не измерялись.

Сеанс `/tmp/open-bsl-server-measure-os2_na2c` завершился с кодом 0.
Перед загрузкой сняты свежие CF/XML. После пробы CF и конфигурация
БД восстановлены; XML совпал, кроме корневого `ConfigDumpInfo.xml`.
Сценарий не создаёт файлов или каталогов: он обращается к заведомо
отсутствующему потомку уникального временного имени.

- Сценарий: `file-attribute-access-order.bsl`, SHA-256
  `8f083005832a99a50847990ff3a589fe157e9be322141c3d8c90e2105f7c28a5`.
- Oracle: `file-attribute-access-order.platform.txt`, SHA-256
  `71fc7604e9369ed75e0e5506a87da1ecbde2138bc08bf65735d7f5a6b2f50bdb`.

## Результат

Измерены четыре RU/EN-имени setter только чтения и невидимости,
каждое в sync и Async-форме с валидным `Ложь` и невалидной строкой
`Да`: 16 случаев.

- С `Ложь` вызов доходит до файлового доступа и отказывает на
  отсутствующем пути.
- С `Да` возникает ошибка типа параметра до обращения к пути.
- Async в обоих случаях сначала возвращает обещание; ошибка возникает
  при `Ждать`.
- RU/EN-имена и оба атрибута ведут себя одинаково.

open-bsl уже имел такой порядок; изменение runtime не потребовалось.
Структурные строки без `context.compatibility` и `.detail` совпали полностью.
Точные тексты ошибок различаются; измеренная локализация сохранена в oracle,
но относится к общей диагностике runtime, а не к семантике файловых методов.
Строковая грамматика закрыта совместно с `file-attribute-arguments` и
`file-attribute-string-edges`, поэтому прежний открытый вопрос снят из кода,
реестра и общего измерителя. Подменять общую модель `RtError`
локальными текстами этих методов нельзя.
