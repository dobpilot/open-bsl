## Фактическое поведение

Для каждого из NUL, U+0001, TAB, LF, CR, SPACE, U+007F, U+0085, NBSP,
U+200B и U+FEFF проверены позиции после и перед именем `leaf`. Проба отдельно
фиксирует запись трёх байтов, лексическое равенство `ПолноеИмя`, четыре
метода объекта `Файл`, существование базового имени и число элементов дерева.

- NUL после имени сохраняется в `ПолноеИмя`, но завершает путь I/O:
  записан `leaf`, а методы исходного объекта видят файл размером три байта.
- NUL перед именем завершает путь на существующем корне. Запись в каталог
  отказывает; `Существует/ЭтоКаталог` возвращают Истина, `ЭтоФайл` — Ложь,
  `Размер` отказывает.
- Конечные TAB, LF, CR, SPACE, U+0085 и NBSP удаляются и лексически, и перед
  I/O. Запись создаёт базовое имя, которое видят методы `Файл`.
- U+0001, U+007F, U+200B и U+FEFF сохраняются в обеих позициях и образуют
  отдельное физическое имя.
- Начальные измеренные пробельные символы сохраняются.

Это не измеряет все Unicode-коды, необычные корни, ошибки прав доступа либо
прочие конструкторы файлового I/O.

## Исправление и проверка

До изменения open-bsl передавал исходный путь `ДвоичныеДанные.Записать`
непосредственно host. При конечном пробельном символе создавалось иное имя,
поэтому нормализованный объект `Файл` не видел записанное; NUL отклоняла ОС.

Добавлен единый `file::operation_path`: префикс до NUL проходит существующие
`normalize_path` и `trim_path_end`. Его используют запись двоичных данных и
все синхронные, Async- и Begin-запросы метаданных `Файл`. Нормализация
происходит до host; `SystemFileSystem` не получает отдельного правила.

Полные 22 строки совпадают с oracle в source/bytecode × plain/optimize.
Отдельный виртуальный host подтверждает ключи `leaf` и `tab`, исключая
случайное исправление системной ФС. Нативный oracle сохранён без локализации
или генерации из open-bsl. `FILE.EDGE_BEHAVIOR` остаётся в реестре для явно
неизмеренного остатка.
