# Операционный путь `ТекстовыйДокумент`

Измерение выполнено напрямую на серверной `localhost/test`, Linux,
1С 8.3.27.2342. Unica не использовалась. Сессия
`/tmp/open-bsl-server-measure-418zgala` завершилась с кодом 0, восстановила
CF и БД; контрольная XML-выгрузка совпала с исходной.

- Исходник `file-textdoc-io-edges.bsl`: SHA-256
  `594f858e9c3336d6ca392e44a3ffab9e2a8f2b5c496359e25e5301662cd1da0f`.
- Oracle `file-textdoc-io-edges.platform.txt`: SHA-256
  `0b4c6d7628373342cf3800c6b4209872648acf53c2f811d1e149139de91ce2cd`.

Writer-проба начинает с `ABC`, записывает текст `1` и проверяет байты
базового файла. Нормализованный путь даёт UTF-8 BOM и число — `EFBBBF31`;
сохранённый суффикс оставляет базовые `414243`. Reader-проба начинает с
байта `31` и проверяет возвращённый текст.

NUL и суффиксы TAB, LF, CR, SPACE, U+0085 и NBSP снимаются до host.
U+007F, U+200B и U+FEFF сохраняются. Writer с начальным NUL отказывает на
каталоге без изменения базового файла. Reader-вариант начального NUL не
повторялся после измеренного зависания JSON-чтения каталога и не входит в
oracle.

До исправления оба метода передавали путь напрямую в `FileSystem`.
`ТекстовыйДокумент.Прочитать/Записать` теперь переиспользуют
`prepare_file_operation_path`; отдельного правила в компоненте нет.
Сквозной тест сверяет все 23 строки в source/bytecode × plain/optimize.
