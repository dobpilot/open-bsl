## Два разных значения с одинаковыми полями

На одном файле сначала установлен локальный минимум Дата(1, 1, 1),
сохранён результат UTC-getter (`local_min`), затем установлен UTC-минимум
и сохранён второй результат (`utc_min`). Это продолжение
[замера времени и mtime](file-time-edges-server-2026-09-09.md),
не новое внешнее измерение mtime.

У обоих значений год, месяц, день, час, минута и секунда равны нулю.
Однако значения не равны друг другу; оба заполнены, не равны пустой дате
и при сравнении оказываются больше неё. Соответствие сохраняет два разных
ключа как для пары этих значений, так и для пары каждого с пустой датой.

| Операция | local_min | utc_min |
| --- | --- | --- |
| Значение − пустая дата | -9017 | -0.1616 |
| Пустая дата − значение | 9017 | 0.1616 |
| Значение + 0 | Нулевые поля | Нулевые поля |
| Значение + 1 | 9999-12-31 23:59:59 | 0001-01-01 00:00:00 |
| Значение − 1 | Нулевые поля | Нулевые поля |
| Значение + 86400 | 0001-01-01 21:29:43 | 0001-01-01 23:59:59 |
| ДеньНедели | 4 | 4 |

Разность local_min − utc_min равна -9016.8384; обратная — 9016.8384.
Отрицательное вычитание при сравнении «больше» — измеренный результат,
а не основание подменять одну операцию другой. Наблюдения согласуются
с сохранением дробных внутренних единиц и переполнением, но точный
алгоритм хранения/арифметики этим набором не установлен.

Начало дня, месяца и года для обоих значений даёт пустую дату.
Концы дня/месяца/года дают соответственно 0001-01-01 23:59:59,
0001-01-31 23:59:59 и 0001-12-31 23:59:59. НачалоНедели сохраняет нулевые
поля. Позднейший точный замер показал, что оба результа равны между собой,
не равны исходным датам и имеют разность с пустой датой -298955.1616 секунды.
ДобавитьМесяц с 0 даёт пустую дату, с 1 — 0001-02-01.

## Представление и сериализация

Строка в измеренном сеансе возвращает `11/30/0002 12:00:00 AM` для
local_min и `11/30/0001 12:00:00 AM` для utc_min. Проба Формат возвращает
вторую строку для обоих. Эти тексты нельзя читать как календарные поля:
они явно противоречат шести отдельным getter. Влияние локали и других
шаблонов не измерено; точные выражения сохранены в исходнике пробы.

ЗначениеВСтрокуВнутр для обоих возвращает `{"D",00010101000000}`.
Обратное чтение даёт обычную пустую дату, то есть этот round-trip теряет
различие значений. XMLСтрока даёт `0001-01-01T00:00:00`, стандартная
ЗаписатьJSON — строковый JSON с тем же календарным значением.

Дата(0, 0, 0) вызывает ошибку преобразования. Дата("00000000000000")
и вычисление литерала '00000000000000' дают обычную пустую дату,
не исследуемые значения с нулевыми полями.

## Исходное состояние open-bsl и план исправления

Обычный и оптимизированный запуски измерителя исполнимы и совпадают
побайтно, но выводят file.setup_error на первом UTC-getter: результат
вне диапазона дат. Логи: `/tmp/open-bsl-file-zero-date-plain.log`
и `/tmp/open-bsl-file-zero-date-optimize.log`. Код CLI 0 не означает
совпадение: исключение намеренно поймано измерителем.

Один специальный BslDate «нулевые поля» недостаточен: два значения должны
различаться как ключи и сохранять разные дробные разности. Текущий BslDate
хранит целые секунды, diff_seconds возвращает i64, BSL-вычитание строит
целое BslNumber. Простая замена ошибки в file.rs на empty() также неверна.

Исправление остаётся в действующем extend-filesystem-operations:

1. Дополнить измерения соседними mtime, долями секунды и обычными контрольными
   датами; проверить равенство после арифметики, порядок пары, повторное чтение
   и форматирование с явно заданной локалью. Получить таблицу границ,
   не выводить универсальный алгоритм только из двух значений.
2. До реализации согласовать в design представление в bsl-rt: календарное
   разложение, сравнение/хеш, точная числовая разность и сдвиги — отдельные
   наблюдаемые операции. Сохранить прежний публичный Rust-контракт либо явно
   описать его изменение. BslDate::seconds/from_seconds и diff_seconds имеют
   существующих потребителей, скрыто менять единицу нельзя.
3. Проверить потребителей bsl-format, JSON/XML, внутренней сериализации,
   ZIP, часовых поясов и констант байткода. Потеря различия при измеренной
   BSL-сериализации не разрешает терять его при копировании значения в VM.
   Менять формат байткода только если изменяется его контракт; тогда обновить
   FORMAT_VERSION и round-trip вместе, не объявлять это уже необходимым.
4. Подключить getter к измеренному представлению, затем проверить sync,
   Async/Begin, RU/EN, dynamic, plain/optimize и source/bytecode на одном
   host. Не считать два прошедших календарных поля полной приёмкой.

## Реализация 2026-09-17

Последующие пробы соседних значений и дробных дат подтвердили единицу
1/10000 секунды. `BslDate` теперь хранит `u64` тактов. Для обоих результатов
минимального mtime сырое значение получается сложением Unix-времени с эпохой
BSL по модулю 2^64: `local_min = 2^64 - 90170000`,
`utc_min = 2^64 - 1616`. Без отдельного sentinel это одновременно объясняет
разные ключи, беззнаковый порядок и знаковую циклическую разность oracle.

Синхронный UTC-getter сохраняет эти значения. Календарные поля, сравнение,
хеш, арифметика, границы периода и `ДобавитьМесяц` проверены тестом
по нативным строкам. Внутренний формат, XML и JSON нормализуют только при
записи, не изменяя исходное значение. Измеренное исключение разбора ровно
четырнадцати нулей реализовано для строковой формы `Дата` и литерала; числовая
форма `Дата(0, 0, 0)` остаётся ошибкой. 62 строки, для которых не требуется
локализованный текст ошибки или невыясненное строковое форматирование,
совпадают в plain/optimize и source/bytecode. Отдельный unit-тест фиксирует
точные сырые значения и циклические разности.

FILE.TIME_EDGE_BEHAVIOR, его маркеры и единственная строка measure-all
сохранены: открыты точное `Строка`/`Формат`, текст ошибки числового
конструктора, RU/EN, dynamic и доставка тех же значений через Async/Begin.
Полный интерфейс времени и весь файловый план не завершены.

Отдельный прямой прогон `file-zero-date-order` на той же серверной базе
зафиксировал строгий порядок `local_min < utc_min`, обратные сравнения и
тождество обоих значений после прибавления нуля. Артефакты находятся в
`/tmp/open-bsl-server-measure-cq1xarop`; CF и конфигурация БД восстановлены,
XML совпал. Измеритель имеет SHA-256
`d62ae15ca9aa4d5b15240cd8c09ae107fe82070d7074ad7a918c61f230b17488`,
oracle — `b3076df77fbdbd33759266207a9d9bbb880e2fb898fa94e129bda8ed2e593e9c`.
Все восемь строк совпали в source/bytecode × plain/optimize.
