## Фактическое поведение

Один физический файл `leaf` из трёх байтов прочитан тремя входами: `Новый
ДвоичныеДанные`, `Новый ФайловыйПоток(..., Открыть)` и
`ФайловыеПотоки.ОткрытьДляЧтения`.

- Конечные NUL, TAB, LF, CR, SPACE, U+0085 и NBSP удаляются из пути I/O:
  все три входа читают базовый файл и возвращают размер 3.
- Конечные U+007F, U+200B и U+FEFF сохраняются: отдельного файла с таким
  именем нет, поэтому все три входа отказывают.
- NUL перед `leaf` завершает путь на родительском каталоге. Все три входа
  отказывают, а не открывают каталог как файл.

Замер не объявляет отдельно поведение записывающих режимов потоков, полный
набор управляющих символов, необычные корни или ошибки доступа.

## Исправление и проверка

До изменения open-bsl передавал исходную строку всем трём читателям. После
общего нормализатора два потоковых входа стали совпадать, но Linux позволил
менеджеру открыть каталог только для чтения и вернуть его служебный размер.
Добавлена явная проверка метаданных: файловый поток не открывает каталог.

Публичный Rust-помощник `prepare_file_operation_path` в `bsl-rt` получает
разделитель у host и переиспользует уже измеренный `operation_path`.
`Новый ДвоичныеДанные` и общая точка открытия `bsl-stream` вызывают его до
host. Исходная строка остаётся в свойстве `ИмяФайла`.

Все 11 проб совпадают с oracle в source/bytecode × plain/optimize.
Виртуальная ФС отдельно подтверждает нормализацию чтения двоичных данных и
потока до host. `FILE.EDGE_BEHAVIOR` остаётся для перечисленного
неизмеренного остатка.
