# Операционный путь файловых входов JSON

Измерение выполнено напрямую на серверной `localhost/test`, Linux,
1С 8.3.27.2342. Unica не использовалась.

Первый запуск `/tmp/open-bsl-server-measure-pxssq9qh` дошёл до чтения JSON
по пути с начальным NUL. После нормализации этот путь обозначает каталог;
платформа не вернула управление до таймаута 120 секунд. Raw-вывод содержит
четыре завершённые строки, но прогон не принят как oracle. Runner восстановил
CF и БД; XML совпал, кроме служебного `ConfigDumpInfo.xml`.

Из успешной матрицы исключён только зависающий reader-вариант. Повторный
сеанс `/tmp/open-bsl-server-measure-6r9bq0zi` завершился с кодом 0,
восстановил CF и БД; контрольная XML-выгрузка совпала с исходной.

- Исходник `file-json-io-edges.bsl`: SHA-256
  `74b89bf3c04dbaea04fda58eeb0c01f1c81e3e81ae487bffb963f6121e7bae40`.
- Oracle `file-json-io-edges.platform.txt`: SHA-256
  `13dd610a1fb680b04463f46c43218ad22f2857d1b02a9780c9dd7a630702070a`.

Writer-проба сначала записывает `ABC` в базовый файл, затем сохраняет число
1 по изменённому пути; байты `31` отличают нормализацию к базе от создания
соседнего файла. Reader-проба кладёт `1` в базовый файл и проверяет реально
прочитанное значение.

NUL и суффиксы TAB, LF, CR, SPACE, U+0085 и NBSP снимаются до host.
U+007F, U+200B и U+FEFF остаются частью физического имени. Writer с начальным
NUL отказывает на каталоге без изменения базового файла. До исправления оба
JSON-объекта передавали host исходный путь, поэтому все снимаемые суффиксы
расходились с 1С.

`ЧтениеJSON.ОткрытьФайл` и `ЗаписьJSON.ОткрытьФайл` теперь вызывают
`prepare_file_operation_path` через файловую систему своего сеанса.
Сквозной тест сверяет 23 строки в source/bytecode × plain/optimize;
embedding-тест отдельно проверяет нормализованное имя виртуального host и
чтение пути с NUL.
