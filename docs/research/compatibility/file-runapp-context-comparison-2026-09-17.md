# `RunApp`: серверный и клиентский контексты

Сопоставлены три прямых измерения 1С 8.3.27.2342 на Linux в серверной базе
`/S localhost/test`: синхронный вызов в серверной процедуре, синхронный вызов
тонкого клиента и клиентский `RunAppAsync`. CLI open-bsl не выдаётся за любой
из этих контекстов: его host API остаётся явным и не использует shell.

## Сравнение

| Случай | Серверный `RunApp` | Клиентский `RunApp` | Клиентский `RunAppAsync` |
|---|---|---|---|
| true/false с ожиданием | 0 / 1 | 0 / 1 | 0 / 1 |
| без ожидания | `Неопределено` в выходной переменной | `Неопределено` | результат обещания `Неопределено` |
| пустая команда с ожиданием | 0 | 0 | 0 |
| отсутствующая программа с ожиданием | 127 | `Неопределено` | `Неопределено` |
| несуществующий cwd для true | 0 | 0 | 0 |
| команда/cwd `Неопределено`, флаг 0 | ошибка, выход не меняется | ошибка, выход не меняется | ошибка при `Ждать` |
| команда в кавычках, false | 1 | 1 | 1 |
| `exit 17` | 17 | `Неопределено` | `Неопределено` |
| `true ; false` | 1 | 1 | 1 |

Так выявлено фактическое контекстное различие: серверный sync превращает
отсутствующий executable в 127, а обе клиентские формы дают
`Неопределено`. Shell-семантика наблюдается во всех трёх формах. Строгая
проверка типов и очистка результата без ожидания общие; async отличается
отложенной ошибкой и отсутствием четвёртого аргумента.

open-bsl сохраняет ранее согласованный контракт: Unix-команда разбирается
на executable/argv без shell, cwd передаётся host строго, sync NotFound
отображается в server-like 127, async NotFound — в `Неопределено`.
Поэтому shell-последовательность и fallback cwd намеренно расходятся с 1С,
а `RUNAPP.EDGE_ARGUMENTS` остаётся для прочих границ и Windows-разбора.
