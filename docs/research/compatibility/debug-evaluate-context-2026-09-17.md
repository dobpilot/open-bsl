# Контекст остановленного кадра в evaluate

## Обнаруженные расхождения с контрактом open-bsl

Это проверка собственного DAP-контракта, не измерение отладчика 1С.
Действующая спецификация требует вычислять выражение в выбранном кадре
существующим динамическим исполнителем. Delta уточняет каталог, обещания
и сохранение остановки других задач до реализации изменения.

Красные проверки в `/tmp/open-bsl-debug-context-red.log` показали:

- при остановке в модуле Б осмотр вызывающего отдавал `АргБ = Undefined`
  вместо `АргВхода = 11`;
- обещание async-функции из evaluate отвергалось после продолжения как
  принадлежащее другому запуску.

Дополнительная проверка выявила отказ evaluate в корректном отладочном
кадре без локальных переменных: пустая таблица имён ошибочно считалась
отсутствием отладочной информации.

Последующая проверка ленивой инициализации показала ещё один дефект:
вызывающий показывал строку 2 вместо 3. При входе в тело модуля его
инструкция ещё не продвинута, поэтому поправка pc − 1 здесь неверна.
Красный лог — `/tmp/open-bsl-debug-lazy-line-red.log`; после исправления
проверка проходит.

## Реализация

FrameValues выбирает программу и линковку отдельно для каждого кадра.
Локальные читаются через `reg_index`, учитывая ссылочные параметры;
строки вызывающих по-прежнему относятся к инструкции вызова, не следующей.
Наличие отладочной информации определяется таблицей строк.

Вложенный ProgramExecution evaluate использует обычный poll, исходный
AsyncState, корневое состояние, экземпляры каталога и RuntimeShapes.
Служебный корень содержит DynamicImage и владельца выбранного модуля.
Динамический компилятор получает его точные импорты; права экспортности
не расширяются до всего каталога.

Готовая очередь приостановленного запуска временно отделяется. Во вложенном
poll исполняются только задачи с номерами начиная с корня evaluate;
завершения host для прежних задач остаются отложенными. Результат корня
возвращается без ожидания его async-обещаний. Новые задачи, обещания,
host-операции и события возвращаются исходному владельцу. Ошибка выражения
не откатывает записи в аргументы и модули. Служебный корень снимается
с очереди и ожидателей при завершении или отмене; дочерние задачи сохраняются.

Старый необязательный маршрут HostIo.file_promises не используется новым
evaluate. Его удаление из обработчиков инструкций отложено: оно затронуло
бы step за пределами этого исправления и потребовало бы отдельного
согласования с требованием неизменного машинного кода диспетчера.

## Проверки

Четыре теста `open-bsl/tests/debug_context.rs` покрывают 14 запусков:

- четыре кадра трёх модулей: имена, значения, строки, ЭтотОбъект, допустимые
  и недопустимые импорты, неэкспортный метод, ссылочные аргументы;
- сохранение модульных и ссылочных записей после исключения evaluate;
- async-функция выбранного общего модуля продолжает работать с тем же
  состоянием после возврата evaluate и дописывает общий массив;
- прямое и вложенное динамическое async-обещание, файловое обещание,
  сохранение обещания после исключения evaluate, ошибка при Ждать;
- готовая соседняя задача не выполняется внутри evaluate;
- исходник и загруженный байткод для модульных и обещательных сценариев;
- строка вызывающей инструкции во время ленивой инициализации модуля;
- задержанный файловый host не завершается до возврата evaluate: разрешение
  worker выдаёт сам отладочный обработчик после получения обещания.

Фокусный VM-набор и эти тесты прошли. Логи:
`/tmp/open-bsl-debug-context-{focused,vm}.log`.
Два дополнительных unit-теста проверяют, что старая задача, пробуждённая
host-завершением, остаётся в очереди, а удаление служебного корня evaluate
не теряет чужих ожидателей или отложенных ошибок. Лог:
`/tmp/open-bsl-debug-queue-unit.log`.

Финальный полный `cargo test --workspace` прошёл, включая обычное/
оптимизированное исполнение, прежние DAP-тесты, реестр измерений и API reference.
Clippy всех targets с `-D warnings`, rustdoc с `-D warnings`, fmt,
`git diff --check` и строгий OpenSpec (11/11) прошли. Логи:
`/tmp/open-bsl-debug-context-{workspace,clippy,doc}-final.log`.
Закрытые большие случаи table_compare2 без отдельной переменной окружения
не проверяются; игнорируемый MXL dump также не считается пройденным oracle.

## Граница диспетчера

До изменения сохранён release-бинарник текущего рабочего дерева, после —
кандидат. Оба собраны с одинаковыми настройками, без переменных RUSTFLAGS
и CARGO_ENCODED_RUSTFLAGS. Нормализатор функции dump взят без изменения из
benchmarks/hot-code-diff.sh. Сравнение включает размер, операнды и длины
инструкций; обе функции совпали: step — `0xea77`, step_cold — `0x59e4`.
Артефакты: `/tmp/open-bsl-debug-eval-baseline-BTbaSK/`, протокол:
`/tmp/open-bsl-debug-eval-hot-code.log`. Это экран машинного кода,
не измерение ускорения или стоимости evaluate.

Весь файловый план этим не завершён. В частности, безопасная системная
очистка временных носителей и CreateTempFileAsync остаются открытыми.
