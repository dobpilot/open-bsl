# Операционный путь `ДокументPDF`

Измерение выполнено напрямую на серверной `localhost/test`, Linux,
1С 8.3.27.2342. Unica не использовалась. Сессия
`/tmp/open-bsl-server-measure-pb8oy34b` завершилась с кодом 0,
восстановила CF и БД; контрольная XML-выгрузка совпала с исходной.

- Исходник `file-pdf-io-edges.bsl`: SHA-256
  `10cb9a9c88e2206779535282c01a90d33889760002545199535b1d1a74fba6d5`.
- Oracle `file-pdf-io-edges.platform.txt`: SHA-256
  `4eff2425c7f739ad2761905dfca5adb539ca3f997a30fe19458ba68ba530c52e`.

Проба материализует ранее снятый с платформы PDF из его
шестнадцатеричного корпуса. Reader различает успех по числу страниц.
Writer добавляет вложение и отличает изменение базового PDF по размеру
от записи соседнего имени.

Оба метода снимают конечные TAB, LF, CR, SPACE, U+0085 и NBSP,
но сохраняют U+007F, U+200B и U+FEFF. NUL обрабатывается асимметрично:
`Прочитать` обрезает конечный NUL и видит базовый файл, а `Записать`
отказывает как с конечным, так и с начальным NUL, не изменяя базовый PDF.

До исправления оба метода передавали имя напрямую в `FileSystem`.
Теперь reader вызывает `prepare_file_operation_path`; writer пользуется им
при отсутствии NUL, но передаёт NUL host для измеренного отказа.
Сквозной тест сверяет все 23 строки в source/bytecode × plain/optimize;
все 43 теста `bsl-pdf` также проходят.
