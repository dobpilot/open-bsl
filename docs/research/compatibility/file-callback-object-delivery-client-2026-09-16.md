# Доставка файловых оповещений в обычные объекты

## Контур и восстановление

Измерено на 1С 8.3.27.2342, Linux, тонком клиенте серверной
`/S localhost/test`, кластер от kan. Запуск native без Unica. В XML
CompatibilityMode=Version8_3_27, эффективный режим из Метаданные —
НеИспользовать. Серверное исполнение этих методов, 8.5, файловая база
и веб-клиент не измерялись.

Сессия `/tmp/open-bsl-server-measure-wt01cn1j` завершилась кодом 0:
свежие CF/XML, проверка перед загрузкой, восстановление CF/конфигурации БД
и побайтная сверка XML, кроме корневого ConfigDumpInfo.xml. Скрипт создал
и удалил только собственный временный каталог с трёхбайтовым файлом.
Резервные копии и подтверждение восстановления сохранены.

## Шесть успешных операций

Все шесть вызовов вернулись; последующее наблюдение показало ready=1,
errors=0, без ошибок подготовки, проверки или очистки. Это исполнение
методов, а не только принятие их имён конструктором ОписаниеОповещения.

| Операция | Получатель и дополнительные данные | Наблюдаемый результат |
|---|---|---|
| НачатьУстановкуТолькоЧтения(Ложь) | Массив.Добавить, структура | В массив добавлена именно переданная структура |
| BeginGettingSize | Соответствие.Insert, структура | Ключ 3 содержит ту же структуру |
| BeginCheckingExistence | Массив.Set, 99 | Массив [10,20] стал [10,99]: Истина выбрала индекс 1 |
| НачатьПроверкуЭтоКаталог | Массив.Вставить, 77 | Массив [10,20] стал [77,10,20]: Ложь выбрала индекс 0 |
| BeginInitialization к first | Первое соответствие.Insert, first | По исходному объекту Файл найдено значение first |
| BeginInitialization к second | Второе соответствие.Insert, second | По тому же объекту найдено значение second |

Две инициализации идут последовательно над одним объектом. После второго
вызова его путь уже second. Ключи обоих соответствий при последующей
проверке также имеют путь second. Результат инициализации — живая ссылка
на исходный объект, не независимый снимок его прежнего пути first.

Структура дополнительных данных изменена после всех вызовов и найдена
в обоих получателях с новым значением поля. Проверка выполняется позже
доставки, поэтому сама по себе **не доказывает** порядок доставки
относительно присваивания полю. Отложенность модульных обработчиков
измерена отдельно в file-callbacks и file-callback-methods; здесь не
устанавливаются ни FIFO, ни момент готовности отдельных операций.

Наблюдатель использует клиентский обработчик ожидания и прекращает ожидание
не позднее десятой проверки. Наличие file.end без ready=1 не считается
подтверждением доставки. Ошибки успешных обработчиков и действительное
исполнение обработчика ошибки эта успешная серия не измеряет.

## Первая попытка и границы

`/tmp/open-bsl-server-measure-reertsy7` остановилась на CheckModules:
ТаблицаЗначений недоступна в тонком клиенте. ENTERPRISE не запускался,
CF/конфигурация БД восстановлены и XML совпал. Из клиентской пробы убраны
создание таблицы и доставка в строку; серверный замер её Get/Set не
подменяет клиентскую доступность. Вывод неуспешной попытки не стал oracle.

В текущем open-bsl сценарий проходит до file.end, но все шесть операций
отказывают при создании описания: ЭтотОбъект для модуля обработки ошибки
не определён. ready=0, содержимое коллекций не изменено. Это не зелёная
conformance-фикстура и не проверка реализации Begin: её ещё нет.
Публичный способ ссылки на BSL-модуль требует согласования; также остаются
передача изменяемого флага ошибки и доставка в исполнении VM.

Этот этап меняет измерительный сценарий, свидетельства и предлагаемый
контракт, не Rust-реализацию. Три теста генератора оболочки прошли.
Повторно прошли fmt, Clippy --workspace --all-targets с запретом предупреждений,
полный cargo test --workspace (включая plain/optimize и текстовый round-trip),
rustdoc с запретом предупреждений, git diff --check и все 11 строгих
проверок OpenSpec. Логи — /tmp/open-bsl-callback-object-delivery-*.log.
Зелёные проверки существующей реализации не подтверждают отсутствующие
Begin-методы.
