# Операционный путь `ЗаписьТекста`

Измерение выполнено напрямую на серверной `localhost/test`, Linux,
1С 8.3.27.2342. Unica не использовалась. Сессия
`/tmp/open-bsl-server-measure-ye5b743q` завершилась с кодом 0, восстановила
CF и БД; контрольная XML-выгрузка совпала с исходной.

- Исходник `file-text-writer-io-edges.bsl`: SHA-256
  `85de28f87b42c589fc92fb7cbfd0e689476f0991e885774d04b4358e316b744a`.
- Oracle `file-text-writer-io-edges.platform.txt`: SHA-256
  `0e44743515cd83fba5eaea476865efb358037e24646b99947531b23389790f66`.

Каждая изолированная проба сначала записывает `ABC` в базовый файл, затем
создаёт и закрывает `ЗаписьТекста` по изменённому пути. Пустой писатель
оставляет в открытом файле UTF-8 BOM `EFBBBF`; это отличает нормализацию к
базовому имени от успешного создания отдельного файла.

Суффиксы NUL, TAB, LF, CR, SPACE, U+0085 и NBSP снимаются до host, поэтому
базовый файл заменяется BOM. U+007F, U+200B и U+FEFF сохраняются в физическом
имени, поэтому базовый файл остаётся `414243`. NUL в начале конечного
компонента обрезает путь до каталога и вызывает ошибку без изменения базы.

До исправления open-bsl передавал исходный путь непосредственно в
`FileSystem::open`: NUL вызывал ошибку Rust, а остальные суффиксы создавали
соседний файл. `new_text_writer_with_files` теперь переиспользует
`prepare_file_operation_path`, как двоичные данные и файловые потоки.
Сквозной тест сверяет все 13 строк в source/bytecode × plain/optimize.
