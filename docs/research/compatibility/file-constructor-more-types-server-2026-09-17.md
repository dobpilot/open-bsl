# Дополнительные типы конструктора `Файл`

## Контекст и сохранность

Измерение выполнено напрямую на серверной 1С 8.3.27.2342, Linux,
`/S localhost/test`, без Unica. Проба вызывает только `Строка`, конструктор
`Файл` и пять лексических свойств; файлового I/O и создания путей нет.
Эффективный режим совместимости — `НеИспользовать`.

Сессия `/tmp/open-bsl-server-measure-xmtihb1a` завершилась кодом 0. Исходный
CF восстановлен; повторная XML-выгрузка совпала с исходной, кроме служебного
корневого `ConfigDumpInfo.xml`.

- Сценарий: `file-constructor-more-types.bsl`, SHA-256
  `794a6242879387d8048c18b26578a8f39a02e81b6055849f06bf4f44eb14ee99`.
- Нативный вывод: `file-constructor-more-types.platform.txt`, SHA-256
  `fdd3f7742cbc2969094db811da7017746c91ec759cc8b8e8e33d38d81d681898`.

## Результат

Проверены Соответствие, ФиксированныйМассив, ФиксированнаяСтруктура,
ФиксированноеСоответствие, ТаблицаЗначений, СписокЗначений, UUID, Файл,
ДвоичныеДанные, значение перечисления и Тип. Все одиннадцать аргументов
приняты; во всех случаях `ПолноеИмя` равно `Строка(Аргумент)`.

Для десяти значений лексические свойства open-bsl уже следовали тому же
правилу. Пустой СписокЗначений выявил расхождение: 1С даёт пустую строку и
пять пустых свойств, open-bsl печатал `СписокЗначений`. Исправление ограничено
пустым списком; представление заполненного списка не измерено и не изменено.

`Тип("Строка")` в этой сессии печатается как `String`, а open-bsl — как
`Строка`. Оба конструктора получают строку собственного runtime и соблюдают
измеренный файловый контракт равенства. Выбор канонического языка значения
Тип — отдельный общий контракт типов, поэтому файловое изменение его не
подменяет.

CLI-тест сверяет нативное равенство и пустой СписокЗначений, затем повторяет
матрицу в source/bytecode × plain/optimize. Отдельный unit-тест фиксирует
новое строковое представление пустого списка.
