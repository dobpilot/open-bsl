# Операционный путь записывающих файловых потоков

Измерение выполнено напрямую на серверной `localhost/test`, Linux,
1С 8.3.27.2342. Unica не использовалась. Сессия
`/tmp/open-bsl-server-measure-ov0350ah` завершилась с кодом 0, восстановила
CF и БД; контрольная XML-выгрузка совпала с исходной.

- Исходник: `tests/conformance/measure/filesystem/file-write-io-edges.bsl`,
  SHA-256 `669f31e57dd8de321702330fc65e3e7b1e5b23227bbe2e74ac2de0734a96a73b`.
- Oracle: `file-write-io-edges.platform.txt`, SHA-256
  `a453861ea06598f79fe0276192578dc5f7565af582a3f70976ee9b06bdbe6111`.

Для каждого пути создаётся отдельный базовый файл `ABC`. Проверены
`Новый ФайловыйПоток` в режимах `Создать` и `ОткрытьИлиСоздать`, а также
`ФайловыеПотоки.ОткрытьДляЗаписи` и `ОткрытьДляДописывания`. Операция пишет
байт `Z`, после закрытия измеритель читает именно базовый путь:

- создание даёт `5A`;
- открытие для записи с позиции 0 даёт `5A4243`;
- дописывание даёт `4142435A`;
- если необычный суффикс сохранён как часть другого физического имени,
  базовый файл остаётся `414243`.

Суффиксы NUL, TAB, LF, CR, SPACE, U+0085 и NBSP снимаются до открытия host.
U+007F, U+200B и U+FEFF сохраняются. NUL в начале конечного компонента
обрезает путь до каталога, поэтому все четыре операции отказывают и не
меняют базовый файл. Все 44 результата серверной 1С побайтно совпали с
текущим open-bsl: дополнительного изменения runtime не потребовалось.

Oracle проверяется в source/bytecode × plain/optimize. Вместе с ранее
сохранёнными `file-object-io-edges` и `file-read-io-edges` эта матрица
закрывает общий операционный путь `ДвоичныеДанные`, чтения и записи
`ФайловыйПоток`, а также трёх менеджерских входов. Другие I/O-конструкторы
и классы ошибок остаются `НЕ ИЗМЕРЕНО(FILE.EDGE_BEHAVIOR)`.
