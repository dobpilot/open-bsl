# Каталог со звёздочкой в файловом поиске

Измерение выполнено напрямую на серверной `localhost/test`, Linux,
1С 8.3.27.2342. Unica не использовалась. Во время платформенного запуска
placeholder корня был заменён на `/tmp/open-bsl-sfile-directory.ePb3H1`.
Сессия `/tmp/open-bsl-server-measure-bmur9sbz` завершилась с кодом 0,
восстановила CF и БД; контрольная XML-выгрузка совпала с исходной.

- Канонический исходник: `file-search-sfile-directory.bsl`, SHA-256
  `bf1f5e9fbbe34cd04950237e1f043eed356bdfa0f2130d0b777f8efe466c80fb`.
- Исполненный исходник с подставленным корнем: SHA-256
  `60fe799e372a127ad0f9039f34c219ed5668b2b7c8b7637aa1263c6bbe026f00`.
- Oracle: `file-search-sfile-directory.platform.txt`, SHA-256
  `46581efc0eb66ebf766e211068e13d7a1c054d4812728e784f2eaabdf4dd1735`.
- Внешнее дерево до и после запуска содержало каталог `a*` и пустой файл
  `a*/deep.txt`; оно не изменилось. SHA-256 снимка:
  `d5583b86eaf2f3310e777f5dfd1b2f516d9be611b62063e3f1ceb2db9377bc3c`.

На текущем уровне каталог ведёт себя как уже измеренный специальный файл:
литеральная, экранированная и вопросительная маски возвращают объект с
`ПолноеИмя=sfile://sfile://a*`; вызов `ЭтоКаталог()` у него ошибочен, а
маска `*` его не выбирает. Прямой поиск пути `root/a*` без маски пуст.

Главное новое наблюдение относится к рекурсии. Серверная 1С никогда не
входит в физический каталог со звёздочкой. Это верно и когда специальный
объект выбран маской, и когда маска `*` либо `*.txt` не выбрала его:
вложенный `deep.txt` не возвращается. До исправления open-bsl ошибочно
возвращал этот файл в двух последних случаях.

Обход open-bsl теперь не добавляет специальную запись в стек каталогов,
не меняя её правила выбора на текущем уровне и физические пути удаления.
Полный oracle совпадает в source/bytecode × plain/optimize; отдельный
host-тест проверяет отсутствие второго `read_dir`. Иные формы `sfile`,
ссылочные варианты, дополнительные циклы и ошибки host остаются
`НЕ ИЗМЕРЕНО(FIND.TRAVERSAL)`.
