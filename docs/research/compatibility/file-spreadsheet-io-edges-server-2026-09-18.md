# Операционный путь `ТабличныйДокумент`

Измерение выполнено напрямую на серверной `localhost/test`, Linux,
1С 8.3.27.2342. Unica не использовалась. Финальная сессия
`/tmp/open-bsl-server-measure-kkffa8ey` завершилась с кодом 0,
восстановила CF и БД; контрольная XML-выгрузка совпала с исходной.

- Исходник `file-spreadsheet-io-edges.bsl`: SHA-256
  `97a17bb02f637895b8b7106a5101f7fd493c92df7c4e9ce22fbc6583e4ea4987`.
- Oracle `file-spreadsheet-io-edges.platform.txt`: SHA-256
  `393651be5b9fb8614fa35ce46313aba095c9a261cc8486d3a2985a2f5eb38210`.

Writer-проба начинает с базового файла `ABC`, записывает минимальный
MXL и различает изменение базового файла по размеру. Reader-проба
заранее создаёт валидный MXL и проверяет текст первой ячейки.

NUL и суффиксы TAB, LF, CR, SPACE, U+0085 и NBSP снимаются до host.
U+007F, U+200B и U+FEFF сохраняются. Writer с начальным NUL
отказывает на каталоге без изменения базового файла. Reader-вариант
начального NUL не повторялся после измеренного зависания JSON-чтения
каталога и в oracle не входит.

До исправления оба метода передавали путь напрямую в `FileSystem`.
Теперь `Прочитать/Записать` переиспользуют `prepare_file_operation_path`;
сквозной тест сверяет все 23 строки в source/bytecode × plain/optimize.

Предварительный сеанс `/tmp/open-bsl-server-measure-cqrvtu71` остановился
на compile-check: платформа не принимает вызов `.Размер()` сразу после
`Новый ДвоичныеДанные(...)`. Runner восстановил CF; XML совпал, кроме
служебного `ConfigDumpInfo.xml`. Oracle из этой попытки не создавался.
