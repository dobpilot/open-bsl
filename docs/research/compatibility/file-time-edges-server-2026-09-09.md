## Воспроизводимость и сохранность

Сессия `/tmp/open-bsl-time-edges-approved-osfJz9` содержит свежий CF,
исходный/измерительный/восстановленный XML, логи и `scratch` с 13 файлами.
В сгенерированном модуле единственная дополнительная замена — значение
`__OPEN_BSL_PROBE_ROOT__` на полный путь этого заранее созданного scratch.
Это отключает самоочистку, чтобы внешний наблюдатель мог прочитать mtime
после выхода клиента. Обычный запуск исходника создаёт и удаляет свой temp.

Перед каждой пробой создан отдельный файл `ABC`, время сброшено в
UTC 2020-01-01. После прогона GNU find считал `%f`, `%T@` и `%s` из
этого scratch, строки отсортированы только в наблюдательном файле.
Все файлы имеют размер 3; mtime сохранён с дробной частью, равной нулю.
Файлы и резервная копия оставлены в каталоге сессии как артефакты измерения.

Обёртка дошла до `file.end` без ошибки подготовки. Свежий CF восстановлен,
повторная XML-выгрузка совпала с исходной, кроме `ConfigDumpInfo.xml`.
Код обёртки 0. Это проверка конфигурации, не побайтная проверка данных ИБ.

## Установка UTC и локального времени различается до epoch

| Проба | Фактический mtime, секунды Unix | Местный getter | UTC-getter |
|---|---:|---|---|
| UTC 1969-12-31 23:59:59 | 1844674407370954 | 0001-01-01 00:00:00 | 1969-12-31 23:59:58 |
| UTC 1970-01-01 00:00:00 | 0 | 1970-01-01 03:00:00 | 1970-01-01 00:00:00 |
| UTC 1970-01-01 00:00:01 | 1 | 1970-01-01 03:00:01 | 1970-01-01 00:00:01 |
| UTC 1960-01-15 12:34:56 | 1844674093006651 | 0001-01-01 00:00:00 | 1960-01-15 12:34:55 |
| Местное 1960-01-15 12:34:56 | -314375104 | 1960-01-15 12:34:56 | 1960-01-15 09:34:56 |

Во всех случаях setter завершился успешно. Огромное положительное время
возникает уже при записи UTC, не только при форматировании getter.
Значения согласуются с переполнением беззнакового 64-битного промежуточного
счётчика с шагом 1/10000 секунды, но это **гипотеза алгоритма**, не измерение
всего диапазона. Системный host open-bsl не должен сам вносить этот эффект:
локальный setter 1С отрицательное время записывает нормально.

## Границы календаря и переходы зоны

UTC-setter для 0001-01-01 записал mtime `1844612271774155`, локальный —
`-62135605817`. В обоих случаях местный getter дал дату 0001-01-01,
а UTC-getter — значение типа Date с полями **0-0-0 0:0:0**. Это отличается
от результата Формат из первого замера; выводить календарное значение
из того форматированного текста нельзя. `BslDate` open-bsl пока не способен
представить такую дату, что является отдельным препятствием полной совместимости.

UTC-setter для 9999-12-31 23:59:59 записал `253402300799`: UTC-getter
воспроизводит дату, местный getter возвращает 0001-01-01. Локальный setter
записал `253402289999`: местный getter воспроизводит дату, UTC-getter
возвращает 9999-12-31 20:59:59.

Местная дата в пропуске Moscow 2011-03-27 02:30 записала **mtime -1**,
после чего местный getter дал 1970-01-01 02:59:59, UTC — 1969-12-31 23:59:59.
Местная дата в повторённом интервале 2014-10-26 01:30 записала
`1414276200`, UTC 2014-10-25 22:30, то есть выбрана сторона +03:00.
Нельзя автоматически считать общий `TimeZone::offset_for_local` готовой
семантикой файлового setter: пропуск требует отдельного решения по oracle.

Оба setter преобразовали строку `20210314151617` и изменили сброшенную
дату: UTC-вариант записал `1615734977`, локальный — `1615724177`.

## Следствие для плана

Нужны четыре BSL-метода поверх host, но обычной взаимно-обратной конверсии
недостаточно. Сначала следует отделить измеренные обычные даты от вопросов
переполнения, нулевых календарных полей и пропуска зоны; неизвестные границы
регистрируются по правилам репозитория. Этот отчёт не разрешает подменять
полный интерфейс только обычным диапазоном. Проверка open-bsl пока доказывает
лишь исполнимость измерителя с ловимыми ошибками отсутствующих методов.
