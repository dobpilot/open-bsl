# Получить/Установить массива: зависимость оповещений

Измерено на сервере `localhost/test`, Linux, 1С 8.3.27.2342, прямым
запуском `1cv8`, без Unica. Сессия `/tmp/open-bsl-notification-array-xuFvdv`
завершилась с кодом 0 после восстановления свежего CF и побайтной сверки
XML, кроме ConfigDumpInfo.xml. Проверяемые изменения затрагивали только
массивы в памяти пробы.

- [Сценарий](../../../tests/conformance/measure/filesystem/notification-array-access.bsl).
- [Оригинальный вывод](../../../tests/conformance/measure/filesystem/notification-array-access.platform.txt): 44 строки, включая начало и конец.

Девять индексов проверены для Получить/Get и Установить/Set: каждый вызов
получает новый массив `[10, 20]`. Setter записывает 99. Дополнительно
проверены шесть форм вызова. В строках сохранён результат и состояние
массива; причина ошибки не классифицировалась глубже `error`.

| Индекс | Getter | Setter |
|---|---|---|
| 0 | 10 | `[99, 20]` |
| 1 | 20 | `[10, 99]` |
| 1.9 | 20 | `[10, 99]` |
| строка `"1"` | 20 | `[10, 99]` |
| Истина | 20 | `[10, 99]` |
| -1, 2, Неопределено, Null | Ошибка | Ошибка без изменения массива |

Getter отвергает 0 и 2 аргумента; setter отвергает 0, 1 и 3 аргумента.
Установить в позиции выражения отвергается, массив остаётся `[10, 20]`.
По одной положительной дроби нельзя определять поведение отрицательных
дробей, по строке `"1"` — все правила числового разбора. Другие значения,
точные классы исключений и прямой путь без Вычислить/Выполнить ещё не измерены.

## Почему это не простая переадресация

Текущий open-bsl даёт ошибки на всех четырёх методных путях; прямое чтение
массива через `[]` в выводе работает. Его `index_as_usize` требует именно
число и точное целое. Поэтому переадресация новых методов к существующему
индексатору без отдельной подготовки индекса потеряет три измеренных случая.
Семантика самого индексатора этим измерением не меняется.

Есть и отдельная граница позиции вызова: открытый CallObjectMethod уже
имеет result_required, а закрытый CallMethod — нет. Реализация setter
должна сохранить измеренный отказ в выражении до изменения массива,
не возвращать молча Неопределено и не менять формат байткода без OpenSpec.
Вариант решения — сохранить открытый путь для вызовов, которым нужна такая
проверка; решение ещё не принято и требует тестов обоих путей.

Это продолжение [матрицы доступности](notification-core-methods-2026-09-10.md),
а не реализация всех методов коллекций. Callback может указывать на эти
методы, но сама доставка здесь не проверялась. Rust-код не менялся;
новые conformance-ожидания из вывода open-bsl не генерировались.

## Реализация после измерения

Добавлены массивные ветки Get и Set. Подготовка индекса общая для этих
двух методов: число усечено, Boolean преобразован в 0/1, строка проходит
существующий parse_canonical. Остальные строки, дроби и точные ошибки
остаются ARRAY.METHOD_INDEX вместе с реестром и measure-строкой; это не
объявляется универсально измеренным преобразованием.

Чтение использует выделенный из индексатора общий доступ к элементу;
запись — существующий set_index после подготовки. Тест подтверждает, что
сам индексатор по-прежнему отвергает дробь, строку и Boolean.
Set сохраняет открытый опкод и result_required даже для статически
известного массива. VM отвергает использование результата до вызова
setter; для компонентных получателей действуют их собственные дескрипторы.
Формат байткода не изменялся.

Все 42 результата теперь совпадают с нормализованным оригинальным выводом.
Добавлена notification_array_access в conformance; ожидания взяты из 1С,
не из интерпретатора. Проверены прямые RU/EN-вызовы и динамический сценарий,
неизменность массива при ошибочной арности/индексе, реестр открытых вопросов,
полный workspace с plain/optimize/round-trip, fmt, Clippy, rustdoc и OpenSpec.
Логи: `/tmp/open-bsl-array-access-{clippy,doc,workspace}.log`.
