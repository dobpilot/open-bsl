# Операционный путь файловых TLS-сертификатов

Измерение выполнено напрямую на серверной `localhost/test`, Linux,
1С 8.3.27.2342. Unica не использовалась. Сессия
`/tmp/open-bsl-server-measure-bjwhpuv7` завершилась с кодом 0,
восстановила CF и БД; контрольная XML-выгрузка совпала с исходной.

- Исходник `file-http-certificate-io-edges.bsl`: SHA-256
  `f9a9c8bc4478a0ae8297de61ffb3178e1a8652da2d8623c5c8d9285fa45b1ec7`.
- Oracle `file-http-certificate-io-edges.platform.txt`: SHA-256
  `e646c06afbe31badab75e8a47970848fb792d3d56d8a995fd646477ff949e2cc`.

Матрица проверяет `СертификатыУдостоверяющихЦентровФайл` и
`СертификатКлиентаФайл` на одинаковых десяти суффиксах. Файл
намеренно не является сертификатом: ранее измерено, что оба объекта
создаются без немедленного разбора, поэтому результат изолирует именно чтение пути.

Оба конструктора снимают NUL, TAB, LF, CR, SPACE, U+0085 и NBSP, но
сохраняют U+007F, U+200B и U+FEFF. До исправления оба передавали имя
напрямую в `FileSystem`. Теперь они получают один `Rc<FileSystem>`, готовят
имя через `prepare_file_operation_path` и читают через тот же host.

Сквозной тест сверяет 22 строки в source/bytecode × plain/optimize.
Полные тесты `bsl-http` проходят при разрешённых loopback-сокетах;
в sandbox семь сетевых тестов ожидаемо получили `EPERM`, что не является отказом кода.
