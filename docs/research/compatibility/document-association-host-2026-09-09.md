# Открытие документа системным host: граница ожидания

Это проверка Linux-host, не измерение семантики 1С.

## Условия и результат

На рабочей машине `/usr/bin/gio open` проверен с изолированными
`XDG_DATA_HOME`, `XDG_CONFIG_HOME` и `XDG_CONFIG_DIRS` в
`/tmp/open-bsl-document-association-hvbV97`. Пользовательские ассоциации
не менялись. Для `text/plain` задан собственный `open-bsl-probe.desktop`.
Его `Exec` запускает тестовый обработчик с `%f`; обработчик записывает путь,
ждёт отдельного файла-разрешения и только после этого выполняет `exit 17`.
Ожидание ограничено 20 секундами; проба не запускает редактор пользователя.

Наблюдавшийся вывод:

```text
gio_status=0
handler_finished_before_gio_return=no
handler_exit_intent=17
handler_argument=/tmp/open-bsl-document-association-hvbV97/document.txt
```

`17` здесь — записанное обработчиком намерение завершиться, а не полученный
через `wait` статус. Существенное наблюдение: `gio` уже вернул 0, но обработчик
ещё ожидал разрешения продолжить. Следовательно, статус `gio` нельзя выдавать
за статус приложения, открывшего документ, даже в этом простом сценарии.
Проверка не доказывает поведение всех desktop-сред, порталов и ассоциаций.

Локальная справка `xdg-open(1)` также предупреждает о зависимости от нижележащего
открывателя: в некоторых случаях `xdg-open` остаётся работать вместе с
приложением. Это не универсальная гарантия ожидания приложения.

## Следствие для реализации

Текущий `ApplicationCompletionSink` принимает `ApplicationExit`, то есть
завершение процесса. Подключить `gio open` как обычный executable и назвать
его успешный выход завершением приложения означало бы нарушить этот контракт.
Нужны отдельный результат передачи документа приложению и явная семантика
запроса ожидания, когда отслеживаемый процесс недоступен. Вопрос передан
пользователю; до решения системный адаптер продолжает явно отклонять документ,
а задача поддержки ассоциаций остаётся открытой.
