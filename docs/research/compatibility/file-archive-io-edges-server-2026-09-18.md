# Операционный путь ZIP-архивов

Измерение выполнено напрямую на серверной `localhost/test`, Linux,
1С 8.3.27.2342. Unica не использовалась. Сессия
`/tmp/open-bsl-server-measure-dpx4v35y` завершилась с кодом 0,
восстановила CF и БД; контрольная XML-выгрузка совпала с исходной.

- Исходник `file-archive-io-edges.bsl`: SHA-256
  `640b612355b15e1776b13804cf48cd7ee82d0a94926cbfd7b1c428494b43d097`.
- Oracle `file-archive-io-edges.platform.txt`: SHA-256
  `4103265f4af8580f08381392c402fd7b1f766953c0fc17202abc95cf18a6d2f7`.

Матрица покрывает конструктор и `Открыть` четырёх типов:
`ЧтениеZipФайла`, `ЧтениеФайлаАрхива`, `ЗаписьZipФайла` и
`ЗаписьФайлаАрхива`. Каждый reader проверяется по одному элементу
заранее созданного архива, writer — по изменению базового `ABC`.

Все восемь входов одинаково снимают NUL и конечные TAB, LF, CR,
SPACE, U+0085 и NBSP до host. U+007F, U+200B и U+FEFF сохраняются.
Writer с начальным NUL отказывает на каталоге и не меняет базовый файл.
Reader-вариант начального NUL не включён из-за риска зависания при чтении
каталога, уже подтверждённого JSON-пробой.

До исправления `read_source` и `writer_write` передавали строку напрямую
в `FileSystem`. Теперь они вызывают `prepare_file_operation_path` перед
фактическим I/O; потоковые источники и цели не меняются. Сквозной
тест сверяет все 86 строк в source/bytecode × plain/optimize.
