# Уточняющие серверные замеры ожидания

Источник — `followup.bsl`, `legacy.bsl` и общий `followup-worker.bsl`;
результаты — `followup.platform.tsv` и `legacy.platform.tsv`.
Контекст прежний: серверная 1С 8.3.27.2342, `Version8_3_27`,
`localhost/test`. Это не отдельное измерение 8.5 и не файловый режим.

## Новый менеджер

Свежий `completed` и старый `active` снимки уже завершённого задания дают
одинаковый немедленный возврат при активном втором задании. То же измерено
для `failed`, включая повторный вызов с возвращённым массивом. Следовательно,
возраст входного снимка не объясняет возврат: достаточно любого текущего
конечного состояния в переданной группе. Полностью завершённая группа
также возвращается сразу. Отрицательные `-1` и `-0.2` на двух активных
заданиях возвращают первое завершение, не ждут всю группу.

В первых отменяемых пробах работа длилась лишь 100 мс и иногда завершалась
раньше обработки отмены. Строки `mix.canceled.*`, фактически вернувшие
`completed`, не доказывают поведение отменённых заданий. Контроль в
`legacy.bsl` удерживает работу 5000 мс и дожидается отмены перед проверкой:
`new.manager.canceled.stale` и `new.manager.canceled.fresh` возвращают
`canceled:active` немедленно. Во вложенных объектном и менеджерном ожиданиях
отменённый ребёнок возвращается как отменённый объект, без ошибки нового API.

## Числовой таймаут

Сто последовательных ожиданий по `0`, `0.0001`, `0.0009` секунды занимают
99–100 мс, а по `0.0011`, `0.0019` — 200–201 мс. Результат соответствует
отбрасыванию дробной части миллисекунд; накладные расходы вызова около 1 мс
не считаются временем таймаута. Отрицательное `-0.0001` возвращает активное
задание немедленно, в отличие от `-0.2`. Знак следует проверять после
усечения миллисекунд к нулю, а не до преобразования.

## Старые методы

Оба `ОжидатьЗавершения` — процедуры: использование в выражении выдаёт
`Object procedure called as function` до выполнения ожидания.
Объект принимает необязательный таймаут, менеджер — обязательный массив
и необязательный таймаут. Пустой массив допустим. Менеджер без массива
выдаёт ошибку недостаточного числа аргументов; число вместо массива — ошибку
типа. Объект с двумя аргументами выдаёт ошибку избыточного числа аргументов.

Менеджер ждёт успешного окончания всей группы: 300 мс + 900 мс дают возврат
через 907–913 мс без таймаута, с 2 секундами и с -1. Ошибка первого задания
завершает ожидание ошибкой через 308 мс, пока второе активно; уже отменённое
задание вызывает ошибку сразу. Таймауты 0 и 0.05 завершаются ошибкой при
активных заданиях. Объект ведёт себя аналогично для одного задания:
успешное окончание разрешает возврат, таймаут, сбой и отмена вызывают ошибку.

Открытая справка старых методов не описывает измеренную сигнатуру полностью;
при реализации источником контракта служат эти вызовы, не вывод по справке.
Точные тексты вложенных причин ошибок этим протоколом не измерены.

## Проверка реализации и исправление подготовки пробы

В `verified.open-bsl.tsv` и `verified.open-bsl-optimize.tsv` все 28 основных
проб совпали с `platform.tsv` по исходу и состояниям. Сравнение не требует
тождественного текста ошибки или времени в миллисекундах.

Первый повтор уточняющего сценария сохранён как
`followup.setup-failure.open-bsl.tsv` и его вариант `-optimize`.
Обе вложенные пробы дали `failed`: причиной оказался не метод ожидания,
а передача объекта `УникальныйИдентификатор` в параметрах задания.
Диагностика: «объект типа „УникальныйИдентификатор“ не переносится между
сеансами». В `followup-worker.bsl` параметр теперь передаётся строкой
и восстанавливается в отменителе. Это изменение подготовки, не расширение
сериализации runtime; исходный серверный TSV снят до этой правки.
Исправленная подготовка повторена на сервере:
`followup.verified.platform.tsv` подтверждает оба `completed:canceled=Yes`.
Дополнительно отменяемое задание в матрице смесей продлено до 5000 мс
с обязательной проверкой состояния подготовки. Все свежие/устаревшие
смеси и повторные ожидания теперь действительно измерены для `canceled`.
Строки `mix`, `repeat`, `negative`, `all.terminal`, `precision`, `nested`
совпали с обоими режимами open-bsl по результату (локализованное `Да`
сопоставлено с `Yes`, время не сравнивается на точное равенство).
Короткая старая проба `old.object.canceled` в этом повторе закончилась
успехом до обработки отмены и не является свидетельством поведения
отменённого задания; для этого сохраняется исходная строка с фактическим
`canceled` и контролируемая матрица `legacy`.
Регрессия `canceling_the_child_returns_its_canceled_snapshot_to_the_parent`
использует тот же файл worker и проверяет успешное окончание родителя
с сообщением `canceled=Да` для обоих новых методов.
