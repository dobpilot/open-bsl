# Импортированная переменная в обычном Call

Закрыт отдельный пробел, обнаруженный при проверке
[живых модульных ссылок](module-aliases-2026-09-17.md).
До исправления компилятор сохранял импортированную ссылочную цель для
CallImported и открытого модульного вызова, но обычный Call получал Value.
Новый тест падал на проверке общей ячейки двух параметров (`shared cell`).

## Изменение

`compile_call` теперь передаёт импортированную переменную без Знач как
существующий `ArgMode::ByRefImportedVar`. VM подготавливает ленивых
владельцев всех таких аргументов до продвижения инструкции и создания
кадра. Чтение активной ячейки и привязка используют общие помощники с
CallImported и открытым вызовом. Знач продолжает передавать вычисленную
копию, async-параметры — прежние независимые снимки.

Дополнительный красный тест выявил ошибку поиска обработчика при сбое
ленивого тела: инициализация не продвигает инструкцию вызывающего, но
разматывание вычитало единицу из pc как после обычного Call. Теперь
инициализационный кадр сохраняет проверку текущей инструкции владельца;
обычный вызов по-прежнему проверяет предыдущую. Неудачная инициализация
ловится исходной Попытка, тело вызываемой функции не исполняется.

Проверка повторных вызовов дополнительно обнаружила накопление временных
ячеек параметров: после 20 вызовов оставалось 25 слотов при пяти регистрах
entry. Граница освобождения кадра бралась после размещения модульных
аргументов. В Call и CallImported она перенесена перед их размещением;
существующий открытый вызов уже использовал правильную границу. Сначала
выполняется запись аргументов в состояние владельца, затем освобождение
слотов. Повторно используемая ячейка внешнего кадра не освобождается.

Это конфигурационное расширение open-bsl, использующее уже измеренное
правило живого ссылочного параметра. Наличие экспортируемых переменных
у общего модуля 1С этим не утверждается. Новая платформенная сессия для
этого этапа не запускалась; markers и oracle не изменялись. Сценарии
добавлены в существующую delta до реализации. Формат остаётся 31,
публичные имена/арности не добавлены, API reference не требует регенерации.
Утверждений о производительности нет.

## Проверяемый объём

Три новые проверки в `crates/open-bsl/tests/module_aliases.rs`:

- Обычный вызов из entry и модуля каталога, lazy/eager initialization,
  повторный и вложенный аргументы, чтение/запись исходной переменной,
  Знач/default и сохранение записи после исключения: 16 комбинаций
  source/bytecode × plain/optimize × entry/catalog × lazy/eager.
- Async-снимки импортированных аргументов при активном родительском
  параметре; изменение параметра не меняет второй снимок, запись в модуль
  видна родителю; четыре режима source/bytecode × plain/optimize.
- Два обращения к сбойному ленивому владельцу, два пойманных исключения,
  отсутствие входа в вызываемую функцию и записи в первый аргумент;
  четыре режима source/bytecode × plain/optimize.

Прежние модульные тесты также проходят. Красные логи:
`/tmp/open-bsl-static-import-red.log` (копия вместо ссылки) и
`/tmp/open-bsl-static-import-edges.log` (исключение инициализации).
Зелёный целевой прогон: `/tmp/open-bsl-static-import-edges-fixed.log`.

VM-тест `module_argument_cells_are_released_on_return_and_exception`
проверяет четыре пути (свой модульный аргумент, импортный аргумент Call,
CallImported и открытый вызов) × возврат/исключение × plain/optimize.
В каждой комбинации выполняются 20 вызовов, проверяются итоговое значение
20 и точный размер оставшегося стека. Красный/зелёный логи:
`/tmp/open-bsl-static-import-stack-{red,fixed}.log`.
Все восемь фасадных модульных тестов после исправления прошли повторно:
`/tmp/open-bsl-static-import-final-focused.log`.

После последнего изменения полный `cargo test --workspace` завершился
с кодом 0, включая conformance, plain/optimize, bytecode round-trip,
API reference и реестр измерений. Повторно прошли fmt, Clippy
workspace/all-targets с `-D warnings`, rustdoc с запретом предупреждений,
`git diff --check` и все 11 строгих проверок OpenSpec. Итоговые логи:
`/tmp/open-bsl-static-import-{workspace,clippy,doc,openspec}-final.log`.

Динамический каталог, чужие модульные аргументы внутри фрагмента, перенос
BSL-обещания и доставка Begin остаются незавершёнными. Этот этап не
объявляет закрытым весь модульный вызов или общий файловый план.

## Свидетельство для следующего динамического этапа

Дополнение: коллизия ниже устранена [следующим этапом](dynamic-module-scope-2026-09-17.md),
с разделением владельца модуля и номера фрагмента. Воспроизведение оставлено
как свидетельство исходного дефекта.

Отдельная CLI-проба без изменения кода во время полного тестового прогона
выявила коллизию динамического кэша между статическими функциями разных
модулей. В `/tmp/open-bsl-dynamic-scope-ENXGns` созданы три файла:

```bsl
// a.bsl
Перем Первый, Нужная;
Функция Получить() Экспорт Возврат Вычислить("Нужная"); КонецФункции
Первый = 11; Нужная = 22;
```

```bsl
// b.bsl
Перем Нужная, Второй;
Функция Получить() Экспорт Возврат Вычислить("Нужная"); КонецФункции
Нужная = 33; Второй = 44;
```

```bsl
// main.bsl
//@используй(a.bsl как ПервыйМодуль)
//@используй(b.bsl как ВторойМодуль)
Сообщить(ПервыйМодуль.Получить());
Сообщить(ВторойМодуль.Получить());
```

`target/debug/bsl-cli /tmp/open-bsl-dynamic-scope-ENXGns/main.bsl` вернул
`22` и `44`, а должен читать `Нужная` своего модуля: `22` и `33`.
Лог `/tmp/open-bsl-dynamic-scope-red.log`. При построении DynamicRequest
для ненулевого чанка область сбрасывается в ROOT, а DynamicCode привязан
к единому entry, не текущему модулю каталога. Эта коллизия ещё не исправлена
и не покрывается зелёными тестами статической передачи аргументов.
