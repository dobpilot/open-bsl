# Обход фиксированного соответствия при запуске UNF

Диагностический read-only запуск установил вызов default collection_len у ФиксированногоСоответствия. Публичный метод Количество существовал, но протокол Для Каждого отсутствовал. Нативный собственный контроль `tests/conformance/measure/1c/measure-fixed-map-iteration.{bsl,platform.txt}` подтвердил пустой обход, пары КлючИЗначение, независимость снимка от замены/вставки исходных записей и запрет изменения значения пары. Порядок обхода этим контролем не закреплён.

После strict validation support-reached-fixed-map-iteration добавлены только collection_len и collection_item. Повторно использованы BslObject::KeyValuePair и существующая проверка числового индекса, видимость которой расширена только до pub(crate). Публичное индексирование и методы изменения не менялись. Новый потребительский тест прошёл. Полный bsl-rt и all-target Clippy bsl-rt/open-bsl-consumer прошли после запуска файловых тестов вне sandbox, запрещавшего Unix-сокеты. Старые тесты не менялись. Логи: `target/diagnostics/fixed-map-{rt-tests,clippy,iteration-test}-1013.log`.

Read-only повтор оригинального UNF с отдельным бинарником fixed-map-unf-probe-1013 запущен; успешная инициализация пока не заявляется.

При добавлении контроля в conformance обнаружено различие текстового представления типа пары между английским контуром 1С и CLI: Key and value / КлючИЗначение. Исходный нативный вывод сохранён отдельно в `fixtures/fixed-map-iteration/initial-native-presentation.tsv`. Контроль заменяет только текстовое представление проверкой равенства Тип("КлючИЗначение") с явными YES/NO; повтор на реальной платформе дал YES. Все девять строк повторного oracle побайтово совпали с обычным и оптимизированным CLI: `target/diagnostics/fixed-map-native-control-{plain,optimized}-1013.log`. Общий conformance-прогон ещё выполняется с первой новой фикстурой; её обновление ожидает его завершения. Этот дефект нового контроля не требует менять старые фикстуры или поведение представления типов.

Первый общий conformance-прогон завершился: три проверки прошли, включая the_optimizing_passes_agree_with_the_plain_run_on_every_script; две упали только на исходном представлении типа в новой фикстуре. Все старые фикстуры сохранились. После окончания прогона новая фикстура обновлена побайтово повторным нативным oracle. Повтор conformance_fixtures_match_oracle_output прошёл; повтор исполнения из текстового байт-кода ещё выполняется. Логи сохранены отдельно: fixed-map-conformance-initial-control-1013.log, fixed-map-conformance-oracle-1013.log и fixed-map-conformance-bytecode-1013.log в target/diagnostics.

Повтор fixtures_produce_the_same_output_when_run_from_printed_bytecode также прошёл. Все пять conformance-проверок имеют положительный результат по указанным отдельным прогонам; после обновления нового контроля обычный и оптимизированный вывод этого контроля отдельно совпадают с платформой. Полный workspace-прогон остаётся открытым.

Оригинальный read-only UNF завершился за446,46с, код1, пик RSS7444424КиБ. Прежний отказ collection_len пройден. Следующий отказ UnknownProperty("РазделениеДанных"), получатель уточняется; оригинальная инициализация не доказана. Лог: `target/diagnostics/readonly-startup/unf-fixed-map-host-1013-startup.log`.

Отдельная диагностика завершилась за444,66с, код1, пик RSS7426768КиБ. Получатель следующего UnknownProperty — ПользовательИнформационнойБазы, текущая функция СеансЗапущенБезРазделителей. Это другой контракт, чем уже реализованное РазделениеДанных общих реквизитов. Лог: target/diagnostics/readonly-startup/unf-separation-property-host-1013-startup.log.
