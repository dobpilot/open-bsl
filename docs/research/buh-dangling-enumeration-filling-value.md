# Значение заполнения buh вне списка перечисления

## Свидетельства на 2026-10-02

Повтор оригинального тонкого сеанса остановился при проекции значения
заполнения, до исполнения стартового обработчика. Сообщение называет
`7c33f4b3-1467-4a46-a348-be2331940c1b` ресурсом, но путь
`document_attributes::filling` передаёт в `malformed` идентификатор типа.
Это идентификатор ссылки перечисления `ВидыОперацийОтчетКомиссионера`.

В сохранённой нативной XML-выгрузке buh
`Documents/ОтчетКомиссионераОПродажах.xml` реквизит `ВидОперации`
(`b9b6b0cf-8221-4e2b-824d-436c06a46702`) имеет
`FillFromFillingValue=true` и `FillValue`
`7c33f4b3-1467-4a46-a348-be2331940c1b.7664d5d3-bca6-4114-8409-3272f9787060`.
Оба идентификатора также присутствуют в исходном Config ресурсе
`cf00de56-2f8f-4328-8058-803afff59319` фикстуры SDK buh.

Нативная XML перечисления и исходный Config ресурса
`f3326189-6fa8-475d-83cc-d9c901dd544e` содержат четыре значения:

- `374c7d31-4e5e-4eef-b509-9e63acdccd07` — ОтчетОПродажах;
- `04ab4ebb-722a-44d3-a8f2-0a4fae915636` — ОтчетОСписании;
- `cfe75599-9a30-431c-a6f5-9656b609946a` — ОтчетОРозничныхПродажах;
- `1e1b3fb0-2193-4836-b2a6-8e177c9af6c9` — ОтчетОбОприходовании.

UUID значения заполнения не совпадает ни с одним из них. Это исключает
объяснение только потерей существующего значения при проекции: исходные
артефакты сами содержат ссылку вне списка. Причина её появления неизвестна.

## Следующая проверка

На платформе требуется прочитать значение заполнения именно этого
реквизита и проверить создание документа и заполнение. До замера нельзя
делать вывод, что платформа заменяет ссылку пустой, допускает неизвестное
значение или откладывает ошибку. Никакой такой семантики пока не внедрено.
Рабочая база и исходники не изменялись.

Подготовлена отдельная проба
`docs/research/probes/buh-dangling-enumeration-fill.bsl`: только чтение
метаданных, тип, представление, заполненность и сравнение с пустой ссылкой.
Она ещё не исполнена на платформе; ожидаемого результата нет. Проба
создания и заполнения документа должна идти отдельно в изолированной базе,
поскольку обработчики исходного документа могут иметь побочные эффекты.

В УНФ новый отказ `Записать` подтверждён исходным модулем:
`Documents/Событие/Ext/ObjectModule.bsl` содержит голые вызовы на строках
165 и 216. Фабрика уже регистрирует платформенные методы собственного
получателя через `document_object_receiver_methods`, но таблица объекта
документа не содержит `Записать`. Это следующий отдельный недостаток
поверхности документа, а не основание менять общий порядок поиска имён.

## Измерение отсутствующего значения на платформе

На 1С 8.3.27.2342 в отдельной файловой базе создана настройка заполнения
в нативной форме `EnumRefTypeUUID.ValueUUID`, с отсутствующим
`7664d5d3-bca6-4114-8409-3272f9787060`. Проба
`measure-dangling-enum-filling.bsl` завершилась успешно, эталон сохранён.
Метаданные возвращают ссылку нужного типа; она не равна пустой и заполнена.
Новый документ сначала содержит пустую ссылку, после `Заполнить(Неопределено)`
получает отсутствующее значение. Представление платформы:
`<Object not found> (54:84093272f97870604114bca67664d5d3)`.

Таким образом, отсутствие UUID среди перечисленных значений не делает
ссылку повреждённой и не должно блокировать приобретение каталога. Нужен
отдельный контракт сохранения такой идентичности в ORM и графе значений.
Число 54 в представлении относится к изолированной базе; его нельзя
перенести в buh или вывести из измеренного UUID. Локализация и источник
этого числового кода требуют самостоятельной проверки перед форматированием.
Ни рабочая buh, ни оригинальный документ не записывались.

## Числовой код представления

Дополнительная нативная проба `measure-dangling-enum-storage.bsl`
получила таблицу `_Enum54` для того же перечисления, чьё представление
содержит `(54:...)`. UUID в представлении совпадает с физическим порядком
байтов 1С для измеренной идентичности. SDK уже публикует приобретённый
главный номер DBNames как `MetadataObject.number`; новый запрос к БД
не нужен. Первое обращение к русским именам колонок было отклонено,
поскольку в конфигурации английский ScriptVariant: успешная проба
использует StorageTableName и Metadata. Это граница подготовки пробы,
не изменение семантики ссылки. Локализация текста ещё не измерена.

## Локализация представления

Проба `measure-dangling-enum-storage-russian-ui.bsl` с теми же
метаданными и английским ScriptVariant, но с запуском Enterprise `/Lru`,
получила `<Объект не найден> (54:84093272f97870604114bca67664d5d3)`.
В английском интерфейсе текст был `<Object not found>`. Номер, тип,
заполненность и UUID не меняются. Следовательно, локализация зависит
от интерфейса сеанса, а не от ScriptVariant этих метаданных.
Нельзя сохранять выбранный текст в общем каталоге, изменяя его для
одного пользователя, или угадывать по основному языку конфигурации.

Текущий ObjectProtocol.display не получает CallContext, а граф
материализуется в том числе при приобретении до открытия пользовательского
сеанса. Для представления требуется пройти по существующему форматированию
с текущим языком; это должно быть отражено в публичном контракте до кода.

## Реализация сохранения ссылки

Материализатор теперь сохраняет корректный отсутствующий UUID независимо от списка значений; поиск по имени остаётся ограничен объявленными значениями. Приобретённый основной номер DBNames передаётся в описание объекта, язык интерфейса — в данные конкретного сеанса. Перестановка физических байтов UUID вынесена из адаптера в общий модуль runtime, доступный через фасад. Восемь тестов перечислений прошли, включая сохранение типа, заполненности, равенства и перенос через ХранилищеЗначения; отдельный тест приобретения значения заполнения при пустом списке перечисления также прошёл. Прежние ожидания тестов не менялись. Полный прогон и повтор исходной buh ещё требуются.

Повтор исходной buh завершился через 196,5 с, CLI вернул 1. Каталог приобретён; вместо прежнего отказа на UUID перечисления получена ошибка семантики модуля АдминистрированиеКластераRAS: не поддержано выражение Новый АдминистрированиеСервера. Лог: /tmp/open-bsl-buh-096-missing-enum.log. Пользовательский скрипт не достигнут.

Отдельный интеграционный тест документа совпал с последними тремя наблюдениями нативного скрипта для английского и русского сеансов: созданный документ содержит пустую ссылку, Заполнить переносит отсутствующую ссылку и её измеренное представление. Полный семистрочный скрипт пока невозможен: Метаданные.Документы.<имя>.Реквизиты не реализованы. Диагностический запуск также выявил отказ ОписаниеОшибки в обработчике этого случая; он не исправлялся в рамках сохранения ссылки. Эталон платформы не менялся, успешный блок создания/заполнения исполнялся без изменения исходных выражений.

Проверки после реализации: fmt, Clippy workspace, cargo test workspace (352,7 с), rustdoc с -D warnings, open-bsl-consumer, cargo tree bsl-rt/bsl-vm и openspec validate --all --strict завершились успешно. Лог /tmp/open-bsl-missing-enum-096-gates.log. Добавленный после начала общего прогона тест заполнения отдельно прошёл вместе с Clippy своего test-target; ожидания существующих тестов не менялись.
