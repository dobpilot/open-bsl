# Критическая ошибка внутри обработчика загрузки

1С 8.3.27.2342: деление на ноль внутри `ОбработкаЗагрузки` вызывает диалог Restart/Finalize с требованием перезапуска. Подробный локальный отчёт (`division-report/text/0xc001f5.png`) подтверждает именно `Division by zero` при исполнении `LoadProcessing`, `ScriptRuntimeError, ScriptUseError`. Внешний BSL-перехват и продолжение не выполняются. Ранее сохранённый контроль явного исключения находится в `../settings-storage-handler-error-1017/`.

Критическая политика теперь применяется в существующем VM-мосте только после подготовки цели и к ошибке, покинувшей обработчик. Исходная причина сохраняется; State становится терминальным. Внутренний перехват самого обработчика действует по-прежнему. Ошибки подготовки и обычная политика вызова не меняются; отмена, компиляция и повреждённый байт-код не переклассифицируются. Нового типа ошибки подготовки нет.

## Исправленная трактовка нативного контроля

Начальный диалог менеджера с операторами после определений методов ошибочно трактовался как runtime-инициализация. Его подробный отчёт (`initialization-report/text/0xc00232.png`) доказал `ScriptCompileError`: такой исходный текст менеджера отвергается. Счётчик тела поэтому не запускался. Followup подтвердил лишь отдельное действие после отказа компиляции; retry не доказывает runtime-повтор. Старые выводы сохранены с явной отметкой superseded в `native-result-before-cause-review.json` и `superseded-initialization-interpretation/`; они не являются доказательством текущей семантики.

После предварительной строгой валидации OpenSpec ошибочно добавленный ConfigurationHandlerInitialization удалён. Осталась минимальная политика Critical(operation) на существующем мосте. Синтетическое тело модуля хоста проверяет неизменность ошибки подготовки, но не изображает допустимый исходник менеджера 1С. `SETTINGSSTORAGE.LOAD_HANDLER_ERROR` сохранён для других классов ошибок обработчика. `JOB.MODULE.INIT` вне этого callback не менялся.

`red.log` сохраняет исходные два отказа до поправки. Тест подготовки из этого лога допустим как вход API хоста, но не как нативный менеджер. Текущие тесты находятся в отдельных файлах; существующие ожидания не менялись. Итоги повторных общих проверок записываются после завершения соответствующих процессов.

Все снимки ограничены PID собственной тестовой базы. Локальные окна подробного отчёта прочитаны; отчёты не отправлялись. Таймаут отдельно не является семантическим эталоном.

## Имена обработчика

Нативный английский `LoadProcessing` успешно обработал ошибку внутри своего тела и вернул `caught-inside`. Все четыре профиля двух имён (оба ScriptVariant × оба порядка определений) выбрали русский обработчик. Результаты находятся в `english-handler/` и `dual-handlers-*/`. До исправления два новых теста падали из-за отсутствия английского fallback (`handler-names-red.log`); после исправления пять проверок имён/арифметики и три старых сеансовых проверки проходят (`handler-names-green.log`). Регистр проверяется существующим сравнением имён. Если оба имени отсутствуют, сохраняется старая русская диагностика.

Неудачный общий прогон до этого fallback сохранён в `before-handler-alias-fix/`: старый тест document_association увидел marker-файл пустым, затем прошёл без изменений. Ожидания этого теста не исправлялись. Новый общий прогон относится к снимку исходников с fallback.

Текущий окончательный прогон: 3868 тестов прошли, 0 отказов, 1 ignored; 4339 файла исходников и входных данных сохранили хеши, новых исходников во время проверок нет. Clippy, rustdoc, фасадный потребитель, fmt и строгая валидация прошли; обычные деревья RT и VM совпали с предыдущим этапом. DEMO прошла на текущей release-сборке (`cli-demo-settings-handler-names-1017-result.json`). BUH и UNF прошли на предшествующих сборках, их результаты не выдаются за свежую матрицу текущего бинарного файла. Основное изменение и 14 неподтверждённых требований остаются открытыми.
