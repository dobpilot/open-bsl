# Граница доступа функциональной опции через Session-адаптер

На собственном временном PostgreSQL выполнен фактический путь BSL → ORM →
DatabaseDataAccess → SDK → SQL. Рабочие DEMO/BUH/UNF и `.pgpass` не используются.
Config даёт имя/тип константы и режимы опций, а физические номера и роль
Read=false заданы стендом явно. Это проверка исполнения, не приобретения БД.

В двух повторениях прямое чтение константы и обычная опция запрещены,
привилегированная опция с обоими языковыми именами возвращает Boolean true.
Журнал собственного PostgreSQL содержит ровно четыре чтения таблицы —
все относятся к четырём привилегированным вызовам. Последующие обычные
вызовы сохраняют отказ до SQL. Ожидания основаны на отдельной квитанции
`measure-functional-option-rights.platform.txt`, она не менялась.

Первый запуск остановился на проверке текста новой диагностики стенда:
SDK вернул правильный отказ по-английски, а assert искал русскую фразу.
Первичная квитанция сохранена в `actual-postgres/first-harness-assertion/`.
Повтор проверяет отказ именно выбранному пользователю и проходит.

Новых API, зависимостей и изменений существующих тестов нет. Каталог,
ресурс регистра, RLS и разделение данных этим тестом не подтверждаются.
Обычный workspace-запуск без переменной стенда не исполняет SQL этого теста.

Полный ROOT-прогон завершён: 3805 passed, 0 failed, 1 ignored; все
обязательные проверки зелёные, normal-деревья RT/VM прежние. Логи в
`root-gates/`. Положительный SQL-путь подтверждён отдельным запуском,
а не обычным env-unset workspace-прогоном.
