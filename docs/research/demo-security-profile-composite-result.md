# Составной результат константы профиля безопасности demo

Повторный оригинальный read-only запуск с зарегистрированной строкой соединения воспроизвёл прежний отказ чтения `ПрофильБезопасностиИнформационнойБазы`. Квитанция: `target/diagnostics/readonly-startup/demo-chart-empty-host-1013-startup.log`. Измерение RSS в этой квитанции дало ноль и не считается измерением памяти.

Метаданные SDK объявляют B и S(120,1), то есть Булево и Строка. Отдельная компиляция фиксированного SELECT (без выполнения SQL) через публичный QueryCompiler дала три физических колонки: `_fld2262_l` Boolean, `_fld2262_s` String(120), `_fld2262_type` Binary. Все три имеют один ColumnOrigin с composite_member=true. Квитанция: `target/diagnostics/readonly-startup/demo-security-profile-projection-1013.log`.

Адаптер преобразует каждую физическую колонку отдельно, затем пытается вернуть первую BSL-колонку константы. Преобразование последнего однобайтового признака Binary завершается отказом до возврата полезного значения. Двоичный результат здесь не является ХранилищеЗначения или ссылкой.

Нужно материализовать одно логическое значение по признаку типа. В CompiledQuery внутренние logical_columns существуют при генерации, но потребителю не предоставлены; CompiledColumn.name приватно, а публичные label обрезаны и дополнены суффиксами. Восстановление логической структуры по строковым label ненадёжно; группировка только по ColumnOrigin также не различает два выбора одного поля. Требуется проверить минимальный публичный контракт логической проекции SDK прежде, чем расширять адаптер. Это не основание вручную разбирать Config или возвращать пустую строку.

SDK-черновик логической проекции имеет замороженный API-снимок `/tmp/open-sdbl-logical-projection-api-snapshot-1013`. В изолированном адаптере физическая ширина SQL теперь определяется `compiled.columns.len()`, а BSL-колонки — полной логической проекцией. Сборка dev прошла; два теста материализации подтверждают активный Boolean/String и ошибки неверных индексов/дискриминатора. Неактивная полезная ячейка намеренно содержит недекодируемые байты в тесте и не преобразуется. Исходный новый тест ошибочно использовал неподдерживаемый source-free CASE: после отказа компилятора изменён только новый тест на поддерживаемый CASE с источником. Прежние тесты и принятие запросов не менялись. Полный повтор оригиналов ещё не запущен; release-сборка выполняется.

Release-сборка изолированного потребителя завершилась успешно (`logical-result-integration-build-1013.log`). Запущены оригинальные read-only повторы `demo-logical-result-1013-startup.log` и `unf-logical-result-1013-startup.log`, с отдельными соединениями и точными зарегистрированными строками. На момент записи оба процесса активны; прохождение константы или успешная инициализация ещё не подтверждены.

Первые логические повторы завершились terminal1: demo151.19с/peakRSS7162208КиБ, UNF446.22с/peakRSS7408752КиБ. Получен отказ неизвестного признака составного типа; фактический байт первым бинарным снимком не выводился, поэтому отождествлять его с tag1 нельзя. SDK предоставил snapshot2 с измеренным вариантом Undefined(tag1,columnNone) для составных полей хранения. Пять тестов потребителя (включая tag1 без полезной ячейки, повторные позиции, неверный неактивный индекс/дублированные теги) и Clippy прошли. Release-сборка snapshot2 тоже прошла. Запущены `demo-logical-undefined-1013-startup.log` и `unf-logical-undefined-1013-startup.log`; новая диагностика выводит только байт типа, не полезное значение. Оба процесса активны.

Нативный собственный контроль SDK в `/tmp/sdbl-logical-priv-context-native-1013/target.oracle` завершился с completedYES: один столбец ЧислоОпции, UNION BooleanNo/BooleanYes/Stringnative-string, CASEBooleanNo, NULL|String и Undefined|String сохраняют соответствующие типы. Для принятых форм, в которых прежний SQL не даёт однозначного рецепта, SDK оставляет логическую проекцию недоступной; SQL и прежний физический API не меняются.

Второй demo-повтор подтвердил actualTYPE=1; логическая константа преобразована в Undefined и пройдена. Следующий отказ — отсутствие EventLogWriter в ресурсе сеанса (`demo-logical-undefined-1013-startup.log`). UNF-повтор тоже прошёл константу и остановился на том же отсутствии приёмника (`unf-logical-undefined-1013-startup.log`). В диагностическом хосте подключён существующий EventLogWriter: события действительно сохраняются в отдельном сеансовом буфере до1000записей, stdout содержит только имя/уровень/длину комментария. Содержимое данных и комментария не выводится, журнал оригинальной базы не изменяется. Новые повторы `demo-event-log-host-1013-startup.log` и `unf-event-log-host-1013-startup.log` активны; никакого вывода о завершении сеанса ещё нет. Это диагностическая настройка существующего API, не изменение CLI или поведения языка.

Полный переносимый патч потребителя сохранён в `target/diagnostics/logical-result-complete-adapter-proposal-1013.patch` и прошёл `patch --dry-run -p1`. Он содержит адаптер, логический материализатор и пять тестов с собственной уже имеющейся фикстурой Config; абсолютного пути к SDK-тестам и диагностической печати в нём нет. Старые файлы тестов не правятся. Main не применён до доступности согласованного SDK API.

Лог: `target/diagnostics/logical-result-final-sdk-tests-1013.log`. Основной ../open-sdbl305f4f1 не менялся. Полный lib-набор bsl-config-db с финальным SDK ещё выполняется.
