# Оптимизация цикла исполнения VM, 24 октября 2026

Исправление регрессий из [профиля горячих точек](../hotspots-2026-10-24/README.md).
База — текущий `main` `a590b73f`; кандидат — рабочее дерево с изменениями ниже.

## Изменения (`crates/bsl-vm`)

1. **`TaskSecurityModes::synchronize_frames` больше не работает вхолостую.**
   Цикл `poll_linked` зовёт её вокруг каждого шага, а число кадров
   меняется только на вызове, возврате и раскрутке. При прежнем числе
   кадров она выходит сразу.
2. **Пять векторов режимов безопасности — один вектор структур
   `FrameSecurityModes`.** На вызове и возврате вместо пяти `resize_with` и
   пяти `truncate` — один `resize_with`.
3. **Кадр снова 128 байт.** Поле `handled_errors` (с `e6cd0378`) выросло
   `Frame` со 128 до 152 байт, и LLVM стал строить кадр во временной памяти
   и копировать через `memcpy` на каждом вызове. Оно и `module_copybacks`
   вынесены в `cold: Option<Box<FrameCold>>`; память выделяется, только
   если вызову нужны обратные записи модульных переменных или кадр поймал
   ошибку. Размер кадра теперь 112 байт; тест
   `a_frame_fits_the_inline_copy_budget` не даст ему снова перерасти 128.
4. **`CatalogContext::execution_parts` берёт программу модуля один раз.**
   Раньше — дважды на каждом шаге кадра модуля конфигурации, и каждый раз
   это два динамических вызова каталога.

`bind` кэшей из цикла не выносился: на `call_overhead` он стоит 0,19%.
Изменения внутренние, наблюдаемого поведения не меняют (освобождение от
OpenSpec-изменения). `cargo test --workspace` (включая
`the_optimizing_passes_agree_with_the_plain_run_on_every_script`), clippy,
fmt и rustdoc проходят. `benchmarks/hot-code-diff.sh HEAD`: `step` и
`step_cold` изменились и уменьшились ([лог](hot-code-diff.log)), поэтому
решение принимается по A/B ниже.

время многопоточного прогона не изменилось: его ограничивает не работа
VM.

### Контроль плацебо для сценариев с замедлением

Чтобы отделить эффект изменений от эффекта раскладки, база `a590b73f`
собрана с правкой-плацебо ([placebo.patch](placebo.patch)): функции-заглушки
в `bsl-cli` и `bsl-vm`, вызываемые один раз при старте. Логика не меняется,
но код сдвигается на 32 байта по модулю 64 — так же, как у кандидата:
горячий цикл поиска `str_find` у базы стоит на 32 по модулю 64, у
кандидата и плацебо — на 0. Первое плацебо, сдвинувшее код ровно на
5 × 64 байта, раскладку по модулю 64 не меняло и дало около нуля
([placebo.summary.txt](placebo.summary.txt)) — поэтому контролем служит второе.

| Сценарий | база → плацебо, % | плацебо → кандидат, % | база → кандидат, % |
|---|---:|---:|---:|
| str_find plain / optimize | +8,49 / +6,59 | −1,01 / −1,59 | +7,35 / +8,01 |
| bmp_rotate plain / optimize | +4,12 / +3,82 | +8,38 / +0,76 | +5,56 / +1,76 |
| xml_write plain / optimize | +1,44 / +1,52 | +3,11 / +2,95 | +4,29 / +5,62 |
| goto_bench plain / optimize | +0,70 / +1,21 | — | −7,22 / −7,57 |

Данные: [placebo2.summary.txt](placebo2.summary.txt),
[placebo2-vs-cand.summary.txt](placebo2-vs-cand.summary.txt).

- **str_find** — эффект раскладки целиком: плацебо без изменения логики
  воспроизводит замедление, а против плацебо кандидат нейтрален. Сценарий
  на 73–79% стоит в `memcmp`, остальное — цикл поиска, положение которого
  и сдвинулось.
- **bmp_rotate optimize** — то же самое: замедление даёт сдвиг раскладки.
- **xml_write** (+3%) и **bmp_rotate plain** (+8%) против плацебо остаются
  медленнее, хотя инструкций у кандидата не больше (−0,1% и −2,5%).
  Горячие функции этих сценариев в плацебо и кандидате выровнены одинаково.
  Профиль `bmp_rotate` показывает, что у кандидата доля
  `drop_glue::<BslValue>` выше на 2,9 пункта, а доли `step` и
  `poll_linked` ниже: компилятор иначе решил, где встраивать освобождение
  значений внутри изменённого `step`. Это решение кодогенерации внутри
  изменённой функции, а не дополнительная работа; закрепить его с нашей
  стороны можно только переписав горячий путь, а не этой правкой.

### Независимая раскладка: сборка с указателями кадров

Те же два исходника (`a590b73f` и кандидат) собраны иначе — profiling с
`-C force-frame-pointers=yes` и тем же `-align-all-functions=5`. Логика
та же, раскладка кода другая. A/B по восьми копиям
([fp-build.summary.txt](fp-build.summary.txt)):

| Сценарий | release, % | frame pointers, % |
|---|---:|---:|
| bmp_rotate plain / optimize | +5,56 / +1,76 | −6,67 / −7,25 |
| xml_write plain / optimize | +4,29 / +5,62 | +1,65 / −0,59 (медиана +0,34 / 0,00) |
| str_find plain / optimize | +7,35 / +8,01 | −3,27 / +2,91 |
| goto_bench plain / optimize | −7,22 / −7,57 | −10,32 / −12,34 |

Выигрыш сценариев, упирающихся в цикл VM, сохраняется при другой
раскладке, а замедление `bmp_rotate` меняет знак, `xml_write` уходит в
шум. Значит, остаток, который release-сборка показывает против плацебо, —
свойство её конкретной раскладки, а не следствие изменений: правка
уменьшает работу во всех этих сценариях, а куда при этом ляжет код, от
неё не зависит.

### Отклонённая подстройка

Вынос медленной ветки `synchronize_frames` в `#[cold] #[inline(never)]`
функцию дал против кандидата `xml_write` −2…−3% и `bmp_rotate` optimize
−3…−4%, но `goto_bench` +5…+11% при неизменном числе инструкций и сильно
перекрывающемся разбросе копий
([rejected-cold-resize.summary.txt](rejected-cold-resize.summary.txt)).
Это перераспределение по раскладке, а не меньшая работа, поэтому правка не
принята. Тот же прогон показал и предел метода: два побайтно одинаковых
бинарника по шести копиям разошлись на goto_bench на 7%, потому что одна
копия легла на 689–728 мс. Скрипт теперь печатает и медиану по копиям.

Полный прогон драйвером из A/B 23 октября (по одной копии на сторону,
пути одной длины) — [results.md](results.md). Его числа для чувствительных
сценариев смещены, как показано ниже: например, goto_bench там +18%,
хотя инструкций на 20% меньше, а средняя по копиям −7%.

## Методика: время зависит от копии файла

Один и тот же бинарник, запущенный по разным путям, дал на `str_index`
+22…+24%, на `table_total` +11%, на `goto_bench` +6% при одинаковом числе
инструкций ([same-binary-two-paths.txt](path-bias/same-binary-two-paths.txt)).
Сдвиг стека переменной окружения разной длины этого не воспроизводит
([env-pad-sweep](path-bias/env-pad-sweep.summary.txt)). А побайтно
одинаковые копии по путям одной длины стабильно дают на `goto_bench`
500, 580 и 700 мс — время задаёт сама копия файла, вероятнее всего
физическое размещение её страниц кода.

Значит, чередующийся A/B с одной копией на сторону сравнивает две
случайные выборки из разброса до ±20%. Этим смещены и полный прогон этого
каталога, и [A/B 23 октября](../full-ab-2026-10-23/README.md) — в той
части выводов, где время менялось без изменения числа инструкций
(`str_index`, `pi_leibniz*`). Выводы по числу инструкций это не
затрагивает. [ab_sweep.py](ab_sweep.py) копирует каждую сторону N раз
в `/tmp/abbin/` и усредняет по копиям.
