# XML: резервирование имён и разделение фаз

Продолжение `../xml-utf8-2026-09-18/README.md`. Исходная сторона —
рабочее дерево после той правки, сохранённое отдельным release-бинарником.
Изменение затрагивает только внутренний `XmlParser::read_name` и его тест:
нового OpenSpec change, публичного API и зависимостей нет.

## Проверка предыдущей регрессии

В измерительную копию xml_parse добавлен таймер подготовки и вывод его
значения непосредственно перед штатным таймером чтения. Штатный benchmark
не изменён. В `previous-change-phases.csv` семь чередующихся пар старого
бинарника до UTF-8-оптимизации (`old`) и после неё (`utf8`):

| Фаза | old, среднее мс | utf8, среднее мс |
|---|---:|---:|
| Подготовка документа | 124,00 | 103,43 |
| Основной цикл чтения | 927,29 | 951,43 |

Итак, запись ускорилась, а регрессия локализована в чтении. Она не
объясняется дополнительным проходом преобразования входного документа:
этот путь уже был восстановлен в итоговом варианте предыдущего эксперимента.
По nm размеры step и step_cold совпадают (0xece7 и 0x7156), но адреса
сдвинуты на 0x440. Это основание проверить размещение кода/кэши, а не
доказательство причины: сравнение только размеров не сравнивает инструкции.

## Локальная оптимизация

Парсер хранит исходный текст как Vec<char>. read_name сканировал границы,
затем собирал String через collect с начальной ёмкостью по числу char.
На кириллице требовалось перевыделение. Теперь длина UTF-8 накапливается
в уже существующем цикле поиска границы. String создаётся точного размера;
дополнительного прохода для подсчёта нет. Тест проверяет ASCII, кириллицу,
трёх- и четырёхбайтовые символы, разделители и пустое имя.

Основной цикл xml_parse, измеренный alloc-profile:

| Метрика | До | После |
|---|---:|---:|
| Запросы памяти | 7 376 779 | 6 416 773 |
| Realloc | 1 736 731 | 776 725 |
| Суммарно запрошено байт | 568 472 104 | 555 812 038 |
| Пик живых запрошенных байт | 77 074 836 | 77 074 836 |

Удалено 960 006 realloc: около 55,3% оставшихся перевыделений. Учёт
отделяет подготовку от основного цикла, но включает постоянный небольшой
расход переключающих маркеров. Правила счётчика — в отчёте allocation-profile.

## A/B

Пять чередующихся пар release CLI, без измерительного allocator.
Для xml_parse используется копия с дополнительным таймером подготовки;
для остальных сценариев — исходные benchmark. Инструкции и такты относятся
ко всему процессу, время чтения — только к штатному циклу xml_parse.
В ab.csv parse_ms для writers означает время их штатного основного цикла,
prepare_ms=0 означает отсутствие отдельного измерения подготовки.

| Сценарий | Инструкции, среднее (диапазон), % | Такты, среднее (диапазон), % |
|---|---:|---:|
| json_write | 0,000 (−0,002…+0,002) | −1,87 (−3,84…−0,12) |
| xml_parse | −1,53 (−1,54…−1,50) | −2,66 (−3,74…−1,87) |
| xml_write | +0,006 (−0,019…+0,035) | −3,81 (−4,55…−2,66) |

Основной цикл чтения xml_parse ускорился в среднем на 2,24%
(−3,19…−1,28% времени). Контрольный вывод совпал во всех парах.
Writers не исполняют read_name; изменение их тактов не приписывается
сокращению аллокаций этой правкой. Полное устранение предыдущей регрессии
относительно old отдельным итоговым A/B не проверялось.

## Проверки

`cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`
и `cargo test --workspace` прошли, включая проверку plain/optimized и новый
тест имён. Первые попытки полного прогона прервала квота `/tmp`: сначала
при сборке в отдельном target, затем при записи временного байткода.
После удаления только временного каталога сборки повторный полный прогон
в основном target завершился с кодом 0.
