# XML: точная ёмкость UTF-8 вместо промежуточного Display

Исходное состояние — рабочее дерево после устранения копий `name_from` и
`value_from`, описанных в `../allocation-profile-2026-09-18/README.md`.
Сравниваются сохранённый release CLI до правки и release CLI после неё.
Профиль аллокаций снят примером `alloc-profile`, отдельно для подготовки
и основного цикла. Его счётчики и ограничения описаны в предыдущем отчёте.
RSS всего инструментированного процесса хранится отдельно в `*.rss` (KiB).

## Локализованный источник

`xml::need_str` использовал `BslString::to_string()`: Display сначала
декодирует UTF-16 в String, затем форматирование копирует его в результат.
Существующий `to_utf8_string()` сначала считает длину UTF-8, затем выделяет
точную ёмкость и декодирует непосредственно в возвращаемый String.
Этот путь применён к строковым аргументам XML-методов.

Для `ЧтениеXML.УстановитьСтроку` сохранён прежний путь конверсии целого
документа. В первоначальном эксперименте замена и этой конверсии снизила
инструкции xml_parse на 0,52%, но такты выросли в среднем на 5,18%
(+0,85…+17,50%). Дополнительный проход для подсчёта длины — возможное,
но не изолированно доказанное объяснение. Сырые пары этого промежуточного
варианта — `ab-all-conversions.csv`; итоговый вариант измерен в `ab.csv`.

## Аллокации итогового варианта

| Фаза | Запросов до → после | Realloc до → после | Суммарно запрошено байт до → после |
|---|---:|---:|---:|
| xml_write: run | 7 076 860 → 4 050 145 | 1 436 777 → 30 065 | 330 203 296 → 286 664 482 |
| xml_parse: prepare | 2 359 111 → 1 350 206 | 478 940 → 10 036 | 110 148 469 → 95 635 531 |
| xml_parse: run | 7 376 779 → 7 376 779 | 1 736 731 → 1 736 731 | 568 472 104 → 568 472 104 |

Счётчики json_write не изменились. Пики живых выделений не изменились
ни в одном сценарии. У xml_write удалены 3 026 715 запросов и
1 406 712 realloc (около 98% перевыделений), без нового пула или арены.
В основном цикле xml_parse эти realloc не устранены: его внутренний
парсер требует отдельного исследования.

Контрольные строки до/после совпали во всех трёх сценариях, исключалась
только последняя строка времени. Добавлена проверка преобразования XML-
аргументов для пустой строки, NUL, кириллицы, суррогатной пары и одиночных
суррогатов. Публичные API, bytecode и семантика объектов не меняются;
это внутренний рефакторинг без нового OpenSpec change.

## A/B итогового варианта

Пять чередующихся пар обычных release CLI без счётчика аллокаций.
Среднее отношение after/before − 1, в скобках диапазон пар:

| Сценарий | Инструкции | Такты |
|---|---:|---:|
| json_write | −0,001% (−0,004…+0,000%) | +0,89% (−1,87…+2,35%) |
| xml_parse | −2,14% (−2,16…−2,13%) | +3,75% (+2,51…+5,27%) |
| xml_write | −17,67% (−17,71…−17,64%) | −20,50% (−22,86…−19,20%) |

XML-запись ускорилась; JSON не даёт значимого результата. У xml_parse
общий счётчик включает подготовительную запись документа: именно она
сократилась, тогда как основной цикл сохранил число запросов памяти.
Рост тактов xml_parse сохранился даже после возврата прежней конверсии
входа; следовательно, объяснение только двойным проходом по документу
недостаточно. Регрессия в этом замере зафиксирована, её причина не
изолирована. Изменение укладки машинного кода и кэш-поведение — гипотезы,
а не вывод из имеющихся счётчиков. Общего ускорения всех XML-сценариев
этот эксперимент не доказывает.
