# Преобразование файлового представления в буфере строки

## Решение

После сериализации `String::into_bytes` передаёт владение прежним буфером.
После подсчёта LF вектор расширяется под CRLF и BOM; непересекающиеся
с исходным непрочитанным префиксом фрагменты сдвигаются справа налево
через безопасный `copy_within`. Одиночный CR и превращение уже имеющегося
CRLF в CRCRLF сохранены, как у прежнего `split('\n')`.

Host по-прежнему получает один `FileSystem::write` после полной успешной
сериализации. Изменение не переводит запись на дескрипторы, не вводит
частичную запись при ошибке сериализации и не обещает атомарность файла.
BSL API, публичный Rust API, формат и маркеры совместимости не изменены.
Это внутренний рефакторинг; новый OpenSpec change не требуется.

## Память

Полный table_save_load, существующий пример alloc-profile. Подготовка
отделена маркерами в копиях `target/table-allocation-study/`; файл пишется
туда же, а не поверх существующего `/tmp/open-bsl-bench-vt-save.txt`.

| Показатель | До | После |
|---|---:|---:|
| Сохранение: запросы памяти | 212 | 210 |
| Сохранение: realloc | 28 | 27 |
| Сохранение: суммарно запрошено байт | 801 978 473 | 416 199 407 |
| Сохранение: пик живых байтов | 830 406 653 | 645 486 014 |
| Сохранение + загрузка: запросы | 1 140 875 | 1 140 873 |
| Сохранение + загрузка: суммарно запрошено байт | 1 462 787 192 | 1 077 008 126 |
| Сохранение + загрузка: пик живых байтов | 884 490 887 | 884 490 887 |

Пик включает исходную таблицу и не является RSS; счётчик не видит
внутренний пик System при переносе realloc. Суммарно запрошенные байты
считают полный новый размер realloc, а не прирост. Пик сохранения
снизился на 184 920 639 байт; пик всего сценария не изменился, поскольку
его определяет загрузка. Подготовительные счётчики совпали.
Логи: `before-save.log`, `alloc-save.log`, `before-save-load.log`, `alloc.log`.
Время инструментированных запусков не считается результатом A/B.

## Методика A/B

База — release после прямой сериализации чисел,
`target/table-number-write-after/bsl-cli`. Кандидат —
`target/table-file-buffer-after/bsl-cli`. Штатное выравнивание из
`.cargo/config.toml`, обычные release-сборки. По три чередующиеся пары
на каждый из трёх табличных сценариев в plain/optimize: 36 запусков.
Во время A/B агент не запускает сборки и тесты.

`ab.py` сверяет код выхода, счётчик perf, контрольный текст без таймеров
и SHA-256 выходного файла. Время — последняя строка benchmark;
инструкции относятся ко всему процессу, включая генерацию и проверку.
Диапазон пар не является доверительным интервалом. Внешняя нагрузка
машины не фиксировалась.

## Результаты A/B

Все 36 запусков прошли, контрольный вывод совпал, сохранённые файлы
совпали по SHA-256. Сырые значения — [ab.csv](ab.csv), дельты —
[ab.log](ab.log), хэши бинарников — [binaries.sha256](binaries.sha256).
Дельта — среднее попарное после/до − 1; минус означает снижение стоимости.

| Сценарий | Режим | Время, % | Диапазон пар, % | Инструкции, % |
|---|---|---:|---:|---:|
| table_compare | plain | +0,71 | −0,96…+2,67 | +0,008 |
| table_compare | optimize | +2,11 | +0,82…+3,75 | −0,012 |
| table_compare2 | plain | −3,79 | −7,04…+0,63 | −0,005 |
| table_compare2 | optimize | +2,94 | +2,20…+3,31 | +0,013 |
| table_save_load | plain | −1,14 | −1,77…−0,15 | +2,505 |
| table_save_load | optimize | −1,50 | −4,05…+0,07 | +2,538 |

Отдельная фаза сохранения по stdout: plain −3,68%
(−7,60…+2,25), optimize −6,30% (−7,50…−4,97). Надёжное ускорение
plain-сохранения и optimized-суммы не утверждается: диапазоны пересекают
ноль. В optimize оба контрольных сравнения замедлились на 2–3%, хотя
их инструкции практически не изменились; причина не установлена.
Это не объявляется отсутствием побочных регрессий.

Правка оставлена как оптимизация памяти с явной ценой: дополнительные
проходы по байтам увеличили число инструкций всего table_save_load на
2,5%. Пик сохранения уменьшился на 185 МБ, но общий пик сценария прежний.
Следующий предмет исследования — память загрузки; в этой серии её
реализация не менялась.

## Функциональные проверки

Тест `file_bytes_preserves_the_existing_bom_and_lf_expansion` прошёл
на прежнем преобразовании до замены алгоритма и после неё. Он проверяет
пустой текст, отсутствие LF, соседние/крайние LF, Unicode, одиночный CR,
уже существующий CRLF и BOM в данных, с запасом ёмкости и без него.
Прежний `file_pair_matches_the_platform_byte_for_byte_and_round_trips`
остаётся платформенным оракулом. Новые платформенные предположения
не добавлены.

`cargo test --offline --workspace` прошёл, включая conformance и
`the_optimizing_passes_agree_with_the_plain_run_on_every_script`;
штатные пропуски и недоступные закрытые данные не объявляются измеренными.
`cargo clippy --offline --workspace --all-targets -- -D warnings`,
`cargo fmt --all -- --check` и `git diff --check` прошли.
Логи: `tests.log`, `clippy.log`, `build.log`.
