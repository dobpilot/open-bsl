# Аллокации JSON/XML и первый эксперимент

Исследовано рабочее дерево над `1335406cba2d957999fd4a254b819da976ce66f4`
после предварительной проверки linked call-site. Новых аллокаторов и CoW
для ссылочных объектов в продукт не добавлено.

## Методика

`cargo run --release -p open-bsl --example alloc-profile -- benchmarks/xml_parse.bsl`
запускает тот же сценарий через Engine. В измерительную копию исходника
добавляются два сообщения-маркера у границ внутреннего таймера.
Output-приёмник переключает счётчики: `prepare` включает связывание и
подготовку документа, `run` — основной цикл. Компиляция исключена из
счётчиков запросов. Benchmark-файлы не изменены.

Обёртка над System учитывает успешные alloc/realloc; requested_bytes содержит
полный новый размер каждого realloc, а не только прирост. Гистограмма
содержит непересекающиеся диапазоны 0–16, 17–32, 33–64, 65–128, 129–256,
257–512 и >512 байт. Она считает запросы, включая realloc, а не уникальные
объекты или времена их жизни. Основа счётчика — подход из тестов value_graph.

live_bytes и peak_live_bytes — запрошенные Rust-аллокациями живые байты
всего процесса, включая ранее созданные Engine, module и State. Внутренний
пик System во время переноса realloc, служебные заголовки allocator и
не-Rust выделения не учитываются. RSS из `/usr/bin/time` относится ко всему
инструментированному процессу; это не RSS отдельно для фазы. Последняя строка
файлов `*.csv` содержит max_rss_kib и не является строкой основной CSV-таблицы.
Сами маркеры добавляют небольшой постоянный расход. Время инструменти-
рованного исполнения не используется для оценки ускорения.

## Устранение промежуточных XML-копий

В `name_from` и `value_from` данные текущего события раньше копировались
в String, затем преобразовывались в BslString. Теперь конверсия читает &str
под существующим заимствованием состояния. Возвращаемая BSL-строка остаётся
самостоятельным значением, порядок и содержимое результатов сохранены.

Основной цикл xml_parse: 7 376 779 запросов вместо 7 976 782
(−600 003, примерно −7,52%); 568 472 104 запрошенных байт вместо
576 272 170 (−7 800 066). Пик живых байт остался 77 074 836.
JSON/XML writers не изменили счётчики. Снижение RSS одного запуска
с 69 716 до 68 816 KiB не рассматривается как доказанный выигрыш.

Пять чередующихся A/B-пар обычных release CLI без измерительного allocator
сохранены в `ab.csv`. Обе стороны используют одинаковые флаги сборки.
У xml_parse весь процесс, включая подготовку, выполняет в среднем на
0,65% меньше инструкций (диапазон −0,68…−0,63%). Такты нестабильны:
−1,97…+13,08%; ускорение по времени не подтверждено. Контрольный вывод
совпал после исключения последней строки с временем.

## Решение по аренам и CoW

Следующий обоснованный эксперимент — повторное использование небольших
буферов и изучение происхождения realloc в XML. Счётчики показывают спрос
на небольшой размер, но ещё не дают распределения по типам объектов,
стекам и срокам жизни. Для выбора классов пула потребуется именно это.

Пул оболочек BSL-объектов не перехватит автоматически внутренние Vec/String.
Арену, сохраняющую все временные данные до конца запуска, эти измерения
не оправдывают: накопленный объём существенно выше живого пика.
Прототип пула должен сохранять индивидуальное освобождение и деструкторы;
отдельно нужно проверить длительную сессию, удержание значения host и
несколько исполнений. Существующие Rc и строковый append уже разделяют
данные; CoW при присваивании массивов/структур нарушит ссылочную семантику.

Изменение модели владения или component ABI потребует OpenSpec proposal.
Текущее измерение и устранение промежуточной копии — внутренние изменения
без нового публичного контракта и зависимости.
