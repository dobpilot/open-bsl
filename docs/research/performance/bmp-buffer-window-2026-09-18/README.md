# Одно выделение вместо двух для окна двоичного буфера

## Изменение

`BslObject::BinaryBuffer` содержит непосредственно `RefCell<BinBufData>`.
Убрана внутренняя `Rc`-обёртка, внешнее владение объектом и разделение
массива байтов между окнами сохранены. Арены, CoW, новые зависимости и
изменения VM dispatch не вводятся.

Это изменение поля публичного Rust-варианта: потребитель, клонировавший
внутренний Rc, должен удерживать BslValue. Методы `binary_buffer_*` не
меняются; BSL API и измеренная семантика остаются прежними.

## Аллокации

Измерение существующим `alloc-profile` отдельно от проверки скорости:

```sh
cargo run --offline --release -p open-bsl --example alloc-profile -- benchmarks/bmp_rotate.bsl
```

| Измеряемая часть bmp_rotate | До | После |
|---|---:|---:|
| Запросы, включая realloc | 480 037 | 240 031 |
| Realloc | 1 | 1 |
| Суммарно запрошенные байты | 42 241 439 | 28 801 103 |
| Пик живых запрошенных байтов, не RSS | 3 962 241 | 3 962 122 |
| sizeof(BslValue) | 24 | 24 |
| sizeof(BslObject) | 88 | 88 |

Удалено 240 006 запросов по 56 байт: 240 000 окон пикселов и шесть
остальных объектов буфера. Суммарный объём уменьшился на 13 440 336 байт.
Пик практически не изменился: временные окна и прежде освобождались,
а массивы изображений остались прежними. Разница малых постоянных
накладных расходов не интерпретируется как экономия памяти изображений.

Сырые результаты: [до](before-alloc.txt), [после](after-alloc.txt).
Инструментированное время не используется как результат A/B.

## Методика A/B

База — незакоммиченный снимок текущей ветки из
`target/flamegraphs/after-allocations-2026-09-18/current-src`, не main.
До правки `diff -qr` подтвердил совпадение всех исходников crates.
Кандидат — текущее дерево после удаления внутреннего Rc. Оба бинарника
собраны release, без RUSTFLAGS/CARGO_ENCODED_RUSTFLAGS и с одинаковым
выравниванием из `.cargo/config.toml`; кандидат сохранён отдельно в
`target/bmp-buffer-window-after/bsl-cli`.

[ab.py](ab.py) выполняет пять чередующихся пар в plain/optimize для
bmp_rotate и контрольных json_write/xml_parse/xml_write. Сверяется весь
вывод, кроме последнего таймера. Последний таймер — время измеряемой
части BSL, `instructions:u` — весь процесс, включая контрольную сумму
после таймера. Поэтому знаменатели времени и инструкций различаются.
Числовые дельты — среднее попарное после/до − 1; диапазон пар не является
доверительным интервалом. Нагрузка и частота CPU не фиксируются.

Полный benchmark-корпус этим локальным экспериментом не заменяется.

## Результаты A/B

Все 80 запусков завершились успешно, контрольный вывод совпал между
сторонами и режимами. Сырые значения — [ab.csv](ab.csv), итоговые дельты —
[ab.log](ab.log), хэши — [binaries.sha256](binaries.sha256).

| Сценарий | Режим | Время, среднее % | Диапазон времени, % | Инструкции, среднее % |
|---|---|---:|---:|---:|
| bmp_rotate | plain | −7,96 | −30,36…+1,79 | −0,9071 |
| bmp_rotate | optimize | −1,78 | −4,97…+3,89 | −0,9964 |
| json_write | plain | +15,92 | −25,34…+94,53 | −0,0014 |
| json_write | optimize | −9,62 | −36,47…+21,50 | −0,0016 |
| xml_parse | plain | +3,42 | −4,07…+10,19 | +0,0009 |
| xml_parse | optimize | +13,80 | −9,82…+58,70 | +0,0002 |
| xml_write | plain | −2,54 | −12,86…+5,48 | −0,0293 |
| xml_write | optimize | −2,42 | −7,69…+0,32 | +0,0042 |

Во время прогона внешняя нагрузка выросла: `uptime` показал load average
13,96 / 9,52 / 7,29. Других сборок или тестов этого агента при A/B не было.
Все диапазоны времени пересекают ноль; уверенное ускорение по времени
не установлено. Особенно нельзя интерпретировать средние JSON/XML как
регрессию или выигрыш: разброс огромен, число инструкций почти неизменно.

У bmp_rotate диапазоны дельт инструкций узкие: plain
−0,9077…−0,9067%, optimize −0,9970…−0,9957%. Подтверждены сокращение
аллокаций почти вдвое и уменьшение вычислительной работы около 1%.
Это не доказательство, что следующий пул даст сопоставимый выигрыш:
оставшаяся доля CPU в allocator отдельно не измерена.

Правка оставлена без добавления allocator. Следующий возможный шаг —
профиль стоимости оставшихся выделений, а не внедрение нескольких арен.

  корпуса и закрытые данные `OPEN_BSL_TABLE_COMPARE2_CASES` не заменены
  новыми оракулами.
