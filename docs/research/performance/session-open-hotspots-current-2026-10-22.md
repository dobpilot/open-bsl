# Hotspot открытия сеанса после исправлений, 22 октября 2026

Свежий профиль показывает два разных крупных участка: повторную подготовку
метаданных в UNF и семантический анализ с обработкой имён в BUH. Линейные
обходы коллекций метаданных после индексации перестали быть крупным hotspot.
Это исследование текущей версии, без изменений исполнения и без обещания
нового ускорения.

## Условия и достоверность

Один последовательный запуск UNF, затем BUH, затем DEMO. PostgreSQL,
`thin-client`, версия платформы в контексте `8.3.27.2342`, SDK 0.9.39.
Исполняется исходный модуль сеанса конфигурации и контрольный сценарий.
Защищённые модули остаются в согласованном режиме заглушек экспортов:
результат не доказывает исполнение их оригинальных тел.

Использован неизменяемый release-бинарник
`bsl-cli-session-hotspot-fixes-final22-1021`, SHA-256
`1e4bc9c3fe309193f7be79d01642162d89bc47306745fad514f90464bdf9592e`.
Перед запуском проверены хеши исходников из сохранённого build receipt,
после каждого запуска — неизменность бинарника. Все три процесса завершились
кодом 0 и выдали `configured.cli.startup=ok`. Операции SDK с базами — read-only;
файловая система процесса смонтирована read-only, временные файлы — в tmpfs.

`perf record`: `cycles:u`, 199 Hz, DWARF, стек 8192 байта; одновременно
`perf stat` и существующие фазовые таймеры. Границы профиля открытия —
получение `cli.resources` и `cli.session_open` в stderr, с отступом 10 мс
внутрь с каждой стороны. Вложенные таймеры собраны только между этими
границами. Доли ниже — **self sampled cycles внутри открытия**, не доли
wall time и не inclusive стоимость вызывающего кода. Одинаковые
деманглированные имена символов суммированы.

По одному запуску достаточно для обнаружения крупных hotspot, но недостаточно
для заявления об ускорении или устойчивых различиях в несколько процентов.
Для будущей оптимизации требуется чередующийся A/B. Предыдущий такой замер
сохранён в [отчёте исправлений](session-hotspot-fixes-2026-10-22.md).

## Время и память

Секунды, под профилировщиком. Столбцы фаз — отдельные существующие таймеры;
«весь процесс» включает также запуск, завершение и накладные расходы измерения.

| Фаза | UNF | BUH | DEMO |
|---|---:|---:|---:|
| Получение конфигурации `cli.acquire` | 2,470 | 2,824 | 0,905 |
| Декодирование `cli.decode` | 3,337 | 2,332 | 1,203 |
| Подготовка доступа `cli.access` | 0,020 | 0,041 | 0,010 |
| Фабрика `cli.factory` | 0,477 | 0,846 | 0,169 |
| Ресурсы сеанса `cli.resources` | 0,004 | 0,004 | 0,003 |
| **Открытие сеанса `cli.session_open`** | **10,178** | **6,538** | **3,140** |
| Контрольный сценарий `cli.execute` | 0,207 | 0,221 | 0,157 |
| Весь процесс | 17,34 | 13,34 | 5,94 |
| CPU процесса между границами открытия | 9,90 | 7,22 | 3,24 |
| Наблюдаемый VmHWM, МиБ | 700,5 | 697,3 | 253,4 |

CPU включает потоки процесса и может превышать wall time. VmHWM читается раз
в две секунды: последний пик перед завершением мог не попасть в наблюдение.
Это не профиль аллокаций. Переменная `OPEN_BSL_PREPARE_THREADS=2` сохранена
как в предыдущих измерениях; индексированный путь подготовки сериализован,
значение переменной не доказывает его параллельного исполнения.

## Какие работы занимают открытие

Суммы таймеров и число их срабатываний. Число подготовок модулей — число
срабатываний фазовых таймеров, не размер всего каталога конфигурации.

| Работа | UNF | BUH | DEMO |
|---|---:|---:|---:|
| Runtime metadata | 1,502 с / 17 | 0,496 с / 12 | 0,238 с / 8 |
| Полный query-ready snapshot | 2,330 с / 11 | 0,782 с / 8 | 0,493 с / 6 |
| Эти два этапа вместе | **3,831 с** | **1,278 с** | **0,732 с** |
| Получение дополнительных ресурсов метаданных | 0,317 с | 0,097 с | 0,065 с |
| Приём ресурсов в кэш разбора | 0,027 с | 0,010 с | 0,005 с |
| Чтение исходников модулей | 0,061 с | 0,074 с | 0,024 с |
| Разбор BSL | 0,332 с / 99 | 0,440 с / 105 | 0,200 с / 57 |
| Семантический анализ BSL | **1,451 с / 99** | **2,265 с / 105** | **0,857 с / 57** |
| Компиляция | 0,048 с | 0,059 с | 0,027 с |
| Проверка байткода | 0,194 с | 0,238 с | 0,077 с |

Не следует складывать все вложенные таймеры в одну «точную декомпозицию»:
области могут включать другую работу. Runtime и полная финализация — отдельные
последовательные вызовы; их сумма полезна для оценки этого участка.

В UNF эти две подготовки метаданных занимают около 37,6% открытия, в BUH —
19,5%, в DEMO — 23,3%. В BUH семантический анализ занимает около 34,6%,
в UNF — 14,3%, в DEMO — 27,3%.

Причина повторов видна в
[`indexed_metadata.rs`](../../../crates/bsl-config-db/src/indexed_metadata.rs):
при росте набора ресурсов сбрасываются runtime facts и полный snapshot;
`runtime_metadata` вызывает `resolve_runtime`, а явный запрос
`metadata_snapshot` затем вызывает полный `resolve`. Кэш распакованных
ресурсов уже работает, но нормализация накопленного состава при этих вызовах
по-прежнему повторяется. Разделение runtime/query убрало ненужную
query-финализацию из чистого ORM-пути, а не превратило весь resolver в
инкрементальный алгоритм по добавленным объектам.

## Горячие символы открытия

Проценты self sampled cycles; строки таблицы не являются независимыми
продуктовыми фазами и не объясняют весь профиль.

| Символ / операция | UNF | BUH | DEMO |
|---|---:|---:|---:|
| `memmove` | 10,28% | 7,07% | 6,76% |
| `memcmp` | 7,04% | 5,08% | 7,14% |
| `_int_malloc` | 5,63% | 3,32% | 3,45% |
| `snapshot_fingerprint::Fingerprint::write_str` | **5,59%** | **2,79%** | **4,37%** |
| Unicode alphabetic lookup | 4,31% | **11,00%** | **9,26%** |
| Unicode conversions lookup | 4,87% | **6,49%** | **7,30%** |
| `bsl_rt::fold::folded_eq` | 0,29% | **9,60%** | **2,43%** |
| SipHash `Hasher::write`, сумма экземпляров символа | 3,83% | 3,50% | 4,64% |
| `recase_postgres_identifier` | 2,34% | 1,14% | 2,08% |
| `index_custom_field_names` | 1,12% | 0,64% | 2,85% |

Fingerprint действительно остаётся горячим: SDK хеширует содержимое через
`Debug`-форматирование и `fmt::Write`, включая схему, таблицы, объекты, поля,
значения и индексы. Это конкретная работа полного снимка, подтверждённая
исходником SDK `src/metadata/resolve.rs`, `snapshot_fingerprint`.
Убирать или менять fingerprint без проверки его контракта нельзя.

Высокая стоимость Unicode и `folded_eq` подтверждает остаточные затраты на
имена. Однако неполные стеки не позволяют приписать все Unicode-вызовы
одному резолверу, а все `memmove` и аллокации — копированию метаданных.
Профиль не измеряет объём выделенных байтов и не доказывает утечку RAM.

`MetadataCollection::collection_len` в свежих сэмплах не встретился;
`get_index` — 0,05% в UNF и 0,07% в BUH, `positions` — 0,06% в BUH
и 0,16% в DEMO. Отсутствие сэмпла не означает нулевую стоимость, но прежнего
крупного hotspot обхода коллекций здесь больше нет.

Отдельно фабрика остаётся преимущественно в `folded_eq`: 81,69% её сэмплов
в UNF, 84,53% в BUH, 55,91% в DEMO. Это другой временной интервал, его
проценты нельзя складывать с таблицей открытия. Абсолютная длительность
фабрики уже мала относительно открытия; короткие окна дают меньше сэмплов.

## Приоритет дальнейшей работы

1. **UNF: повторная нормализация метаданных.** Проверить возможность повторного
   использования уже построенных runtime facts при полной финализации и
   приращении состава. Сейчас измерены 17 runtime и 11 полных построений;
   это конкретная повторяемая работа. Изменение требует отдельного контракта
   SDK, сохранения эквивалентности полных снимков и A/B.
2. **BUH: семантический анализ и сравнение имён.** Сначала получить надёжную
   атрибуцию вызывающих мест `folded_eq`, затем заменять повторные поиски
   индексами там, где они действительно остались. Не менять Unicode-семантику
   сравнения и не считать все Unicode-функции одной причиной.
3. **Полный snapshot: fingerprint и query-индексы.** Проверить повторное
   использование на неизменном составе и необходимость каждого явного
   запроса полного снимка. Прямой self fingerprint — несколько процентов,
   поэтому его одного недостаточно для большого кратного ускорения.
4. **Копирование и аллокации.** Для доказательства владельцев затрат нужен
   отдельный профиль с надёжными стеками либо узкие таймеры/счётчики.
   Текущие `memmove` и malloc показывают стоимость, но не её владельца.

Код в рамках этого исследования не менялся. Ни один из этих пунктов пока
не является реализованной оптимизацией.
