# Четыре направления ускорения открытия сеанса, 22 октября 2026

Продолжение [профиля после предыдущих исправлений](session-open-hotspots-current-2026-10-22.md).
Все четыре направления исследованы и реализованы в измеренных горячих местах.
Три чередующиеся пары обычных release-сборок подтвердили ускорение открытия
на 22–33%. Это не двадцатикратное ускорение всего процесса.

## Что изменено

### 1. Повторная нормализация метаданных

SDK 0.9.40 позволяет финализировать полный снимок из уже готовых
`RuntimeMetadataFacts`. `bsl-config-db::metadata_snapshot` передаёт текущие
факты в `ConfigurationMetadataCache::finalize_runtime`, вместо повторного
`resolve` на тех же ресурсах. Перед публикацией сохранена проверка актуальности
фактов относительно состояния провайдера.

Новый состав по-прежнему нормализуется: алгоритм не заявляется как resolver
только по дельте новых объектов. Устранён второй проход нормализации того же
состава при переходе от ORM к полному query-ready snapshot. Кэш разбора
ресурсов, явное приобретение зависимостей и строгие ошибки сохранены.

Повторное использование при росте проверено отдельно: старый опубликованный
снимок удерживает прежние коллекции, новый состав получает новые facts;
неизменный состав переиспользует прежний `Arc`. Простое дописывание новых
объектов в нормализованный результат не выбрано: разрешение именованных типов,
ссылок, разделителей и наложение расширений связывает несколько описателей.
Оно требует отдельной модели зависимостей и инвалидирования прежних связей.
В этом изменении сохранена полная нормализация один раз на новый состав,
вместо небезопасного обещания O(дельта).


### 2. Сравнение имён и анализ исходников

Новый профиль с frame pointers показал, что крупный `folded_eq` в BUH
принадлежит прежде всего `EngineBuilder::build` в фоновом работнике:
119 из 128 сэмплов с листом `folded_eq` имеют этот кадр. В контрольном
профиле окончательной версии найдено 16 таких листьев, без этого кадра.
Проверка каждого владельца контекста обходила все модули, затем предыдущие
контексты. Теперь один хеш-индекс имён и отдельные множества владельцев
проверяют принадлежность и дубли за O(M+C) ожидаемого времени вместо
O(M×C+C²), без изменения порядка ошибок и Unicode-свёртки.

В лексере повторяющееся написание идентификатора проверяется по таблице
ключевых слов один раз на исходник: кэш заимствует срезы текста, не копирует
их. Быстрые проверки ASCII и русских букв обходят Unicode-таблицы; остальные
символы используют прежние предикаты. Эквивалентность обоих предикатов
проверена для каждого допустимого Unicode scalar, а не только русских примеров.
Порядок разрешения имён BSL и реализация `folded_eq` не менялись.

### 3. Полный snapshot, fingerprint и query-индексы

Повторный запрос неизменного состава использует прежний `Arc<MetadataSnapshot>`.
Константная функциональная опция больше не финализирует промежуточный снимок
перед приобретением самой константы: её чтение получает нужный снимок своего
объекта. Для параметризованного источника полный снимок по-прежнему получается
перед подготовкой плана. Права, разделение данных и ошибки чтения не заменяются
пустыми значениями.

Fingerprint и query-индексы строятся для реально необходимого нового полного
снимка. Во всех трёх контрольных прогонах количество финализаций осталось прежним:
11 / 8 / 6 для UNF / BUH / DEMO. Перенос константной опции устраняет лишний
запрос API, но на этих трассах тот запрос попадал в тёплый кэш, поэтому
снижение числа построений не заявляется. Основной эффект здесь — исключение
повторной нормализации и копирования внутри каждой финализации.

Сам алгоритм fingerprint и его байты сохранены. SDK проверяет
эквивалентность полных фактов, порядка, диагностик и fingerprint на четырёх
последовательно растущих составах каждой из DEMO, BUH и UNF.

### 4. Копирование и аллокации

Получена отдельная диагностическая сборка с frame pointers, таблицами
раскрутки и debug=1, а также выборочные стеки malloc/calloc/realloc через
`LD_PRELOAD`. Она не используется для заявления об ускорении обычного release.
В BUH известен второй кадр у 1617/1711 CPU-сэмплов, вместо 166/1566 в прежнем
профиле. Это существенно улучшает атрибуцию, но не доказывает полноту каждого стека.

Подтверждены и исправлены три конкретных владельца затрат:

- Обновление частей одного документа, бизнес-процесса, обработки или отчёта
  пересоздавало описания частей всех владельцев. Теперь создаются только
  описания изменяемого владельца; остальные `Arc` сохраняются вместе с порядком.
- Нормализованные описатели, объекты, значения и вспомогательные индексы SDK
  разделяются через приватные `Arc`. Старые опубликованные снимки неизменны;
  полного глубокого копирования всего состава для финализации больше нет.
- Стабильная сортировка перемещала большие `ConfigDescriptor` многократно.
  SDK сортирует индексы и затем применяет перестановку с O(N) обменов больших
  значений. Исходный порядок одинаковых ключей сохранён и проверен сравнением
  с прежней стабильной сортировкой.

Исходный диагностический счётчик между первым и последним сэмплом открытия:

| База | Вызовы аллокатора | Сумма запрошенных байтов |
|---|---:|---:|
| UNF | 73 539 584 | 10 568 437 496 |
| BUH | 36 737 024 | 6 710 181 666 |
| DEMO | 18 444 288 | 3 357 167 599 |

Это оборот запросов malloc/calloc/realloc, включая realloc, не объём живой RAM.
Внутренние аллокации самого диагностического обработчика исключены; другие
точки входа вроде `posix_memalign` не перехватываются. Границы счётчиков —
первый/последний сэмпл внутри открытия, поэтому крайние участки окна пропущены.
Стек снимается на каждом 4096-м вызове и дополнительно для запросов ≥1 МиБ;
добавочные крупные запросы не включаются в распределение регулярной выборки.
Выборка систематическая, не случайная: её доли не объявляются точной оценкой
процента всех аллокаций.

Окончательная диагностическая сборка с тем же аллокатором дала:

| База | Вызовы до → после | Запрошенные байты до → после | Снижение байтов |
|---|---:|---:|---:|
| UNF | 73.54 → 43.32 млн | 10.57 → 6.83 ГБ | 35.4% |
| BUH | 36.74 → 26.27 млн | 6.71 → 5.54 ГБ | 17.5% |
| DEMO | 18.44 → 15.75 млн | 3.36 → 2.94 ГБ | 12.6% |

Эти числа относятся к тем же границам сэмплирования, а не к полному
жизненному циклу процесса. Прогоны атрибуции выполнялись при работающем
SDK-наборе тестов: их wall time не используется для вывода об ускорении.

В регулярной выборке UNF 5524 из 17955 стеков содержали `owner_types`.
После исправления — 93 из 10578 регулярных сэмплов (точное число сохранено в JSON).
Это конкретное доказательство повторной генерации типов, а не предположение
по символу malloc. Категории по стеку могут пересекаться.

## Проверки и измерение

Обычный production baseline: SHA-256
`1e4bc9c3fe309193f7be79d01642162d89bc47306745fad514f90464bdf9592e`, SDK 0.9.39.
Кандидат: SHA-256
`ebabc9629d2660e765e57c47d2fe8b822075505ca7d23fcd7afb7db97f8c10bd`, SDK 0.9.40.
Сборки имеют одинаковое обычное release-выравнивание функций, без
диагностического аллокатора. Каждый реальный CLI запускается последовательно.

Три чередующиеся пары по каждой базе, всего 18 запусков. Между сторонами
не работали наши тесты, сборки или SDK-бенчмарки. Во всех случаях код 0,
контрольный сценарий успешен, stdout побайтово одинаков внутри каждой базы,
хеши бинарников не менялись. Защищённые экспорты — в прежнем согласованном
режиме заглушек; исполнение их исходных защищённых тел этими измерениями
не доказывается.

Медианы секунд и фактические диапазоны трёх запусков:

| База | Открытие до → после | Диапазон до | Диапазон после | Снижение |
|---|---:|---:|---:|---:|
| UNF | 10.281 → 6.868 | 10.039–10.328 | 6.859–6.899 | 33.2% |
| BUH | 6.567 → 4.690 | 6.518–6.604 | 4.675–4.772 | 28.6% |
| DEMO | 3.147 → 2.466 | 3.117–3.191 | 2.465–2.492 | 21.6% |

| База | Весь процесс до → после, с | Фабрика до → после, с | Инструкции до → после, млрд | Снижение инструкций |
|---|---:|---:|---:|---:|
| UNF | 17.04 → 13.04 | 0.481 → 0.119 | 150.982 → 109.523 | 27.5% |
| BUH | 12.94 → 10.24 | 0.841 → 0.148 | 141.533 → 87.017 | 38.5% |
| DEMO | 5.74 → 4.89 | 0.165 → 0.071 | 53.833 → 41.800 | 22.4% |

Во всех девяти отдельных парах кандидат быстрее по открытию; диапазоны
сторон не пересекаются. Инструкции посчитаны по всему процессу `perf stat
instructions:u`, а не только по окну открытия. Три пары не заменяют
доверительный интервал большой выборки; приведены сами наблюдаемые диапазоны.

Наблюдаемый VmHWM с чтением раз в две секунды:

| База | До → после, МиБ |
|---|---:|
| UNF | 699.6 → 651.9 |
| BUH | 694.6 → 677.3 |
| DEMO | 253.3 → 290.5 |

Редкое чтение дало ложный сигнал роста DEMO: последний опрос эталона шёл
до его позднего пика. Дополнительно выполнены три чередующиеся пары DEMO,
опрос каждые 50 мс и `/usr/bin/time` непосредственно над CLI внутри bwrap.
Медиана `%M` (kernel ru_maxrss) **330.0 → 308.1 МиБ**,
то есть **−6.6%**; диапазоны
329.6–330.1 и
307.3–308.4 МиБ.
Высокочастотный VmHWM также снизился:
332.0 → 310.2 МиБ.
Показания VmHWM и rusage сохранены раздельно; требование их строгого равенства
в первоначальном wrapper оказалось неверным. Первые диагностические попытки
не засчитаны как завершённые пары; успешные шесть запусков находятся в
`memory-check-v3`. Их времена не добавляются к основному A/B.

Снижение запрошенных байтов не объявляется автоматически снижением пика RAM:
это разные метрики. Для UNF/BUH таблица выше остаётся наблюдаемым VmHWM,
без заявления о точном максимуме всего жизненного цикла.

### Регрессия и границы

- Root: **4044 passed, 0 failed, 1 штатный ignored**, полный workspace.
- SDK: **1166 passed, 0 failed, 13 прежних ignored**, полный последовательный
  прогон на окончательном исходном состоянии, включая doctest.
- fmt, Clippy всех целей с `-D warnings`, rustdoc с `-D warnings`, consumer,
  строгий OpenSpec — зелёные. Root OpenSpec: 76/76; SDK: 46/46 до архивирования и 45/45 после.
- Деревья normal-зависимостей `bsl-rt` и `bsl-vm` побайтово совпали с прежними.
- Контроль оптимизатора на всём корпусе, генератор справочника и реестр
  вопросов платформы прошли. Новых BSL API и формата байткода нет.
- Существующие ожидания тестов не менялись. Начальный sandbox-прогон отказал
  на bind локального HTTP-сервера; полный запуск с разрешённым loopback прошёл.
- Конфиденциальные большие случаи `OPEN_BSL_TABLE_COMPARE2_CASES` не были
  настроены; реальные SQL Server-прогоны не проводились.

Остаточные затраты: один проход нормализации при росте, формирование обычных
полей/индексов и прежнего fingerprint при новом полном снимке, сравнение и
копирование строк. Новый профиль не даёт основания объявить эти стоимости
нулевыми или приписать весь libc одному владельцу.


Новая семантика платформы не вводится, новых вопросов `НЕ ИЗМЕРЕНО` нет.
В root изменения — внутренние оптимизации уже заданного поведения
`configuration-session` и `execution-engine`; основание исключения из нового
root OpenSpec записано в плане. Для публичного SDK API агент создал отдельный
OpenSpec до реализации и заархивировал его после зелёных проверок как
`2026-10-22-finalize-query-from-runtime-facts`. Существующие тесты не менялись.

## Проверка завершения цели

Повторная сверка 22 октября подтвердила все 18 исходных результатов A/B:
код завершения 0, успешный контрольный сценарий, неизменность бинарников
в каждом запуске и совпадение хешей stdout со сводкой. Хеш сохранённого
release-кандидата совпадает с build receipt. Полные проверки выше относятся
к измеренному состоянию; после последующих изменений XML/EDT они не выдаются
за новый полный прогон.

использование runtime facts, сохранение прежнего снимка и отказ неполного

ключевых слов; сохранение описателей остальных владельцев при обновлении
частей; Unicode и порядок первой ошибки проверки контекстов. Оптимизации
финализации, индексов и общего владения данными сохранены в текущем коде.
