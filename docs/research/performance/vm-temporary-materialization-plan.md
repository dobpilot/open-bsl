# Уменьшение временных значений и кадров на машинном стеке VM

Статус: предложенный план экспериментов, 7 сентября 2026 года.
Критерии принятия и пределы поиска согласованы с владельцем при ревью.
Завершён этап 0; [журнал и свидетельства](vm-temporary-materialization-results.md).
Кандидаты проверяются в изолированных деревьях, ускорение не обещано.
Изменения исполнения в основную ветку не приняты. Единственный checklist этой
работы находится ниже; корневой `TASKS.md` не используется.

## Цель и границы

Проверить, можно ли воспроизводимо уменьшить общую работу программы
локальными изменениями подготовки временных `BslValue` и `Frame`,
не меняя публичные интерфейсы, семантику, ошибки и владение ресурсами.
Цель — не минимальное число `mov` и не минимальный размер кадра `step`.
Устранение конкретной копии — гипотеза механизма, а не обязательное
условие успеха: цель — воспроизводимо уменьшить общую работу программы.

По правилам OpenSpec это внутренняя оптимизация без наблюдаемого эффекта:
новый change не требуется. Действуют
[границы Rust-модулей](../../../openspec/specs/rust-module-boundaries/spec.md),
[контракт образа](../../../openspec/specs/bytecode-image/spec.md) и
[контракт отладчика](../../../openspec/specs/debug-adapter/spec.md).
Изменение API, поведения, формата, владельца кэшей или архитектурной
границы потребует отдельного OpenSpec до реализации. Архив разделения
модулей не открывается заново. A/B каждого эксперимента ниже нужен для
проверки уменьшения общей работы, а не вводит пошаговые замеры серии переносов.

В первой серии запрещены новые `unsafe`, `MaybeUninit`, `set_len`,
сырые записи в незаполненную ёмкость, изменения layout `BslValue`/`Frame`,
новые зависимости, traits, `dyn`/`Box` и дополнительные клонирования.
Не менять профили, `.cargo/config.toml`, bytecode, алгоритмы runtime,
политику кэшей и список исключений тестов. Ядро и помощники остаются
в `bsl-vm/src/lib.rs`; закреплённые inline-атрибуты не снимать попутно.
Не устранять Drop или проверки индексов ради красивого дизассемблера.
Допустимая дополнительная сложность — небольшой приватный помощник
или локальное изменение порядка подготовки данных с сохранением
поведения. Дублирование алгоритмов, специальное представление значений
и отдельные ветки под конкретный бенчмарк не допускаются.

## Общая дисциплина эксперимента

Один кандидат — одна гипотеза, отдельный diff и проверяемый бинарник.
Сначала кандидаты сравниваются независимо с исходной базой, а не
накапливаются без измерения. Принятые кандидаты соединяются лишь в
заключительном сравнении; их проценты не складываются.

После привязки профиля к исходникам бюджет поиска — максимум два
варианта для `BslValue` и два для `Frame`. Если полезного результата
нет, зафиксировать отрицательный результат и остановиться, не расширяя
поиск автоматически. `step_cold` рассматривается отдельно по решению
владельца и не служит автоматическим продолжением неудачной серии.

До правки записать: участок исходника, цепочку появления временного
значения, предполагаемый механизм устранения, целевой сценарий и тесты.
После правки ответить на два разных вопроса:

1. Исчезли ли конкретные копирования/временные слоты в машинном коде,
   или они только переместились в вызываемую функцию?
2. Стало ли полное исполнение дешевле без неприемлемой регрессии?

Новый помощник с меньшим self step не считается успехом, если работа
просто переехала в него. Сравниваются суммарные счётчики процесса и
новые hotspots. Выигрыш скорости с иной причиной записывается честно,
а не приписывается устранению spill.
Если копия сохранилась или переместилась, но простой вариант
воспроизводимо уменьшил общее число инструкций, он может быть принят.
Фактический механизм описывается отдельно; если он пока не установлен,
это отмечается как неопределённость, а не как доказанное устранение spill.

  при необходимости использовать отдельную диагностическую сборку с
  отладочной информацией/LLVM IR, не подменяя ею измеряемый release.
  Результат: таблица «участок → владелец временного объекта → причина →

- [ ] **1. Один путь результата BslValue в горячем ядре.** Выбрать

  pi_leibniz. Проверить гипотезу: объединение существующего вычисления
  и окончательной записи в узкой внутренней функции позволяет не
  возвращать `Result<BslValue, RtError>` через границу большого step;

## Корректность: что должно остаться прежним

Для значения проверяются `dst == src`, `dst == a`, `dst == b`,
`a == b`, разные номера параметров, указывающие в один слот,
и полностью различные слоты. Матрица включает число, строку,
булево, Undefined/Null и владеющее объектное значение там, где путь
их принимает либо отвергает. Операция сначала завершает вычисление;
ошибка не должна преждевременно уничтожать/заменять получатель.
Не подменять Clone перемещением через Undefined. Сохранить порядок
ошибок операндов/операции/приёмника и освобождения старых значений;
для наблюдаемого Drop использовать тестовый объект с журналом событий.
Сначала проверить существующее покрытие, добавлять только недостающие
тесты на базе до изменения. Непредставимый через публичный образ случай
проверяется приватным unit-тестом, не ослаблением верификатора.

Для кадра: передача по значению/ссылке, алиасы параметров, пропущенные
аргументы и их прологи, возврат, исключение при подготовке и внутри
вызова, рост обоих Vec, рекурсия до предела, модульные copybacks,
async и DAP. Адрес ячейки Vec нельзя удерживать через возможный рост.
`call_start`, `own_base`, `pc` и владение гардами не перепроектируются.

Существующие опорные тесты в bsl-vm:
`by_reference_swap_via_two_parameters`,
`by_value_parameter_does_not_mutate_callers_variable`,
`skipped_call_argument_uses_declared_default`,
`by_ref_arguments_cross_the_module_boundary_both_ways`,
`exception_raised_inside_a_called_function_is_caught_by_callers_try`,
`unbounded_recursion_is_a_catchable_error_not_oom`,
`async_tasks_share_module_state_but_not_local_stacks`.
Фильтр принимается только по исполненному тесту, не по exit code при
нулевом числе тестов. Дополнительно — open-bsl embedding/configuration,
scheduler/http_async, CLI dap_handshake и compiler debug_info.

Полные ворота каждого принятого кандидата:

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo build --workspace
cargo test --workspace
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps
cargo test -p bsl-cli the_jit_agrees_with_the_interpreter_on_every_script
```

Сверять списки тестов, старые публичные пути, API-reference и registry
маркеров. `.expected`, generated API, Cargo.lock и реестр измерений
не исправлять ради зелёного прогона. Конфиденциальный table_compare2
без переменной окружения отмечать как неисполненный. Доказательство
эквивалентности JIT обязательно, даже когда измеряется интерпретатор.

## Измерение и решение

Для каждого кандидата — отдельные worktree и target-dir для базы и
варианта, один rustc, release без дополнительных features, неизменное
выравнивание; переменные RUSTFLAGS не должны подменять конфигурацию.
После сборки дождаться стабилизации нагрузки; до начала серии записать
одинаковое правило допуска, например load1 ≤ 1,5 при питании от сети,
performance и no_turbo=1. Не менять настройку частоты без согласования.

Четыре основные цели: bmp_rotate, str_find, pi_leibniz, call_overhead.
Полный прогрев каждой стороны, затем семь пар AB/BA с чередованием
порядка. `perf stat` измеряет instructions:u и cycles:u отдельно от
профилирования. Сохранять сырые пары, абсолютные числа, медиану парных
дельт и min/max, загрузку, stdout и 100% времени работы счётчиков.
Вывод сравнивать без строки времени; это не оракул 1С.
Не отбирать пары по полученному знаку. Испорченную внешним условием
серию помечать непригодной целиком, сохраняя причину, и повторять.

Профилировать обе стороны отдельными прогонами с проверкой THROTTLE,
LOST и числа отсчётов; при ограничении частоты профиль не принимать.
Сравнивать машинный код step, step_cold и изменённых помощников,
включая перенесённые копирования, вызовы и размер стека.
Штатный hot-code-diff — экран различий, а не требование совпадения
для намеренной оптимизации горячего ядра. Различия должны быть объяснены.

Для итогового сочетания добавить json_write, table_total, table_sort,
background_jobs как канарейки раскладки и компонентных вызовов.
`empty_for` не включать в вердикт. Если вариант затронул общий путь
с JIT-потребителем, дополнительно снять отдельный A/B с --jit;
числа разных режимов не объединять.

Кандидат с прежним количеством работы, неустойчивыми тактами и одной
лишь меньшей долей self не объявляется оптимизацией. Уменьшение
инструкций при неясных тактах допустимо как полезный результат, если
код остаётся в согласованных границах сложности. Оно записывается как
уменьшение вычислительной работы, не доказанное ускорение по времени.
Убедительный выигрыш повторить независимой серией.

Результаты предъявлять по каждому сценарию отдельно, без усреднения
между сценариями. При воспроизводимом ухудшении контрольного сценария
вариант автоматически не принимать: решение о компромиссе принимает
владелец. Ухудшение, неотличимое от шума, отмечать как неопределённость,
а не объявлять подтверждённой регрессией. Если такты меняются при
равных инструкциях, исследовать раскладку и DSB/MITE, а не называть
эффект устранением spill. Числовой порог выигрыша не выдумывается.

## Решения, не входящие в этот план

Прямое заполнение spare capacity через unsafe, смена представления
значения/кадра, глобальная смена inline-политики, изменение семантики
Clone/Drop и новый ABI результата — отдельные решения, не запасной
вариант, автоматически разрешённый отрицательным экспериментом.
Соответствие горячих точек веткам Rust записано в причинной карте шага 0;
оно не заменяется догадкой о том, какой опкод «должен» тормозить.
