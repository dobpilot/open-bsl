# Полный корпус A/B: текущее рабочее дерево против main

## Итог

Завершены все 29 сценариев в двух режимах: 58/58 комбинаций, 532 успешных
запуска. Контрольный вывод и проверяемое содержимое выходных файлов совпали
между main/current и plain/optimized. Восемь первоначальных отказов из-за
импортов измерительного runner заменены успешным повтором, а не включены
в расчёт производительности.

Средние попарные изменения времени (минус — быстрее):

| Сценарий | plain | --optimize |
|---|---:|---:|
| json_write | +5,19% | +16,64% |
| xml_parse | −5,31% | −2,88% |
| xml_write | −15,51% | −8,28% |
| background_jobs | +16,44% | +8,67% |
| simple_parquet_reader | +10,00% | +6,16% |
| str_find | +12,02% | +11,07% |

У `xml_parse --optimize` диапазон времени пересекает ноль: ускорение по
времени неустойчиво, хотя число инструкций уменьшилось на 3,52%.
У `json_write --optimize` выросло и число инструкций (+13,10%): это
приоритетный кандидат для разбора регрессии. У `str_find` инструкции
практически не изменились, поэтому причину замедления эти замеры не
устанавливают. Сетевой `cbr_rates`, короткие сценарии порядка 1–2 мс и
шумный `csv_write --optimize` не дают надёжного вывода по одному среднему.
Полные диапазоны приведены в [таблицах](results.md).

## Состав и условия

29 сценариев `benchmarks/*.bsl`, каждый в режимах plain и `--optimize`.
Сравнивается текущий **незакоммиченный** снимок ветки `bsl-rt-v4.3` над
`1335406cba2d957999fd4a254b819da976ce66f4` с локальной main
`22fa7c07a48b018e030252fac22bc374d22a8618`. Продуктовые исходники совпадают
со снимками [предыдущего flamegraph-прогона](../flamegraphs-after-allocations-2026-09-18/README.md),
но бинарники здесь заново собраны профилем **release без frame pointers**.
Числа нельзя напрямую смешивать с profiling-сборками предыдущего отчёта.

Обе стороны используют одинаковые текущие сценарии, включая версии
background_jobs и call_overhead из рабочего дерева. Старые сценарии
ветки main не подставляются для обхода несовместимостей.

На каждый режим — пять чередующихся пар. Для background_jobs, csv_write,
csv_write_batched, table_compare, table_compare2 и table_save_load — три
пары. Ни один масштаб вычислений не уменьшен. Запуски последовательные,
без конкурирующих сборок или других benchmark этого агента.

Команда сборки в каждом из двух отдельных снимков:

```sh
env -u RUSTFLAGS -u CARGO_ENCODED_RUSTFLAGS CCACHE_DISABLE=1 \
  cargo build --offline --locked --release -p bsl-cli
```

Выравнивание функций на 32 байта берётся из `.cargo/config.toml`.
Хэши бинарников сохранены в [binaries.sha256](binaries.sha256).
Процесс запускается через `perf stat -x ';' -e instructions:u,cycles:u`.
Последняя строка stdout — внутренний таймер benchmark; wall_seconds,
инструкции и такты относятся ко всему запуску. Фоновый сценарий включает
работу потоков, сетевой — реальный HTTP: эти времена не являются чистой
ценой VM. Нагрузка и частота CPU не фиксировались.

## Проверки результатов

До подсчёта дельт проверяются код возврата, числовой таймер и оба
счётчика perf. Из контрольного текста убирается только последний таймер
и числовые времена вида `: N мс`; числа строк, суммы и прочие результаты
остаются. `РАЗОШЛОСЬ` считается отказом. Контрольные результаты сравниваются
между обеими сторонами и между plain/optimized.

Файлы каждого запуска сохраняются в отдельном рабочем каталоге. Проверяется
наличие обязательных результатов, затем их содержимое:

- CSV, MXL, PDF, текстовые документы и сериализованные таблицы: SHA-256
  байтов целиком.
- ZIP/XLSX: имена записей и распакованные байты; ZIP-метаданные времени и
  способ упаковки не сравниваются.
- edata_writer.xml: случайные UUID заменяются последовательными номерами
  по первому появлению. Повторные ссылки сохраняют соответствие; остальной
  XML сравнивается побайтно.
- zip_read: хэши всех распакованных файлов.

Файлы в проекте и существующие `/tmp/open-bsl-*` не перезаписываются.
В измерительных копиях BSL только входные `benchmarks/data/` сделаны
абсолютными, а `/tmp/` перенаправлен в `scratch/` рабочего каталога.
Исходные benchmark не изменены. Импорты модулей читаются из текущего снимка.

## Артефакты и воспроизведение

- [results.md](results.md) — полные таблицы обоих режимов.
- [summary.csv](summary.csv) — медианы, средние попарные дельты и диапазоны.
- [final-runs.csv](final-runs.csv) — итоговые сырые измерения.
- [run.py](run.py), [summarize.py](summarize.py) — runner и строгая проверка
  полноты пар. Неполные/неуспешные сценарии не получают дельту ускорения.
- `logs/`, `retry/logs/` — stdout, stderr/perf и манифесты файлов.

Сырые выходные файлы находятся в `target/full-ab-2026-09-18/`.
Бинарники и исходные снимки — в
`target/flamegraphs/after-allocations-2026-09-18/{main,current}-src/`.
Runner отказывается перезаписывать существующий рабочий каталог.
Для нового запуска можно передать ему новое имя подкаталога; `AB_ONLY`
ограничивает список сценариев при повторе.

Первый проход обнаружил ошибку самого измерительного runner: для
background_jobs и cbr_rates не были перенесены относительные импорты.
Их начальные отказы оставлены в исходных логах, но исключаются из итоговой
сводки и заменяются отдельным повтором из `retry/`. Это не объявляется
несовместимостью интерпретаторов. Отсутствующие импорты исправлены в runner.

Изменений продуктового кода нет. Проверены сборки обеих сторон, синтаксис
измерительных Python-скриптов, распознавание таймеров и отказов. Это полный
benchmark-корпус open-bsl против main, не новый прогон Rust/conformance-
тестов, не запуск Python/Lua и не повторное измерение платформы 1С.
