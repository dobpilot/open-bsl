# Неизвестный состав реквизитов обработки buh

Повторный оригинальный запуск после добавления измеренного перечисления
подписчиков остановился при компиляции модуля объекта обработки
`ПомощникСозданияАвтономногоРабочегоМеста` на имени
`АвтономноеРабочееМесто`.

Отдельное чтение до компиляции завершилось успешно. В исходнике процедура
`СоздатьНачальныйОбразАвтономногоРабочегоМеста` присваивает это имя на строке
60. Другая процедура `ЗаписатьНачальныйОбразАвтономногоРабочегоМеста`
читает его на строке 104, не получая соответствующего параметра.
Объявления `Перем` для этого имени в модуле нет. Это свидетельство для
проверки реквизита обработки, а не основание добавлять глобальный объект
платформы или менять правила видимости локальных переменных.

UUID обработки: `4507a92e-abb6-4329-88b2-3429bc694bc6`.
Наблюдение SDK: `descriptor.data_processor_attributes=None`.
Наблюдение каталога: `object.data_processor_attributes() == None`.
Неизвестный состав сохраняется при проекции; обработчик построения
движка регистрирует только известные имена реквизитов.

Журнал наблюдения:
`target/diagnostics/readonly-startup/buh-autonomous-metadata-1013-startup.log`.
Чтение выполнено неизменяемым диагностическим бинарным файлом
`session-bmeta-startup-probe-1013`, его хеш и хеш исходника наблюдателя
сохранены в соседней квитанции. SDK — подготовленная ветка с ранее
проверенными исправлениями; исходная база не изменялась.

Следующая проверка — описатель этой обработки в SDK и соответствующий
нативный XML-артефакт. До неё нельзя объявлять имя измеренным реквизитом,
выдавать неизвестный список за пустой или менять публичный контракт SDK.

Отдельно сохранён исходный ресурс `4507a92e-abb6-4329-88b2-3429bc694bc6`:
`target/diagnostics/readonly-startup/buh-autonomous-owner-1013.deflate`
(782 байта), распакованный `.config` и `.receipt.json` с хешами.
Успешное чтение завершилось за 5 с; запись разрешалась только в собственный
диагностический каталог. В ресурсе есть коллекция
`ec6bb5e5-b7a8-4d75-bec9-658107a699cf` с объявленным количеством 3:
`URLВебСервиса`, `НаименованиеАвтономногоРабочегоМеста`,
`АвтономноеРабочееМесто`. У последнего GUID
`0e2107e2-8648-4b2e-9dfb-c23b1ff5b007`, тип объявлен через ссылку
`0a52f9de-73ea-4507-81e8-66217bead73a` в `Pattern`.
Следовательно, отсутствие коллекции в исходном ресурсе исключено.
Почему SDK не признаёт её полной, пока не установлено. Эти исходные байты
не подменяют независимый нативный XML-контроль формата.

Проверка через существующий SDK `parse_serialized` локализовала отказ.
Форма объекта `17/12`, его заголовок `2/8`, обёртка `0/2`, GUID-позиции,
счётчик коллекции и все тела реквизитов `27/23` соответствуют проверкам.
Заголовки самих реквизитов имеют версию `2`. Функция `header` в
`src/metadata/runtime_metadata.rs` принимает только версию `3`.
Она вызывается как при чтении `declared_types` в `attribute_bodies`, так
и при сборке состава через `membership` в `complete_attributes`.
Поэтому типы остаются неизвестными и список не признаётся полным.
Синтаксис сохранённых `Pattern` поддержан существующим декодером, но
исполнение не доходит до него. Агент независимо подтвердил обе точки.
Нативная XML-сверка применимости заголовка версии `2` к реквизитам ещё
не выполнена; исходники SDK пока не изменены.

Последующая нативная проверка состоялась: неизменённый owner и объявленные
дочерние ресурсы (всего 11) перенесены существующим упаковщиком в собственный
CF; повторное извлечение подтвердило побайтную сохранность. Штатные
LoadCfg и DumpConfigToFiles завершились с кодом 0. XML подтвердил три
реквизита в исходном порядке; последний имеет TypeSet `ExchangePlanRef`.
Неизвестные внешние объекты не подставлялись.

SDK-коммит `8facccd` прошёл ревью и подключён только к временному
интеграционному SDK как `3ff9202`. Он добавляет узкий fallback для измеренных
собственных реквизитов DataProcessor; общий header и Report не меняются.
Четыре новых теста проверяют неизвестные формы и отсутствие частичной
мутации при повреждённом последнем реквизите. SDK: 939 тестов прошли,
13 пропущены; fmt, Clippy, rustdoc, strict зелёные. Версия и main не менялись.

Повторный исходный buh завершился с кодом 1 за 187,33 с, прежний отказ
пройден. Следующий — имя `ОбщехозяйственныеРасходы` в модуле менеджера
`ПланСчетов.Хозрасчетный`. Лог —
`target/diagnostics/readonly-startup/buh-header2-1013-startup.log`.
