# Подключение отладчика open-bsl к редактору

`bsl-cli --debug` — сервер Debug Adapter Protocol. Он **слушает и ждёт**,
поэтому порядок всегда один: сначала процесс, потом редактор.

```bash
cargo run -p bsl-cli -- --debug путь/к/скрипту.bsl
```

Процесс печатает `отладчик ждёт подключения на 127.0.0.1:4711` и
останавливается до первой инструкции. Адрес и порт меняются ключами
`--debug-host` и `--debug-port`; умолчание — петля, потому что отладчик
вычисляет произвольный BSL, и открытый наружу порт равен удалённому
запуску кода.

## Сначала проверка без редактора

```bash
python3 docs/reference/editors/check.py
```

Скрипт поднимает `bsl-cli --debug` и проигрывает тот же порядок запросов,
что шлёт редактор. Он отвечает на вопрос, который иначе висит между двумя
подозреваемыми: если проверка проходит, а в редакторе не работает — дело
в конфигурации редактора, а не в адаптере.

Ожидаемый вывод — десять строк с «да» и `адаптер готов к подключению
редактора`. Код возврата 0.

## VS Code / VS Code OSS

Редактор не подключается к произвольному DAP-серверу из одного
`launch.json`: конфигурация ссылается на **тип отладчика**, а тип
регистрирует расширение. Свойство `debugServer` подменяет запуск адаптера
подключением к порту, но тип всё равно должен существовать. Поэтому нужен
минимальный плагин — из одного файла, без кода.

```bash
mkdir -p ~/.vscode-oss/extensions/open-bsl-debug
cp docs/reference/editors/vscode/package.json ~/.vscode-oss/extensions/open-bsl-debug/
```

Для обычного VS Code — то же в `~/.vscode/extensions/`. После копирования
редактор нужно перезапустить.

`contributes.breakpoints` с языком `bsl` в плагине не украшение: без него
редактор не даст поставить точку останова в `.bsl`. Идентификатор `bsl`
приходит от расширения `1c-syntax.language-1c-bsl`; если его нет,
поставьте или замените идентификатор на тот, которым у вас открываются
`.bsl`.

Конфигурация запуска — `docs/reference/editors/vscode/launch.json`,
копируется в `.vscode/launch.json` рабочей папки.

## Zed

Конфигурация кладётся в `.zed/debug.json` рабочей папки; образец —
`docs/reference/editors/zed/debug.json`.

**Проверено не полностью.** Ключи `debug.json`, `adapter`, `request`,
`tcp_connection` в Zed 1.14.2 есть — это видно в самом бинарнике, — но
сквозной сценарий на этой машине не проигрывался, и имя адаптера для
чужого DAP-сервера может отличаться. Если Zed откажется, проверка выше
покажет, что адаптер здесь ни при чём, и искать надо в схеме редактора.

## Что работает

Точки останова, в том числе на каждом витке цикла и в цикле, записанном в
одну строку; три шага, различающиеся глубиной кадра; пауза на ходу; стек
с путём к файлу и строкой каждого кадра; локальные переменные; вычисление
выражения в выбранном кадре — то есть окно наблюдения и Debug Console.
Ответы идут в той нумерации строк и колонок, которую редактор объявил.

## Что не работает и почему

- **Шаг внутрь `Выполнить`/`Вычислить`** — фрагмент проходится насквозь,
  как обычный вызов: он исполняется отдельной программой ниже уровня, где
  живёт крючок отладчика.
- **Условные точки останова, точки по данным, перезапуск** — не заявлены
  в `initialize`, и редактор их не предложит.
- **`--debug` вместе с `--optimize`** — отказ на старте: `copy-elim`
  удаляет инструкции, `ssa-regalloc` переставляет слоты, и ни строку, ни
  имя слота потом не вывести.
- Один сеанс на процесс: программа кончилась — адаптер ушёл.

Отладочный прогон медленнее обычного: под отладчиком выключены быстрый
back-edge числового цикла и вход в JIT — иначе они проходят мимо крючка, и
точки останова просто не срабатывают.
