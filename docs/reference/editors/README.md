# Подключение отладчика open-bsl к редактору

`bsl-cli --debug` — сервер Debug Adapter Protocol. Он **слушает и ждёт**,
поэтому порядок всегда один: сначала процесс, потом редактор.

```bash
cargo run -p bsl-cli -- --debug путь/к/скрипту.bsl
```

Процесс печатает `отладчик ждёт подключения на 127.0.0.1:4711` и
останавливается до первой инструкции. Адрес и порт меняются ключами
`--debug-host` и `--debug-port`; умолчание — петля, потому что отладчик
вычисляет произвольный BSL, и открытый наружу порт равен удалённому
запуску кода.

## Сначала проверка без редактора

```bash
python3 docs/reference/editors/check.py
```

Скрипт поднимает `bsl-cli --debug` и проигрывает тот же порядок запросов,
что шлёт редактор. Он отвечает на вопрос, который иначе висит между двумя
подозреваемыми: если проверка проходит, а в редакторе не работает — дело
в конфигурации редактора, а не в адаптере.

Ожидаемый вывод — десять строк с «да» и `адаптер готов к подключению
редактора`. Код возврата 0.

## VS Code / VS Code OSS

Редактор не подключается к произвольному DAP-серверу из одного
`launch.json`: конфигурация ссылается на **тип отладчика**, а тип
регистрирует расширение. Свойство `debugServer` подменяет запуск адаптера
подключением к порту, но тип всё равно должен существовать. Поэтому нужен
минимальный плагин — из одного файла, без кода.

Положить папку в каталог расширений **недостаточно**. Современный VS Code
берёт список пользовательских расширений из реестра `extensions.json`, а
неучтённую папку молча пропускает — то есть плагин просто не появится, и
редактор об этом не скажет. Проверено на Code OSS 1.131 опытом с одной
переменной: каталог, где лежит только эта папка, показывает
`local.open-bsl-debug`; тот же каталог с реестром, где её нет, не
показывает ничего.

Поэтому плагин собирается в `.vsix` и ставится как обычное расширение.
`.vsix` — это zip с манифестом, так что ни `vsce`, ни Node.js не нужны:

```bash
code-oss --install-extension "$(python3 docs/reference/editors/vscode/pack.py)"
```

Скрипт кладёт пакет рядом с собой и печатает абсолютный путь, который тут
же уходит редактору, — поэтому команда работает из любого каталога, лишь
бы путь до `pack.py` был верным. Для обычного VS Code — то же через
`code`. Проверить, что установилось:

```bash
code-oss --list-extensions | grep open-bsl
```

Должно напечатать `local.open-bsl-debug`. После установки редактор нужно
перезапустить.

`contributes.breakpoints` с языком `bsl` в плагине не украшение: без него
редактор не даст поставить точку останова в `.bsl`. Идентификатор `bsl`
приходит от расширения `1c-syntax.language-1c-bsl`; если его нет,
поставьте или замените идентификатор на тот, которым у вас открываются
`.bsl`.

Конфигурация запуска — `docs/reference/editors/vscode/launch.json`,
копируется в `.vscode/launch.json` рабочей папки; для `benchmarks` она
уже лежит там.

`debugServer` умеет только присоединяться: сам процесс редактор не
поднимает. Поэтому конфигураций две.

**«open-bsl: текущий файл»** — процесс поднимает фоновая задача из
`tasks.json`, привязанная к конфигурации через `preLaunchTask`, и F5
работает так же, как в Zed: открытый `.bsl` уходит задаче как `${file}`.
Ждать редактор умеет по выводу — `endsPattern` ловит строку `ждёт
подключения`, после чего присоединяется к порту. Путь к `bsl-cli` в
задаче — `${workspaceFolder}/../target/release/bsl-cli`, то есть сборка
рядом; открыт другой каталог — поправьте путь, как и в Zed.

**«open-bsl: подключиться к запущенному»** — без задачи, для процесса,
запущенного руками:

```bash
./target/release/bsl-cli --debug benchmarks/call_overhead.bsl
```

Он печатает `отладчик ждёт подключения на 127.0.0.1:4711` и ждёт.

**Порядок проверки.**

1. `cargo build --release -p bsl-cli`, если релизной сборки ещё нет.
2. Открыть в редакторе папку, где лежит `.vscode/` — для `benchmarks` обе
   конфигурации уже там, — и в ней любой `.bsl`.
3. Поставить точку останова. Не ставится — дело в
   `contributes.breakpoints` и языке `bsl` (см. выше).
4. F5 с конфигурацией «open-bsl: текущий файл».

Отладка должна остановиться на точке, показать стек и локальные
переменные. Один процесс — один сеанс: измерено, что после разрыва
соединения процесс завершается и следующая попытка получает «в соединении
отказано». Значит, на каждый заход `bsl-cli --debug` запускается заново.

## Zed

Здесь одной конфигурации мало. В VS Code есть лазейка `debugServer`, у
Zed её нет: поле `adapter` — это имя, которое редактор обязан разрешить в
известный ему адаптер, а сторонние приходят только из расширений (ключ
`debug_adapters` в манифесте). Поэтому расширение обязательно.

Оно лежит в `docs/reference/editors/zed-extension/` и умеет оба режима.
Есть `program` — расширение отдаёт Zed команду запуска вместе с
`connection`, редактор сам поднимает `bsl-cli --debug` и соединяется по
TCP; так и написано в описании интерфейса: «Zed will use TCP transport if
`connection` is specified». Нет `program` — команда пустая, остаётся один
`connection`, и расширение только говорит, куда подключаться к процессу,
запущенному руками.

Установка — через палитру команд Zed: `zed: install dev extension`, и
указать папку `docs/reference/editors/zed-extension`. Zed соберёт её сам.
Собрать заранее и проверить, что собирается, можно так:

```bash
rustup target add wasm32-wasip1
cd docs/reference/editors/zed-extension && cargo build --release --target wasm32-wasip1
```

Рядом появится `extension.wasm` — его пишет Zed при установке, и в
репозитории его нет намеренно. Он не тот, что даёт `cargo`: Zed
превращает модуль в компонент (`\0asm 0d00 0100` против `\0asm 01000000`),
то есть подложить туда результат `cargo build` нельзя. А закоммиченная
копия молча расходилась бы с исходником и повторяла бы уже виденное:
правку внесли, расширение пересобрали, поведение прежнее.

После правки исходника расширение нужно **переустановить** той же
командой — пересборки в терминале Zed не видит.

Конфигурация — `.zed/debug.json` рабочей папки, образец в
`docs/reference/editors/zed/debug.json`. Сценария там два, и разницу
делает поле `program`:

- **есть `program`** — Zed сам запускает `bsl-cli --debug` и подключается;
  это обычная кнопка «начать отладку», ничего заводить заранее не нужно.
  В образце стоит `$ZED_FILE` — открытый файл, поэтому F5 отлаживает то,
  что сейчас на экране. Значение подставляет сам Zed, он же такую запись
  и предлагает: подсказка его поля «Program» — `Ex: $ZED_WORKTREE_ROOT`.
  Ручаться за каждую версию редактора мы не можем, поэтому расширение
  проверяет: переменную, дошедшую до него неподставленной, оно назовёт и
  запускать откажется. Постоянный путь вместо переменной пишется
  абсолютным либо от корня проекта — того, что открыт в Zed, а не того,
  где лежит `.zed/debug.json`. Читается ли файл, расширение тоже
  проверяет и в отказе называет корень, от которого считало.
- **нет `program`** — присоединение к процессу, который вы запустили сами.

Поле `bsl_cli` — путь по тем же правилам. В образце это
`../target/release/bsl-cli`: сборка рядом, без `PATH` и без чьего-либо
домашнего каталога. Запись рассчитана на то, что в Zed открыт каталог
уровнем ниже корня репозитория — так открыт `benchmarks`; открыт другой —
поправьте путь.

Без этого поля `bsl-cli` берётся из `PATH`, и тогда **проверьте, какой
именно**. Отладка появилась недавно, ссылка на бинарник из другой копии
репозитория — обычное дело, а сборка без отладчика ответит «неизвестная
команда «--debug»» и выйдет до открытия порта: редактор покажет «process
exited before debugger attached», не назвав причины. Одна строка отделяет
одно от другого:

```bash
bsl-cli --help | grep -- --debug
```

Пусто — значит, в `PATH` не тот. Расширение делает эту же проверку само и
отказывается запускать сборку без отладчика, назвав путь; если пробный
запуск не удался, оно молчит и запускает — проверка вправе добавить
знание, но не отнять возможность.

Поля `request` у сценария Zed НЕТ — вид запроса адаптер сообщает сам, и
наш всегда отвечает «присоединение» даже в режиме запуска: какую
программу исполнять, решает командная строка `bsl-cli`.

Адрес и порт расширение подставляет те же, что у `bsl-cli`
(`127.0.0.1:4711`), и задавать их нужно, только если порт занят.

**Если Zed пишет «Connection to TCP DAP timeout»** — значит, на порту
никто не слушал. Проверено измерением, что сам адаптер открывает порт за
0,08 с и принимает соединение сразу, поэтому причина почти всегда одна:
сценарий был без `program`, то есть на присоединение, а процесс никто не
запустил. Возьмите сценарий с `program` — или запустите `bsl-cli --debug`
сами.

**Что проверено.** Форма интерфейса — по `dap.wit` самого API, а не по
памяти. Расширение собирается в wasm. Адаптер открывает порт и принимает
соединение, а полный диалог DAP на файле вне проекта останавливается на
заданной строке и показывает верный кадр. Сеанс в живом Zed с этим
расширением тоже прошёл: F5 по открытому `.bsl` запускает отладку. Если
редактор всё же откажется, `check.py` выше отделит его конфигурацию от
адаптера.

## Что работает

Точки останова, в том числе на каждом витке цикла и в цикле, записанном в
одну строку; три шага, различающиеся глубиной кадра; пауза на ходу; стек
с путём к файлу и строкой каждого кадра; локальные переменные; вычисление
выражения в выбранном кадре — то есть окно наблюдения и Debug Console.
Ответы идут в той нумерации строк и колонок, которую редактор объявил.

## Что не работает и почему

- **Шаг внутрь `Выполнить`/`Вычислить`** — фрагмент проходится насквозь,
  как обычный вызов: он исполняется отдельной программой ниже уровня, где
  живёт крючок отладчика.
- **Условные точки останова, точки по данным, перезапуск** — не заявлены
  в `initialize`, и редактор их не предложит.
- **`--debug` вместе с `--optimize`** — отказ на старте: `copy-elim`
  удаляет инструкции, `ssa-regalloc` переставляет слоты, и ни строку, ни
  имя слота потом не вывести.
- Один сеанс на процесс: программа кончилась — адаптер ушёл.

Отладочный прогон медленнее обычного: под отладчиком выключены быстрый
back-edge числового цикла и вход в JIT — иначе они проходят мимо крючка, и
точки останова просто не срабатывают.
