# Очистка временных ресурсов

Сеанс учитывает ресурсы, явно зарегистрированные host через
`State::temporary_files()`. Callback задаётся при создании State через
`temporary_file_cleanup`; он получает владение ресурсами, а не разрешение
удалить произвольные пути. Без callback фасад сам файлы не удаляет.

CLI подключает callback, вызывающий `TemporaryFileResource::remove` для
каждого полученного ресурса. При обычном запуске State освобождается до
выхода процесса, в том числе после ошибки BSL. Запуск байткода использует
ту же политику. REPL сохраняет ресурсы между строками, включая ошибочные,
и очищает их при завершении сеанса после освобождения его значений.

Отказ одного ресурса не отменяет попытки очистить остальные. Диагностика
содержит класс первой ошибки, без пути и текста host. Код завершения BSL
не меняется. CLI не сканирует TEMP/TMP и не подбирает остатки прошлых запусков.
Принудительное уничтожение процесса не запускает callback.

## Отличие от измеренного срока жизни 1С

На серверной 1С 8.3.27.2342 четыре файла — закрытый временный поток,
освобождённый временный поток, оставленный открытым поток и отдельно записанный
путь из `ПолучитьИмяВременногоФайла` — сохранялись после возврата серверной
функции и в следующем RPC. После штатного завершения ENTERPRISE все четыре
уже отсутствовали. Точная внутренняя точка между последним клиентским
наблюдением и выходом процесса не измерена.

open-bsl не воспроизводит эту границу буквально. Runtime передаёт callback
только ресурсы, право очистки которых host явно зарегистрировал в текущем
сеансе. CLI вызывает callback при штатном завершении State или REPL; путь,
выданный как свободное временное имя и впоследствии записанный BSL-кодом,
сам по себе таким ресурсом не становится. После принудительного уничтожения
процесса следующий запуск не сканирует `TEMP`/`TMP` и не подбирает остатки.
Это намеренная политика владения open-bsl, а не вывод о внутреннем механизме
1С.

## Временный поток в собственном host

Компонент `bsl-stream` создаёт временный поток через файловую систему host.
Она должна объявлять `supports_temporary_file_ownership` и возвращать
`OpenedTemporaryFile::new_owned`: открытый носитель и право очистки одного
и того же файла. Поток использует полученный дескриптор без повторного
открытия пути; ресурс сразу регистрируется в исходном сеансе.

Менеджер сохраняет файловую систему, источник случайного имени и реестр
сеанса, в котором создан. Передача менеджера другому State не меняет
владельца. После завершения исходного сеанса создание отвергается до I/O.
Прежний Rust-конструктор менеджера без контекста не получает эти возможности
из контекста последующего вызова.

Файл существует до первой записи. Закрытие потока сохраняет `ИмяФайла`
и не удаляет носитель; удаление остаётся ответственностью callback.
Обычный файловый поток также предоставляет readonly-имя после закрытия.
Измеренные абсолютные пути с `./`, `../`, двойным разделителем и конечным
пробелом возвращаются без нормализации. У потока в памяти такого свойства нет.

## Асинхронное и системное создание

Для асинхронного создания host реализует отдельный
`FileSystem::create_transferable_temporary_file`. Его результат
`TransferableTemporaryFile` содержит открытый `FileHandle + Send` вместе
с `TemporaryFileResource + Send`; оба относятся к одному созданному файлу.
В потоке владельца `into_local()` возвращает прежний `OpenedTemporaryFile`
для регистрации в сеансе без повторного открытия пути. Старые host-типы
не обязаны быть Send, а новая операция по умолчанию возвращает Unsupported
без создания файла. `CreateTempFileAsync` запускает worker, а mapper потока VM
регистрирует перенесённое право и создаёт BSL-поток без повторного открытия.

При штатном освобождении execution ожидается результат уже начатого
создания временного файла. Его право регистрируется до закрытия
реестра `State`; затем обычный callback удаляет ресурс. Это ожидание
не распространяется на прочие host-операции. Аварийное уничтожение
процесса по-прежнему не запускает очистку.

На Linux `SystemFileSystem` публикует право отложенного удаления и
создаёт носитель атомарно с правами 0600. Ресурс запоминает device/inode
и отказывается удалять уже подменённый путь. Проверка и последующий
`unlink` не атомарны: системная политика явно доверяет процессам того же
Unix UID и не заявляет защиту от их конкурентной подмены. На Linux
сквозные CLI-тесты проверяют source/bytecode, sync/async, успех/ошибку,
отказ удалять подмену и отсутствие подбора остатка после `SIGKILL`.

Системный Linux-носитель запрещает независимое чтение через FileSystem::read
до освобождения дескриптора, включая hard link и переименование.
Это учёт внутри процесса, а не межпроцессная OS-блокировка.
В частности, выдача временного имени сама по себе сейчас не регистрирует
файл, который прикладной код впоследствии запишет по этому пути.

Это политика open-bsl, а не универсальное утверждение о сроках жизни 1С.
Нативное наблюдение закрытия потока, возврата вызова и окончания клиента
сохранено в [отчёте](../../research/compatibility/file-temp-return-server-2026-09-15.md).
