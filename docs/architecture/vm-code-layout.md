# Раскладка кода VM и границы модулей

> **Статус: принято по измерениям 21–24 августа 2026 года.** Это ограничение
> текущей сборки, а не пожелание к стилю исходников.

## Контекст

Горячий цикл интерпретатора чувствителен к расположению функций в машинном
коде. Новый Rust-модуль внутри `bsl-vm` меняет границы codegen units, порядок
функций и решения об инлайнинге даже тогда, когда вынесенный код на сценарии
не исполняется.

## Измерения

- Вынос 414 строк динамической компиляции в `snippet.rs` дал `empty_for`
  **+29 % тактов** при разнице всего 736 инструкций из 192 миллионов. Вариант,
  где уезжала только машинерия компиляции и кэш, дал **+22 %**. Оба изменения
  откачены.
- Перенос 421 строки проверки образа законному владельцу в другой крейт,
  `bsl-bytecode`, дал `empty_for` **0 %** и `+0,00 %` инструкций. Такой перенос
  принят: другой крейт не перекраивает codegen units `bsl-vm`.
- Вынос `prop_cache` и `method_cache` из `Chunk` в состояние запуска дал
  `empty_for` **+53 % тактов при неизменном числе инструкций**. Пять вариантов
  размещения и инлайнинга регрессию не сняли; изменение откачено.

## Решение

1. `step`, `step_cold`, внешний цикл и их горячие помощники не разносятся по
   модулям ради уменьшения файла.
2. Холодный код переносится только при наличии законного владельца в другом
   крейте и с A/B против базового бинарника.
3. `prop_cache` и `method_cache` остаются в `Chunk`, пока новый дизайн не
   пройдёт собственные ворота.
4. Для любой правки VM действуют выравнивание из `.cargo/config.toml`, обе
   метрики `perf stat` и чередующийся A/B. Равное число инструкций не отменяет
   регрессию по тактам.

Решение можно пересмотреть при переходе на PGO, управляемую сортировку функций
или другой механизм, который делает раскладку воспроизводимой. До этого новый
модуль внутри `bsl-vm` — изменение производительности, а не механический
рефакторинг.
