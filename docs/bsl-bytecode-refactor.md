# Рефакторинг `bsl-bytecode`

## Цель

Сделать `bsl-vm` исполняющим слоем без прямой и транзитивной
зависимости от `bsl-syntax` и `bsl-sema`. Для этого `bsl-bytecode` нужно
разделить на представление байткода и компилятор из семантического
представления.

Рефакторинг не меняет:

- текстовый формат байткода;
- набор и размер `Instr`;
- семантику исполнения;
- горячий цикл VM и JIT;
- владение кэшем динамического кода.

## Текущее состояние

`bsl-bytecode` совмещает шесть ролей:

| Роль | Текущее место |
|---|---|
| Инструкции и структура программы | `instr.rs`, `chunk.rs` |
| Анализ VLIW-бандлов | `bundle.rs` |
| Текстовый формат | `text.rs` |
| Кодоген `bsl-sema → bytecode` | `compiler.rs` |
| Контракт VM ↔ хост для динамического кода | первая часть `dynamic.rs` |
| Лексика, разбор, резолвинг и кодоген динамического текста | вторая часть `dynamic.rs` |

`compiler.rs` напрямую использует `bsl-sema` и `bsl-syntax`. Поэтому даже после
удаления прямых зависимостей от фронтенда из `bsl-vm` они остаются в её
обычном графе:

```text
bsl-vm
└── bsl-bytecode
    ├── bsl-sema
    │   └── bsl-syntax
    └── bsl-syntax
```

В `dynamic.rs` смешаны нейтральный протокол `DynamicCompiler` и конкретная
реализация конвейера `parse → resolve → compile`.

Единственная производственная связь, мешающая механически перенести
`compiler.rs`, — вызов `compiler::instr_touches_objects` из `text.rs`. Это
классификация инструкции, а не логика компилятора.

## Аудит функциональной чистоты

Вычислительные части крейта уже устроены как функциональное ядро:

- `compile_program`, `compile_snippet`, `bundle::compute`, `parse_program` и
  `write_program` детерминированы своими аргументами;
- крейт не читает файлы, окружение, время или случайность;
- `Instr`, `ArgMode`, `DynamicKind`, `CompileError` и `TextError` —
  закрытые алгебраические типы с исчерпывающими `match`;
- мутация `Compiler`, `Reader` и аккумуляторов `bundle.rs` локальна,
  наружу не наблюдается и эквивалентна вычислению с явным состоянием;
- эффект динамической компиляции явно внедрён через
  `DynamicCompiler::compile(&mut self, ...)`.

Переписывать эти алгоритмы на рекурсивные списки, цепочки комбинаторов
или неизменяемые коллекции не нужно. Для Rust локальный императивный
построитель — это простой и дешёвый способ реализовать снаружи чистую функцию.

Нечистота сосредоточена в модели данных:

1. `Chunk` хранит `RefCell`-кэши, поэтому исполнение фактически изменяет
   объект за `&Program`. `Rc<Shape>` также содержит скрытые кэши переходов.
2. Все поля `Program` и `Chunk` публичны, поэтому типы допускают несогласованные
   состояния. Среди них — пустой `chunks`, разные длины `function_names` и
   `chunks[1..]`, несогласованные `n_params`/`param_by_val`/`n_locals`/`n_regs`,
   неверные длины кэшей и ложные `bundle_len`/`touches_objects`.
3. `module_base` — свойство размещения конкретного запуска, а не сериализуемого
   образа байткода.
4. `Chunk::consts` принимает любой `BslValue`, включая изменяемый
   `Object`, хотя текстовый формат такую константу отвергает.
5. `SnippetOutput` — неименованное произведение из трёх связанных таблиц, а
   `bundle::verify` и динамическая компиляция слишком рано стирают типы ошибок в
   `String`.
6. Индексы регистров, функций, констант, форм и таблиц аргументов представлены
   одинаковыми `u8`/`u16`; тип не мешает случайно перепутать их.

Отдельный дефект тотальности: `write_program(&Program) -> Result<_>` может
паниковать на публично конструируемом `Instr::Call { func: 0, .. }`: комментатор
листинга вычитает единицу из нулевого номера чанка. Публичная функция,
возвращающая `Result`, не должна иметь такой скрытой частичности.

## Целевой граф

Добавить внутренний workspace-крейт `bsl-compiler`:

```text
bsl-syntax
    ↓
bsl-sema
    ↓
bsl-compiler ──→ bsl-bytecode
                      ↑
                    bsl-vm

open-bsl ──→ syntax + sema + compiler + bytecode + vm
bsl-cli  ──→ compiler + bytecode + open-bsl
```

### `bsl-bytecode`

Остаются:

- `Instr`, `ArgMode`;
- `Chunk`, `Program`, `ExceptionRange`;
- `bundle::{compute, verify, module_overlap}`;
- `parse_program`, `write_program`, `TextError`, `FORMAT_VERSION`, `OPCODES`;
- `DynamicCompiler`, `DynamicKind`, `DynamicRequest`, `DynamicScope`,
  `DynamicSignature`, `DynamicUnit` как нейтральный протокол VM и хоста.

Обычные зависимости крейта после разделения:

```toml
bsl-rt = { path = "../bsl-rt" }
bsl-number = { path = "../bsl-number" }
```

Зависимость от `bsl-rt` остаётся намеренно: константы, встроенные функции,
методы, `NameId`, формы и требования библиотек являются частью текущего
представления байткода. Их отвязка потребует перепроектирования кодировки и
не входит в эту задачу.

### `bsl-compiler`

Переносятся:

```rust
CompileError
SnippetOutput
compile_program
compile_snippet
compile_snippet_with_requirements
compile_dynamic_snippet
```

Зависимости:

```toml
bsl-bytecode = { path = "../bsl-bytecode" }
bsl-sema = { path = "../bsl-sema" }
bsl-syntax = { path = "../bsl-syntax" }
bsl-rt = { path = "../bsl-rt" }
bsl-number = { path = "../bsl-number" }
```

Публичные вызовы меняют путь механически:

```rust
bsl_bytecode::compile_program
// → bsl_compiler::compile_program

bsl_bytecode::CompileError
// → bsl_compiler::CompileError

bsl_bytecode::compile_dynamic_snippet
// → bsl_compiler::compile_dynamic_snippet
```

Обратный re-export из `bsl-bytecode` не нужен: `bsl-compiler` зависит от
`bsl-bytecode`, и фасад вернул бы неправильное направление зависимости.

## Минимальная подготовка

`instr_touches_objects` нужно перенести из `compiler.rs` к `Instr`:

```rust
impl Instr {
    pub fn touches_objects(&self) -> bool {
        // Исчерпывающая классификация объектных опкодов.
    }
}
```

Его одинаково используют:

- `bsl-compiler` при построении `Chunk`;
- `bsl-bytecode::text` после разбора листинга;
- тест классификации опкодов рядом с `Instr`.

Это устраняет единственную связь `text.rs → compiler.rs`.

До переноса файлов нужна отдельная малая правка тотальности `write_program`:

1. Добавить тест, собирающий `Program` с `Instr::Call { func: 0, .. }`.
2. Проверить, что до правки он паникует, а не возвращает ошибку.
3. Заменить вычитание и прямую индексацию на проверяемый путь и вернуть
   типизированную ошибку `TextError`, а не печатать заведомо битый листинг.

Эта правка не меняет формат корректной программы и не должна смешиваться с
переносом компилятора.

## Миграция тестов

Тесты формата внутри `bsl-bytecode` сейчас компилируют BSL через
`bsl-syntax` и `bsl-sema`. Обратную dev-зависимость `bsl-bytecode → bsl-compiler`
заводить не нужно: она вернёт архитектурный цикл в тесты.

Тесты следует разделить по проверяемой границе.

### Перенести в `bsl-compiler`

- компиляторный round-trip-корпус;
- проверки генерации всех опкодов;
- границы `i16` для целей переходов;
- проверки `CompileError`.

### Оставить в `bsl-bytecode`

- `parse → write → parse`;
- отвергание повреждённых целей переходов;
- невозможные счётчики секций;
- `bundle::verify`;
- разбор констант и инструкций.

Для тестов только текстового парсера нужно использовать фиксированный корректный листинг
или вручную собранный `Program`, а не компиляцию BSL.

`jump_target.rs` нужно разделить:

- превышение лимита при кодогене — в `bsl-compiler`;
- отвергание испорченного листинга — в `bsl-bytecode`.

## Что не входит в рефакторинг

### Кэши `Chunk`

`prop_cache` и `method_cache` архитектурно похожи на состояние исполнения, но их
вынос из `Chunk` уже был реализован, измерен и отклонён. `empty_for`
получил +53 % тактов при неизменном числе инструкций. До появления нового
измеренного дизайна `RefCell`-кэши остаются в `Chunk`.

### Текстовый формат

Формат и кодировка не меняются. `FORMAT_VERSION` не повышается.

### Статическая валидация

Текстовый парсер и VM сейчас проверяют часть одних и тех же статических
инвариантов. Их централизация может изменить диагностику ошибок и поэтому
должна идти отдельным этапом.

## Порядок реализации

1. Отдельной правкой сделать `write_program` тотальной на любом публично
   конструируемом `Program`.
2. Добавить `Instr::touches_objects` и перевести на него `compiler.rs` и `text.rs`.
3. Создать `bsl-compiler` и перенести туда `compiler.rs` без изменения кодогена.
4. Перенести туда реализацию `compile_dynamic_snippet`, оставив контрактные типы
   и `DynamicCompiler` в `bsl-bytecode`.
5. Перевести `open-bsl`, REPL, тесты и примеры VM на `bsl-compiler`.
6. Разделить тесты компилятора и тесты только текстового парсера.
7. Удалить `bsl-syntax` и `bsl-sema` из `bsl-bytecode/Cargo.toml`.
8. Обновить комментарий о графе зависимостей в `bsl-vm/Cargo.toml`.

Каждый этап должен быть механическим: не менять кодоген одновременно с
переносом файлов и не централизовывать валидацию в том же дифе.

## Критерии приёмки

Главная проверка графа:

```bash
cargo tree -p bsl-vm -e normal
```

В результате в дереве не должно быть `bsl-syntax` и `bsl-sema`.

Механическая проверка границы:

```bash
rg 'bsl_(syntax|sema)' crates/bsl-bytecode
```

Ожидается ноль вхождений и в боевом, и в тестовом коде крейта.

Полная проверка:

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps
cargo test --workspace
```

Отдельно должны пройти:

- тест `write_program` на `Call func=0`: типизированная ошибка без panic;
- `the_jit_agrees_with_the_interpreter_on_every_script`;
- проверка `bundle::verify` на полном conformance-корпусе;
- побайтовый round-trip текстового формата;
- проверка `size_of::<Instr>() == 8`;
- проверка, что `FORMAT_VERSION` не изменился.

Хотя исходный код VM не меняется, после разделения нужен чередующийся A/B
прогон как минимум для:

- `empty_for`;
- `call_overhead`;
- `pi_leibniz`;
- строковых сценариев;
- объектных сценариев;
- XML, JSON и таблиц.

Изменение границ единиц кодогенерации и связывания способно повлиять на укладку бинаря,
поэтому отсутствие регрессии нельзя выводить только из неизменного числа
инструкций.

## Отдельные последующие задачи

Они не должны входить в первый диф разделения.

1. Ввести `bsl_bytecode::validate_program` с типизированной `ValidationError` и
   сохранить контекстные диагностики текстового парсера при её преобразовании в
   `TextError`.
2. Сделать поля `Program` и `Chunk` закрытыми. Компилятор и парсер должны
   создавать их через один валидирующий конструктор, который считает `bundle_len`,
   `touches_objects` и ячейки кэшей. Доступ VM к данным идёт через узкие методы, а не
   публичные поля.
3. Перенести `module_base` в контекст исполнения VM: сериализуемый модуль не должен
   знать, где в стеке размещён конкретный запуск.
4. Заменить `SnippetOutput` именованной структурой, а `bundle::verify` — типизированной
   ошибкой. Ошибки лексики, разбора, резолвинга и кодогена сохранять структуру до
   адаптера `DynamicCompiler`, где они превращаются в текст для VM.
5. После стабилизации публичного API рассмотреть прозрачные newtype-типы для регистров,
   констант, функций и форм. Их введение не должно менять `size_of::<Instr>()`.
6. Отдельно оценить `BytecodeConst` — закрытый тип сериализуемых констант без
   `BslValue::Object`. Это затронет загрузку констант VM и поэтому не совмещается с разделением
   крейта.
7. Рассмотреть перенос `DynamicCompiler` в `bsl-vm`, поскольку обратный вызов требуется
   именно VM. Для первого этапа нейтральный контракт остаётся в
   `bsl-bytecode`, чтобы не смешивать две архитектурные миграции.
8. Пересмотреть границу между неизменяемым образом и кэшами исполнения только
   после появления нового измеренного дизайна. Строгий вариант такой границы —
   неизменяемый `BytecodeProgram` и подготовленный `ExecutableProgram`, чья раскладка `Chunk` с
   кэшами остаётся измеренной и не меняется из соображений чистоты.
