# План собственного SSA overlay для JIT

## Цель и границы

Цель — добавить в `bsl-vm::jit` собственное статическое представление в SSA-форме и распространение типов, чтобы template JIT мог выбирать специализированные машинные шаблоны без изменения семантики байт-кода. SSA здесь — **производный overlay над `bsl_bytecode::Chunk`**: исходные `Instr`, абсолютные `pc`, VLIW-бандлы и текстовый формат остаются источником истины. Overlay не сериализуется, не добавляет opcode и строится только при ленивой компиляции чанка под `--jit`.

Первая версия не делает межпроцедурный анализ, удаление или перестановку инструкций, раскрутку циклов, глобальную нумерацию значений между чанками и объектные shape-типы. Она не добавляет внешних crates: для графа, битовых множеств и очередей достаточно `Vec`, `VecDeque` и новых типов-индексов. Зависимость `bsl-vm -> bsl-syntax/bsl-sema` недопустима.

Критерий корректности: при любом отказе анализа или проверки типа JIT продолжает с исходного `pc` в интерпретаторе, а `the_jit_agrees_with_the_interpreter_on_every_script` сравнивает результат и код возврата на всём корпусе. SSA не определяет новую семантику 1С. Если работа обнаружит несовместимость самого рантайма с платформой, её нужно вынести в отдельное измерение, а не закреплять правилом оптимизатора.

## Архитектура

Поток компиляции должен стать таким:

```text
Chunk -> CFG -> SSA overlay -> неподвижная точка TypeSet -> выбор шаблона -> x64::Assembler
```

Предлагаемые модули:

- `crates/bsl-bytecode/src/analysis.rs` — единая исчерпывающая классификация чтений, записей и передачи управления. Текущий закрытый `bundle::effects` следует вынести сюда и переиспользовать в `bundle`, CFG и SSA; второй `match` по всем opcode недопустим.
- `crates/bsl-vm/src/jit/ssa.rs` — CFG, SSA-значения, построитель, проверка инвариантов и стабильное тестовое представление.
- `crates/bsl-vm/src/jit/types.rs` — решётка типов и передаточные функции. Отделить после появления второго потребителя; до этого допустим один `ssa.rs`.
- `crates/bsl-vm/src/jit/mod.rs` — оркестрация анализа и выбор обычного либо специализированного `Compiled`.
- `crates/bsl-vm/src/jit/x64.rs` — только кодирование машинных инструкций; знания о CFG и типах сюда не переносятся.

`jit::compile` должен принимать не только `&Chunk`, но и `module_overlap`, вычисленный из номера чанка и `Program::module_vars`. Это тот же контекст, который уже получает `bundle::compute`: у обычного верхнего уровня модульные слоты накладываются на первые регистры кадра, у функций — нет. Неизвестный overlap означает отказ от специализации, а не предположение. Динамические фрагменты сейчас исполняются с `JitMode::Off`; перед их будущим включением overlap потребуется передавать из фактического `Program::module_base`.

Минимальная модель данных:

```rust
struct BlockId(u32);
struct ValueId(u32);

struct SsaBlock {
    start_pc: usize,
    end_pc: usize,
    predecessors: Vec<BlockId>,
    successors: Vec<BlockId>,
    phis: Vec<ValueId>,
}

enum ValueDef {
    EntryReg(u8),
    Const(u16),
    Instr { pc: usize, reg: u8 },
    Phi { block: BlockId, reg: u8, inputs: Vec<ValueId> },
    Unknown,
}
```

Для каждой инструкции overlay хранит разрешённые `uses` и все `defs`. Множественность `defs` обязательна: `Call` записывает `ret`, а аргументы `ByRefLocal` могут изменить несколько слотов. Сам `Instr` не копируется — `pc` ссылается в `Chunk`.

## CFG и построение SSA

Лидеры блоков: `pc = 0`, все цели `Instr::jump_target()`, инструкция после завершающей управление, а также `start_pc`, `end_pc` и `handler_pc` каждого `ExceptionRange`. Обычные рёбра задают `Jump`, условные `Jump*`, оба `NumericForNext*` и fallthrough; у `Return` и `Raise` продолжения нет. Недостижимые блоки сохраняются для диагностики, но получают `Bottom` и не компилируются как входы.

SSA строится алгоритмом запечатанных блоков:

1. Пройти блоки в reverse postorder и завести текущую версию каждого точного регистра.
2. При чтении ещё неизвестной версии в незапечатанном блоке создать неполный `Phi`.
3. После появления всех предшественников заполнить входы `Phi`.
4. Схлопнуть тривиальные `Phi`; ссылки переписать через таблицу канонических `ValueId`, не перемещая байт-код.
5. Запустить проверку инвариантов.

Проверка подтверждает: одно определение на `ValueId`; один вход `Phi` на предшественника; определение доминирует обычное использование; вход `Phi` доступен на соответствующем ребре; номера `pc`, регистров и целей лежат в проверенном `Chunk`; алиасная память не объявлена обычным SSA-регистром. Ошибка в debug/test — panic с текстовым представлением, в release — отказ JIT для чанка.

## Алиасы, вызовы и динамический код

SSA-нумерации подлежат только собственные регистры и параметры `Знач`. Параметры без `Знач` — память: два номера могут ссылаться на один слот вызывающего или модульную переменную. Их чтения дают `Unknown`, записи не создают переносимый факт.

- Все версии регистров на входе сначала имеют `Any`: один и тот же чанк может получить параметры извне, а верхний уровень — уже материализованные модульные значения. Более точное `Undefined` для доказанно собственных временных — последующее улучшение.
- `GetModuleVar` возвращает `Any`. `GetModuleVar`, `SetModuleVar`, `Call` и `RunDynamic` обновляют также наложенные точные регистры согласно переданному `module_overlap`; это должна делать общая классификация из `bsl-bytecode`, а не особое правило JIT.
- После `Call` его `ret` получает новый `ValueId`, а каждый `ByRefLocal(slot)` — новое значение `Any`. Вызов остаётся барьером для модульной памяти и кучи.
- `RunDynamic` может читать и писать все именованные локали. На первом этапе чанк с этой инструкцией строит CFG для проверки, но не получает специализированных шаблонов; позднее инструкция должна убивать факты всех видимых локалей.
- Вызовы встроенных функций, методов, компонентов, свойства и индексация сначала возвращают `Any`. Контракты результатов добавляются только в одну исчерпывающую таблицу рантайма, а не отдельным списком в JIT.

## Исключения

Почти любая операция над `BslValue` может бросить ошибку. Моделировать только явный `Raise` недостаточно: обработчик должен увидеть состояние после успешно завершённых предыдущих инструкций и точный `pc` сбоя, как сейчас делает `run_shim`.

Поэтому первая оптимизирующая версия консервативно не специализирует чанки с непустым `exception_ranges`; template JIT продолжает работать как раньше. Следующий отдельный этап добавляет исключительные рёбра от потенциально бросающей инструкции к самому внутреннему обработчику, разрезает блок перед таким местом и строит состояние обработчика из значений, материализованных до инструкции. Нельзя переносить запись через потенциально бросающую операцию. Проверка типа и медленный путь обязаны выйти до частичного изменения видимого состояния и поставить `frame.pc` на исходную инструкцию.

## Решётка и распространение типов

`TypeSet` — конечный битовый набор вариантов `BslValue`: `Undefined`, `Null`, `Boolean`, `Number`, `String`, `Date`, `Type`, `Enum`, `EnumType`, `Object`; отдельно `Bottom` означает недостижимость, полный набор — `Any`. `Phi` объединяет типы, поэтому неподвижная точка достигается без специального расширения решётки.

Начальные правила:

- входные параметры и неизвестные чтения — `Any`;
- `LoadConst` берёт точный tag из `chunk.consts`, `LoadBool` — `Boolean`, `LoadUndefined` — `Undefined`, `LoadNull` — `Null`;
- `Move` сохраняет набор, сравнения при успешном завершении дают `Boolean`;
- арифметика специализируется только для доказанного `Number × Number` и вызывает существующую десятичную реализацию `bsl-number`;
- конструкторы дают только `Object`, без различения конкретного типа;
- неизвестный opcode либо неизвестная комбинация типов даёт `Any`, а не предположение.

Очередь хранит пользователей изменившегося `ValueId`; объединение монотонно. Сужение по ветвям, константное вычисление, типы объектов и сводки функций — последующие улучшения. Передаточные функции должны опираться на существующие операции рантайма и тесты, а не создавать вторую семантику BSL.

## Интеграция и откат

Сначала SSA лишь сопровождает текущий `compile_instr` и ничего не меняет в машинном коде. Затем `compile_instr` получает типы операндов и выбирает специализированный shim только при доказанном единственном типе; иначе остаётся нынешний общий shim.

Первый безопасный кандидат — числовые `Neg`, `Add`, `Sub`, `Mul` и сравнения: убрать повторный `match BslValue`, но оставить ту же операцию `BslNumber` и тот же `RtError`. Деление и остаток подключать отдельно из-за нуля и точной ошибки. Параметры с `Any` требуют проверки типа на прогоне. При её промахе JIT возвращает исходный `pc`, и интерпретатор выполняет инструкцию один раз. Это естественное продолжение нынешнего `CompiledChunk::run`, а не новый механизм исключений.

Пока значения остаются обычными `BslValue`, промах проверки просто возвращает исходный `pc`: состояние уже находится в стеке. Материализация нужна только после появления будущих неупакованных регионов; она выполняется перед выходом и не должна быть частью первой специализации.

Неупакованные регионы `i64` — отдельный поздний этап. Перед выходом в интерпретатор, вызовом, обработчиком и любой наблюдаемой записью число материализуется в `BslNumber`; переполнение выходит на общий путь до фиксации результата. До профиля, подтверждающего пользу, эта сложность не вводится.

VLIW-разметка остаётся независимой: точки входа по-прежнему только в начале бандла, а SSA оперирует исходными `pc`. Первая версия не удаляет и не переставляет инструкции, поэтому не пересчитывает `bundle_len` и не меняет `FORMAT_VERSION`.

## Этапы реализации

### 0. База и воспроизводимость

Сохранить baseline release-бинарник и снять чередующийся A/B для `goto_bench`, `empty_for`, `pi_leibniz`, `bmp_rotate`, `call_overhead` и `table_compare`. Зафиксировать вывод, время выполнения, время первой JIT-компиляции и размер машинного кода. Это проверка, которая может опровергнуть дальнейшие performance-утверждения.

### 1. Общий анализ инструкций

Вынести регистровые эффекты и класс управления из `bundle.rs`, перевести `bundle::compute` на новый API. Формат байт-кода и результат `bundle::compute` должны остаться побайтово прежними. Добавить тест каждой группы opcode и исчерпывающую компиляционную классификацию.

### 2. CFG

Построить блоки, рёбра, списки предшественников, обратный порядок обхода и стабильное текстовое представление. Покрыть ромб, цикл с обратным ребром, пустой/недостижимый хвост, `NumericForNext`, несколько соседних целей и границы `ExceptionRange`.

### 3. SSA overlay

Добавить построитель запечатанных блоков, тривиальные `Phi`, канонизацию и проверку инвариантов. Отдельно проверить цикл с loop-`Phi`, ромб, перезапись регистра, параметр `Знач`, ссылочный параметр и `Call` с двумя `ByRefLocal`.

### 4. Type propagation без кодогенерации

Реализовать `TypeSet`, вычисление неподвижной точки и представление `ValueId -> TypeSet`. Проверить объединение `Number | String`, стабилизацию loop-`Phi`, константы, неизвестный вызов и недостижимый блок. В release overlay пока не должен менять `CompiledChunk` и поведение.

### 5. Первая специализация

Подключить доказанные числовые типы к существующим shim-путям, затем добавить проверки типа для горячих `Any`-входов. Каждый opcode включать отдельным изменением с тестом общего пути, специализированного пути, промаха проверки и ошибки без локального обработчика. Отдельный тест фиксирует, что чанк с `Попытка` остаётся на прежнем template-пути; специализированная ошибка внутри обработчика допускается только после этапа исключительного CFG.

### 6. Расширение только по профилю

Рассматривать сужение типов по ветвям, контракты результатов встроенных функций, версии чанка по типам параметров, виды объектов и неупакованные `i64` только если hotspot после этапа 5 показывает их стоимость. Межпроцедурные сводки должны быть отдельным планом: они требуют ключа версии и инвалидирования для динамических фрагментов.

## Проверки и критерии допуска

После каждого этапа:

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test -p bsl-bytecode
cargo test -p bsl-vm
cargo test -p bsl-cli the_jit_agrees_with_the_interpreter_on_every_script
cargo tree -p bsl-vm -e normal
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps
```

Перед слиянием специализации — `cargo test --workspace` и чередующийся A/B тем же baseline-бинарником. Вывод benchmark должен совпадать. Решение принимается не по одному прогону: минимум девять чередующихся запусков на сценарий, одинаковые частоты CPU и неизменённый `.cargo/config.toml`. Этап принимается, если улучшает целевой hotspot, не даёт воспроизводимого регресса более 3% на контрольных сценариях и не увеличивает заметно JIT startup/code size без компенсирующего выигрыша. Если порог не пройден, overlay можно оставить как проверенный анализ, но кодогенерацию этого шаблона не включать.

## Основные риски

- Неверная модель ссылочных параметров превращает оптимизацию в изменение наблюдаемой семантики.
- Неполный CFG с исключительными рёбрами заставляет обработчик видеть значение, которое исходная инструкция ещё не успела записать.
- Дублирование таблиц эффектов или builtin-контрактов неизбежно разойдётся при новом opcode.
- Слишком общий `Any` не даст ускорения; преждевременная специализация создаст дорогие проверки и увеличит код.
- Сам размер кода JIT и изменение layout могут сдвинуть горячий dispatcher; поэтому обязательны baseline-бинарник и A/B, а не сравнение двух последовательных сборок.
- SSA строится лениво, но крупные чанки могут увеличить задержку первого входа. Нужно измерять отдельно построение CFG, SSA, неподвижной точки и машинную эмиссию.

Итог первой поставки — проверяемый SSA overlay и консервативная типизация без изменения формата или поведения. Оптимизация допускается поверх него только по одной доказанной операции за раз, с материализацией состояния и возвратом на исходный `pc` как универсальным безопасным fallback.
