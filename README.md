# open-bsl

Интерпретатор BSL (встроенный язык 1С:Предприятие) на Rust: регистровая
байт-код VM в стиле Lua, без LLVM (имя репозитория осталось от исходного
замысла).

Крейты по слоям: `bsl-number` (десятичное число), `bsl-syntax` (лексер и
парсер), `bsl-sema` (резолвинг), `bsl-bytecode` (кодоген), `bsl-rt`
(значения, коллекции, строки, даты), `bsl-format` (`Строка`/`Формат`/
`Число`), `bsl-vm` (цикл диспетчеризации), `bsl-cli` (запуск скрипта и
REPL).

```bash
cargo test --workspace
cargo run -p bsl-cli -- --help   # список команд
```

## REPL

```bash
cargo run -p bsl-cli
```

Подсветка ввода и дополнение по Tab. Что дополняется — зависит от места в
строке: после точки только методы объектов и имена полей/колонок, после
`Новый` только конструируемые типы, в остальных местах встроенные функции,
ключевые слова и переменные этой сессии. Отбор регистронезависим (`стрн`
находит `СтрНайти`), подставляется каноническое написание. Второй Tab
показывает список вариантов.

Списки имён берутся из тех же таблиц, по которым идёт настоящий разбор
(`bsl_rt::BUILTIN_FN_NAMES`, `bsl_syntax::KEYWORD_SPELLINGS`,
`bsl_sema::NEW_TYPES`), а тесты в этих крейтах не дают им разъехаться с
`lookup` — предложить то, чего интерпретатор не знает, дополнение не может.

Цвет отключается `NO_COLOR=1` и при `TERM=dumb`. Если терминал не удаётся
перевести в сырой режим, REPL откатывается на построчное чтение stdin.

Единственная внешняя зависимость проекта сверх `num-bigint` — `rustyline`
(редактирование строки, история, сырой режим), и она только в `bsl-cli`:
ядро остаётся без зависимостей. Подсветка (`crates/bsl-cli/src/highlight.rs`)
и дополнение (`complete.rs`) написаны здесь, rustyline лишь вызывает их.

## Байт-код: посмотреть и исполнить

```bash
cargo run -p bsl-cli -- --emit-bytecode script.bsl          # в stdout
cargo run -p bsl-cli -- --emit-bytecode script.bsl out.bslc # в файл
cargo run -p bsl-cli -- --run-bytecode out.bslc             # исполнить
```

Формат печати и формат исполнения — ОДИН И ТОТ ЖЕ: напечатанное не отчёт о
байт-коде, а сам байт-код, его можно прочитать, поправить руками и
запустить. Всё от `;` до конца строки — комментарий; печать выносит туда
то, что иначе пришлось бы искать по таблицам глазами:

```
  .handlers 1
    0 3 11 12  ; Попытка 3..11 -> обработчик 12
  .code 14
    0000 LoadConst dst=1 k=0  ; = 5
    0002 NewStructure dst=0 shape=0 base=1 count=2  ; поля: цена, количество
    0004 GetProp dst=4 obj=5 name=0  ; .цена
    0007 Call func=1 base=4 arg_modes=0 ret=3  ; -> .chunk 1
```

Полезно там, где иначе приходится гадать: во что развернулось короткое
замыкание `И`/`ИЛИ`, встал ли `NumericForNextI64` вместо общего пути цикла,
сколько регистров съел кадр, попала ли форма структуры в таблицу форм.

Гарантия формата — печать → разбор → печать даёт побайтово ту же строку, а
исполнение разобранной программы даёт тот же вывод, что и исходной; второе
проверяется на всех фикстурах с оракулом
(`fixtures_produce_the_same_output_when_run_from_printed_bytecode`).
Инлайн-кэш (`prop_cache`) не сохраняется — это рантайм-кэш, он
восстанавливается пустым. Номер формата в заголовке (`bslc 1`) загрузчик
сверяет и чужой отвергает целиком: байт-код здесь не контракт между
версиями, а способ посмотреть и прогнать то, что скомпилировал этот же
бинарник.

## JIT (`--jit`)

```bash
bsl-cli --jit script.bsl
```

Байт-код чанка компилируется в машинный код x86-64 прямо в память
(`crates/bsl-vm/src/jit/`). Только по ключу: без него ничего не меняется,
и обычный путь исполнения не начинается с проверки «а не JIT ли у нас».
Только Linux/x86-64 — на остальных платформах ключ принимается и не делает
ничего.

JIT шаблонный, не оптимизирующий. Для каждой инструкции порождается вызов
маленькой обёртки, которая зовёт ТЕ ЖЕ функции, что и соответствующая
ветка интерпретатора; переходы становятся настоящими `jmp`/`jcc`, и тело
цикла крутится внутри одной нативной функции, не возвращаясь в
диспетчер. Компилируются присваивания, арифметика, сравнения и переходы;
всё остальное — вызовы, возвраты, `Выполнить`, работа с объектами —
остаётся интерпретатору, и переключение туда-обратно происходит само по
карте точек входа. Неизвестная инструкция поэтому не ошибка, а выход.

Ни одной внешней зависимости JIT не добавил: исполняемая страница берётся
сырыми `mmap`/`mprotect`, кодировщик x86-64 свой, ровно на нужные формы
инструкций.

**Что это даёт.** JIT — отдельная колонка в общем прогоне
(`./benchmarks/run.sh`), рядом с lua, luajit, oscript и платформой; полная
таблица и разбор — в [benchmarks/README.md](benchmarks/README.md). Коротко
(медиана 7 прогонов, миллисекунды):

| сценарий | интерпретатор | `--jit` | | 1С 8.3.27 |
|---|---:|---:|---:|---:|
| `pi_leibniz` | 509 | **368** | 1.38x | 1160 |
| `pi_leibniz_15` | 703 | **522** | 1.35x | 1318 |
| `table_total` | 265 | **241** | 1.10x | 3205 |
| `csv_write_batched` | 64 | **60** | 1.07x | 217 |
| всё остальное | | | 1.00x | |

Выигрыш ровно там, где горячий цикл состоит из арифметики и сравнений, —
других инструкций JIT пока и не компилирует. Где работа уходит в
строковые функции, коллекции или файлы, его нет: там нативный код только
передаёт управление обратно. Зато на `pi_leibniz` отрыв от платформы
вырастает с 2.4x до **3.2x**.

Большую часть этого дала компиляция инструкции, ЗАМЫКАЮЩЕЙ числовой цикл
(`NumericForNext`). Без неё тело цикла компилировалось, а шаг счётчика —
нет, и нативный код уходил в интерпретатор на каждой итерации: нативные
переходы при этом не давали ничего. С ней всё тело `pi_leibniz` —
одиннадцать инструкций — остаётся нативным.

`empty_for` при этом не сдвинулся, и не потому, что ждёт той же правки:
его цикл — это одна `NumericForNextI64`, которую интерпретатор и так
обслуживает компактным циклом внутри `drive_with`, ни разу не заходя в
диспетчер. Убирать там нечего.

**Чем гарантируется, что режимы не расходятся.** Тяжёлую часть семантики
(сложение, сравнение, равенство, условие) обёртки не переписывают — они
зовут общий код. Но обвязку вокруг него (какой регистр читать, куда
класть результат) они повторяют за веткой интерпретатора, и это место
уже разъезжалось: `=` сначала сравнивал через порядок вместо
структурного равенства, и `ТипЗнч(1) = ТипЗнч(2)` под `--jit` падало
ошибкой типа. Поэтому есть
`the_jit_agrees_with_the_interpreter_on_every_script`: он гоняет весь
корпус фикстур и скриптов замеров обоими режимами и сравнивает вывод
вместе с кодом возврата. Ту ошибку он поймал на первом прогоне.

## Замеры для человека

Целевая семантика снимается с РЕАЛЬНОЙ 1С, а не выводится логически: числа
в `bsl-number` (27 знаков у деления, half-up на ничьей, точное умножение)
подтверждены измерениями, и заменить их нечем. Всё остальное, что выбрано
рассуждением, проходит через один конвейер:

1. **Метка в коде.** `// НЕ ИЗМЕРЕНО(ОБЛАСТЬ.ВОПРОС)` там, где решение
   принято без сверки с платформой. ID обязателен — метка без него роняет
   тест.
2. **Запись в реестре.** `crates/bsl-rt/src/open_questions.rs`: что за
   вопрос, что выбрано, что этим заблокировано. Там же якоря — уже
   измеренные значения, которые служат канарейкой сеанса.
3. **Строка в скрипте замеров.** `tests/conformance/measure/measure-all.bsl`
   — единственный файл, который человек прогоняет у платформы. Вывод
   машинный: `ИД<таб>ЗНАЧЕНИЕ`, ровно одна строка на ID.

Три источника держит вместе тест
`open_questions_registry_matches_source_markers` (в `bsl-rt`): метка без
записи в реестре, запись без метки, ID без строки в скрипте — всё это
падение с указанием, что именно осиротело. Забыть не выйдет.

Прогон у платформы и приём результата:

```bash
./tests/conformance/measure/1c/run-on-1c.sh          # снять замеры с 1С
cargo run -p bsl-cli -- --ingest-measurements tests/conformance/measure/platform.tsv
```

Скрипт сам создаёт пустую файловую базу, собирает внешнюю обработку из
исходников (`1c/epf-src`) и исполняет её. Почему так, а не «запустить .bsl»:
платформа умеет исполнять только модуль объекта метаданных, `/Execute` НЕ
компилирует модуль объекта внешней обработки (заведомо битый модуль
«выполняется» с кодом 0), а `Сообщить` в батче никуда не попадает и
затенить её своей процедурой платформа не даёт. Поэтому код уезжает в модуль
ФОРМЫ, в `&НаСервере Процедура ВыполнитьТестНаСервере()`, а вывод копится
через `СообщитьВФайл` — генератор подменяет вызов в КОПИИ текста, сам скрипт
замеров не меняется. Все три факта проверены на 8.3.27, подробности и
особенности окружения — в шапке `run-on-1c.sh`.

`tests/conformance/measure/platform.tsv` — снятые значения. Это
единственный файл в репозитории с данными платформы, и попадают они туда
только этим путём.

Приём раскладывает вывод в `tests/conformance/measure/platform.tsv`,
сравнивает его с нашим выводом на том же скрипте и печатает расхождения
списком: ID, наше, платформенное, что было выбрано. **В коде ничего не
правится автоматически** — решение по каждому расхождению принимает
человек. Эталон никогда не берётся из вывода этой же реализации: тест,
сравнивающий систему саму с собой, хуже отсутствующего.

**Защита от опасных действий.** Платформа считает запуск внешней
обработки потенциально опасным и показывает модальное предупреждение —
прогон замеров при этом ждёт человека с мышью. Ключа командной строки для
этого нет. Снимается параметром `DisableUnsafeActionProtection` в общем
`conf.cfg` установки (каталог берётся из `ConfLocation` в
`/opt/1cv8/x86_64/<версия>/conf/conf.cfg`, обычно это `/opt/1cv8/conf/`).
Файл принадлежит root и лежит вне проекта, поэтому правится руками, а не
скриптом.

Путь к тестовой базе — `/tmp/open-bsl-ib`, и он стабильный именно
поэтому: параметр задаётся списком баз, и база должна называться одна и та
же.

Способ через свойство `ПользовательИнформационнойБазы.ЗащитаОтОпасныхДействий`
здесь не работает — проверено: конфигурация пустая, ролей в ней нет, и
платформа отказывается записывать первого пользователя («не осталось бы ни
одного пользователя с административными правами»).

Скрипт замеров прогоняется у платформы целиком, но так же можно снять
эталон и с любой фикстуры: `run-on-1c.sh <файл>.bsl` кладёт вывод рядом
файлом `<файл>.platform.txt`. Именно так получены `.expected` — вручную
их никто не пишет.

### Что особенно вероятно разойдётся

1. **`SQRT.SMALL_ARG`.** Модель «15 значащих с округлением» воспроизводит
   `Sqrt(2)`, но не `Sqrt(0.02)`, и ни одно простое правило не описывает обе
   точки. Тест `sqrt_small_argument_unresolved` в
   `crates/bsl-number/tests/oracle.rs` остаётся под `#[ignore]`, пока это не
   разрешено.
2. **`EXEC.NEW_VARIABLE_SCOPE`.** Переменная, впервые созданная внутри
   `Выполнить`, у нас не переживает вызов. `Выполнить` в 1С исполняется в
   контексте текущей области видимости, так что попадает ли туда новое имя —
   вопрос замера, а не рассуждения.
3. **`FMT.DATE.DEFAULT`.** Пустая дата печатается как `01.01.0001 00:00:00`.
   Открыто и ведёт ли платформа ведущий ноль в часах, и опускает ли время у
   полуночной даты вообще.

### Фикстуры без `.expected`

Раннер conformance такие фикстуры пропускает и печатает сводку в конце
прогона:

```bash
cargo test -p bsl-cli -- --nocapture
```

```
conformance: 2 проверено, 11 пропущено (нет .expected)
  пропущены: dates, dynamic-execute, n-body-perf, ..., table-wave3, measure-all
```

Это и есть очередь на замер: прогон фикстуры целиком у платформы даёт
готовый эталон построчно. `n-body-precision.bsl` снимается именно так —
отдельным прогоном, а не через `measure-all.bsl`.

## Уже измеренные эталоны

Менять эти значения нельзя — они сняты с платформы.

```
1/3                     -> 0,333333333333333333333333333    (27 знаков)
2/3                     -> 0,666666666666666666666666667    (округление вверх)
10/3                    -> 3,333333333333333333333333333    (27 после точки, 28 значащих)
1/268435456             -> 0,000000003725290298461914063    (half-up на ничьей)
Sqrt(2)                 -> 1,4142135623731
Sqrt(0.02)              -> 0,141421356237309                (ОТКРЫТО, см. выше)
1.10 * 1.00             -> 1,1
Pow(10, 30)             -> 1 000 000 000 000 000 000 000 000 000 000  (точно)
СтрДлина(Строка(1/3))   -> 29
Строка(1000.5)          -> 1 000,5
КодСимвола(разделитель) -> 160                              (NBSP)
Число(Строка(1000000))  -> 1 000 000                        (round-trip живой)
Строка(Истина)          -> Да
Строка(Новый Массив)    -> Массив
```

Почему это именно так, чтобы не «исправить» как баг:

* Лимит деления — на МАСШТАБЕ, а не на значащих: `1/3` даёт 27 значащих,
  `10/3` — 27 знаков после точки при 28 значащих.
* Half-up подтверждён точной ничьей: 1/2²⁸ = 0,0000000037252902984619140625
  ровно; платформа дала `...063`, half-even и truncate дали бы `...062`.
* Умножение без границы масштаба — это семантика, а не недосмотр: `x = x * x`
  в цикле подвешивает саму платформу. `MAX_SCALE` в коде — защита от OOM.
* `Pow(10,30)` точный: через f64 вышло бы `1 000 000 000 000 000 019 884 624 838 656`.
* n-body с `Для i = 1 По 50000000` неисполним нигде, включая 1С: масштаб
  растёт примерно на 50 знаков за итерацию. Фикстуры намеренно урезаны до
  100/3/200 итераций — увеличивать их обратно не нужно.

Целимся в 1С, не в OneScript. OneScript, судя по всему, на C# `decimal` с
кэпом 28–29 разрядов, и округлит там, где 1С не будет: расхождения с ним
ожидаемы и документируются, а не чинятся.
