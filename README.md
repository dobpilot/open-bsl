# onec_llvm

Интерпретатор BSL (встроенный язык 1С:Предприятие) на Rust: регистровая
байт-код VM в стиле Lua, без LLVM (имя репозитория осталось от исходного
замысла).

Крейты по слоям: `bsl-number` (десятичное число), `bsl-syntax` (лексер и
парсер), `bsl-sema` (резолвинг), `bsl-bytecode` (кодоген), `bsl-rt`
(значения, коллекции, строки, даты), `bsl-format` (`Строка`/`Формат`/
`Число`), `bsl-vm` (цикл диспетчеризации), `bsl-cli` (запуск скрипта и
REPL).

```bash
cargo test --workspace
```

## Замеры для человека

Целевая семантика снимается с РЕАЛЬНОЙ 1С, а не выводится логически: числа
в `bsl-number` (27 знаков у деления, half-up на ничьей, точное умножение)
подтверждены измерениями, и заменить их нечем. Всё остальное, что выбрано
рассуждением, проходит через один конвейер:

1. **Метка в коде.** `// НЕ ИЗМЕРЕНО(ОБЛАСТЬ.ВОПРОС)` там, где решение
   принято без сверки с платформой. ID обязателен — метка без него роняет
   тест.
2. **Запись в реестре.** `crates/bsl-rt/src/open_questions.rs`: что за
   вопрос, что выбрано, что этим заблокировано. Там же якоря — уже
   измеренные значения, которые служат канарейкой сеанса.
3. **Строка в скрипте замеров.** `tests/conformance/measure/measure-all.bsl`
   — единственный файл, который человек прогоняет у платформы. Вывод
   машинный: `ИД<таб>ЗНАЧЕНИЕ`, ровно одна строка на ID.

Три источника держит вместе тест
`open_questions_registry_matches_source_markers` (в `bsl-rt`): метка без
записи в реестре, запись без метки, ID без строки в скрипте — всё это
падение с указанием, что именно осиротело. Забыть не выйдет.

Прогон у платформы и приём результата:

```bash
# 1. Прогнать tests/conformance/measure/measure-all.bsl на реальной 1С,
#    вывод сохранить в файл (например, platform-output.txt).
# 2. Скормить обратно:
cargo run -p bsl-cli -- --ingest-measurements platform-output.txt
```

Приём раскладывает вывод в `tests/conformance/measure/platform.tsv`,
сравнивает его с нашим выводом на том же скрипте и печатает расхождения
списком: ID, наше, платформенное, что было выбрано. **В коде ничего не
правится автоматически** — решение по каждому расхождению принимает
человек. Эталон никогда не берётся из вывода этой же реализации: тест,
сравнивающий систему саму с собой, хуже отсутствующего.

`measure-unsupported.bsl` рядом — замеры, которые НАШ интерпретатор пока не
исполняет (обращение к имени, созданному внутри `Выполнить`; вызов
пользовательской функции из фрагмента). Их надо прогнать у платформы
отдельно; `--ingest-measurements` принимает объединённый вывод.

### Что особенно вероятно разойдётся

1. **`SQRT.SMALL_ARG`.** Модель «15 значащих с округлением» воспроизводит
   `Sqrt(2)`, но не `Sqrt(0.02)`, и ни одно простое правило не описывает обе
   точки. Тест `sqrt_small_argument_unresolved` в
   `crates/bsl-number/tests/oracle.rs` остаётся под `#[ignore]`, пока это не
   разрешено.
2. **`EXEC.NEW_VARIABLE_SCOPE`.** Переменная, впервые созданная внутри
   `Выполнить`, у нас не переживает вызов. `Выполнить` в 1С исполняется в
   контексте текущей области видимости, так что попадает ли туда новое имя —
   вопрос замера, а не рассуждения.
3. **`FMT.DATE.DEFAULT`.** Пустая дата печатается как `01.01.0001 00:00:00`.
   Открыто и ведёт ли платформа ведущий ноль в часах, и опускает ли время у
   полуночной даты вообще.

### Фикстуры без `.expected`

Раннер conformance такие фикстуры пропускает и печатает сводку в конце
прогона:

```bash
cargo test -p bsl-cli -- --nocapture
```

```
conformance: 2 проверено, 11 пропущено (нет .expected)
  пропущены: dates, dynamic-execute, n-body-perf, ..., table-wave3, measure-all
```

Это и есть очередь на замер: прогон фикстуры целиком у платформы даёт
готовый эталон построчно. `n-body-precision.bsl` снимается именно так —
отдельным прогоном, а не через `measure-all.bsl`.

## Уже измеренные эталоны

Менять эти значения нельзя — они сняты с платформы.

```
1/3                     -> 0,333333333333333333333333333    (27 знаков)
2/3                     -> 0,666666666666666666666666667    (округление вверх)
10/3                    -> 3,333333333333333333333333333    (27 после точки, 28 значащих)
1/268435456             -> 0,000000003725290298461914063    (half-up на ничьей)
Sqrt(2)                 -> 1,4142135623731
Sqrt(0.02)              -> 0,141421356237309                (ОТКРЫТО, см. выше)
1.10 * 1.00             -> 1,1
Pow(10, 30)             -> 1 000 000 000 000 000 000 000 000 000 000  (точно)
СтрДлина(Строка(1/3))   -> 29
Строка(1000.5)          -> 1 000,5
КодСимвола(разделитель) -> 160                              (NBSP)
Число(Строка(1000000))  -> 1 000 000                        (round-trip живой)
Строка(Истина)          -> Да
Строка(Новый Массив)    -> Массив
```

Почему это именно так, чтобы не «исправить» как баг:

* Лимит деления — на МАСШТАБЕ, а не на значащих: `1/3` даёт 27 значащих,
  `10/3` — 27 знаков после точки при 28 значащих.
* Half-up подтверждён точной ничьей: 1/2²⁸ = 0,0000000037252902984619140625
  ровно; платформа дала `...063`, half-even и truncate дали бы `...062`.
* Умножение без границы масштаба — это семантика, а не недосмотр: `x = x * x`
  в цикле подвешивает саму платформу. `MAX_SCALE` в коде — защита от OOM.
* `Pow(10,30)` точный: через f64 вышло бы `1 000 000 000 000 000 019 884 624 838 656`.
* n-body с `Для i = 1 По 50000000` неисполним нигде, включая 1С: масштаб
  растёт примерно на 50 знаков за итерацию. Фикстуры намеренно урезаны до
  100/3/200 итераций — увеличивать их обратно не нужно.

Целимся в 1С, не в OneScript. OneScript, судя по всему, на C# `decimal` с
кэпом 28–29 разрядов, и округлит там, где 1С не будет: расхождения с ним
ожидаемы и документируются, а не чинятся.
