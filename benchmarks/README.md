# Микробенчмарки

## Сценарии

| Сценарий | Что измеряет |
|---|---|
| `bmp_rotate` | Поворот 32-битного BMP 600x400 на 90°: 240 000 пар `ПолучитьСрез`/`Записать` над `БуферДвоичныхДанных` плюс сборка заголовков. |
| `call_overhead` | 1 000 000 вызовов пользовательской функции с одним сложением. |
| `csv_write` | Запись 300 001 строк CSV по 21 полю, 42 вызова записи на строку. |
| `csv_write_batched` | Та же выгрузка CSV, но строка собирается один раз и записывается одним вызовом. |
| `edata_writer` | Выгрузка EnterpriseData 1.0.1 фабрикой XDTO: 1000 «Документ.ЗаказКлиента» по пять строк товаров каждый со случайными ссылками-УИД, «ЗаписатьXML» фабрики в файл сообщения обмена 5,4 МБ. Фабрика по двум XSD из `data/` (494 КБ, 348 масок `xs:any`) строится вне замера; размер выгрузки совпадает с платформенным байт в байт (формат записи зафиксирован побайтным сличением детерминированной редакции сценария). |
| `empty_for` | Накладные расходы пустого числового цикла: 10 проходов по 1 000 001 итерации. |
| `json_parse` | 3 разбора документа JSON на 10 000 записей контрагентов (5 653 941 код-юнит, вложенность в четыре уровня) через `ПрочитатьJSON`. |
| `json_write` | Порождение того же документа через потоковую `ЗаписьJSON`, 3 прохода. |
| `pi_leibniz` | 1 000 000 членов ряда Лейбница; точная десятичная арифметика BSL. |
| `pi_leibniz_15` | Тот же ряд с округлением до 15 знаков на каждой итерации. |
| `str_concat` | Десятикратная сборка строки из 3 000 фрагментов конкатенацией. |
| `xml_parse` | 3 обхода документа XML на 10 000 записей контрагентов (6 854 005 код-юнитов, 540 002 узла, 100 000 атрибутов) потоковым `ЧтениеXML`. |
| `xml_write` | Порождение того же документа через потоковую `ЗаписьXML`, 3 прохода. |
| `str_find` | 500 поисков подстроки в конце строки длиной около 215 000 символов. |
| `simple_parquet_reader` | Разбор файла parquet на 100 000 строк и четыре колонки (Thrift-подвал, цепочки страниц PLAIN, распаковка IEEE 754 вручную) в `ТаблицаЗначений`. |
| `table_compare` | Сравнение двух `ТаблицаЗначений`: 18 колонок, 4 измерения, 50 000 внешних циклов генерации (900 000 строк на таблицу) и свёртка по всем колонкам. |
| `table_compare2` | Разница двух `ТаблицаЗначений` по обезличенному профилю реальной выгрузки: 564 564 + 483 939 строк, пять колонок, уникальный на строку ключ, «Свернуть со знаками». |
| `table_save_load` | `ТаблицаЗначений` в 564 564 строки через `ЗначениеВФайл`/`ЗначениеИзФайла` (файл ~130 МБ) с проверкой тождественности повторной сериализации. |
| `table_sort` | Три сортировки и линейный поиск в `ТаблицаЗначений` из 100 000 строк. |
| `table_total` | Заполнение 200 000 строк и 50 вызовов `Итог` по числовой колонке. |
| `textdoc_invoice` | Формирование `ТекстовыйДокумент` по макету расходной накладной с 100 000 позициями. |

## Результаты

Методика: `./run.sh`, медиана пяти прогонов на одной машине (тяжёлые
сценарии — трёх), сборка `--release` с выравниванием функций из
`.cargo/config.toml`. Файловые выходы (`csv_write*`) после замера
сверяются побайтно между всеми рантаймами — разошёлся вывод, значит
бенчмарк провален, а не быстр. Колонка 1С не меряется живьём: это медиана
из [`1c/combined.platform.txt`](1c/combined.platform.txt), снятого
отдельным прогоном на платформе; сценарии, которых в сводном файле нет
(`bmp_rotate`, `simple_parquet_reader`, `edata_writer`), несут в этой
колонке число одиночного прогона из своего `<сценарий>.platform.txt`.
Версии в этом прогоне: Lua 5.4.8, LuaJIT 2.1, Python 3.14,
OneScript 2.1.0, 1С 8.3.27; `pandas` для двойника parquet у Python 3.14
этой сессии недоступен, отсюда его «ошибка».

Строка `bmp_rotate` снята ОТДЕЛЬНЫМ прогоном, позже остальной таблицы:
сценарий добавлен после того, как она была снята. Внутри строки прогон
один (`./run.sh bmp_rotate 5`), поэтому колонки между собой сравнимы, а
вот с числами соседних строк её сопоставлять нельзя — сеанс другой.
Колонка 1С у неё берётся не из `1c/combined.platform.txt`, а из
[`bmp_rotate.platform.txt`](bmp_rotate.platform.txt): свод переснимается
целиком тремя проходами всех сценариев, и ради одной строки его гонять
незачем. У OneScript 2.1 `БуферДвоичныхДанных.ПолучитьСрез` объявлен, но
не реализован (`System.NotImplementedException`) — отсюда «ошибка», а не
число; `Записать` и `Скопировать` у него работают.

`simple_parquet_reader` снят тем же отдельным прогоном и с той же
оговоркой, что `bmp_rotate`; его колонка 1С — из
[`simple_parquet_reader.platform.txt`](simple_parquet_reader.platform.txt).
Входной файл лежит в дереве — [`data/simple.parquet`](data/simple.parquet),
пять мегабайт; породил его [`make-parquet.py`](make-parquet.py) с
фиксированным зерном, и запускать генератор ради прогона не нужно.

Строка снята семью прогонами, а не пятью, и целиком одним заходом:
машина в тот день гуляла на десяток процентов, и смешивать в одной строке
числа из разных заходов нельзя тем более, чем внутри одной строки их и
сравнивают.

Двойники у этого сценария РАЗНЫЕ по замыслу, и колонки надо читать
по-разному. Lua разбирает файл сам — тот же подвал Thrift, те же цепочки
страниц, те же значения по одному, — и его число сравнимо с нашим напрямую
(с поправкой на то, что числа в Lua это double: точных целых шире 2^53 у
него нет, на этом файле вопрос теоретический). Python же читает
`pandas.read_parquet`, то есть уходит в pyarrow и меряет векторизованный
C++, а не язык: 40 мс против 762 — это цена разбора руками против готовой
библиотеки, а не разница языков. Сравнение языков даёт колонка Lua, а не
эта. Ещё одна асимметрия у обоих: `DataFrame` и
массив массивов колоночные, а `ТаблицаЗначений` построчная, и перекладку
столбцов в строки версия на BSL оплачивает, а `pandas` нет.

Системный `python3` на машине оракула pandas не содержит, и колонка снята
через `PYTHON=…/bin/python ./run.sh` из venv (pandas 3.0.5, pyarrow
25.0.1); без pandas двойник печатает подсказку, и в колонке будет
«ошибка». У OneScript всё та же нереализованная `ПолучитьСрез`.

Числа из разных прогонов таблицы между собой не сравнимы: машина
дрейфует на десяток процентов от дня ко дню, и дрейф виден по чужим
колонкам, которые уезжают вместе с нашей. Чтобы проверить, замедлила ли
что-то правка, собирают бинарник коммита, которым снята предыдущая
таблица (`git log -- benchmarks/README.md`), и гоняют прогоны двух сборок
вперемежку, беря медиану по каждой. Для подтверждения регрессии время —
худшая из метрик: `perf stat -e instructions:u` повторяется с точностью
до сотых долей процента там, где время шумит на три.
