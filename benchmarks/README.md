# Микробенчмарки

Набор сравнивает `bsl-cli` в режимах интерпретатора и JIT с Lua, LuaJIT,
OneScript и платформой 1С. Каждый сценарий сам измеряет время работы и
печатает миллисекунды последней строкой. Так запуск процесса и прогрев .NET
не попадают в замер.

## Сценарии

| Сценарий | Что измеряет |
|---|---|
| `call_overhead` | 1 000 000 вызовов пользовательской функции с одним сложением. |
| `csv_write` | Запись 300 001 строк CSV по 21 полю, 42 вызова записи на строку. |
| `csv_write_batched` | Та же выгрузка CSV, но строка собирается один раз и записывается одним вызовом. |
| `empty_for` | Накладные расходы пустого числового цикла: 10 проходов по 1 000 001 итерации. |
| `json_parse` | 20 разборов документа JSON на 2 000 записей (286 573 код-юнита) через `ПрочитатьJSON`. |
| `pi_leibniz` | 1 000 000 членов ряда Лейбница; точная десятичная арифметика BSL. |
| `pi_leibniz_15` | Тот же ряд с округлением до 15 знаков на каждой итерации. |
| `str_concat` | Десятикратная сборка строки из 3 000 фрагментов конкатенацией. |
| `str_find` | 500 поисков подстроки в конце строки длиной около 215 000 символов. |
| `table_sort` | Три сортировки и линейный поиск в `ТаблицаЗначений` из 100 000 строк. |
| `table_total` | Заполнение 200 000 строк и 50 вызовов `Итог` по числовой колонке. |

Файлы `.lua` — функциональные двойники сценариев BSL. Они не гарантируют равную
семантику: Lua использует аппаратные `double` и байтовые строки, а BSL — точные
десятичные числа и UTF-16. Строго сравнимы по семантике колонки `bsl-cli`,
OneScript и 1С.

У `json_parse` к этому добавляется ещё одно, более грубое расхождение. JSON нет
ни в стандартной библиотеке Lua, ни в виде установленной библиотеки на машине
замера, поэтому разборщик написан прямо в двойнике — и колонки Lua меряют
ИНТЕРПРЕТИРУЕМЫЙ разбор, тогда как остальные четыре меряют разбор, реализованный
внутри рантайма на компилируемом языке. Читать эти числа как «Lua медленнее
нас в N раз» нельзя: сравниваются не языки, а способ доставки JSON в язык.
Осмысленная тройка здесь — `bsl-cli`, OneScript и 1С.

## Запуск

```bash
cargo build --release -p bsl-cli
./benchmarks/run.sh              # все сценарии, 5 прогонов
./benchmarks/run.sh str_find 9   # один сценарий, 9 прогонов
```

Скрипт печатает медиану, чтобы один выброс планировщика не искажал результат.
`csv_write*` по умолчанию выполняются 3 раза и пишут в
`${TMPDIR:-/tmp}/onec-bench-scratch`; число прогонов задаётся через `HEAVY_RUNS`.
После замера скрипт побайтно сверяет созданные CSV.

Для обновления колонки 1С соберите все сценарии в один скрипт и запустите его
на платформе:

```bash
python3 benchmarks/1c/build-combined.py 3
ONEC_TIMEOUT=900 ./tests/conformance/measure/1c/run-on-1c.sh \
  benchmarks/1c/combined.bsl
```

## Результаты базового замера

Все результаты в таблице измерены в **миллисекундах (мс)**; меньшее значение
означает более быстрое выполнение. Указана медиана 5 прогонов, для `csv_write*` — 3.
Значение `0` означает, что замер оказался меньше разрешения таймера.
Замер выполнен 31.07.2026 на Intel Core i5-8250U, Linux 7.1.3, ревизия `572a804`,
Rust 1.97.1, Lua 5.4.8, LuaJIT 2.1 и OneScript 2.1.0. Колонка 1С 8.3.27 взята из
`benchmarks/1c/combined.platform.txt` и не переизмерялась в этом запуске.

| Сценарий | `bsl-cli`, мс | `bsl-cli --jit`, мс | Lua 5.4, мс | LuaJIT, мс | OneScript, мс | 1С 8.3.27, мс |
|---|---:|---:|---:|---:|---:|---:|
| `call_overhead` | 135 | 138 | 26 | 1 | 915 | 1868 |
| `csv_write` | 1571 | 1485 | 900 | 120 | 22561 | 5033 |
| `csv_write_batched` | 64 | 57 | — | — | 1191 | 237 |
| `empty_for` | 2 | 2 | 4 | 0 | 195 | 319 |
| `json_parse` | 485 | 481 | 889 | 538 | 1208 | 512 |
| `pi_leibniz` | 485 | 360 | 20 | 1 | 1197 | 1282 |
| `pi_leibniz_15` | 663 | 525 | — | — | 1392 | 1388 |
| `str_concat` | 1 | 1 | 560 | 524 | 1179 | 164 |
| `str_find` | 47 | 47 | 312 | 38 | 35 | 134 |
| `table_sort` | 1513 | 1527 | 543 | 479 | 1111 | 3356 |
| `table_total` | 280 | 258 | 231 | 127 | 1046 | 3272 |

Строка `json_parse` снята позже остальных — 01.08.2026, ревизия `c0374ec`, та же
машина и те же версии рантаймов. Внутри строки все шесть колонок измерены в одну
сессию, поэтому сравнение рантаймов между собой корректно; сравнивать её с
другими СТРОКАМИ таблицы — уже нет.

Два наблюдения по `json_parse`, которые стоит держать в голове при чтении
таблицы:

* **JIT не даёт ничего** (481 против 485). Это не сбой замера: почти всё время
  уходит внутрь разборщика в `bsl_rt::json`, то есть в нативный код, а JIT
  убирает только диспетчеризацию байт-кода. Ускорять ему здесь нечего.
* **Все четыре рантайма, читающие JSON «настоящим» разборщиком, сошлись в
  пределах ×2.5**, и наш результат совпал с платформенным с точностью до шума.
  Контрольная сумма (40 000 записей, 4 002 000) у всех шести колонок одна — то
  есть меряется одна и та же работа, а не разные объёмы разбора.

Эти цифры зависят от машины, частоты CPU и фоновой нагрузки. Для оценки
регрессий сравнивайте колонки, полученные в одной сессии на одном и том же компьютере.
